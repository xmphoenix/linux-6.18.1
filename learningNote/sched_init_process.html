一、架构全景

1.1 调度器在系统中的位置

调度器是内核中连接进程管理与CPU 硬件的桥梁。每当需要选择"下一个要运行的任务"时，调度器就被触发。

4.3 pick_next_task 遍历逻辑

core.c:5950 — 按优先级从高到低尝试每个调度类：

__pick_next_task(rq, prev, rf):
    for_each_class(class) {              // stop → dl → rt → fair → ext → idle
        p = class->pick_next_task(rq, prev);
        if (p) return p;                 // 高优先级有任务立马返回
    }

核心规则：高优先级调度类有就绪任务时，低优先级类的任务绝不被选中。

五、核心调度流程

5.1 schedule() 入口

core.c:7016：

asmlinkage __visible void __sched schedule(void)
{
    do {
        preempt_disable();
        __schedule_loop(SM_NONE);       // → __schedule()
        sched_preempt_enable_no_resched();
    } while (need_resched());          // 如果又被设 NEED_RESCHED，重来
}

5.2 __schedule() 主逻辑

core.c:6784 — 约150行的调度决策核心：

static void __sched __schedule(int sched_mode)
{
    cpu  = smp_processor_id();
    rq   = cpu_rq(cpu);
    prev = rq->curr;                   // 1. 记录当前任务

    rq_lock(rq, &rf);                  // 2. 锁 rq
    update_rq_clock(rq);               // 3. 更新时钟

    prev_state = READ_ONCE(prev->__state);

    // 4. 如果 prev 阻塞 (state != RUNNING) → 出队
    if (prev_state && !(prev_state & TASK_RUNNING))
        try_to_block_task(rq, prev, ...);  // deactivate

    // 5. ★ 选下一个任务
    next = pick_next_task(rq, prev, &rf);

    // 6. 切换
    if (prev != next) {
        rq->nr_switches++;
        context_switch(rq, prev, next, &rf);
    }
}

5.3 pick_next_task()

core.c:6042。CFS 优化路径：当 prev 是 CFS 任务且所有更高优先级类无任务时，直接调用 pick_next_task_fair() 跳过遍历——因为系统里绝大多数任务都是 CFS 的。

5.4 context_switch()

core.c:5269：

context_switch(rq, prev, next, rf):
    // 1. 切换地址空间 (页表基址)
    switch_mm_irqs_off(prev->active_mm, next->mm, next);

    // 2. 切换寄存器上下文
    switch_to(prev, next, prev);
    //   └→ arch/arm64/kernel/entry.S: cpu_switch_to()
    //       保存 x19-x28, fp, sp, lr 到 prev->thread.cpu_context
    //       从 next->thread.cpu_context 恢复

    return finish_task_switch(prev);

在 ARM64 上，cpu_switch_to 汇编保存/恢复 callee-saved 寄存器 (x19-x28)、fp (x29)、sp、pc。这是整个调度的物理切换点。

六、CFS 完全公平调度

6.1 vruntime — 虚拟运行时间

CFS 核心思想：让每个任务获得等比例的 CPU 时间。但如何比较不同 nice 值的任务？

vruntime = 实际运行时间 × (NICE_0_LOAD / 任务权重)

  • nice=-20 (weight=88761)：vruntime 增长慢 → 红黑树左边 → 更早被选中
  • nice=+19 (weight=15)：vruntime 增长快 → 红黑树右边 → 更晚被选中

更新在 update_curr() 中 (每次 tick 或 enqueue/dequeue)：

update_curr(struct cfs_rq *cfs_rq):
    delta_exec = now - curr->exec_start;          // 本次物理运行时间
    curr->sum_exec_runtime += delta_exec;
    // ★ 核心公式: 物理时间 → 虚拟时间
    curr->vruntime += calc_delta_fair(delta_exec, curr);
    //                    └→ delta * NICE_0_LOAD / curr->load.weight
    cfs_rq->min_vruntime = max(min_vruntime, curr->vruntime);

6.2 红黑树组织

每个 CPU 的 cfs_rq.tasks_timeline 是一棵以 vruntime 为 key 的红黑树：

cfs_rq (per CPU) ├─ tasks_timeline (rb_root) ← 红黑树根 │ ├─ se[A] vruntime=100ns ← 最左 (最小 vruntime, 会先被选) │ ├─ se[B] vruntime=150ns │ ├─ se[C] vruntime=200ns │ └─ se[D] vruntime=500ns ← 最右 ├─ min_vruntime = 98ns ← 跟踪最小值 (防 vruntime 回绕) ├─ nr_running = 4 └─ curr → se[A] ← 当前正在运行的

6.3 enqueue / dequeue / pick

操作函数调用链做了什么
入队enqueue_task_fair() → enqueue_entity()计算 vruntime → 插入红黑树
出队dequeue_task_fair() → dequeue_entity()从红黑树删除
选择pick_next_task_fair() → set_next_entity()取最左节点 → 从树摘下 → 设为 curr
ticktask_tick_fair() → entity_tick()update_curr → 检查是否该抢占

6.4 调度周期与时间片

CFS 不分配固定时间片。它维护一个目标调度延迟 sysctl_sched_latency (默认 6ms)，在此周期内所有 runnable 任务都至少运行一次。时间片 = latency × (task_weight / total_weight)。

参数位置默认含义
sysctl_sched_latencyfair.c6ms目标调度延迟
sysctl_sched_min_granularityfair.c0.75ms最小时间片 (防切换过多)
sysctl_sched_wakeup_granularityfair.c1ms唤醒抢占粒度 (防频繁)

七、初始化流程

7.1 sched_init() — 早期 UP 初始化

core.c:8643。在 start_kernel() 早期调用：

void __init sched_init(void)
{
    // 1. 验证 sched_class 优先级顺序
    BUG_ON(!sched_class_above(&stop_sched_class, &dl_sched_class));
    BUG_ON(!sched_class_above(&dl_sched_class,   &rt_sched_class));
    BUG_ON(!sched_class_above(&rt_sched_class,   &fair_sched_class));
    BUG_ON(!sched_class_above(&fair_sched_class, &idle_sched_class));

    // 2. 分配 root_task_group 的 per-CPU 数组
    root_task_group.shares = ROOT_TASK_GROUP_LOAD;  // = 1024

    // 3. 为每个 CPU 初始化 rq
    for_each_possible_cpu(i) {
        rq = cpu_rq(i);
        raw_spin_lock_init(&rq->__lock);
        init_cfs_rq(&rq->cfs);           // 初始化 CFS 队列
        init_rt_rq(&rq->rt);             // 初始化 RT 队列
        init_dl_rq(&rq->dl);             // 初始化 DL 队列
        rq->cpu_capacity = SCHED_CAPACITY_SCALE;  // = 1024
    }

    // 4. init_task (0号进程) → fair_sched_class
    init_task.sched_class = &fair_sched_class;
    __sched_fork(0, current);
    init_idle(current, smp_processor_id());

    // 5. 初始化 fair/ext class、PSI、uclamp
    init_sched_fair_class();
    psi_init();
    init_uclamp();

    scheduler_running = 1;   // ★ 调度器已就绪
}

八、负载均衡

8.1 sched_domain — 调度域层级

描述 CPU 间的拓扑关系。QEMU virt -smp 4 的典型层级：

CPU0 ─┬─ MC (Multi-Core) ───── CPU0, CPU1, CPU2, CPU3 │ 同一 cluster, 共享 LLC └─ DIE ─────────────── CPU0-3 (单 die) └─ NUMA ──────── (未使用, 单 NUMA 节点)

8.2 负载均衡触发路径

  • 周期均衡：scheduler_tick() → trigger_load_balance() → 软中断 SCHED_SOFTIRQ → run_rebalance_domains()
  • 新任务：wake_up_new_task() → select_task_rq_fair() 选择最优 CPU
  • 空闲均衡：CPU 进入 idle 时 newidle_balance() 从忙 CPU "拉取"任务

8.3 PELT — 负载追踪

pelt.c。用指数衰减平均计算每个 sched_entity 的 CPU 使用率，是负载均衡的决策依据。衰减因子 y ≈ 0.97857206（每 32ms 衰减一半）。公式：L = L0 + L1×y^32 + L2×y^64 + ...

十、QEMU 实践实验

环境：qemu-system-aarch64 -machine virt -cpu cortex-a57 -m 1024 -smp 4 -kernel arch/arm64/boot/Image --append "rdinit=/linuxrc console=ttyAMA0" -nographic

实验1: 观察调度器启动

目标：在内核启动日志中观察 sched_init() 的输出。

操作：在 core.c:sched_init() 末尾添加打印：

pr_info("=== sched_init: nr_cpu_ids=%d ===\n", nr_cpu_ids);
for_each_possible_cpu(i)
    pr_info("CPU%d: rq=%px capacity=%lu\n", i, cpu_rq(i), cpu_rq(i)->cpu_capacity);

重新编译启动后预期输出：

=== sched_init: nr_cpu_ids=4 ===
CPU0: rq=ffff80008000c000 capacity=1024
CPU1: rq=ffff80008000c800 capacity=1024
CPU2: rq=ffff80008000d000 capacity=1024
CPU3: rq=ffff80008000d800 capacity=1024

学到：四个 CPU rq 静态分配(capacity=1024 全对称)、sched_init() 在 start_kernel() 早期(~L984)调用。

实验2: ftrace 追踪调度事件

目标：使用 ftrace 观察 sched_switch 事件，理解任务切换模式。

前提：确认 ybzhang_defconfig 中 CONFIG_FUNCTION_TRACER=y 和 CONFIG_SCHED_TRACER=y。

# 在 QEMU 虚拟机内:
mount -t tracefs none /sys/kernel/tracing
echo 1 > /sys/kernel/tracing/events/sched/sched_switch/enable
cat /sys/kernel/tracing/trace | head -20

预期输出示例：

<idle>-0     [000] d... 100.123: sched_switch: prev_comm=swapper/0 prev_pid=0 prev_state=R ==> next_comm=linuxrc next_pid=1
linuxrc-1     [000] d... 100.234: sched_switch: prev_comm=linuxrc prev_pid=1 prev_state=S ==> next_comm=swapper/0 next_pid=0

学到： idle (swapper)始终存在、prev_state=R=被抢占 prev_state=S=主动睡眠、每CPU独立调度。

实验3: 观察 CPU 拓扑

目标：查看内核解析出的 CPU 拓扑和调度域信息。

# 在 QEMU 虚拟机内:
cat /sys/devices/system/cpu/cpu*/topology/core_id
cat /sys/devices/system/cpu/cpu*/topology/cluster_id
cat /sys/devices/system/cpu/cpu*/cpu_capacity
cat /sys/devices/system/cpu/cpu0/topology/core_siblings_list

预期输出：

core_id:  0, 1, 2, 3  (各不相同)
cluster_id: 0, 0, 0, 0 (全在同一 cluster)
cpu_capacity: 1024 × 4  (完全对称)
core_siblings: 0-3  (全在同一 package)

学到：QEMU virt 四核全在同一 cluster/package，capacity 对称。对比大小核 SoC 会看到不同 cluster_id 和不对称 capacity。

实验4: 观察 CFS vruntime

目标：创建不同 nice 值的 CPU 密集任务，观察 vruntime 增长速度差异。

# 在 QEMU 虚拟机内创建 CPU 密集任务:
nice -n -20 sh -c 'while true; do :; done' &   # pid=A, 高优先级
nice -n  19 sh -c 'while true; do :; done' &   # pid=B, 低优先级

# 观察调度信息:
cat /proc/sched_debug | grep -E "vruntime|sum_exec"
cat /proc/$PID_A/sched   # 查看具体任务的 se.vruntime
cat /proc/$PID_B/sched

关键观察：

  • nice=-20 的 sum_exec_runtime 增长远快于 nice=+19 的
  • 但 vruntime 增长相反——nice=-20 增长慢（权重高），nice=+19 增长快
  • 这就是 calc_delta_fair() 的效果
提示：如果 QEMU 小系统没有 nice 命令，可写一个内核模块用 kthread_create() 创建不同优先级线程，再从 /proc/sched_debug 观察。
