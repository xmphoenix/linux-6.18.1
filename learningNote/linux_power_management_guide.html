Linux 内核功耗管理子系统 —— 深度源码学习指南

基于 Linux 6.18.1 · 涵盖 CPUidle / CPUFreq / Schedutil / Energy Model / Runtime PM / 系统休眠 / PM QoS

1. 功耗管理子系统全景架构

1.1 为什么需要功耗管理

现代 SoC 的功耗管理不是简单的"不用就关"，而是一个多层级的动态平衡问题。以 ARM64 移动设备为例：


一颗 A57 大核跑满 2.0GHz：           ~2.0W
同一颗核 idle 在 WFI（C1）：          ~0.1W
同一颗核 power collapse（C3/PSCI）：  ~0.001W

差距是 2000 倍。但这只是静态功耗——实际情况中，CPU 在 busy/idle
之间以毫秒级切换，功耗管理必须：
  (1) 快速响应——不能为了省电而让用户感觉到卡顿
  (2) 准确预测——选错了 C-state 代价很大（浅了浪费电，深了延迟大）
  (3) 全局优化——不能单颗 CPU 省电却把任务全堆到另一颗上面

1.3 ARM64 上的典型功耗管理堆栈

在 ARM64 A53/A57 平台（如 Hikey960、DB820c、Raspberry Pi 5）上，典型配置如下：


BootLoader (U-Boot/EDK2) → PSCI 1.0+
                           │
Linux Kernel ──────────────┼─────────────────────────────
                           │
  CPUFreq:  scmi-cpufreq / cpufreq-dt / qcom-cpufreq-hw
            governor = schedutil (默认)
  CPUidle:  cpuidle-psci (ARM PSCI 标准接口)
            governor = menu 或 teo
  EM:       由 CPUFreq 驱动自动注册或
            DT 中的 "opp-table" 节点提供数据
  Runtime PM: 由各设备驱动独立使用
  System PM:  PSCI system_suspend()
关键理解：在 ARM64 上，CPUidle 和 CPUFreq 最终都通过 PSCI (Power State Coordination Interface) 调用到 ATF (ARM Trusted Firmware) 的 EL3 固件层。内核不直接操作电源门控寄存器——那是 EL3 的职责。

2.1 核心数据结构

2.1.2 cpuidle_driver —— 硬件平台定义的空闲状态

// drivers/cpuidle/driver.c  + include/linux/cpuidle.h
struct cpuidle_driver {
    const char          *name;
    struct module       *owner;
    struct cpumask       *cpumask;              // 此驱动覆盖哪些CPU
    int                  state_count;           // 有几个idle状态（含state[0]=poll）
    struct cpuidle_state states[CPUIDLE_STATE_MAX];  // ★ 核心：状态表
};

struct cpuidle_state {
    char    name[CPUIDLE_NAME_LEN];  // "C1", "C2", "cluster-sleep" 等
    char    desc[CPUIDLE_DESC_LEN];
    u64     exit_latency_ns;         // ★ 退出延迟：从唤醒到开始执行需要多久
    u64     target_residency_ns;     // ★ 目标驻留时间：至少睡多久才能回本
    int     (*enter)(struct cpuidle_device *, struct cpuidle_driver *, int index);
    int     (*enter_dead)(struct cpuidle_device *, int index);  // CPU hotplug off
    unsigned int flags;
    // CPUIDLE_FLAG_TIMER_STOP: 进入该状态后本地timer停止，需要broadcast timer
    // CPUIDLE_FLAG_RCU_IDLE:   RCU不在该状态下做grace period跟踪
    // CPUIDLE_FLAG_TLB_FLUSHED: 进入该状态后TLB被刷掉
};
关键字段理解：
  • exit_latency_ns：这个值决定了 Governor 是否敢选这个状态。如果 PM QoS 要求延迟 < 50μs，那 exit_latency 100μs 的状态直接不可用。
  • target_residency_ns：节能的"盈亏平衡点"。假设进 C3 花费 200μs（进+出），额外省电 100mW。那么睡 100μs 电没省到反而亏了延迟，至少睡 200μs 才回本。这个值由硬件数据手册和实测决定。
C-State 的含义：C 中的 "C" 代表 Cpu（或 Core），是 ACPI 规范中定义的状态分类字母编号。它与 P-State 和 T-State 构成完整的处理器电源管理分类体系：
  • C-State（CPU Power State）— CPU 空闲时睡多深（关时钟？关电源？）
  • P-State（Performance State）— CPU 忙碌时频率/电压（DVFS）
  • T-State（Throttle State）— 强制降频（过温保护，已被 P-State 替代）
C-State 的数字越大表示睡得越深（省电更多、唤醒更慢）：
C-State通用名称含义
C0Active / RunCPU 正在执行指令
C1Halt停止指令执行，时钟和电源保持（最快恢复）
C2Stop-Clock关闭部分时钟，保留缓存（比 C1 慢但省电）
C3Sleep关闭全部时钟 + 部分电源域，缓存一致性可能丢失
C4+Deep Sleep更深电源门控，甚至关掉 L2 缓存电源
在 ARM64 上，实际使用 Device Tree 中 arm,psci-suspend-param 定义的平台相关名称（如 cpu-sleep-0、cluster-sleep-0），但概念上等价于 ACPI 的 C-State 体系——一个是字母编号（x86），另一个是 PSCI suspend 参数描述（ARM）。

2.2 从空闲线程到 C-State 的完整调用链

2.2.1 入口：do_idle() 循环

// kernel/sched/idle.c:257
static void do_idle(void)
{
    int cpu = smp_processor_id();

    nohz_run_idle_balance(cpu);          // Step 1: 跑一次idle负载均衡
    __current_set_polling();             // Step 2: 设置 TIF_POLLING_NRFLAG
    tick_nohz_idle_enter();             // Step 3: 通知NO_HZ子系统进入idle

    while (!need_resched()) {            // ★ 主循环：只要没有需要调度的
        local_irq_disable();

        if (cpu_is_offline(cpu)) {
            cpuhp_report_idle_dead();    // CPU hot-unplug 路径
            arch_cpu_idle_dead();
        }

        arch_cpu_idle_enter();

        if (cpu_idle_force_poll || tick_check_broadcast_expired())
            cpu_idle_poll();             // 路径A: 轮询模式（不进深度睡眠）
        else
            cpuidle_idle_call();         // 路径B: ★ 走CPUidle框架选状态

        arch_cpu_idle_exit();
    }

    // 退出 idle 循环: TIF_NEED_RESCHED 被置位了
    tick_nohz_idle_exit();
    __current_clr_polling();
    schedule_idle();                     // 调用 schedule() 切到就绪任务
}

2.2.2 cpuidle_idle_call() —— CPUidle 核心决策

// kernel/sched/idle.c:172
static void cpuidle_idle_call(void)
{
    struct cpuidle_device *dev = cpuidle_get_device();
    struct cpuidle_driver *drv = cpuidle_get_cpu_driver(dev);
    int next_state, entered_state;

    if (need_resched()) {               // 快速检查：如果已经有任务要跑了
        local_irq_enable();             // 直接返回do_idle循环，不进idle
        return;
    }

    if (cpuidle_not_available(drv, dev)) {
        tick_nohz_idle_stop_tick();     // CPUidle不可用，走fallback
        default_idle_call();            // → arch_cpu_idle()（ARM64是wfi）
        goto exit_idle;
    }

    if (idle_should_enter_s2idle() || dev->forced_idle_latency_limit_ns) {
        // Suspend-to-idle 路径: 不经过governor，直接选最深状态
        next_state = cpuidle_find_deepest_state(drv, dev, max_latency_ns);
        call_cpuidle(drv, dev, next_state);
    } else {
        bool stop_tick = true;
        // ★ 正常路径：让 Governor 决策
        next_state = cpuidle_select(drv, dev, &stop_tick);

        if (stop_tick || tick_nohz_tick_stopped())
            tick_nohz_idle_stop_tick();      // 停掉sched tick（NO_HZ）
        else
            tick_nohz_idle_retain_tick();    // 保留tick（浅idle状态）

        entered_state = call_cpuidle(drv, dev, next_state);
        cpuidle_reflect(dev, entered_state);  // 反馈给governor学习
    }

exit_idle:
    __current_set_polling();
}

2.2.3 cpuidle_enter_state() —— 真正进入硬件空闲

// drivers/cpuidle/cpuidle.c:215
noinstr int cpuidle_enter_state(struct cpuidle_device *dev,
                                 struct cpuidle_driver *drv, int index)
{
    struct cpuidle_state *target_state = &drv->states[index];
    ktime_t time_start, time_end;

    // Step 1: 如果状态会让本地timer停掉，先设置broadcast timer
    if (broadcast && tick_broadcast_enter()) {
        index = find_deepest_state(drv, dev, ...);  // 降级到不需要broadcast的状态
    }

    // Step 2: 通知调度器，当前CPU要进idle了
    sched_idle_set_state(target_state);
    time_start = ns_to_ktime(local_clock_noinstr());

    // Step 3: ★ 硬件进入idle —— 这是"沉睡"的关键时刻
    entered_state = target_state->enter(dev, drv, index);
    //                 ↑ 调用到 arch/arm64 的 psci_cpu_suspend()
    //                   在 ARM64 上: wfi 或 power down

    // Step 4: ★ 醒来！更新统计
    sched_idle_set_state(NULL);          // 通知调度器idle结束
    time_end = ns_to_ktime(local_clock_noinstr());

    // Step 5: 统计 —— 判断选的深度对不对
    diff = ktime_sub(time_end, time_start);
    dev->last_residency_ns = diff;
    dev->states_usage[entered_state].time_ns += diff;
    dev->states_usage[entered_state].usage++;

    // Step 5a: 如果实际睡眠时间 < target_residency → 选深了，above++
    if (diff < drv->states[entered_state].target_residency_ns) {
        dev->states_usage[entered_state].above++;
    }
    // Step 5b: 如果实际睡眠远超 exit_latency → 选浅了，below++
    else if (diff > delay) {
        if (diff - delay >= drv->states[i].target_residency_ns) {
            dev->states_usage[entered_state].below++;
        }
    }

    return entered_state;
}

2.3 CPUidle Governor 机制

Governor 是 CPUidle 的"大脑"——它要根据预测的空闲时长，结合 PM QoS 约束，在功耗和延迟之间做出权衡。


// 决策流程 (cpuidle_select)
cpuidle_select(drv, dev, &stop_tick)
  → cpuidle_curr_governor->select(drv, dev, stop_tick)
     输入: 驱动定义的状态表（exit_latency, target_residency）
           设备统计历史（states_usage[].time_ns, usage, above, below）
           PM QoS 延迟约束
           下一个定时器的到期时间 (next_timer_event)
     输出: 选中的状态 index
           stop_tick: 是否可以关掉 sched tick

Governor 的核心权衡：

  ┌─ 预测空闲时长 ─┐     ┌─ 状态属性 ─┐     ┌─ PM QoS 约束 ─┐
  │ next_timer=2ms  │     │ C1: 2μs/1μs │     │ latency=50μs │
  │ 历史修正因子0.5  │     │ C2: 20μs/10μs│     │ (来自用户空间 │
  │ 预测:1ms        │     │ C3: 200μs/100μs│   │  /dev/cpu_dma │
  └────────┬────────┘     └──────┬──────┘     │   _latency)   │
           │                     │            └───────┬───────┘
           └─────────────────────┼────────────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │  Governor 决策算法       │
                    │  选 exit_latency ≤ QoS   │
                    │  且 target_residency     │
                    │  最接近预测值的状态       │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐

    struct cpuidle_device *dev, struct cpuidle_driver *drv, int idx, bool s2idle)
{

    else

    ret = psci_cpu_suspend_enter(state) ? -1 : idx;

    //        └→ ATF (EL3): 关中断、刷cache、power gate、设唤醒源

    // 恢复 pd
    if (s2idle)
        dev_pm_genpd_resume(pd_dev);
    else
        pm_runtime_get_sync(pd_dev);

    cpu_pm_exit();
    return ret;
}

  • below++：实际睡眠时间足够长，可以进更深的状态，说明 governor "低估"了空闲时长，选浅了。错过了更省电的机会。

2.8 C-State 决策深度解析 —— CPU 空闲时到底选哪个状态？

这是整个 CPUidle 子系统最核心的问题。前面 2.4 节从表格层面对比了四个 governor，本节从算法细节和源码层面展开每个 governor 的完整决策逻辑，并说明 stop_tick 信号、PM QoS 约束如何参与决策。

2.8.1 决策框架总览

无论哪个 governor，决策都遵循相同的框架（见 cpuidle_select()）：

  cpuidle_select(drv, dev, &stop_tick)
    │
    ├─ Step 1: 获取 PM QoS 延迟约束
    │    latency_req = cpuidle_governor_latency_req(cpu)
    │    └→ 来自两处: dev_pm_qos + cpu_latency_qos，取最小值(ns)
    │
    ├─ Step 2: Key Question #1 — "大概会睡多久？"
    │    ┌─ menu:   next_timer × 历史校正因子 + 重复间隔检测
    │    ├─ teo:    先看历史 hits/intercepts，必要时再查 sleep_length
    │    ├─ ladder: 不预测！只看上次的 residency 决定升降级
    │    └─ haltpoll: 也不预测！交替 poll/halt
    │
    ├─ Step 3: Key Question #2 — "哪个状态回本？"
    │    遍历 states[]: if exit_latency ≤ latency_req &&
    │                     target_residency ≤ predicted_ns → 可选
    │
    ├─ Step 4: Key Question #3 — "tick 要不要关？"
    │    stop_tick = (选的状态够深 && 预期睡够久) || tick已停
    │
    └─ 返回选中的 index

每个 governor 的核心差异在于 Step 2：如何预测会睡多久。CPU 无法预知未来，只能靠最近的下一次定时器（"最晚什么时候一定醒"）和历史行为模式（"通常会被什么提前打断"）来推测。

2.8.2 menu governor 决策算法逐行分析

2.8.2.1 核心数据结构

// drivers/cpuidle/governors/menu.c:70-78
struct menu_device {
    int             needs_update;          // 需要先更新历史数据
    int             tick_wakeup;           // 这次醒来是tick唤醒的吗？
    u64             next_timer_ns;         // 下一个定时器的剩余时间
    unsigned int    bucket;                // next_timer落在哪个档位(0~5)
    unsigned int    correction_factor[6];  // ★ 6个档位的校正因子
    unsigned int    intervals[8];          // ★ 最近8次实际的idle时长(us)
    int             interval_ptr;          // 环形缓冲区指针
};

// bucket 分档（which_bucket函数）:
// bucket 0: < 10μs     (极短idle，通常是中断密集场景)
// bucket 1: 10~100μs   (短idle)
// bucket 2: 100μs~1ms  (中等idle)
// bucket 3: 1ms~10ms   (较长idle)
// bucket 4: 10ms~100ms (长idle)
// bucket 5: > 100ms    (极长idle，几乎等于休眠)

2.8.2.2 决策前：更新历史（menu_update）

在每次 menu_select() 决策之前，先通过 menu_reflect() → menu_update() 学习"上次预测得准不准"。

// menu.c:414-498 — 核心学习算法
static void menu_update(struct cpuidle_driver *drv, struct cpuidle_device *dev)
{
    // 1. 取出上次预测的 bucket 和实际的停留时间
    measured_ns = dev->last_residency_ns;
    // 扣除退出延迟（因为退出延迟不是真正"睡眠"的时间）
    if (measured_ns > 2 * target->exit_latency_ns)
        measured_ns -= target->exit_latency_ns;

    // 2. 更新该 bucket 的校正因子（EWMA 指数加权移动平均）
    new_factor = data->correction_factor[bucket];
    new_factor -= new_factor / DECAY;     // 衰减旧值（DECAY=8，即衰减1/8）
    new_factor += RESOLUTION * measured_ns / next_timer_ns;  // 加入新观测
    data->correction_factor[bucket] = new_factor;

    // 校正因子的物理含义：
    //   factor ≈ RESOLUTION * (实际睡眠 / next_timer)
    //   例: next_timer=2ms, 实际睡了1ms → 校正因子=RESOLUTION/2=512
    //       意思是"下次别按2ms预测，打五折"

    // 3. 记录到重复间隔检测数组
    menu_update_intervals(data, measured_ns);
}
校正因子的 EWMA 公式：
new_factor = old_factor × 7/8 + RESOLUTION × (measured_ns / next_timer_ns)
其中 RESOLUTION = 1024，所以初始值 = 1024 × 8 = 8192（即校正因子=1.0）。
如果 measured_ns 总是 next_timer_ns 的一半，校正因子会收敛到 4096，预测值就打五折。

2.8.2.3 决策核心：menu_select()

// menu.c:218-390 — 完整的决策流程

static int menu_select(struct cpuidle_driver *drv, struct cpuidle_device *dev,
                       bool *stop_tick)
{
    s64 latency_req = cpuidle_governor_latency_req(dev->cpu); // Step 1: QoS约束

    // ─── prediction 1: 重复间隔检测 ───
    predicted_ns = get_typical_interval(data) * NSEC_PER_USEC;

    // get_typical_interval() 分析最近8次实测idle时长的标准差:
    //   if (方差很小) → 返回平均值    // 有固定周期模式
    //   else          → 返回 UINT_MAX // 无规律，放弃这个预测

    if (predicted_ns > RESIDENCY_THRESHOLD_NS) {
        // ─── prediction 2: next_timer × 校正因子 ───
        delta = tick_nohz_get_sleep_length(&delta_tick);  // 最近定时器剩余时间
        bucket = which_bucket(next_timer_ns);             // 时间落在哪个档位
        timer_us = next_timer_ns * correction_factor[bucket] / (RESOLUTION * DECAY);

        // ★ 关键：取两个预测的最小值
        predicted_ns = min(timer_us, predicted_ns);
    }

    // ─── 短路：如果连最浅的状态都不值得进 → 直接选 state 0 ───
    if (next_timer_ns < drv->states[1].target_residency_ns ||
        latency_req < drv->states[1].exit_latency_ns)
        return 0;  // 马上就醒了，不值得进idle

    // ─── 遍历状态表，找最深的"回本"状态 ───
    for (i = 0; i < drv->state_count; i++) {
        if (s->exit_latency_ns > latency_req) break;  // QoS 拒绝
        if (s->target_residency_ns <= predicted_ns)
            idx = i;  // 这个状态的驻留时间 ≤ 我们预测的时间，可选
    }

    // ─── stop_tick 决策 ───
    if (state_is_polling || predicted_ns < TICK_NSEC)
        *stop_tick = false;    // 预测睡不够一个tick，留着tick更安全
    return idx;
}

  menu_select() 开始
      │
      ├─ get_typical_interval() → 有固定模式吗？
      │   ├─ YES: predicted = 平均值
      │   └─ NO:  predicted = UINT_MAX
      │
      ├─ tick_nohz_get_sleep_length() → next_timer 还有多久？
      │   │
      │   └─ timer_us = next_timer × correction_factor[bucket]
      │
      ├─ ★ predicted_ns = min(timer_us, typical_interval)
      │   (保守原则：取两个预测中较短的)
      │
      ├─ predicted < 最浅状态的 target_residency？
      │   └─ YES → return state0 (不值得进idle，立即返回)
      │
      ├─ 遍历 states[]:
      │   │ exit_latency > QoS → skip
      │   │ target_residency ≤ predicted → 候选
      │   └─ 选 target_residency 最大的（最深的回本状态）
      │
      └─ 返回 idx, stop_tick
menu 的一个典型误判场景：假设历史数据都是 2ms idle，校正因子趋向 1.0。突然来了一个 burst 中断，在 0.1ms 时唤醒 CPU。menu 会：
  1. 预测 2ms → 选 target=1ms 的 C3 状态
  2. 实际只睡了 0.1ms → 远小于 target_residency → above++
  3. 校正因子在这轮更新后会降低，但需要多次才能收敛（EWMA 的惯性）
这就是 TEO governor 试图改进的场景。

2.8.3 teo governor —— 不预测未来，只统计模式

2.8.3.1 设计思想

TEO (Timer Events Oriented) 的核心洞察是：

不要费劲预测空闲时长。只需统计"timer 说会睡 Xμs，但实际被非 timer 中断在 Yμs 时打断了"的频率。如果这种情况频繁发生，就选浅一点的状态。

也就是说，teo 不做预测，它只做模式匹配——根据历史数据判断"timer wakeup 主导"还是"non-timer wakeup 主导"。

2.8.3.2 核心数据结构

// drivers/cpuidle/governors/teo.c:126-147
struct teo_bin {
    unsigned int intercepts;  // ★ "拦截"次数：非timer中断在timer之前唤醒
    unsigned int hits;        // ★ "命中"次数：timer按预期触发
};

struct teo_cpu {
    s64 sleep_length_ns;
    struct teo_bin state_bins[CPUIDLE_STATE_MAX]; // ★ 每个idle状态一个bin
    unsigned int total;           // 总事件数(带衰减)
    unsigned int tick_intercepts; // 在 tick 周期内被非timer中断唤醒的次数
    unsigned int short_idles;     // 短idle的次数（< RESIDENCY_THRESHOLD_NS）
    bool artificial_wakeup;      // 是否是"非真实"唤醒（如poll超时、tick未停）
};

2.8.3.3 bin 的含义

  bin 的边界 = idle 状态的 target_residency

  假设有3个 idle 状态:
    state0: target_residency=0       (poll)
    state1: target_residency=10μs    (WFI)
    state2: target_residency=100μs   (C2)

  产生3个 bin:
    bin[0]: 0 ~ 10μs       对应 state0 (poll)
    bin[1]: 10μs ~ 100μs   对应 state1 (WFI)
    bin[2]: >100μs          对应 state2 (C2)

  每次醒来后:
    1. 找到 sleep_length 落在哪个 bin → idx_timer
       (sleep_length = 到最近定时器的时间)
    2. 找到实际 idle 时长落在哪个 bin → idx_duration
    3. if idx_timer == idx_duration → hits[idx_timer]++
       else                         → intercepts[idx_duration]++
       // "timer预测能睡到bin2，但实际在bin1就被打断了" → 一次 intercept

2.8.3.4 决策核心：teo_select()

// teo.c:268-498

static int teo_select(struct cpuidle_driver *drv, struct cpuidle_device *dev,
                      bool *stop_tick)
{
    s64 latency_req = cpuidle_governor_latency_req(dev->cpu); // QoS约束

    // ─── Round 0: 更新历史统计 ───
    teo_update(drv, dev);
    // 1) 对所有 bin 的 hits/intercepts 做衰减(>>DECAY_SHIFT=÷8)
    // 2) 找到 sleep_length 和 measured duration 各自的 bin
    // 3) idx_timer==idx_duration → hits++ 否则 → intercepts++

    // ─── Round 1: 找最深的候选状态 idx ───
    // 遍历 states[]，同时累加 intercept_sum 和 hit_sum
    for (i = 1; i < drv->state_count; i++) {
        intercept_sum += state_bins[i-1].intercepts;
        hit_sum += state_bins[i-1].hits;
        idx = i;  // 候选 = 最深的 enabled 状态
    }

    // ─── Round 2: 如果有大量 intercept，选浅一点的 ───
    // ★ 关键判断：如果浅于idx的所有状态中intercept占主导...
    if (2 * idx_intercept_sum > cpu_data->total - idx_hit_sum) {
        // 往浅的方向找——从 idx-1 向下
        for (i = idx - 1; i >= 0; i--) {
            intercept_sum += state_bins[i].intercepts;
            if (2 * intercept_sum > idx_intercept_sum) {
                idx = i;  // ← 降级到浅状态
                break;
            }
        }
    }

    // ─── Round 3: QoS 强制降级 ───
    if (idx > constraint_idx)
        idx = constraint_idx;

    // ─── Round 4: 判断是否需要查 sleep_length ───
    // 如果选的状态已经很浅(或QoS很紧)，不用查 timer，直接返回
    if (drv->states[idx].target_residency_ns < RESIDENCY_THRESHOLD_NS &&
        2 * cpu_data->short_idles >= cpu_data->total)
        goto out_tick;  // 短路：历史显示频繁短idle，查timer是浪费

    // ─── Round 5: 用 sleep_length 验证 ───
    duration_ns = tick_nohz_get_sleep_length(&delta_tick);
    if (drv->states[idx].target_residency_ns > duration_ns)
        idx = teo_find_shallower_state(...);  // 最近的timer比当前状态还早→降级

    // ─── Round 6: stop_tick 决策 ───
    // 基于 tick_intercepts 来判断是否保留tick
    return idx;
}

2.8.3.5 teo vs menu 的关键差异

  ┌─────────────────────────────────────────────────────────────────┐
  │ 场景: timer 说还有 2ms，但历史数据显示经常在 50μs 被中断唤醒    │
  ├─────────────────────────────────────────────────────────────────┤
  │ menu:                                                            │
  │   predicted = 2ms × correction_factor                            │
  │   correction_factor 需要多轮才能从 1.0 降到 0.025               │
  │   → 收敛慢，期间会反复选深了被 reality "打脸"                    │
  ├─────────────────────────────────────────────────────────────────┤
  │ teo:                                                             │
  │   sleep_length=2ms → bin[2] (deep)                               │
  │   但 intercepts[0] > hits[2]  → 直接把 idx 从 deep 降到 shallow │
  │   → 瞬时反应，不需要"多轮学习"                                    │
  └─────────────────────────────────────────────────────────────────┘
为什么 teo 可能更省电？
menu 在遇到新模式时会有一段时间的"错误惩罚期"（EWMA 惯性），这段时期的每次错误选择都会消耗额外的电量（进了深状态但很快被唤醒 = 浪费了进出功耗）。teo 的 bin 统计方式可以更快地识别"非 timer 中断主导"的模式。

2.8.4 ladder governor —— 最简单的梯子算法

ladder 不做任何预测。它只根据上一次实际睡了多久来决定升级还是降级：

// ladder.c:67-126 — 核心逻辑

static int ladder_select_state(struct cpuidle_driver *drv,
                               struct cpuidle_device *dev, bool *dummy)
{
    last_residency = dev->last_residency_ns - drv->states[last_idx].exit_latency_ns;

    // Rule 1: 考虑升级 (promotion)
    // 条件: 上次睡得足够久 && 更深状态未被禁用 && 更深状态满足QoS
    if (last_residency > threshold.promotion_time_ns) {
        last_state->stats.promotion_count++;
        if (promotion_count >= 4) {  // 连续4次都睡得够久 → 才升级
            return last_idx + 1;     // 向深一级
        }
    }

    // Rule 2: 考虑降级 (demotion)
    // 条件: 上次睡得不够久 || 当前状态被禁用了 || 当前状态不满足QoS
    if (last_residency < threshold.demotion_time_ns) {
        last_state->stats.demotion_count++;
        if (demotion_count >= 1) {   // 只需1次睡不够 → 就降级
            return last_idx - 1;     // 向浅一级
        }
    }

    return last_idx;  // 保持不变
}

ladder 的升级/降级门槛

参数值含义
promotion_time_ns等于下一级状态的 exit_latency_ns睡得比下一级的进出开销还长 → 值得升级
demotion_time_ns等于当前状态的 exit_latency_ns睡的时间都比不上进出开销 → 赶紧降级
promotion_count需要 ≥ 4保守升级：连续4次都够长才升级
demotion_count需要 ≥ 1激进降级：1次不够就降
ladder 的局限性：它是"瞎子"，不知道下一个 timer 什么时候到。在变化快的场景中可能根本来不及升级就被频繁打断。只在 NO_HZ 关闭（nohz=off）的古老配置中仍然使用（此时 ladder rating 被提升到 25 超过 menu，因为无 dynticks 时 menu 的校正因子计算基本没有优势）。

2.8.5 haltpoll governor —— KVM 虚拟化专用

haltpoll 是专门为 KVM 虚拟化设计的，思想完全不同：

        if (dev->poll_time_limit == true)
            return 1;    // poll 超时了→退到halt(真正的idle)
        return 0;        // poll 没超时→继续poll
    }
    return 0;            // 上次halt→这次poll

    // adjust_poll_limit(): poll_limit_ns 根据 block_ns 动态调整
    //   block 时间长 → grow poll_limit(多poll，因为值得等)
    //   block 时间短 → shrink poll_limit(少poll，不值得等)
}
为什么虚拟机需要 haltpoll？
在虚拟化环境中，进入真实的 C-State（通过 HLT 指令）会触发 VM Exit，让 hypervisor 把 pCPU 调走。但如果在 HLT 和 VM Exit 之间的时间非常短，来回的开销（VM Exit + VM Entry + cache 刷新）可能比收益还大。haltpoll 通过在 HLT 之前先 poll 一段时间（类似忙等），等待可能很快到达的中断，从而减少昂贵的 VM Exit。

2.8.7 stop_tick 决策详解

stop_tick 是 governor 的第二个输出（第一个是状态 index）。它告诉 cpuidle_idle_call() 是否可以关掉 sched tick。


// 为什么 stop_tick 重要？
// 如果 tick 不停，每 4ms (HZ=250) 一次 tick 中断就会把 CPU 从 C-State 中唤醒
// → 深状态根本没法用（因为 exit_latency 可能比 4ms 还大，但实际上 tick 4ms 就打断）
// → 所以：要进深状态，必须先关 tick

// 决策规则（menu/teo 共同的逻辑）:
if (selected_state == polling)        → stop_tick = false  // poll 不能关 tick
else if (predicted_ns < TICK_NSEC)    → stop_tick = false  // 预计很快醒，留 tick
else if (tick_nohz_tick_stopped())    → stop_tick = true   // tick 已经停了
else                                   → stop_tick = true   // 预计睡够久，关 tick

menu 的额外策略：如果 stop_tick == false（tick 不停），menu 会额外检查选中的状态的 target_residency 是否合理——因为 tick 大约 4ms 后就到，选一个 target=10ms 的状态显然不合适：

// menu.c:367-387
if (!*stop_tick) {
    // tick 不停→预期 sleep 不会超过 tick 周期
    // 如果选的状态 target > delta_tick(≈2ms) → 往回找一个浅的
    if (idx > 0 && drv->states[idx].target_residency_ns > delta_tick) {
        for (i = idx - 1; i >= 0; i--)
            if (drv->states[i].target_residency_ns <= delta_tick)
                idx = i;  // 选一个在 tick 到来前能"回本"的浅状态
    }
}

teo 的额外策略：利用 tick_intercepts 的统计——如果大多数 wakeup 都发生在 tick 周期内，说明 tick 还没到就已经被其他中断打断了，那就没必要保留 tick：

// teo.c:472-474
if (drv->states[idx].target_residency_ns < TICK_NSEC &&
    cpu_data->tick_intercepts > cpu_data->total / 2 + cpu_data->total / 8)
    duration_ns = TICK_NSEC / 2;  // 故意设短，导致后续不满足 stop_tick 条件

4. Schedutil —— 调度器驱动的频率调节器

4.1 设计思想：为什么需要 schedutil

传统 governor（如 ondemand）的致命缺陷：采样延迟。


ondemand 模式下的悲剧场景:
  T+0ms:    任务被唤醒，但采样还没到
  T+5ms:    任务以最低频率在跑，卡顿明显
  T+10ms:   ondemand采样到来 → 发现负载高了 → 升频到 max
  T+10.1ms: 任务终于在高频下执行
  → 浪费了 10ms 的延迟，而这恰好是用户能感知的量级

schedutil 的做法:
  T+0ms:    任务被唤醒 → enqueue_task → update_load_avg
            → cpufreq_update_util() → sugov_update_single_freq()
            → 立即升频！(在 μs 级别完成)
  T+0.05ms: 任务已经在高频下执行
  → 延迟从 10ms 级降到 μs 级
关键设计原则：schedutil 直接嵌入调度器的热路径。它不是"定时采样"，而是"事件驱动"——每次任务唤醒、每次 PELT 衰减、每次 tick 都会触发频率重新评估。

// kernel/sched/cpufreq_schedutil.c:193
static unsigned int get_next_freq(struct sugov_policy *sg_policy,
                                   unsigned long util, unsigned long max)
{
    struct cpufreq_policy *policy = sg_policy->policy;
    unsigned int freq;

    freq = get_capacity_ref_freq(policy);    // Step 1: 获取参考频率
    freq = map_util_freq(util, freq, max);   // Step 2: 利用率映射
    return cpufreq_driver_resolve_freq(policy, freq); // Step 3: 取整到支持的OPP
}

// map_util_freq() 的核心公式:
// next_freq = 1.25 * max_freq * util / max
//
// 为什么是 1.25？
// 因为 80% 利用率时, next_freq = 1.25 * max_freq * 0.8 = 1.0 * max_freq
// 即: 当利用率达到80%时，频率已经到达最大值
// 这留下了 20% 的 headroom 用于处理突发负载

// get_capacity_ref_freq() 返回的参考频率:
// (1) arch_scale_freq_ref() — arch 提供的硬件参考频率
// (2) policy->cpuinfo.max_freq — 如果 arch freq invariant
// (3) policy->cur * 1.25 — 降级方案（加了25%余量）

4.7 频率保持与下降延迟

schedutil 有一个重要的启发式策略——不轻易降频：


// kernel/sched/cpufreq_schedutil.c:358
static bool sugov_hold_freq(struct sugov_cpu *sg_cpu)
{
    // 如果 CPU 最近没有 idle（tick_nohz_get_idle_calls_cpu 计数没有增加）
    // 说明 CPU 一直在忙 → 不要降频
    //
    // 原因: CPU 连续忙碌时，短暂的计算间隙不代表负载真的下降了
    //       过早降频会导致下次再忙时又得升回去（频率震荡）
    //
    // 例外: uclamp_max 钳制——即使要 hold 也得降（用户显式要求的）
    idle_calls = tick_nohz_get_idle_calls_cpu(sg_cpu->cpu);
    ret = idle_calls == sg_cpu->saved_idle_calls;  // true → hold
    sg_cpu->saved_idle_calls = idle_calls;
    return ret;
}

4.8 Schedutil 核心总结

#要点
1Schedutil 是事件驱动而非采样驱动——在调度器的每个关键点实时决策
2通过 update_util hook 嵌入调度器，延迟从 ~10ms 降到 μs 级
3频率公式 1.25 * max_freq * util / max 确保 80% util 时已达 max freq
4IO wait boosting 对数据库/web服务器等 IO 密集负载至关重要
5fast_switch 允许在调度器关中断上下文中直接调频（无阻塞路径）
6sugov_hold_freq 防止频率震荡——CPU 持续 busy 时不轻易降频

5. Energy Model —— 能耗模型与 EAS

5.1 为什么需要 Energy Model

前面章节讲了如何在 "忙碌" 时调频（CPUFreq）和 "空闲"时选深度（CPUidle），但有一个更根本的问题没回答：

任务应该放在哪个 CPU 上执行，才能让整个系统的能耗最小？

这是 Energy-Aware Scheduling (EAS) 要解决的问题。而 EM 就是 EAS 的"数据库"——它告诉调度器每个 (CPU, 频率) 组合对应多少功耗和算力。

5.2 核心数据结构


// include/linux/energy_model.h
struct em_perf_domain {
    struct em_perf_table __rcu *em_table;  // ★ RCU 保护的性能状态表
    int                         nr_perf_states;
    unsigned long               flags;
    unsigned long               cpus[];        // 这个 domain 包含的 CPU bitmap
};

struct em_perf_state {
    unsigned long frequency;     // 频率 (kHz)
    unsigned long power;         // ★ 功耗 (mW) — 由驱动或DT提供
    unsigned long cost;          // ★ 能效比 (power/performance × 10) — EAS用
    unsigned long performance;   // 该频率下的算力 (0~1024)
    unsigned long flags;         // EM_PERF_STATE_INEFFICIENT 标记
};

// em_perf_state[] 按频率从低到高排列:
// table[0]: 500MHz, 100mW, performance=250, cost=400
// table[1]: 800MHz, 200mW, performance=400, cost=500
// table[2]: 1.2GHz, 400mW, performance=600, cost=667 ← 这是最优点?
// table[3]: 1.6GHz, 700mW, performance=800, cost=875
// table[4]: 2.0GHz, 1200mW, performance=1024, cost=1172

5.3 Energy Model 的构建

EM 可以通过多种方式构建，取决于平台提供的数据：


// kernel/power/energy_model.c

// 方法1: 驱动通过 em_dev_register_perf_domain() 主动注册
//        传入 em_data_callback {
//            .active_power() → 返回该频率下的功耗(mW)
//        }
// 方法2: 从 Device Tree 的 "opp-table" 节点解析
//        opp-table { opp-500000000 { opp-hz = ... ; opp-microwatt = <100000>; }; }

5.4 Cost 的计算与低效状态标记

这是 EM 中最关键的计算——cost 直接决定了 EAS 的任务放置决策：


// kernel/power/energy_model.c:229
static int em_compute_costs(...)
{
    for (i = nr_states - 1; i >= 0; i--) {
        // cost = power * 10 / performance
        // 含义: 每单位算力的功耗 × 10（放大精度）
        power_res = table[i].power * 10;
        cost = power_res / table[i].performance;
        table[i].cost = cost;

        // ★ 效率标记:
        // 如果升到更高频率后 cost 并没有降低 → 说明升频不划算
        // 标记为 EM_PERF_STATE_INEFFICIENT
        if (table[i].cost >= prev_cost) {
            table[i].flags = EM_PERF_STATE_INEFFICIENT;
            // 调度器在选频率时会跳过这个点
        } else {
            prev_cost = table[i].cost;
        }
    }
}

// 低效状态的直观理解:
// 假设：
//   1.0GHz: 200mW, perf=500 → cost=400
//   1.2GHz: 350mW, perf=600 → cost=583  ← 升了20%频率功耗涨了75%，cost反而大了
//
// 那么 1.2GHz 会被标记为 INEFFICIENT
// → EAS 知道如果不需要 600 的算力，宁愿跑 1.0GHz = 500 的算力

5.5 EM 与 EAS 的交互


// EAS (Energy-Aware Scheduling) 的任务放置决策:
// 对于每个可放置任务的 CPU，计算放置后的预期能耗:

energy_diff = em_cpu_energy(cpu, new_util_after) - em_cpu_energy(cpu, old_util_before);
//            └→ compute_energy() in fair.c
//               利用 em_perf_state 的 cost 值，计算该CPU在新的利用率下需要多少功耗

// → 同时考虑了:
//   (1) 目标任务现在的利用率（决定该走多快）
//   (2) 该 CPU 自身的能效曲线（cost 表）
//   (3) 该 CPU 上已有任务的利用率（共享频率轨的影响）

6. Device Runtime PM —— 设备运行时电源管理

6.1 核心概念：Usage Counter

Runtime PM 管理单个设备的运行时电源状态（而非整个系统）。它的核心是一个简单的引用计数机制：


// include/linux/pm_runtime.h
// 设计思想: "有人用就不关，没人用就可以关"

// 每个 device 有一个 usage_counter:
//  usage_counter > 0: 设备被"使用中"，不能 suspend
//  usage_counter = 0: 设备处于空闲，可以在适当时候 suspend

// 典型使用模式:
// driver_open()    → pm_runtime_get_sync(dev);   // usage_counter++
// ...使用设备...
// driver_release() → pm_runtime_put(dev);         // usage_counter--
//                                                   → 如果变成0，触发suspend

6.2 核心 API


// ★ 引用计数操作
pm_runtime_get(dev);           // 增加引用计数（异步，不保证设备已 resume）
pm_runtime_get_sync(dev);      // 增加引用计数 + 等待 resume 完成
pm_runtime_put(dev);           // 减少引用计数（异步触发 idle/suspend）
pm_runtime_put_sync(dev);      // 减少引用计数 + 等待 suspend 完成

// ★ 控制
pm_runtime_enable(dev);        // 启用 runtime PM
pm_runtime_disable(dev);       // 禁用（force resume + 阻止后续操作）
pm_runtime_forbid(dev);        // 禁止 suspend（引用计数不受影响）
pm_runtime_allow(dev);         // 允许 suspend

// ★ 状态查询
pm_runtime_suspended(dev);     // 设备是否处于 suspended 状态
pm_runtime_active(dev);        // 设备是否 active

6.3 Autosuspend 机制

如果每次 pm_runtime_put 都立即 suspend 设备，频繁的进出延迟会严重影响性能。Autosuspend 解决这个问题：


// include/linux/pm_runtime.h
// autosuspend: put之后不是立即suspend，而是等 idle_timeout

pm_runtime_use_autosuspend(dev);              // 启用 autosuspend
pm_runtime_set_autosuspend_delay(dev, 200);   // 设200ms超时
pm_runtime_mark_last_busy(dev);               // 标记"我刚用过设备"
pm_runtime_put_autosuspend(dev);              // put + 启动autosuspend定时器

// 流程:
// 1. put → 设备进入 RPM_SUSPENDING 状态 → 启动200ms定时器
// 2. 200ms内如果有人 get → 设备回到 active，取消定时器
// 3. 200ms内无人使用 → 定时器到期 → rpm_suspend() → 真正suspend

// 好处: 一个典型的交互式操作可能在100ms内触发多次设备访问
//       autosuspend能避免频繁的 suspend/resume

6.4 Runtime PM 的回调层次

Runtime PM 的回调可以通过多个层级注册（优先级从高到低）：

  dev->pm_domain->ops           → 通用 power domain (如 genpd)
    → dev->type->pm             → 设备类型
      → dev->class->pm          → 设备类
        → dev->bus->pm          → 总线
          → dev->driver->pm     → 驱动 (struct dev_pm_ops {
              .runtime_suspend,
              .runtime_resume,
              .runtime_idle
          })

这个层级设计允许架构代码（如 ARM PSCI genpd）和设备驱动各自处理自己关心的部分。

6.5 Runtime PM 核心总结

#要点
1Runtime PM 管理单个设备的电源，与 CPUidle/CPUFreq 的 CPU 级别管理形成互补
2基于 usage counter——"有人在用就不关"
3Autosuspend 是保持性能和功耗平衡的关键机制——避免频繁进出
4回调优先级：pm_domain > type > class > bus > driver
5ARM64 上 genpd (Generic Power Domain) 常与 PSCI 结合，控制 cluster 级别的 power gate

7.2 Suspend-to-Idle (s2idle) 流程

s2idle 是"最轻量"的休眠——不关闭 RAM，不关闭 CPU 电源。它只做三件事：


// kernel/power/suspend.c

// 入口: echo freeze > /sys/power/state → pm_suspend(PM_SUSPEND_FREEZE)
// 核心流程:
suspend_devices_and_enter(PM_SUSPEND_FREEZE)
  → platform_suspend_begin()           // 通知平台固件
  → suspend_console()                  // 冻结控制台输出
  → dpm_suspend_start(PMSG_FREEZE)     // ★ 设备冻结（调用驱动的.freeze回调）
  → dpm_suspend_end(PMSG_FREEZE)       // ★ 设备后期处理
  → suspend_disable_secondary_cpus()   // 把所有非boot CPU踢出（CPU hotplug）
  → // 所有CPU已冻结，只剩boot CPU在跑
  → tick_freeze()                      // 冻结系统 tick
  → cpuidle_enter_s2idle()             // ★ Boot CPU 进入最深 idle 状态
  // ─── 系统在此休眠 ───
  // 被唤醒中断唤醒
  → tick_unfreeze()
  → suspend_enable_secondary_cpus()   // 恢复次级CPU
  → dpm_resume_start(PMSG_RESUME)     // 恢复设备
  → dpm_resume_end(PMSG_RESUME)
  → resume_console()

7.3 Suspend-to-RAM (STR/Deep Sleep) 流程


// echo mem > /sys/power/state

suspend_devices_and_enter(PM_SUSPEND_MEM)
  → dpm_suspend_start(PMSG_SUSPEND)
  → suspend_disable_secondary_cpus()   // 所有非boot CPU offline
  → syscore_suspend()                  // ★ 系统核心设备 suspend（中断控制器等）
  → // ─── 关键：所有中断被屏蔽 ───
  → platform_suspend_ops->enter(state) // ★ 进入平台特定休眠
  //   └→ ARM64 PSCI: psci_system_suspend() (PSCI 0.2+)
  //      └→ CPU_SUSPEND with StateType=powerdown
  //         └→ ATF: 保存CPU上下文 → 关CPU电源 → DDR进自刷新 → 等唤醒
  //
  // ─── 系统完全 stop，只有唤醒源还在监听 ───
  //
  // 唤醒源触发 → ATF 恢复DDR → 恢复CPU → 从psci_cpu_suspend返回
  → syscore_resume()
  → suspend_enable_secondary_cpus()
  → dpm_resume_start(PMSG_RESUME)

7.4 Hibernate (Suspend-to-Disk)

Hibernate 是"最彻底"的——把整个 RAM 的内容保存到 swap 设备，然后完全断电。唤醒时从 swap 恢复 RAM 镜像。


// kernel/power/hibernate.c + kernel/power/snapshot.c
// 核心流程:
hibernate()
  → freeze_processes()            // 冻结所有用户态进程
  → create_image()                // ★ 将 RAM 快照写入 swap
  //   → 遍历所有 page，将使用的 page 写到 swap
  //   → 压缩（可选 LZO/LZ4）
  → power_down()
  //   → 平台特定：关机或 STR
  // 唤醒后：
  → load_image()                  // ★ 从 swap 读回快照
  //   → 逐页恢复（不覆盖内核自己用的 page）
  → thaw_processes()              // 解冻所有进程

7.5 系统休眠核心总结

#要点
1三种休眠模式：s2idle（最浅，~几μs唤醒）、STR/mem（最常用，~几十ms）、disk（最彻底，~几秒）
2休眠流程是"自底向上 suspend，自顶向下 resume"——设备→CPU→平台
3ARM64 上最终调用 PSCI system_suspend()，由 EL3 固件完成真正的电源门控
4s2idle 并不关 CPU 电源，只是让 CPU 进到最深的 idle 状态（C-state）
5Hibernate 的关键挑战是：写 RAM 镜像时 不能修改 RAM 本身（因此有 snapshot 机制和原子 copy）

8. PM QoS —— 电源管理服务质量约束

8.1 设计目标

PM QoS 提供了一种机制，让应用/驱动/子系统可以向电源管理框架表达自己的延迟需求或带宽需求。它回答："为了省电可以牺牲到什么程度？"


// 两种 QoS：
// 1. CPU Latency QoS:   "CPU 从 idle 醒过来的延迟不能超过 Xμs"
// 2. Device PM QoS:     "这个设备的 resume 延迟不能超过 Xμs"

// 应用场景:
//   - 音频驱动: "我的 DMA 延迟不能超过 500μs" → CPU 不能进太深的 C-State
//   - 用户空间: echo 200 > /dev/cpu_dma_latency → 延迟不超过 200μs

8.2 CPU Latency QoS


// kernel/power/qos.c
// CPU latency QoS 对 CPUidle governor 的影响:

// 每个 CPU 都有 pm_qos 约束
// CPUidle governor 在 select() 中调用:
cpuidle_governor_latency_req(cpu)
  → device_req = dev_pm_qos_raw_resume_latency(device);  // 设备级别的约束
  → global_req = cpu_latency_qos_limit();                 // 全局约束（/dev/cpu_dma_latency）
  → return min(device_req, global_req);                   // 取最严格的

// 状态选择时:
for each state:

        skip  // ← 退出延迟超过QoS要求，不能用这个状态

// 示例: QoS=50μs 时
//    C1 exit_latency=2μs  → ✅
//    C2 exit_latency=20μs → ✅
//    C3 exit_latency=200μs → ❌ QoS拒绝

// 用户空间接口:
$ cat /dev/cpu_dma_latency    // 读取当前最严格的约束
// 打开它并写入一个值来注册约束（保持fd打开，退出自动释放）

// drivers/base/power/qos.c

9. 热管理 —— CPU Cooling 与功率限制

9.1 Thermal Framework 架构

当 SoC 温度过高时，必须限制 CPU 的功耗（降低频率/关核），甚至触发紧急关机。Linux Thermal Framework 使用"导热区（thermal zone）+ 降温设备（cooling device）"模型：


// thermal_zone: 温度传感器 + Trip Points
// cooling_device: CPUFreq / CPUidle / 风扇 等能降低温度的手段

// Trip Points:
trip_point[0]: "passive"  → 65°C → 开始通过降频降温（不影响功能）
trip_point[1]: "hot"      → 85°C → 更激进的降温
trip_point[2]: "critical" → 105°C → 紧急关机（thermal shutdown）

9.2 CPU Cooling Device


// drivers/cpufreq/cpufreq.c + include/linux/cpu_cooling.h

// CPU cooling device 是 cpufreq 的一个"面"
// cpufreq_cooling_register() 注册 cooling device

// 降温级别 (cooling_state) 映射到频率限制:
// state 0: 无限制（可以跑满 freq）
// state 1: 限频到 policy->max * 3/4
// state 2: 限频到 policy->max * 2/4
// state 3: 限频到 policy->max * 1/4
// ...

// thermal governor(如 step_wise, power_allocator) 根据温度决定:
// 当前温度 > trip_temp → cooling_state++
// 当前温度 < trip_temp - hysteresis → cooling_state--

// 用户空间工具:
$ cat /sys/class/thermal/thermal_zone0/temp       // 读取温度(毫摄氏度)
$ cat /sys/class/thermal/cooling_device0/cur_state // 读取当前降频级别

9.3 功率限制 (Power Capping)


// 与温度限制不同，功率限制是"功耗预算"模型
// 使用 thermal power allocator governor:

// 概念: 给一组设备分配一个总功耗预算 (sustainable_power)
// 每个 cooling device 按权重 (weight) 分配降温额度

// 例如: sustainable_power = 5W
//   CPU cooling:     weight=80 → 获得 80% 的降温额度
//   GPU cooling:     weight=20 → 获得 20% 的降温额度

  1. thermal zone + passive cooling 保证不死机
  2. power allocator 或 step_wise governor 进行温控
  3. 配合 EAS 避免把热任务集中在 thermal "热点"CPU上

11.3 ARM64 嵌入式 A53/A57 调优示例

场景：A53 四核 + A57 双核，电池供电设备，需要延长待机时间。


# Step 1: 确认 idle 状态可用
$ ls /sys/devices/system/cpu/cpu0/cpuidle/
state0 state1 state2
$ cat /sys/devices/system/cpu/cpu0/cpuidle/state2/name
cluster-sleep-0
$ cat /sys/devices/system/cpu/cpu0/cpuidle/state2/usage
1342  ← 使用次数很少，说明 governor 很少选这个深状态

# Step 2: 检查 PM QoS 是否挡住了深状态
$ cat /dev/cpu_dma_latency
# 如果输出 "200000" 之类的小值，说明有进程在限制延迟
$ lsof /dev/cpu_dma_latency
# 找出是谁打开的

# Step 3: 检查哪些唤醒源在频繁打断 idle
$ sudo powertop
# → "Top causes for wakeups" 部分
# 假设看到某个驱动每秒产生 100 次中断 → 这就是功耗杀手

# Step 4: 配置 EAS + schedutil
$ cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
$ echo schedutil > /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
# 确认 EM 存在（EAS 需要）
$ ls /sys/kernel/debug/energy_model/
cpu0 cpu4  ← big 和 LITTLE 各有一个 domain

# Step 5: 设置合理的频率范围
$ echo 300000 > /sys/devices/system/cpu/cpu0/cpufreq/scaling_min_freq
$ echo 1400000 > /sys/devices/system/cpu/cpu0/cpufreq/scaling_max_freq
$ echo 500000 > /sys/devices/system/cpu/cpu4/cpufreq/scaling_min_freq
$ echo 2000000 > /sys/devices/system/cpu/cpu4/cpufreq/scaling_max_freq

# Step 6: 对于电池供电场景，考虑在轻负载时offline大核
$ echo 0 > /sys/devices/system/cpu/cpu4/online
# （这会禁用大核，当 wakeup 源不频繁时显著省电）

11.5 核心思维转变

学完整个功耗管理子系统后，最核心的思维转变是：

以前你看 CPU 频率和功耗是两个独立数字，学完之后你看到的是：谁在驱动频率变化（schedutil hook）→ 频率决定功耗（EM cost 表）→ 空闲时进多深由谁决定（governor + PM QoS）→ 温度太高怎么自保（thermal throttling）→ 整个系统如何省电地休眠（s2idle/STR）——从一个静态的"当前频率"变成了一个完整的动态因果链。

能力维度具体体现
功耗问题看得懂 powertop、trace-cmd 输出，能定位深度 idle 进不去的原因
性能调优知道 schedutil rate_limit、io_wait_boost 怎么调，不是在黑盒试参数
系统设计从功耗的角度选择 governor、配置 PM QoS、设计唤醒源
实时系统理解 CPUidle 的 exit_latency 如何影响 real-time deadline，如何用 PM QoS 限制
嵌入式省电知道 idle 状态选择、thermal throttling、EAS 任务放置三者如何协同
故障排查能从"设备发热"追踪到 thermal zone → cooling device → CPUFreq governor → schedutil 的决策
