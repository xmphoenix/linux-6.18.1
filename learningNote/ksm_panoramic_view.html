一、KSM 实现的目标

核心设计目标

KSM（Kernel Samepage Merging）从 Linux 2.6.32 引入，最初为 KVM 虚拟化开发（原名 Kernel Shared Memory）。核心目标：

  1. 内存节省：扫描用户空间匿名页面，将内容相同的页面合并为单个写保护页面，通过 COW 保证写时复制
  2. 透明共享：应用只需 madvise(MADV_MERGEABLE) 标记候选区域，内核自动完成扫描、比较、合并
  3. 安全回退：写操作触发 COW 缺页异常，自动创建私有副本
  4. 可控开销：ksmd 守护线程以可配置频率运行，支持 Smart Scan 和 Advisor 自适应调节
适用场景
  • 虚拟化多个 VM 共享相同 OS 页面
  • 容器多个容器运行相同二进制
  • 应用fork 后子进程共享数据段
约束条件
  • 仅匿名页不合并 pagecache / 文件页
  • 需 MMU依赖写保护机制
  • CPU 开销扫描消耗 CPU
  • 元数据开销rmap_item 占额外内存
KSM 收益公式
# 系统级
general_profit ≈ (pages_sharing + ksm_zero_pages) × PAGE_SIZE
               - (pages_sharing + pages_shared + pages_unshared + pages_volatile) × sizeof(rmap_item)

# 进程级 (/proc/<pid>/ksm_stat)
process_profit ≈ (ksm_merging_pages + ksm_zero_pages) × PAGE_SIZE
               - ksm_rmap_items × sizeof(rmap_item)

# 经验法则 (64-bit): ksm_rmap_items / ksm_merging_pages > 64 → 收益为负

内核 rmap 反向映射机制是什么？

内核页表中存储的是正向映射：虚拟地址 → 物理页（通过 PTE）。但内核经常需要回答一个反向问题：

"给定一个物理页，哪些进程的哪些虚拟地址映射了它？"

这个反向查询在以下场景至关重要：

  • 页面回收：回收物理页前，必须找到并解除所有映射它的 PTE（try_to_unmap()）
  • 页面迁移：NUMA 平衡或内存热插拔时，需要更新所有映射该页的 PTE（try_to_migrate()）
  • 引用计数：判断页面是否被访问过（folio_referenced()）
  • 内存错误：硬件 MCE 发生时，找到所有映射故障页的进程并发送 SIGBUS（collect_procs()）
通用 rmap 的数据结构链
物理页 (folio)
  │
  │  folio->mapping = anon_vma | 0x1    ← 低2位编码类型
  ▼
struct anon_vma                         ← 反向映射树的根
  │  rb_root (interval tree)
  ▼
struct anon_vma_chain                   ← 桥接 VMA 和 anon_vma
  │  ├── vma        → 指向具体的 VMA
  │  ├── anon_vma   → 指回 anon_vma
  │  └── rb         → interval tree 节点
  ▼
struct vm_area_struct (VMA)             ← 进程的虚拟地址区域
  │  vm_start / vm_end / vm_mm
  ▼
页表 PTE                                ← 最终定位到具体的虚拟地址

对于普通匿名页，rmap_walk_anon() 的遍历路径：

// mm/rmap.c
void rmap_walk_anon(struct folio *folio, struct rmap_walk_control *rwc, ...)
{
    // 1. 从 folio->mapping 取出 anon_vma（去掉低2位标志）
    anon_vma = folio_anon_vma(folio);

    // 2. 加读锁
    anon_vma_lock_read(anon_vma);

    // 3. 遍历 interval tree，找到所有映射此页的 VMA
    anon_vma_interval_tree_foreach(vmac, &anon_vma->rb_root, ...) {
        vma = vmac->vma;
        addr = ...;
        rwc->rmap_one(folio, vma, addr, rwc->arg);
        // 回调：try_to_unmap_one / try_to_migrate_one / ...
    }

    anon_vma_unlock_read(anon_vma);
}
KSM 为什么不能用通用 rmap？

通用 rmap 的前提是：一个匿名页只属于一个 anon_vma 树（fork 产生的进程家族）。 但 KSM 页的本质是多个不相关进程的页面被合并成一个——这些进程的 anon_vma 树完全不同！

进程 A (anon_vma_A) ──┐
进程 B (anon_vma_B) ──┤── 内容相同 ──→ 合并为同一个 KSM 页
进程 C (anon_vma_C) ──┘

问题：这个 KSM 页的 folio->mapping 应该指向哪个 anon_vma？
答案：哪个都不能单独指向！需要一种新机制记录所有共享者。
如果强行使用通用 rmap，folio->mapping 只能指向一个 anon_vma， 那么 rmap_walk_anon() 只能遍历一棵 anon_vma 树，会遗漏其他进程的映射—— 导致页面回收/迁移时无法解除所有 PTE，造成数据损坏。
KSM 的解决方案：自建反向映射 + 复用通用基础设施

KSM 采用混合架构：自建一套并行反向映射索引，但在最后定位 VMA 时复用通用的 anon_vma interval tree。

rmap_walk() 分发：KSM 优先判断
// mm/rmap.c — rmap_walk()
void rmap_walk(struct folio *folio, struct rmap_walk_control *rwc)
{
    // ⚠️ KSM 必须在 anon 之前判断！
    // 因为 KSM 页 folio_test_anon() 也返回 true（bit0=1）
    if (unlikely(folio_test_ksm(folio)))
        rmap_walk_ksm(folio, rwc);          // ← KSM 专用路径
    else if (folio_test_anon(folio))
        rmap_walk_anon(folio, rwc, false);   // 普通匿名页
    else
        rmap_walk_file(folio, rwc, false);   // 文件页
}
rmap_walk_ksm() 详解：两轮扫描策略
// mm/ksm.c — rmap_walk_ksm()
void rmap_walk_ksm(struct folio *folio, struct rmap_walk_control *rwc)
{
    stable_node = folio_stable_node(folio);
    search_new_forks = 0;

again:
    // 遍历所有共享此 KSM 页的 rmap_item
    hlist_for_each_entry(rmap_item, &stable_node->hlist, hlist) {
        anon_vma = rmap_item->anon_vma;
        anon_vma_lock_read(anon_vma);

        // 复用通用 interval tree 遍历该 anon_vma 下所有 VMA
        anon_vma_interval_tree_foreach(vmac, &anon_vma->rb_root, 0, ULONG_MAX) {
            vma = vmac->vma;
            addr = rmap_item->address & PAGE_MASK;

            if (addr < vma->vm_start || addr >= vma->vm_end)
                continue;

            // ★ 两轮扫描的关键过滤 ★
            if ((rmap_item->mm == vma->vm_mm) == search_new_forks)
                continue;

            rwc->rmap_one(folio, vma, addr, rwc->arg);
        }
        anon_vma_unlock_read(anon_vma);
    }

    if (!search_new_forks++)    // 第一轮: 0→1, 继续第二轮
        goto again;             // 第二轮: 1→2, 结束
}

两轮扫描的逻辑

轮次search_new_forks处理哪些 VMA目的
第一轮0rmap_item->mm == vma->vm_mm
（原始进程的 VMA）		 先处理 ksmd 扫描时记录的原始映射
第二轮1rmap_item->mm != vma->vm_mm
（fork 产生的新进程 VMA）		 处理扫描后新 fork 出的子进程中的映射

为什么需要两轮：ksmd 扫描合并时记录了 rmap_item->mm（原始进程）。 但合并后原始进程可能 fork 出子进程，子进程继承了 KSM 页面的映射， 其 vma->vm_mm 与 rmap_item->mm 不同。两轮扫描确保不遗漏。

实际场景：rmap_walk_ksm 如何被调用
场景调用链效果
页面回收 try_to_unmap() → rmap_walk() → rmap_walk_ksm() → try_to_unmap_one() 解除所有进程的 PTE，创建 swap entry
页面迁移 try_to_migrate() → rmap_walk() → rmap_walk_ksm() → try_to_migrate_one() 将所有 PTE 从旧页指向新页
KSM 页迁移 folio_migrate_ksm() 直接更新 stable_node->kpfn 更新 stable_node 指向新物理页
硬件内存错误 collect_procs_ksm() → 遍历 stable_node hlist → add_to_kill_ksm() 找到所有映射故障页的进程，发送 SIGBUS
引用检查 folio_referenced() → rmap_walk() → rmap_walk_ksm() 检查 KSM 页是否被任何进程最近访问
总结：KSM 与内核 rmap 的关系是"自建索引 + 复用基础设施"。 KSM 维护自己的 stable_node → rmap_item 反向映射链表（因为一个 KSM 页跨多棵 anon_vma 树）， 但在定位具体 VMA 时复用通用的 anon_vma interval tree、rmap_walk_control 回调接口和锁机制。 通用 rmap 代码通过 folio_test_ksm() 感知 KSM 的存在，并将遍历分发到 rmap_walk_ksm()。

static int ksm_scan_thread(void *nothing) {

六、ARM64 架构特殊处理

MTE 感知页面比较 arch/arm64/kernel/mte.c
int memcmp_pages(struct page *page1, struct page *page2)
{
    ret = memcmp(addr1, addr2, PAGE_SIZE);
    if (!system_supports_mte() || ret)
        return ret;

    // 即使内容相同，若任一页有 MTE 标签 → 拒绝合并
    if (page_mte_tagged(page1) || page_mte_tagged(page2))
        return addr1 != addr2;  // 非零 → 不合并

    return ret;
}
安全原因：若两页内容相同但 MTE 标签不同，合并后 __set_ptes() 会通过 mte_sync_tags() 覆盖标签，导致 MTE 内存安全检查失效。

七、嵌入式设备为何不开启 KSM

问题的提出

嵌入式设备中同样存在 COW 场景（如 fork 后的子进程），但几乎看不到开启 KSM 的实践。 通过源码分析，原因是多维度的：

原因一：结构性内存开销 — 小内存设备上"入不敷出"

KSM 在启动时创建 3 个 slab cache，不论是否实际使用：

// mm/ksm.c — ksm_slab_init()
rmap_item_cache  = KMEM_CACHE(ksm_rmap_item, 0);
stable_node_cache = KMEM_CACHE(ksm_stable_node, 0);
mm_slot_cache    = KMEM_CACHE(ksm_mm_slot, 0);
结构体大小 (ARM64)分配频率
ksm_rmap_item~64 字节每个被扫描的页面
ksm_stable_node~56 字节每个去重后的唯一页面
ksm_mm_slot~40 字节每个参与 KSM 的进程

关键数据：每扫描一个 4KB 页面，需分配 64 字节 rmap_item——1.56% 的元数据开销。 在 256MB 内存的嵌入式设备上，若扫描 10000 个页面，仅 rmap_item 就消耗 640KB。

若 ksm_rmap_items / ksm_merging_pages > 64（64-bit 系统），KSM 净收益为负—— 消耗的元数据内存超过了合并节省的内存。嵌入式设备通常只有单一应用，重复页面极少，几乎必然落入此区间。
原因二：ksmd 内核线程 — CPU 与栈内存的持续消耗
// mm/ksm.c — ksm_init()
ksm_thread = kthread_run(ksm_scan_thread, NULL, "ksmd");
// subsys_initcall → 开机无条件创建
  • 内核栈：ARM64 上永久占用 16KB 内核栈空间
  • CPU 唤醒：默认每 20ms 唤醒一次，即使无任何 MERGEABLE 区域
  • 功耗：嵌入式设备对功耗敏感，持续的背景扫描不利于低功耗设计
原因三：延迟不确定性 — 实时性冲突

许多嵌入式应用有实时或准实时需求。KSM 引入两类不可预测延迟：

  • 扫描延迟：ksmd 在扫描时持有 ksm_thread_mutex，与 __ksm_enter/exit 竞争
  • COW 打破延迟：写入 KSM 页面时触发 break_ksm()，需要分配新页 + 复制内容， 延迟远高于普通缺页

内核文档明确警告："KSM's scans may use a lot of processing power: some installations will disable KSM for that reason."

原因四：工作负载不匹配 — 设计初衷是虚拟化

KSM 的 Kconfig 帮助文本写道："Recommended for use with KVM, or with other duplicative applications."

场景重复页面量KSM 收益
KVM 主机 (10+ VM)极高（相同 OS 内核页）显著
容器宿主机高（共享基础库）明显
桌面 / 服务器中等（fork 子进程）有限
嵌入式单应用极低为负
嵌入式多进程低（进程间数据不同）为负
原因五：内核镜像体积 — Flash 受限

KSM 是 bool 配置（不可编译为模块），启用后永久增加内核 text 段。 mm/ksm.c 有 3980 行代码，编译后约增加 15-20KB 内核镜像体积。 对于 Flash 仅有几 MB 的 MCU 级设备，这一开销不可忽视。

原因六：arch/arm64/mm/init.c 的佐证

ARM64 内存初始化中对极小内存设备的处理方式揭示了内核的设计取向：

// arch/arm64/mm/init.c — arch_mm_preinit()
if (PAGE_SIZE >= 16384 && get_num_physpages() <= 128) {
    // 内存 ≤ 2MB 的极端嵌入式设备
    sysctl_overcommit_memory = OVERCOMMIT_ALWAYS;
}

内核对小内存设备的策略是开启 overcommit（零结构开销），而非启用 KSM（需要 slab + 线程 + 元数据）。 整个 arch/arm64/mm/ 目录中没有任何 KSM 相关代码——KSM 与 ARM64 架构层完全解耦， 没有针对嵌入式的特殊协调。

深入理解：Overcommit 为什么是"零结构开销"？

Overcommit 控制的是虚拟地址空间的审批策略，不是物理页分配。理解这一点是理解内核内存管理的关键：

进程调用 mmap(1GB)
    ↓
内核决策：是否批准这块虚拟地址空间？ ← overcommit 管的是这一步
    ↓
批准后：不分配物理页！只创建 VMA 结构体（几十字节）
    ↓
进程实际读写时 → 缺页异常 → 才按需分配物理页

三种 overcommit 模式（mm/util.c — __vm_enough_memory()）：

模式值行为源码逻辑
OVERCOMMIT_GUESS0默认。粗略检查：单次请求不超过 RAM+swap if (pages > totalram + total_swap) goto error;
OVERCOMMIT_ALWAYS1无条件批准所有虚拟内存请求 if (sysctl_overcommit_memory == OVERCOMMIT_ALWAYS) return 0;
OVERCOMMIT_NEVER2严格记账：总承诺量 ≤ 50%RAM + swap vm_committed_as < vm_commit_limit() ?
"零结构开销"的含义：overcommit 只放宽了虚拟地址的审批门槛。mmap 成功后， 内核只创建了 VMA（几十字节），不分配任何物理页面。物理页在实际缺页时才按需分配。 所以 overcommit 不需要 slab cache、不需要内核线程、不需要每页元数据。

对比 KSM：KSM 需要为每个被扫描的页面分配 64 字节的 rmap_item， 需要 ksmd 线程持续运行——这些都是固定的结构性开销。在 2MB 内存的设备上， KSM 的 slab cache + 线程栈（16KB）就可能占掉总内存的 1% 以上。

总结：嵌入式不开启 KSM 的决策矩阵
因素影响严重程度
rmap_item 元数据开销每页 64 字节，可能净亏损高
ksmd 线程 CPU / 功耗持续唤醒扫描，不利低功耗高
延迟不确定性COW 打破 + 扫描竞争中
工作负载无重复页设计目标是 KVM 多 VM 场景高
内核镜像增大~15-20KB text 段中
无架构层协调与 kswapd 等资源竞争中
例外：若嵌入式设备运行多个相同二进制的容器/进程（如边缘计算网关）， 且内存 ≥ 512MB，KSM 仍可能带来正收益。此时可考虑开启并配合 smart_scan + advisor 降低开销。

八、QEMU 实践指南

以下实验可在 QEMU 模拟的 ARM64 虚拟机中完成，无需物理开发板。

说明：KSM 实验为什么使用匿名页而非 ramfs/tmpfs？

本指南中所有 QEMU 实验的测试程序都使用 mmap(MAP_PRIVATE | MAP_ANONYMOUS) 分配匿名页面。 这是因为 KSM 只合并匿名页面，不合并文件页（pagecache）。具体原因：

  • 匿名页（MAP_ANONYMOUS）：没有文件后端，内核通过 anon_vma / ksm_rmap_item 追踪映射关系。 KSM 可以安全地将其写保护并合并。
  • 文件页 / tmpfs / ramfs：有文件后端（即使 tmpfs 的"文件"在内存中），其一致性由文件系统层保证。 合并文件页会破坏文件系统的语义——两个不同文件的页面不应被合并为同一个。

QEMU 虚拟机的根文件系统使用 qcow2 虚拟磁盘（root=/dev/vda1），测试程序在用户态运行， 通过 mmap / malloc 分配的内存都是匿名页。这与 KSM 的设计目标完全一致。
