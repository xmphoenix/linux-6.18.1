1. 概述与背景

什么是 Memory Compaction？

Memory Compaction（内存压缩/整理）是 Linux 内核 Buddy 分配器的重要组成部分，旨在通过页面迁移来减少外部碎片，使得高阶（high-order）内存分配更容易成功。

核心思想：将分散在内存中的可移动页面（movable pages）迁移到一起，从而在内存的另一端腾出连续的空闲页面块。

为什么需要 Compaction？

  • 透明大页（THP）分配：需要连续的 2MB 物理内存
  • DMA 缓冲区：某些设备需要物理连续的内存
  • 高阶内存分配：内核中各种需要连续页面的场景

Compaction vs Reclaim

特性 Compaction Reclaim
目的 减少外部碎片 释放内存
方式 页面迁移 页面回收/换出
适用场景 碎片化导致的分配失败 内存不足
判断指标 fragmentation_index watermark

Page Migration vs Memory Compaction

页面迁移（Page Migration）是一个基础机制/工具，而 Memory Compaction 是使用这个工具的一个场景。

迁移原因枚举

在代码中，migrate_pages() 有一个 reason 参数来区分不同的使用场景：

// include/linux/migrate_mode.h
enum migrate_reason {
    MR_COMPACTION,           // Memory Compaction 使用
    MR_MEMORY_FAILURE,       // 内存故障恢复
    MR_MEMORY_HOTPLUG,       // 内存热插拔
    MR_SYSCALL,              // move_pages() 系统调用
    MR_MEMPOLICY_MBIND,      // NUMA 内存策略
    MR_NUMA_MISPLACED,       // NUMA 均衡
    MR_CONTIG_RANGE,         // CMA 连续内存分配
    MR_LONGTERM_PIN,         // 长期 pin 的页面
    MR_DEMOTION,             // 内存降级（分层内存）
    MR_PROMOTION,            // 内存升级
    MR_TYPES
};

类比理解

概念 类比 作用
Page Migration 🚚 搬家公司 提供搬运物品的能力
Compaction 🧹 房间整理 使用搬家公司来重新排列，腾出连续空间
NUMA Balancing 📦 就近仓储 使用搬家公司把货物搬到离使用者更近的地方
分开设计的好处：
  • 复用性：页面迁移代码被多个子系统共享（compaction、NUMA、CMA、hotplug 等）
  • 关注点分离：migration 关注"如何安全迁移"，compaction 关注"选择什么页面、迁移到哪里"
  • 可独立配置：可以通过 CONFIG_MIGRATION 和 CONFIG_COMPACTION 分别控制

Compaction 在 Migration 之上增加了什么？

Memory Compaction 在 Page Migration 基础上增加了大量决策层的工作：

层面 Page Migration（只管搬） Compaction（决定搬什么、搬到哪）
页面选择 不关心，调用者指定 双扫描器自动选择源/目标页面
空间策略 不关心 把 movable 页面搬到 zone 末端，腾出前端连续空间
适用性判断 不关心 fragmentation_index 判断碎片是否值得整理
延迟重试 不关心 defer 机制避免无效重复尝试
缓存优化 不关心 缓存扫描器位置，skip hint 跳过无效 pageblock
完成判断 不关心 扫描器相遇、目标 order 已可用即完成
优先级调度 不关心 ASYNC → SYNC_LIGHT → SYNC 逐步升级

Page Migration 的各调用者

以下展示了 migrate_pages() 的各个调用者及其触发条件：

Compaction 特有的触发路径详解

// 触发点 1: Direct Compaction（同步，阻塞分配进程）
__alloc_pages()
  └── __alloc_pages_slowpath()
        └── __alloc_pages_direct_compact()  // 高阶分配失败时
              └── try_to_compact_pages()
                    └── compact_zone_order()
                          └── compact_zone()

// 触发点 2: kcompactd 后台线程（异步，被唤醒执行）
wakeup_kcompactd()  ←── 高阶分配失败时唤醒
  └── kcompactd 线程被唤醒
        └── kcompactd_do_work()
              └── compact_zone()

// 触发点 3: Proactive Compaction（主动，基于碎片分数）
kcompactd() 主循环超时唤醒 (每 500ms 检查一次)
  └── should_proactive_compact_node()
        └── fragmentation_score > wmark_high ?
              └── compact_node(pgdat, true)
                    └── compact_zone()

// 触发点 4: 手动触发
echo 1 > /proc/sys/vm/compact_memory
  └── compact_nodes()
        └── compact_node()
              └── compact_zone()

echo 1 > /sys/devices/system/node/node0/compact
  └── compact_node(NODE_DATA(nid), false)
        └── compact_zone()
总结：Page Migration 就像一个"搬家服务 API"，而 Compaction 是这个 API 最复杂的客户——它自带双向扫描器选页面、碎片化评估决策、多种触发模式、延迟重试策略等完整的"房间整理"逻辑。

Compaction 处理的页面类型

Compaction 的 Migration Scanner 在 isolate_migratepages_block() 中挑选"可以搬走的页面"，能否被搬动由两个维度决定：pageblock 级别的迁移类型 和 单个页面的当前状态。

① pageblock 迁移类型（决定整块是否参与）

迁移类型 含义 Compaction 是否处理
MIGRATE_MOVABLE 可自由迁移：匿名页、文件缓存页、THP 等 ✅ 优先选择，Migration Scanner 的主要目标
MIGRATE_RECLAIMABLE 可回收对象（部分 slab 有 shrinker） ⚠️ 有限支持，取决于对象是否实现迁移回调
MIGRATE_UNMOVABLE 内核固定分配：kmalloc/vmalloc/DMA 无迁移函数 ❌ 整块跳过，是碎片化的"永久障碍"
MIGRATE_CMA CMA 区域，为连续内存预留 ✅ 可被搬走以腾出连续区块
MIGRATE_ISOLATE 已被隔离（正在 compaction 或 hotplug 中） ❌ 跳过，避免重入
MIGRATE_HIGHATOMIC 高阶原子分配预留区 ❌ 跳过

② 单个页面状态（决定某页是否能被隔离）

页面类型 典型来源 能否迁移 原因
匿名页（anon folio） malloc / mmap 私有匿名 ✅ 可迁移 有 swap 后备，内核可安全更新所有 PTE
文件映射页（file folio） mmap 文件、页缓存 read/write ✅ 可迁移 通过 address_space 重定向，不影响文件语义
透明大页（THP folio） PMD 级 2MB 大页 ✅ 整体迁移（需架构支持） ARM64 启用 ARCH_ENABLE_THP_MIGRATION 后整体复制
Slab/kmalloc 页 内核 kmem_cache_alloc() ❌ 通常不可迁移 内核持有裸指针，迁移后旧地址失效会崩溃
vmalloc 页 vmalloc() ❌ 不可迁移 虚拟地址固定，物理页不可挪动
mlock 页（unevictable） mlock() 系统调用 ⚠️ 取决于 compact_unevictable_allowed sysctl 默认为 1 时允许迁移；RT 内核默认禁用
已 pin 页（elevated refcnt） get_user_pages(GUP_PIN)，DMA 映射 ❌ 不可迁移 refcount 升高，迁移会破坏 DMA 映射导致数据损坏
HugeTLB 页 hugetlbfs / MAP_HUGETLB ⚠️ 绕过 compaction 单独处理 由 hugetlb 自身的迁移路径处理，compaction 不直接涉及
Migration Scanner 的跳过判断链（isolate_migratepages_block() 内部）：
  1. pageblock 是 UNMOVABLE / ISOLATE / HIGHATOMIC → 整块 4MB 跳过（设置 skip hint）
  2. 页面未设置 PG_lru（不在 LRU 链表上）→ 跳过单页
  3. 页面 refcount 异常（被 pin/DMA 映射）→ 跳过单页
  4. ASYNC 模式下 folio_trylock 失败 → 跳过（不阻塞当前进程）
  5. unevictable 且 compact_unevictable_allowed=0 → 跳过单页

Compaction 为什么是一个独立概念，而不只是"调用页面迁移"？

核心区别：migrate_pages() 只解决"怎么把已知的页面 A 安全地搬到已知的空位 B"，而 Compaction 解决的是"在 GB 级 zone 里，自动决定哪些页面值得搬、搬到哪里，使宏观效果产生连续空闲区块"。这是两个完全不同层次的问题。

停车场类比

停车场概念 内存对应
挪车操作（司机把车从A位开到B位） Page Migration：把 folio 内容从源物理页复制到目标物理页，更新所有 PTE/地址引用
停车场整理员：巡视全场，决定挪哪辆、挪到哪，使前半区连续空出来 Memory Compaction：双扫描器决策哪些页面可搬、目标位在哪，驱动整体布局优化
大巴车需要连续8个车位 THP / order-9 分配需要 512 个连续物理页
挪车 API 只管"能不能挪"，不管"要不要挪" migrate_pages() 只执行迁移，不做目标选择
整理员知道哪些车位永远被占（固定车位），跳过不浪费时间 Compaction 跳过 MIGRATE_UNMOVABLE pageblock，设置 skip hint 避免重复扫描

Compaction 在 migrate_pages() 之外独有的工作

Compaction 特有能力 如果没有这个，会发生什么
双向扫描器：Migration scanner 从低地址找可移页，Free scanner 从高地址找目标空位，两者相向而行 不知道把哪些页移到哪里，即使调用迁移也无法使空闲页在物理上连续
fragmentation_index 评估：判断分配失败是碎片化导致还是真的内存不足 内存不足时反复做无效 compaction，白白消耗 CPU
Defer 延迟机制：失败后指数退避（最多延迟 64 次），避免无效重试 高负载下同一 zone 被反复整理，严重影响系统响应
Pageblock skip hint：记住哪些 pageblock 上次没有可迁移页，下次跳过 每次都要完整扫描整个 zone，开销随内存大小线性增长（16GB 机器扫描代价极高）
compact_finished() 终止判断：扫描器相遇或目标 order 已满足即停止 不知道何时停止，要么过早停（大页仍分配失败），要么扫全 zone 浪费资源
ASYNC → SYNC_LIGHT → SYNC 优先级升级：先快速异步，再阻塞同步 要么阻塞分配进程过久，要么无法处理持锁的 folio
kcompactd 后台预防：系统空闲时主动整理，减少 direct compaction 触发 所有整理都在分配路径中同步发生，分配延迟出现尖峰
Proactive compaction：基于碎片化分数定期主动整理 等到 THP 分配失败才开始整理，已经太晚
直接用 migrate_pages() 能替代 Compaction 吗？
不能。如果你试图自己实现 compaction 的功能，你需要：①遍历整个 zone 的所有 pageblock，判断哪些是 MOVABLE；②遍历每个 MOVABLE pageblock 里的 LRU 页面，判断是否可隔离；③从 zone 末端的 buddy 系统里找足够的目标空闲页；④调用 migrate_pages()；⑤检查是否已满足目标 order；⑥决定何时放弃。这正是 mm/compaction.c 近 2000 行代码所做的事。Compaction 是整个决策系统，migrate_pages() 只是其中的执行器。

2. 核心数据结构

compact_control 结构体

这是 compaction 过程中最核心的控制结构，定义在 mm/internal.h:

struct compact_control {
    /* 按 order 组织的空闲页面链表 */
    struct list_head freepages[NR_PAGE_ORDERS];
    
    /* 待迁移页面链表 */

    unsigned long migrate_pfn;      // 迁移页扫描器位置
    unsigned long fast_start_pfn;   // 快速扫描起始点
    
    /* 目标 zone */
    struct zone *zone;
    
    /* 统计信息 */
    unsigned long total_migrate_scanned;
    unsigned long total_free_scanned;
    
    /* 分配相关 */
    const gfp_t gfp_mask;           // GFP 分配标志
    int order;                      // 目标分配阶数
    int migratetype;                // 迁移类型
    
    /* 模式控制 */
    enum migrate_mode mode;         // ASYNC/SYNC_LIGHT/SYNC
    bool ignore_skip_hint;          // 忽略跳过提示
    bool direct_compaction;         // 是否为直接压缩
    bool proactive_compaction;      // 是否为主动压缩

    bool contended;                 // 锁竞争标志
    bool finish_pageblock;          // 完成当前 pageblock
};

Pageblock 标志位

定义在 include/linux/pageblock-flags.h：

enum pageblock_bits {
    PB_migrate_0,           // 迁移类型位 0
    PB_migrate_1,           // 迁移类型位 1
    PB_migrate_2,           // 迁移类型位 2
    PB_compact_skip,        // ⭐ Compaction 跳过标记
    PB_migrate_isolate,     // 隔离标记
    __NR_PAGEBLOCK_BITS
};
PB_compact_skip：当一个 pageblock 被标记为 skip 时，compaction 扫描器会跳过它。这个标记在以下情况被设置：
  • pageblock 中没有找到可迁移的页面
  • pageblock 中没有找到空闲页面
  • 迁移失败后

3. 核心算法

双扫描器算法

Compaction 使用两个扫描器相向扫描 zone：

Migration Scanner（迁移扫描器）

  • 从 zone_start_pfn 开始向后扫描
  • 查找 LRU 上的可迁移页面（movable pages）
  • 将找到的页面添加到 cc->migratepages 链表
  • 关键函数：isolate_migratepages()、isolate_migratepages_block()

Free Scanner（空闲扫描器）

  • 从 zone_end_pfn 开始向前扫描
  • 在 buddy 系统中查找空闲页面
  • 将找到的页面添加到 cc->freepages[] 链表
  • 关键函数：isolate_freepages()、isolate_freepages_block()

什么是"隔离"（Isolate）？

"隔离"是 compaction 里的核心专用术语：把页面从它原本所在的管理链表里摘出来，放进 compaction 自己的私有链表，使这期间其他内核路径无法并发分配或回收这些页面。

隔离空闲页（Free Scanner 的工作）

Free Scanner 在 buddy 系统的 free_area[] 链表里找到空闲页后，调用 __isolate_free_page()：

buddy 的 free_area[order] 链表
  ├── [PFN 12-13]  ← buddy 管理的空闲块
  └── [PFN 2-3]

隔离后 → 从 free_area 链表摘出，放入 cc->freepages[]
          buddy 已不知道这些页，其他分配路径无法再拿走它们
          它们将作为迁移的目标位置（destination），等待接收数据

隔离可迁移页（Migration Scanner 的工作）

Migration Scanner 在 LRU 链表里找到可移动页后，调用 isolate_lru_folio()：

zone 的 LRU 链表（active_anon_list / inactive_file_list …）
  ├── [PFN 0]  ← 进程的匿名页，正挂在 LRU 上
  └── [PFN 6]

隔离后 → 从 LRU 链表摘出，folio refcount +1，放入 cc->migratepages
          kswapd / 内存回收路径看不到这些页，不会并发回收它们
          它们将作为迁移的源页面（source），等待内容被复制走

隔离完成后的整体关系

私有链表 来源 角色 迁移完成后
cc->migratepages Migration Scanner 从 LRU 摘出 源页面（内容需要搬走） 旧物理页帧释放回 buddy，形成连续空闲区
cc->freepages[] Free Scanner 从 buddy 摘出 目标槽（用来接收内容） 内容写入后成为进程物理页，PTE 指向新地址
为什么必须"隔离"而不是直接操作？
  • 防止并发竞争：从摘出到迁移完成期间，buddy 分配器、kswapd、其他 CPU 上的进程都可能触碰同一个页面。隔离后这些路径会跳过它们。
  • 原子性保证：migrate_pages() 执行时只操作已隔离的私有链表，不需要持有 zone 锁，减少锁竞争。
  • 失败可回滚：若迁移失败（refcount 异常、I/O 错误等），只需把页面放回原链表（putback_movable_pages()），系统状态不被破坏。

页面迁移流程

/* 在 compact_zone() 中的核心迁移循环 */
while ((ret = compact_finished(cc)) == COMPACT_CONTINUE) {
    /* 1. 隔离待迁移的页面 */
    switch (isolate_migratepages(cc)) {
        case ISOLATE_ABORT:
            // 异常情况，放弃
            goto out;
        case ISOLATE_NONE:
            // 没找到可迁移页面，继续下一个 pageblock
            continue;
        case ISOLATE_SUCCESS:
            // 成功隔离了一些页面
            break;
    }
    
    /* 2. 执行页面迁移 */
    err = migrate_pages(&cc->migratepages, 
                        compaction_alloc,   // 分配目标页面
                        compaction_free,    // 释放失败的页面
                        (unsigned long)cc, 
                        cc->mode,
                        MR_COMPACTION, 
                        &nr_succeeded);
    
    /* 3. 处理迁移结果 */
    if (err) {
        putback_movable_pages(&cc->migratepages);
    }
}

碎片化指数计算

定义在 mm/vmstat.c 中：

/*
 * 碎片化指数：判断分配失败是由于内存不足还是外部碎片
 * 返回值：
 *   -1000: 分配可能会成功
 *   接近 0: 分配失败是由于内存不足
 *   接近 1000: 分配失败是由于碎片化
 */
static int __fragmentation_index(unsigned int order, 
                                   struct contig_page_info *info)
{
    unsigned long requested = 1UL << order;
    
    if (!info->free_blocks_total)
        return 0;
    
    /* 如果有合适大小的空闲块，不需要 compaction */
    if (info->free_blocks_suitable)
        return -1000;
    
    /* 计算碎片化指数 */
    return 1000 - div_u64(
        (1000 + div_u64(info->free_pages * 1000ULL, requested)),
        info->free_blocks_total);
}

/*
 * 外部碎片百分比：小于目标 order 的空闲页占比
 */
unsigned int extfrag_for_order(struct zone *zone, unsigned int order)
{
    struct contig_page_info info;
    fill_contig_page_info(zone, order, &info);
    
    if (info.free_pages == 0)
        return 0;
    
    return div_u64(
        (info.free_pages - (info.free_blocks_suitable << order)) * 100,
        info.free_pages);
}

具体案例：16 页 Zone 的完整 Compaction 过程

以一个只有 16 个物理页帧（PFN 0~15）的简化 Zone 为例，演示双扫描器算法如何解决碎片化问题。每个格子代表 2 个连续页帧（一个 pageblock 简化为 2 页）。

初始内存状态（碎片化，order-2 分配失败）

Step 1：初始化扫描器

migrate_pfn = zone_start_pfn = PFN 0   ← Migration Scanner，从左向右扫
free_pfn    = zone_end_pfn   = PFN 15  ← Free Scanner，从右向左扫

Step 2：Free Scanner 从右向左，隔离空闲页

Free scanner 从 PFN 15 开始向左扫描：PFN 14-15 是 MOVABLE（occupied），跳过；PFN 12-13 是空闲页，调用 __isolate_free_page() 从 buddy 系统中隔离，加入 cc->freepages[]。

cc->nr_freepages = 2
cc->freepages[order-1] → { PFN 12-13 }
free_pfn 更新为 PFN 11（向左移，等待 migration scanner）

Step 3：Migration Scanner 从左向右，隔离可迁移页

依次扫描每个 pageblock：

扫描位置pageblock 类型处理结果
PFN 0-1MOVABLE，anon page，在 LRU 上✅ 隔离成功，加入 migratepages（2 页，已满足空闲目标槽数）
PFN 2-3空闲页，不在 LRU跳过（非 LRU 页，由 free scanner 管理）
PFN 4-5UNMOVABLE（slab）❌ 整块跳过，设置 skip hint

cc->freepages 已有 2 个空闲目标页，隔离到 2 个 migratepages 后本轮即调用 migrate_pages 执行迁移。

cc->migratepages → { PFN 0, PFN 1 }（共 2 页）
migrate_pfn 更新为 PFN 2

Step 4：调用 migrate_pages() 执行迁移

migrate_pages(&cc->migratepages,
              compaction_alloc,   /* 从 cc->freepages 取 PFN 12~13 作为目标 */
              compaction_free,
              (unsigned long)cc,
              MIGRATE_ASYNC,
              MR_COMPACTION);

迁移映射关系：
  PFN 0  → PFN 12  （anon 内容复制 + 进程 PTE 原子更新：va → PFN 12）
  PFN 1  → PFN 13  （同上）

// PFN 0-1 原来的物理页帧现在变为空闲，归还 buddy 系统

Step 5：迁移后内存布局

Step 6：compact_finished() 判断退出

compact_finished() 检查：
  order = 2，需要 4 个连续空闲页
  buddy 系统：PFN 0-1 (order-1) + PFN 2-3 (order-1) → 相邻合并 → PFN 0-3 (order-2) ✅
  返回 COMPACT_SUCCESS → compact_zone() 退出主循环
  zone->compact_cached_free_pfn  更新为 PFN 11（供下次快速扫描）
  zone->compact_cached_migrate_pfn 更新为 PFN 8
案例关键结论：
  • UNMOVABLE 页是"永久障碍"：PFN 4-5 和 PFN 8-9（slab）始终留在原位，compaction 无法移动它们。大量 UNMOVABLE pageblock 会将 zone 分割成孤立的空闲岛，严重限制 compaction 效果——这是为什么内核启动时要将 MOVABLE 和 UNMOVABLE 分配到不同 pageblock。
  • 进程无感知：PFN 0-1 被迁移到 PFN 12-13，进程的虚拟地址（va）通过 PTE 仍然指向正确的物理内容，进程完全感知不到物理位置变化。PFN 6-7（file page）和 PFN 14-15（anon）本轮未被迁移，保持原位。
  • migrate_pages() 是执行器，不是决策者：整个步骤 1~3 都是 compaction 自己的决策逻辑，migrate_pages() 在步骤 4 才被调用一次，执行实际搬迁。

4. 工作流程

compact_zone() 主流程

1

初始化阶段

初始化 compact_control 中的各种计数器和链表，设置扫描器的起始位置。如果是重试（restarting），清除 pageblock 的跳过标记。

2

适用性检查

调用 compaction_suit_allocation_order() 检查是否需要执行 compaction，包括 watermark 检查和碎片化指数评估。

3

迁移扫描

调用 isolate_migratepages() 从 migration scanner 位置开始扫描，找到可迁移的 LRU 页面并隔离到 migratepages 链表。

4

页面迁移

调用 migrate_pages() 执行实际的页面迁移。使用 compaction_alloc() 从空闲链表获取目标页面。

5

完成检查

调用 compact_finished() 检查是否应该停止：两个扫描器相遇、目标 order 的页面已可用、或出现异常情况。

6

清理阶段

释放未使用的空闲页面（release_free_list()），更新缓存的扫描器位置，记录统计信息。

5. 触发机制

Direct Compaction

同步

当高阶内存分配失败时，在页面分配路径中直接触发。

触发条件

  • 分配 order > 0 的页面失败
  • watermark 检查失败但内存碎片化
  • fragmentation_index > extfrag_threshold

调用路径

__alloc_pages_slowpath()
  └── __alloc_pages_direct_compact()
        └── try_to_compact_pages()
              └── compact_zone_order()
                    └── compact_zone()
特点：
  • 阻塞当前进程
  • 会记录 PSI（Pressure Stall Information）
  • 优先级可从 ASYNC 升级到 SYNC_FULL

kcompactd 后台线程

异步

每个 NUMA 节点都有一个 kcompactd 内核线程，在后台执行内存整理。

唤醒条件

  • 高阶分配失败时调用 wakeup_kcompactd()
  • Proactive compaction 定时检查
  • 用户通过 sysctl 手动触发

主循环

static int kcompactd(void *p) {
    while (!kthread_should_stop()) {
        /* 等待唤醒或超时 */
        wait_event_freezable_timeout(
            pgdat->kcompactd_wait,
            kcompactd_work_requested(pgdat),
            timeout);
        
        /* 执行 compaction */
        if (kcompactd_work_requested())
            kcompactd_do_work(pgdat);
        
        /* 主动 compaction */
        if (should_proactive_compact_node())
            compact_node(pgdat, true);
    }
}

Proactive Compaction

主动

基于碎片化分数（fragmentation score）主动执行 compaction，在系统空闲时预防性整理内存。

碎片化分数

/* 节点级别的碎片化分数 */

/* 高水位和低水位 */
wmark_low = 100 - sysctl_compaction_proactiveness;
wmark_high = wmark_low + min(10, wmark_low / 2);

/* 当 score > wmark_high 时开始 compaction */
/* 当 score < wmark_low 时停止 */

控制参数

参数 路径 默认值
proactiveness /proc/sys/vm/compaction_proactiveness 20
检查间隔 HPAGE_FRAG_CHECK_INTERVAL_MSEC 500ms

6. 策略控制

迁移模式

模式 说明 使用场景
MIGRATE_ASYNC 异步迁移，遇到阻塞立即跳过 首次尝试、kcompactd 初始扫描
MIGRATE_SYNC_LIGHT 轻量同步，可等待页面锁但不等待 writeback 默认重试模式、kcompactd 主要工作模式
MIGRATE_SYNC 完全同步，等待所有必要的锁和 I/O 最后一次尝试、手动触发的 compaction

Defer 机制（延迟重试）

当 compaction 失败时，为了避免频繁无效的重试，内核会延迟一段时间再进行 compaction。

/* 失败后延迟 compaction */
static void defer_compaction(struct zone *zone, int order) {
    zone->compact_considered = 0;
    zone->compact_defer_shift++;  // 增加延迟指数
    
    if (order < zone->compact_order_failed)
        zone->compact_order_failed = order;
    
    /* 最多延迟 64 次 (1 << 6) */
    if (zone->compact_defer_shift > COMPACT_MAX_DEFER_SHIFT)
        zone->compact_defer_shift = COMPACT_MAX_DEFER_SHIFT;
}

/* 检查是否应该跳过 */
static bool compaction_deferred(struct zone *zone, int order) {
    unsigned long defer_limit = 1UL << zone->compact_defer_shift;
    
    if (order < zone->compact_order_failed)
        return false;
    
    if (++zone->compact_considered >= defer_limit)
        return false;  // 延迟结束，重新尝试
    
    return true;  // 继续延迟
}
延迟重置条件：
  • compaction 成功后调用 compaction_defer_reset()
  • 分配成功后重置
  • 达到最大延迟次数后重新开始

Pageblock Skip Hint

为了提高效率，compaction 会标记不合适的 pageblock，下次扫描时跳过它们。

/* 设置跳过标记 */
static void update_pageblock_skip(...) {
    set_pageblock_skip(page);
    
    /* 更新空闲扫描器缓存位置 */
    if (pfn < zone->compact_cached_free_pfn)
        zone->compact_cached_free_pfn = pfn;
}

/* 检查是否应该跳过 */
static inline bool isolation_suitable(...) {
    if (cc->ignore_skip_hint)
        return true;
    
    return !get_pageblock_skip(page);
}
Skip 标记清除时机：
  • 当 kswapd 进入睡眠状态时（通过 compact_blockskip_flush 标志）
  • 当 compaction 需要重新开始时（达到最大延迟）
  • 调用 __reset_isolation_suitable() 时

int main() {
    /* 分配 4MB，要求 2MB 对齐以命中 PMD */

    madvise(aligned, HUGEPAGE_SIZE, MADV_HUGEPAGE);

    memset(aligned, 0, HUGEPAGE_SIZE);

各参数效果对比

compaction_proactiveness 触发阈值（wmark_high ≈） 行为 适用场景
0 不触发主动 完全被动，只响应分配失败 延迟敏感型 RT 系统
20（默认） 碎片化分数 > ~82 轻度主动，碎片化严重才动 通用服务器
60 碎片化分数 > ~44 积极主动，频繁后台整理 需要频繁 THP 分配的工作负载
100 碎片化分数 > ~5 极激进，几乎持续整理 数据库 / 大页密集型应用
调参建议：生产环境中建议先用 perf stat -e 'compaction:*' 统计一段时间内的 compaction 频率，再根据 compact_stall（同步阻塞次数）与 thp_fault_alloc 成功率决定是否需要调高 compaction_proactiveness。调高会带来 CPU 消耗，需在 THP 命中率和 CPU 开销之间取得平衡。
