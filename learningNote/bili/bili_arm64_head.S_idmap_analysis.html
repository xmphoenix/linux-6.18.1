1. 概述：什么是 Identity Mapping

// ============ Identity Mapping = VA == PA ============ CPU 发出地址 0x40080000 │ ├── MMU OFF ──▶ 直接访问物理内存 0x40080000 │ └── MMU ON ──▶ 查 PGD→PUD→PMD→PTE ──▶ 翻译得 PA=0x40080000 │ VA 和 PA 完全相等！

为什么需要 Identity Mapping

  • MMU 开启是 CPU 执行那条指令后立刻生效的
  • 下一条指令的 PC 就要经过 MMU 翻译
  • 如果 VA→PA 映射不存在 → 立刻取指异常 → 系统崩溃
  • Identity mapping 保证 MMU 开启瞬间代码不断流

谁负责创建它

  • primary_entry (head.S) 调用 create_init_idmap()
  • 此时 MMU 关闭，CPU 跑在物理地址上
  • C 代码编译为 PIE，使用 PC-relative 寻址
  • 函数运行在物理地址上，直接操作物理内存
💡 Identity mapping 是临时的——MMU 开启后，内核会重建正式页表并切换到高地址虚拟空间（如 0xffff8000xxxxxxxx）。这套 idmap 页表在初始化完成后被废弃。

2. 汇编代码逐行分析 (head.S:89-94)

源码

SYM_CODE_START(primary_entry)
    bl      record_mmu_state       // 记录 MMU 状态 → x19
    bl      preserve_boot_args     // 保存 FDT 等启动参数

    adrp    x1, early_init_stack   // ①
    mov     sp, x1                 // ②
    mov     x29, xzr               // ③
    adrp    x0, __pi_init_idmap_pg_dir // ④
    mov     x1, xzr                // ⑤
    bl      __pi_create_init_idmap // ⑥

逐条解释

行指令作用
①adrp x1, early_init_stack加载 early_init_stack 的 4KB 页基址到 x1
②mov sp, x1设置栈指针（只有 4KB 空间！）
③mov x29, xzr清零帧指针 FP=0，标记栈回溯终点
④adrp x0, __pi_init_idmap_pg_dirx0 = PGD 物理地址 (第1参数 pg_dir)
⑤mov x1, xzrx1 = 0 = clrmask (第2参数)
⑥bl __pi_create_init_idmap调用 C 函数构建 identity mapping

关键设计点

①~③ 栈设置

  • early_init_stack 位于 init_pg_dir 之后，仅 4KB
  • 足够早期简单 C 函数调用（无深层递归，无大局部变量）
  • FP=0 标记栈帧终点：GDB 做 backtrace 时在此终止

④~⑤ 参数传递

  • ARM64 调用约定：x0=第1参数，x1=第2参数
  • clrmask=0：MMU 关闭时不需清除缓存属性位
  • 第二次调用（MMU on 时）会传真正的 clrmask

返回值的使用 (line 101-106)

// create_init_idmap 返回 ptep → 用于 cache 一致性维护 cbnz x19, 0f // MMU 本来就开着？跳过 dmb sy // 内存屏障 mov x1, x0 // x1 = ptep (返回值：页表使用区域结束地址) adrp x0, __pi_init_idmap_pg_dir // x0 = 起始地址 adr_l x2, dcache_inval_poc blr x2 // D-cache invalidate [x0 .. x1)
⚠ MMU 关闭时页表写入是 non-cacheable 的，但 speculative load 可能缓存了旧数据。必须在 MMU 开启前 invalidate 这些 cache lines。

3. C 运行时环境准备 ★

这 6 条指令（line 89-94）在调用 create_init_idmap 之前，为 C 代码执行准备了最小的运行时环境。理解这个环境是理解整个 identity mapping 构建的前提。

3.1 在 MMU 关闭时运行 C 代码 — 为什么可能？

正常 C 运行时依赖

  • 栈指针（SP）有效
  • 数据段可读写
  • BSS 段已清零
  • 全局变量已重定位
  • MMU 提供虚拟地址空间

Early boot 提供的最小集

  • ✓ 栈指针（SP）— 4KB
  • ✓ 代码段可执行（PC-relative）
  • ✗ BSS 未清零
  • ✗ 全局变量未重定位
  • ✓ PIE 编译，无需 MMU
💡 PIE 拯救 early boot：create_init_idmap 和 map_range 所在的 map_range.c 被编译为 位置无关代码（PIE）。所有全局/静态数据访问都使用 PC-relative 寻址，不依赖 MMU 翻译。这就是为什么 MMU 关闭时 C 代码也能正确运行——地址本身就是物理地址。

3.2 三条指令准备运行时

指令寄存器作用为什么需要
adrp x1, early_init_stackx1加载 early_init_stack 的物理地址获取栈空间基址
mov sp, x1SP设置栈指针C 函数调用需要栈（返回地址压栈、局部变量）
mov x29, xzrx29 (FP)清零帧指针标记栈回溯的终点

💡 为什么 4KB 就够了？create_init_idmap 的调用链很简单：create_init_idmap → map_range (2 次) → map_range (递归)。递归深度最多 4 级（PGD→PUD→PMD→PTE），且没有大局部变量。4KB 的栈空间绰绰有余。

3.4 帧指针 FP=0 的意义

正常 C 函数入口Early boot 设置
func:
    stp x29, x30, [sp, #-32]!   // 保存 FP/LR
    mov x29, sp                  // 设置帧指针
 
primary_entry:
    mov x29, xzr                 // FP = 0
    bl  create_init_idmap        // 直接调用

对 backtrace 的影响

  • GDB 中 bt（backtrace）依赖帧指针链
  • FP=0 是链的终止条件（unwinder 见到 0 停止回溯）
  • create_init_idmap 内部有正常的函数序言（prologue），从那里开始有完整的 FP 链
  • 回溯结果：create_init_idmap → ... → ? (FP=0)，准确停在 primary_entry

3.5 PI 编译模型 — __pi_ 前缀

注意到 head.S 中调用的符号是 __pi_create_init_idmap，而不是 create_init_idmap。这是 PI（Position Independent）编译模型的关键：

// ============ PI 编译与链接流程 ============ map_range.c ──编译──▶ map_range.o // 普通 .o │ objcopy --prefix-symbols=__pi_ │ ▼ map_range.pi.o // 所有符号加上 __pi_ 前缀 │ 链接进内核镜像 │ ▼ head.S 调用 __pi_create_init_idmap 为什么这样做？ PI 代码运行在物理地址上，与内核主代码（运行在高虚拟地址）使用不同的地址空间。 加 __pi_ 前缀是为了避免与主内核中的同名符号冲突（虽然 map_range.c 只在 PI 中使用，没有同名冲突）。 更重要的原因是：PI 代码使用的链接脚本段不同（.init 段），objcopy 用 --prefix-alloc-sections=.init 确保这一点。
// arch/arm64/kernel/pi/Makefile

# 将 map_range.o 转换为 map_range.pi.o，所有符号添加 __pi_ 前缀
$(obj)/%.pi.o: OBJCOPYFLAGS := --prefix-symbols=__pi_ \
                                --remove-section=.note.gnu.property
$(obj)/%.pi.o: $(obj)/%.o $(obj)/relacheck FORCE
    $(call if_changed,piobjcopy)

# PI 代码使用特殊的编译标志
KBUILD_CFLAGS := -fpie -Os -ffreestanding \
                 -fno-stack-protector ...
编译标志作用
-fpie生成位置无关可执行代码，所有寻址通过 PC-relative
-ffreestanding独立环境编译，不依赖标准库（没有 memset/memcpy 等）
-fno-stack-protector禁用栈保护，因为没有 __stack_chk_fail
-Os优化代码大小，减少栈使用
CFLAGS_map_range.o += -mstrict-alignMMU off 时不对齐访问会触发异常
⚠ 对比完整 C 运行时：2.6 之前的内核中，early boot C 代码需要手动初始化 BSS、重定位数据段、设置异常向量等。现代内核通过 PIE + 最小栈的方式，在进入 C 之前只需要设置 SP 即可，极大地简化了汇编阶段的准备工作。

3.6 参数传递约定

参数寄存器值含义
第 1 个（pg_dir）x0__pi_init_idmap_pg_dirPGD 的物理地址
第 2 个（clrmask）x10（xzr）不清除任何 protection bit
💡 xzr 的技巧：mov x1, xzr 读的是零寄存器（Zero Register），这是 ARM64 的一个特殊寄存器，永远返回 0。不需要先加载 0 到某个通用寄存器再 mov，xzr 直接提供 0 值，既省指令又省功耗。

4. create_init_idmap C 函数 ★

3.1 函数完整源码

asmlinkage phys_addr_t __init create_init_idmap(pgd_t *pg_dir, ptdesc_t clrmask)
{
    phys_addr_t ptep = (phys_addr_t)pg_dir + PAGE_SIZE; // ① 空闲页指针 = PGD 后的第一个页
    pgprot_t text_prot = PAGE_KERNEL_ROX;               // ② 代码段：只读+可执行
    pgprot_t data_prot = PAGE_KERNEL;                   // ③ 数据段：可读写

    pgprot_val(text_prot) &= ~clrmask;                  // ④ clrmask=0 时无效
    pgprot_val(data_prot) &= ~clrmask;

    // ⑤ 映射代码段 [_stext .. __initdata_begin)  ROX
    map_range(&ptep, (u64)_stext, (u64)__initdata_begin,
              (phys_addr_t)_stext, text_prot, IDMAP_ROOT_LEVEL,
              (pte_t *)pg_dir, false, 0);

    // ⑥ 映射数据段 [__initdata_begin .. _end)  RW
    map_range(&ptep, (u64)__initdata_begin, (u64)_end,
              (phys_addr_t)__initdata_begin, data_prot, IDMAP_ROOT_LEVEL,
              (pte_t *)pg_dir, false, 0);

    return ptep;                                        // ⑦ 返回使用区域的结束地址
}

3.2 保护属性展开

宏展开效果
PAGE_KERNEL_ROX PROT_NORMAL & ~(PTE_WRITE | PTE_PXN) | PTE_RDONLY EL1 可读可执行，禁止写入 ← W^X 安全策略
PAGE_KERNEL PROT_NORMAL | PTE_WRITE EL1 可读写，禁止执行（PXN=1）

3.3 两段映射策略 — 为什么分成两段？

// ============ 内核镜像 ============ _stext ──────────────┐ .head.text │ .text ├─ 第一段: ROX (Read-Only + Execute) .rodata │ map_range(..., text_prot, ...) .init.text │ __initdata_begin ────┤ idmap 页表区域 │ .init.data │ .data ├─ 第二段: RW (Read-Write, XN) .bss │ map_range(..., data_prot, ...) init 页表区域 │ early_init_stack │ _end ────────────────┘
💡 W^X 安全原则：代码不可写，数据不可执行。即使攻击者控制了数据段，也无法执行注入的代码。这是内核最基本的安全防护。

5. map_range 核心递归算法 ★

4.1 参数表

void map_range(
    phys_addr_t *pte,     // [in/out] 空闲物理页指针（分配新页表时递增）
    u64 start,            // 映射起始 VA
    u64 end,              // 映射结束 VA (exclusive)
    phys_addr_t pa,       // 映射起始 PA  ← identity map 时 pa == start !
    pgprot_t prot,        // 保护属性
    int level,            // 当前层级 (0=PGD, 1=PUD, 2=PMD, 3=PTE)
    pte_t *tbl,           // 当前层级页表基址
    bool may_use_cont,    // 是否可用 contiguous bit (此处为 false)
    u64 va_offset         // 页表 PA→VA 偏移 (MMU off 时为 0)
);

4.2 算法伪代码

map_range(..., level, tbl, ...):

    // 每级解析的 VA bit 数: 9 bits
    lshift = (3 - level) * PTDESC_TABLE_SHIFT

    // 本级每个 entry 覆盖范围 - 1
    lmask  = (PAGE_SIZE << lshift) - 1
    // level 0: 512GB-1
    // level 1: 1GB-1
    // level 2: 2MB-1
    // level 3: 4KB-1

    // 定位到覆盖 start 的 entry
    tbl += (start >> (lshift + 12)) % 512
    // 设置描述符类型位
    protval |= (level == 2) ? PMD_TYPE_SECT
                            : PTE_TYPE_PAGE

    while (start < end):
        next = min((start | lmask) + 1,
                   ALIGN(end, PAGE_SIZE))

        if level < 2 OR (level == 2 AND 不对齐):
            // → 递归创建下级页表
            if tbl[entry] 为空:
                分配新物理页作为下级页表
            map_range(..., level+1, ...)

        else:
            // → 直接放 Block/Page 映射
            tbl[entry] = pa | protval

        pa    += next - start
        start  = next
        tbl++

4.3 关键判断逻辑

Level覆盖范围行为原因
0 (PGD)512 GB总是递归 512GB 太粗粒度，必须细分
1 (PUD)1 GB总是递归 1GB 仍太粗，需进一步细分
2 (PMD)2 MB对齐→Block；不对齐→递归 内核 2MB 对齐加载 → 几乎总是 Block
3 (PTE)4 KB直接 Page 映射 最细粒度，没有更下级了
💡 2MB Block Mapping 是性能关键：ARM64 boot protocol 要求 2MB 对齐，所以 PMD level 几乎总能使用 block descriptor。一个 ~30MB 的内核仅需约 15 个 PMD entries，而非 7500+ 个 PTE entries！

6. 实例演练（4KB 页面 + 48bit VA 一步步走）

5.1 参数计算

参数公式值
PAGE_SHIFT—12 (4KB pages)
PTDESC_ORDER—3 (描述符 8 字节 = 2³)
PTDESC_TABLE_SHIFTPAGE_SHIFT - 39 (每级解析 9 bits VA)
PTRS_PER_PTE2^9512 (每级 512 个 entries)
ARM64_HW_PGTABLE_LEVELS(48)(48 - 3 - 1) / 94 (需要 4 级页表)
IDMAP_ROOT_LEVEL4 - IDMAP_LEVELS0 (从 PGD 开始)

5.2 一步步跟踪（假设内核在 0x40080000，~30MB）

  1. Level 0 (PGD) — 分配 PUD
    lshift = (3-0)×9 = 27，lmask = 512GB - 1
    整个内核镜像 < 512GB → 只需 1 个 PGD entry
    tbl_index = (0x40080000 >> 39) % 512 = 0（PGD[0]）
    → PGD[0] 写入 Table descriptor，指向新分配的 PUD 物理页
    → *pte += 4096（分配了 1 页）
  2. Level 1 (PUD) — 分配 PMD
    lshift = (3-1)×9 = 18，lmask = 1GB - 1
    内核 ~30MB < 1GB → 只需 1 个 PUD entry
    → PUD[0] 写入 Table descriptor，指向新分配的 PMD 物理页
    → *pte += 4096
  3. Level 2 (PMD) — 放置 Block 映射
    lshift = (3-2)×9 = 9，lmask = 2MB - 1
    start=0x40080000, pa=0x40080000 → 都 2MB 对齐！✅
    → 直接写 Block descriptor：
    PMD[i] = 0x40080000 | PMD_TYPE_SECT | prot_ROX
    → 无需分配 PTE 页表！
    → 循环放置 ~15 个 block entries（覆盖 ~30MB 代码段）
  4. 第二段 (数据段) 同理
    从 __initdata_begin 开始，保护属性切换为 RW
    → 继续在同一个 PMD 表里放 Block entries
    → 共用已有的 PGD/PUD/PMD 页表（不重复分配）
// ============ 页表结构总览 ============ PGD (Level 0) PUD (Level 1) PMD (Level 2) ┌──────────────┐ ┌──────────────┐ ┌──────────────────────────────┐ │ [0] ─────────┼───▶│ [0] ─────────┼───▶│ [0] empty │ │ [1..511] │ │ [1..511] │ ├──────────────────────────────┤ │ empty │ │ empty │ │ ... │ └──────────────┘ └──────────────┘ ├──────────────────────────────┤ │ [4] 0x40080000 | BLOCK | ROX │ ← 2MB │ [5] 0x400a0000 | BLOCK | ROX │ ← 2MB │ [6] 0x400c0000 | BLOCK | ROX │ ← 2MB │ ... (代码段，~15 个 ROX block) │ ├──────────────────────────────┤ │ [N] 0x4xxx0000 | BLOCK | RW │ ← 2MB │ [N+1] 0x4xxx0000 | BLOCK | RW │ ← 2MB │ ... (数据段，几个 RW block) │ ├──────────────────────────────┤ │ [...] empty │ └──────────────────────────────┘ 共分配: PGD(1页) + PUD(1页) + PMD(1页) = 3 个物理页 映射 ~30MB+ 内核，仅用 ~15 个 PMD block entries

7. ARM64 页表结构详解

6.1 VA 地址划分 (48-bit, 4KB pages, 4-level)

47 39 38 30 29 21 20 12 11 0 ┌──────┬──────┬──────┬──────┬──────────┐ │ L0 │ L1 │ L2 │ L3 │ Offset │ │ 9bit │ 9bit │ 9bit │ 9bit │ 12bit │ └──┬───┴──┬───┴──┬───┴──┬───┴────┬─────┘ │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ PGD PUD PMD PTE Page Offset 512GB 1GB 2MB 4KB (offset within page) /entry /entry /entry /entry

6.2 描述符格式 (64-bit)

类型bits[1:0]物理地址位说明
Table descriptor 11 PA[47:12] @ bits[47:12] 指向下一级页表的物理地址
Block descriptor (L2) 01 PA[47:21] @ bits[47:21] 直接映射 2MB，无需 PTE
Page descriptor (L3) 11 PA[47:12] @ bits[47:12] 映射 4KB 单页

6.3 关键属性位

Bit名称含义
0-1Type00=invalid, 01=Block, 11=Table/Page
2-4AttrIndxMAIR 寄存器索引，决定内存类型 (normal/device/cacheable)
6-7AP[2:1]Access Permission (读写执行权限，与 PXN/UXN 配合)
10AFAccess Flag (硬件置 1 表示该页被访问过)
52Contiguous连续块标志 (此处 idmap 不使用)
53PXNPrivileged Execute Never — EL1 不可执行
54UXN/XNEL0 不可执行 / 所有特权级不可执行
💡 理解 PXN：PAGE_KERNEL_ROX 清除了 PXN 位（允许 EL1 执行），而 PAGE_KERNEL 设置了 PXN 位（禁止执行）。这就是 W^X 在硬件层面的实现。

7.2 页表分配策略 — 线性增长

// ============ idmap 页表区域的线性分配 ============ __pi_init_idmap_pg_dir ──┐ ┌────────────────────────┐ │ PGD (4KB) │ ← pg_dir 参数，调用者传入 ├────────────────────────┤ ← ptep 初始值 = pg_dir + PAGE_SIZE │ PUD (4KB) │ ← map_range 中第一次分配 ├────────────────────────┤ │ PMD (4KB) │ ← map_range 中第二次分配 ├────────────────────────┤ │ (可能更多 PMD/PTE) │ ← 仅在 range 跨多个 PGD/PUD entry 时才分配 ├────────────────────────┤ │ unused │ ├────────────────────────┤ ← ptep 返回值（= 使用结束地址） │ unused │ ├────────────────────────┤ │ early_init_stack │ │ (4KB) │ ← 后面紧跟着（不在 idmap 页表区域内） └────────────────────────┘ 分配的每一页都是物理页，没有复杂的内存管理器 ptep 只是一个递增的 phys_addr_t 指针

7.3 分配代码

// map_range 中，当需要创建下级页表时：
if (pte_none(*tbl)) {
    // 把当前空闲物理页作为下级页表
    *tbl = __pte(__phys_to_pte_val(*pte) |
                 PMD_TYPE_TABLE | PMD_TABLE_UXN);
    // 前进到下一个空闲物理页 (512 entries × 8 bytes = 4096)
    *pte += PTRS_PER_PTE * sizeof(pte_t);
}
💡 PGD 本身是调用者传入的（链接脚本预留），不需要分配。需要分配的是下级页表（PUD、PMD、可能的 PTE）。线性分配极简高效，适合 MMU-off 环境。

define dump_pgtables

    # 功能: 递归 dump 4 级页表，验证 identity mapping

            end

11. 总结 & 关键要点

#要点说明
1 Identity Mapping = VA == PA 开启 MMU 瞬间 PC 还在物理地址，必须有 1:1 映射保证指令不断流
2 两段映射 + W^X 代码段 ROX (Read-Only+Execute)，数据段 RW (no-Execute)，硬件级安全隔离
3 2MB Block Mapping PMD level 使用 block descriptor，比逐页映射效率高 512 倍
4 递归自顶向下 map_range 只在必要时创建下级页表，PGD→PUD→PMD 逐级展开
5 线性分配页表 从 PGD 之后顺序取物理页，ptep 指针简单递增，无需内存管理器
6 clrmask 机制 Cold boot 时 =0 (不需要)；Warm boot 时用来修正 non-cacheable→cacheable 的缓存属性差异
7 PIE 编译 C 代码在物理地址上运行，全部使用 PC-relative 寻址，与 MMU 状态无关
8 Type bits[1:0] 00=invalid, 01=Block(leaf), 11=Table(pointer) 或 Page(leaf)，bit1 区分 leaf vs pointer
