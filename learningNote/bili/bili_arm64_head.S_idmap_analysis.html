1. 概述：什么是 Identity Mapping

// ============ Identity Mapping = VA == PA ============ CPU 发出地址 0x40200000 │ ├── MMU OFF ──▶ 直接访问物理内存 0x40200000 │ └── MMU ON ──▶ 查 PGD→PUD→PMD→PTE ──▶ 翻译得 PA=0x40200000 │ VA 和 PA 完全相等！

为什么需要 Identity Mapping

  • MMU 开启是 CPU 执行那条指令后立刻生效的
  • 下一条指令的 PC 就要经过 MMU 翻译
  • 如果 VA→PA 映射不存在 → 立刻取指异常 → 系统崩溃
  • Identity mapping 保证 MMU 开启瞬间代码不断流

谁负责创建它

  • primary_entry (head.S) 调用 create_init_idmap()
  • 此时 MMU 关闭，CPU 跑在物理地址上
  • C 代码编译为 PIE，使用 PC-relative 寻址
  • 函数运行在物理地址上，直接操作物理内存
💡 Identity mapping 是临时的——MMU 开启后，内核会重建正式页表并切换到高地址虚拟空间（如 0xffff8000xxxxxxxx）。这套 idmap 页表在初始化完成后被废弃。

2. 汇编代码逐行分析 (head.S:89-94)

源码

SYM_CODE_START(primary_entry)

    adrp    x1, early_init_stack   // ①
    mov     sp, x1                 // ②
    mov     x29, xzr               // ③
    adrp    x0, __pi_init_idmap_pg_dir // ④
    mov     x1, xzr                // ⑤

逐条解释

行指令作用
①adrp x1, early_init_stack加载 early_init_stack 的 4KB 页基址到 x1
②mov sp, x1设置栈指针（只有 4KB 空间！）
③mov x29, xzr清零帧指针 FP=0，标记栈回溯终点
④adrp x0, __pi_init_idmap_pg_dirx0 = PGD 物理地址 (第1参数 pg_dir)
⑤mov x1, xzrx1 = 0 = clrmask (第2参数)
⑥bl __pi_create_init_idmap调用 C 函数构建 identity mapping

关键设计点

①~③ 栈设置

  • early_init_stack 位于 init_pg_dir 之后，仅 4KB
  • 足够早期简单 C 函数调用（无深层递归，无大局部变量）
  • FP=0 标记栈帧终点：GDB 做 backtrace 时在此终止

④~⑤ 参数传递 + xzr 技巧

  • ARM64 调用约定：x0=第1参数，x1=第2参数
  • clrmask=0：MMU 关闭时不需清除缓存属性位
  • mov x1, xzr — xzr 是零寄存器，永远返回 0，比先加载 0 再 mov 更高效

返回值的使用 (line 101-106)

// create_init_idmap 返回 ptep → 用于 cache 一致性维护 cbnz x19, 0f // MMU 本来就开着？跳过 dmb sy // 内存屏障 mov x1, x0 // x1 = ptep (返回值：页表使用区域结束地址) adrp x0, __pi_init_idmap_pg_dir // x0 = 起始地址 adr_l x2, dcache_inval_poc blr x2 // D-cache invalidate [x0 .. x1)

3. C 运行时环境准备 ★

这 6 条指令（line 89-94）在调用 create_init_idmap 之前，为 C 代码执行准备了最小的运行时环境。

3.1 在 MMU 关闭时运行 C 代码 — 为什么可能？

正常 C 运行时依赖

  • 栈指针（SP）有效
  • 数据段可读写
  • BSS 段已清零
  • 全局变量已重定位
  • MMU 提供虚拟地址空间

Early boot 提供的最小集

  • ✓ 栈指针（SP）— 4KB
  • ✓ 代码段可执行（PC-relative）
  • ✗ BSS 未清零
  • ✗ 全局变量未重定位
  • ✓ PIE 编译，无需 MMU
💡 PIE 拯救 early boot：create_init_idmap 所在的 map_range.c 被编译为位置无关代码（PIE）。所有全局/静态数据访问都使用 PC-relative 寻址，不依赖 MMU 翻译。地址本身就是物理地址。

3.3 帧指针 FP=0 的意义

对 backtrace 的影响

  • GDB 中 bt（backtrace）依赖帧指针链
  • FP=0 是链的终止条件（unwinder 见到 0 停止回溯）
  • create_init_idmap 内部有正常的函数序言（prologue），从那里开始有完整的 FP 链

3.4 PI 编译模型 — 为什么需要专门构建

head.S 中调用的符号是 __pi_create_init_idmap，不是 create_init_idmap。核心问题：-fpie 指示编译器尽量使用 PC-relative 寻址，但不保证不产生绝对地址引用。PI 编译系统通过 relacheck 工具 提供硬保证。

// ============ PI 编译的完整流程 ============ map_range.c │ ├─ 编译器标志: │ -fpie // 生成 PC-relative 代码 (尽力而为) │ -ffreestanding // 无 libc 依赖 │ -fno-stack-protector // 无栈保护 (无 __stack_chk_fail) │ -mstrict-align // 禁用不对齐访问 (MMU off 会崩溃) │ -Os // 优化体积 → 减少栈使用 │ ▼ map_range.o // 可能仍有 ABS64 重定位！ │ ├─ objcopy: │ --prefix-symbols=__pi_ // 所有符号加 __pi_ 前缀 → 命名空间隔离 │ --remove-section=.note.gnu.property │ ├─ relacheck ★ 关键步骤 │ │ 扫描所有 RELA 段，寻找 R_AARCH64_ABS64 │ ├── 在 .rodata.prel64 中发现 → 转换为 PREL64 (PC-relative) │ └── 在其他段中发现 → 构建失败！ │ ▼ map_range.pi.o // 保证零绝对地址引用

relacheck — 硬保证机制

relacheck 不是可选的检查工具，而是构建流程的强制步骤。objcopy 之后立即运行，如果检测到任何 R_AARCH64_ABS64 重定位不在 .rodata.prel64 段中，就会删除输出文件并导致构建失败。

// arch/arm64/kernel/pi/relacheck.c (关键逻辑)
for (int j = 0; j < numrela; j++) {
    if (ELF64_R_TYPE(info) != R_AARCH64_ABS64)
        continue;                          // 只关心 ABS64 类型
    if (prel64) {
        // .rodata.prel64 中的: 转换为 PC-relative
        info ^= R_AARCH64_ABS64 ^ R_AARCH64_PREL64;
    } else {
        // 其他段中的: 致命错误！删除输出文件，构建失败
        fprintf(stderr, "Unexpected absolute relocations detected\n");
        unlink(argv[1]);
        exit(EXIT_FAILURE);
    }
}

prel64 标志的来源 — 段名决定一切

if (strstr(strtab + swab_elfword(shdr[info].sh_name),
           ".rodata.prel64")) {
    prel64 = true;    // ★ 段名包含 ".rodata.prel64" → 放行
}

这是留给那些"必须使用绝对地址"的场景（极少）的一个可控出口 — 代价是引用代码必须手动配合 prel64_pointer() 宏来解引用。

不是独立工具 — 构建流程的强制环节

// arch/arm64/kernel/pi/Makefile
quiet_cmd_piobjcopy = $(quiet_cmd_objcopy)
      cmd_piobjcopy = $(cmd_objcopy) && $(obj)/relacheck $(@) $(<)
$(obj)/%.pi.o: $(obj)/%.o $(obj)/relacheck FORCE
    $(call if_changed,piobjcopy)
// ============ piobjcopy 的执行流程 ============ map_range.o // 编译产物 (可能含 ABS64) ├─ cmd_objcopy // ① objcopy: 加 __pi_ 前缀，生成 .pi.o ├─ && // ② && — 只有 objcopy 成功才继续 ├─ $(obj)/relacheck $(@) $(<) // ③ relacheck 扫描 .pi.o │ ├── 通过 → .pi.o 就绪 │ └── 失败 → unlink(.pi.o) + exit(1) → make 报错终止

为什么不全用 PI？

1. relacheck 太严格 — 禁止了大量正常 C 代码模式（静态初始化引用链接器符号、switch 跳转表、函数指针数组）。PI 代码只有几百行可手工保证，整个内核几百万行不可能。

2. 不需要。实际上已经全部使用 __pi_ 版本——验证 Makefile 中 obj-y 只有 .pi.o 被链接进 vmlinux。极少数"同名"情况（如 dcache_inval_poc / __pi_dcache_inval_poc）是通过 SYM_FUNC_ALIAS 给同一个函数地址起了两个别名，不是两份代码。

💡 本质上是两种不同的"位置无关"策略：PI 代码通过 relacheck 保证零绝对引用，适用于 MMU-off 环境。CONFIG_RELOCATABLE 通过运行时重定位表修补保证位置无关，适用于整个内核。各司其职，不互相替代。

4. create_init_idmap C 函数 ★

4.1 函数完整源码

asmlinkage phys_addr_t __init create_init_idmap(pgd_t *pg_dir, ptdesc_t clrmask)
{
    phys_addr_t ptep = (phys_addr_t)pg_dir + PAGE_SIZE; // ① PGD 后第一个空闲物理页
    pgprot_t text_prot = PAGE_KERNEL_ROX;               // ② 代码段：只读+可执行
    pgprot_t data_prot = PAGE_KERNEL;                   // ③ 数据段：可读写

    pgprot_val(text_prot) &= ~clrmask;                  // ④ clrmask=0 时无效
    pgprot_val(data_prot) &= ~clrmask;

    // ⑤ 映射代码段 [_stext .. __initdata_begin)  ROX
    map_range(&ptep, (u64)_stext, (u64)__initdata_begin,
              (phys_addr_t)_stext, text_prot, IDMAP_ROOT_LEVEL,
              (pte_t *)pg_dir, false, 0);

    // ⑥ 映射数据段 [__initdata_begin .. _end)  RW
    map_range(&ptep, (u64)__initdata_begin, (u64)_end,
              (phys_addr_t)__initdata_begin, data_prot, IDMAP_ROOT_LEVEL,
              (pte_t *)pg_dir, false, 0);

    return ptep;                                        // ⑦ 返回使用区域的结束地址
}

4.2 保护属性

宏展开效果
PAGE_KERNEL_ROXPROT_NORMAL & ~(PTE_WRITE | PTE_PXN) | PTE_RDONLYEL1 可读可执行，禁止写入 ← W^X
PAGE_KERNELPROT_NORMAL | PTE_WRITEEL1 可读写，禁止执行（PXN=1）

4.3 两段映射策略 — 为什么分成两段？

// ============ 内核镜像 ============ _stext ──────────────┐ .head.text │ .text ├─ 第一段: ROX (Read-Only + Execute) .rodata │ map_range(..., text_prot, ...) .init.text │ __initdata_begin ────┤ idmap 页表区域 │ .init.data ├─ 第二段: RW (Read-Write, XN) .data │ map_range(..., data_prot, ...) .bss │ _end ────────────────┘
💡 W^X 安全原则：代码不可写，数据不可执行。即使攻击者控制了数据段，也无法执行注入的代码。

4.4 核心机制：_stext 明明是链接高地址，运行时怎么变成物理地址？

这是理解 identity mapping 最关键的认知转折点。_stext 在链接时被分配在 0xffff800080010000，但 idmap 声称 VA == PA。这两个值差了 0xffff80003FE00000，怎么相等？

// ============ _stext 的两重身份 ============ 链接时 (linker视角): _stext = 0xffff800080010000 (高 VA) 运行时 (MMU off): _stext = 0x40210000 (物理地址) 同一个符号，两个不同的值。关键在 -fpie 的 PC-relative 寻址!

推导：PC-relative 如何"免费"得到物理地址

编译器处理 (u64)_stext 时，不会嵌入绝对地址 0xffff800080010000，而是生成：

adrp  x0, _stext           // x0 = PC + (_stext_VA - 当前指令_VA)
add   x0, x0, :lo12:_stext // 加上页内偏移

链接器计算并固化的是 offset（符号 VA 和指令 VA 的差值），不是绝对地址。运行时 MMU 关闭，PC 是物理地址：

// ============ 运行时 adrp 解析 ============ adrp 结果 = PC_runtime + offset = 指令_PA + (_stext_VA - 指令_VA) = (指令_VA - voffset) + _stext_VA - 指令_VA = _stext_VA - voffset = 0xffff800080010000 - 0xffff80003FE00000 = 0x40210000 ← 物理地址! offset 在链接时固定，PC 在运行时是物理地址 → 结果天然是物理地址 不需要 kimage_voffset，不需要地址转换，物理地址"免费"获得

于是 idmap 中的 VA 和 PA 确实是同一个值

// create_init_idmap() 中，运行时：
map_range(&ptep,
          (u64)_stext,              // start  = 0x40210000 ← 当作 VA
          (u64)__initdata_begin,    // end    = 0x41530000 ← 当作 VA
          (phys_addr_t)_stext,      // pa     = 0x40210000 ← 当作 PA
          text_prot, ...);

// start == pa == 0x40210000  → 纯正的 identity mapping!
// 写进页表: PMD[1] = 0x40210000 | ROX | PMD_TYPE_SECT
//                         ^^^^^^^^^^
//                         既是 VA 段也是 PA 段

为什么链接器 VA 完全不参与运行时计算

  • 链接器只负责计算 offset（相对差值）
  • offset = 符号_VA - 指令_VA，一个固定常数
  • VA 和 PA 的差值（voffset）对所有符号相同
  • 所以 offset 在 VA 空间和 PA 空间完全相等
  • 用 PA 空间的 PC + offset → 自然得到 PA 空间的符号地址

0x40210000 是怎么得来的？

不需要 PC-relative 推导那么复杂——直接用 Image 扁平二进制的偏移量不变性就能算出来：

// ============ 从已知值推算 _stext 的物理地址 ============ 已知: _text VA = 0xffff800080000000 (KIMAGE_VADDR, nm 输出) _stext VA = 0xffff800080010000 (nm 输出) _text PA = 0x40200000 (QEMU 加载地址, GDB 验证) Image 是扁平二进制 (objcopy -O binary)，段间相对偏移量不变: offset = _stext_VA - _text_VA = 0xffff800080010000 - 0xffff800080000000 = 0x10000 // .head.text 正好 64KB _stext_PA = _text_PA + offset = 0x40200000 + 0x10000 = 0x40210000 三个符号的运行时物理地址都可以这样推算: _stext → 0x40200000 + 0x10000 = 0x40210000 __initdata_begin → 0x40200000 + 0x1530000 = 0x41530000 _end → 0x40200000 + 0x2320000 = 0x42320000

可以用 GDB 在 MMU 关闭时直接验证：

(gdb) p/x (u64)&_stext
$1 = 0x40210000       // 拿到的确实是物理地址 ✓

这就是为什么 map_range((u64)_stext, ..., (phys_addr_t)_stext, ...) 中 start 和 pa 是同一个值——运行时 _stext 就是物理地址 0x40210000。

💡 总结：idmap 中 VA == PA 不是因为"链接器把符号分配在了低地址"，而是因为 -fpie 的 PC-relative 寻址在 MMU-off 环境下自动把符号值解析成了物理地址。map_range 的 start 和 pa 参数拿到的是同一个值，写进页表的 OA 字段就是这个值。这就是为什么注释说 "MMU is off; pointer casts to phys_addr_t are safe" — 不是因为 cast 改变了什么，而是运行时这两个指针本就指向同一个物理地址。

5. map_range 核心递归算法 ★

💡 本节目标：用最直观的方式讲清楚 map_range 的递归设计 — 为什么需要递归、每次递归做什么、什么时候终止。不要求记住每行代码，但要求理解设计思想。

5.1 先理解问题：你要在空白页表上写什么？

假设你有一本空白的 4 级页表（PGD → PUD → PMD → PTE），任务是映射 VA 范围 [0x40200000 .. 0x42000000)（~30MB 的内核镜像）到相同的物理地址。

// ============ 页表就是一棵 4 层树 ============ ┌────── PGD (Level 0) ──────┐ │ 512 entries, 每个 512GB │ 顶层: 粗粒度 │ [0] [1] [2] ... [511] │ └──────────┬───────────────┘ │ PGD[i] 指向 ▼ ┌────── PUD (Level 1) ──────┐ │ 512 entries, 每个 1GB │ │ [0] [1] [2] ... [511] │ └──────────┬───────────────┘ │ PUD[j] 指向 ▼ ┌────── PMD (Level 2) ──────┐ │ 512 entries, 每个 2MB │ ★ 关键层: 可以在这里停下来! │ [0] [1] [2] ... [511] │ └──────────┬───────────────┘ │ PMD[k] 可以直接放 Block (2MB) ← 省掉一整层 PTE! │ 或者指向 ▼ ┌────── PTE (Level 3) ──────┐ │ 512 entries, 每个 4KB │ 底层: 最细粒度 │ [0] [1] [2] ... 核心问题：我应该在树的第几层停下来写映射？

  • 在 PGD/PUD 停下来？→ 1 个 entry 覆盖 512GB/1GB，太粗，无法区分代码和数据
  • 全部写到 PTE？→ 7500+ 个 entry，太细，浪费页表页和 TLB
  • 在 PMD 停下来？→ 1 个 entry 恰好 2MB，内核也是 2MB 对齐加载 → 完美

5.2 递归思想：自顶向下"按需展开"

// ============ 一句话总结递归策略 ============ 在每一层: 计算"本层一个 entry 能覆盖多大范围" 如果范围太大、粒度不够 → 分配下一层页表 → 递归进入下一层 如果范围刚好合适 → 直接放 Block/Page 映射，终止

用一个生活类比来理解

你要管理一个图书馆的藏书：

  1. Level 0 (PGD)：你说"所有书都在 1 楼" — 太粗
  2. Level 1 (PUD)：你说"文学类在 A 区" — 还是太粗
  3. Level 2 (PMD)：你说"《ARM64 架构》在 A 区第 3 排" — 刚好！
  4. Level 3 (PTE)：你说"第 3 排第 2 层左数第 5 本" — 精确但多余

"用到哪个 entry 才建哪个"：

  • PGD 512 个 entry → 只用到了 entry[0]（内核在低 512GB 内）
  • PUD 512 个 entry → 只用到了 entry[1]（0x40200000 在第 1 个 1GB 区域内）
  • PMD 512 个 entry → 只用了 ~15 个（代码段 ROX）+ 几个（数据段 RW）
  • PTE → 根本没分配！因为全部用了 2MB Block

5.4 递归的两个关键条件

条件 A: level < 2

// Level 0 和 Level 1: 永远往下递归
if (level < 2 || ...)
    // → 递归

为什么？ 不是硬件不支持 — ARMv8 在 level 1 支持 1GB block。但内核选择不用：1 个 1GB block 只能设一种保护属性，而代码(ROX)和数据(RW)通常在同一 1GB 范围内，必须分开映射。

条件 B: (start|next|pa) & lmask

// Level 2: 三者都 2MB 对齐 → 放 Block
if (... || (level == 2 &&
    (start|next|pa) & lmask))
    // → 递归到 PTE

为什么三路或？ Block descriptor 的物理地址字段只到 bit 21（2MB 边界）。如果 start/next/pa 任何一者不 2MB 对齐，block 无法精确表达。必须降到 PTE（4KB 粒度）。

条件 B 的实际效果：不足 2MB 的尾部自动穿透到 PTE

// ============ 尾部不足 2MB 时的处理 ============ 假设内核数据段结束于 _end = 0x42320000 (不是 2MB 对齐) level=2 (PMD), 最后一轮循环: start = 0x42200000 // 2MB 对齐 ✓ pa = 0x42200000 // 2MB 对齐 ✓ end = 0x42320000 // PAGE 对齐，但不是 2MB 对齐 (start | lmask) + 1 = 0x42400000 PAGE_ALIGN(end) = 0x42320000 next = min(0x42400000, 0x42320000) = 0x42320000 (start | next | pa) & lmask: start & 0x1FFFFF = 0x000000 ✓ (2MB 对齐) next & 0x1FFFFF = 0x120000 ✗ (不对齐!) → 条件成立 → 递归到 level 3 ! level=3 (PTE): 逐页映射 [0x42200000, 0x42320000) 1152KB = 288 个 4KB pages → 288 个 PTE entries

5.5 混合映射不会有问题吗？

同一个 PMD 里同时存在 Block entries（映射 2MB）和 Table entries（指向 PTE）。ARM64 MMU 在页表遍历的每一步都检查描述符的 bits[1:0]：遇到 Block (01) 就停，遇到 Table (11) 就继续。同一个 PMD 表中不同 entry 的类型可以完全不同，MMU 按 entry 逐个判断，互不干扰。

为什么 IDMAP 只用 48-bit VA，而不是内核配置的 52-bit？

内核的 VA_BITS 由 CONFIG_ARM64_VA_BITS 决定，通常为 48 或 52。但 identity mapping 的 IDMAP_VA_BITS 硬编码为 48，与内核 VA 配置无关：

// arch/arm64/include/asm/kernel-pgtable.h
#define IDMAP_VA_BITS    48        // ★ 硬编码
#define IDMAP_LEVELS     ARM64_HW_PGTABLE_LEVELS(IDMAP_VA_BITS)
#define IDMAP_ROOT_LEVEL (4 - IDMAP_LEVELS)

三个原因：

  1. 物理地址足够：ARM64 物理地址通常 ≤48 位（256TB），内核镜像只加载到低物理地址
  2. 页表层数更少：48-bit → 4 级，52-bit → 5 级。idmap 是临时的，少一级 = 少一页 + 更快
  3. idmap 是临时的：MMU 开启后内核会重建正式页表（含 52-bit VA 支持），idmap 完成使命后被废弃

6.2 一步步跟踪（内核加载在 0x40200000，~30MB）

  1. Level 0 (PGD) — 分配 PUD
    lshift = (3-0)×9 = 27，lmask = 512GB - 1
    tbl_index = (0x40200000 >> 39) % 512 = 0（PGD[0]）
    → PGD[0] 写入 Table descriptor → 分配 PUD 物理页
  2. Level 1 (PUD) — 分配 PMD
    lshift = (3-1)×9 = 18，lmask = 1GB - 1
    tbl_index = (0x40200000 >> 30) % 512 = 1（PUD[1]）

  3. Level 2 (PMD) — 放置 Block 映射
    lshift = (3-2)×9 = 9，lmask = 2MB - 1
    start=0x40200000, pa=0x40200000 → 都 2MB 对齐！
    → 直接写 Block descriptor：PMD[1] = 0x40200000 | PMD_TYPE_SECT | prot_ROX
    → 循环放置 ~15 个 block entries（覆盖 ~30MB 代码段）
    → 无需分配 PTE 页表！

52Contiguous1 连续块标志。置 1 表示连续的 16 个 PTE（或 16 个 PMD block）是同一物理连续区域的映射，TLB 可合并为单个 entry。idmap 不使用。 0 (idmap 不用)
53PXN1 Privileged Execute Never — EL1 不可执行。这是 W^X 的核心实现位：数据段置 1（禁止执行），代码段置 0（允许执行）。注意区分：PXN 控制 EL1，UXN 控制 EL0。 ROX: 0
RW: 1
54XN/UXN1 在 Block descriptor 中称为 XN（所有特权级不可执行），在 Page descriptor 中称为 UXN（仅 EL0 不可执行）。PXN+XN 配合：PXN=1, XN=1 → 完全不可执行 —

以 PAGE_KERNEL_ROX 和 PAGE_KERNEL 为例

7.4 52-bit PA 的分裂格式 (Split PTE)

上一节的图里 OA 标注到 bit 47。但你的内核配置了 52-bit PA，需要更多的地址位。ARM 架构的解决方式是把高位 PA 塞进描述符的空闲 bit 里—OA 从一连串变成了两截：

// ============ 48-bit PA (标准, OA 连续) ============ Page descriptor: +------------------------------------------------+------------------+ | OA[47:12] (连续 36 bits) | 属性 | +------------------------------------------------+------------------+ 63 12 11 0 // ============ 52-bit PA (扩展, OA 分裂) ============ Page descriptor: +----------------------------------------+-------+----+----+---------+ | OA[49:12] (连续 38 bits) | ... | OA | ...| 属性 | | | | 51 | | | | | | 50 | | | +----------------------------------------+-------+----+----+---------+ 63 12 11 10 9 8 7 0 ^^^^^ bits[9:8] 被"挤"到这里的高位 PA

为什么会分裂？

ARM 从 ARMv8.0 (48-bit PA) 演化到 ARMv8.2 (52-bit PA) 时，PTE 描述符的高位已经被现有属性占满：

bits[63:50] — 已被 PXN(53), XN(54), Contiguous(52), DBM(51) 等属性占据
bits[47:12] — 标准 OA 字段 (36 bits)
bits[11:0]  — 低属性位 (AttrIndx, AP, SH, AF, nG, NS, Type)

多出的 4 个 PA 位 (bits[51:48]) 没地方放。ARM 的策略不是全部分裂——而是两截处理：

// ============ 4 个新增 PA 位的分配 ============ 48-bit PA → 52-bit PA, 新增 4 bits: PA[51:48] PA[49:48] → 原位扩容 — 扩展标准 OA 字段, PTE[49:48] 36 bits → 38 bits, 不需要分裂 PA[51:50] → 分裂出去 — PTE[49:48] 上面是属性位没法再扩 只能塞进 bits[9:8] (PTE_ADDR_HIGH) ┌────────────────────────────────────────────────────────────────┐ │ PA bit → PTE bit │ ├────────────────────────────────────────────────────────────────┤ │ PA[51:50] → PTE[9:8] (分裂, 2 bits, PTE_ADDR_HIGH) │ │ PA[49:12] → PTE[49:12] (原位扩容, 38 bits, PTE_ADDR_LOW) │ │ ↑ 标准 PA 只到 bit 47 (36b) │ │ 扩展到 bit 49 多了 2 bits │ │ PA[11:0] → 不用存 (VA offset) │ └────────────────────────────────────────────────────────────────┘ 总计: 2 + 38 + 12 = 52 bits

硬件如何读回分裂的 OA？

// 硬件拼接 PA:
PA[49:12] = PTE[49:12]            // 低位字段（含扩容的 PA[49:48]）
PA[51:50] = PTE[9:8]              // 高位字段从 bits[9:8] 恢复
PA[11:0]  = VA[11:0]              // offset (Page descriptor)

// 对 Block descriptor 同理，OA 是 bits[47:21] → bits[49:21]

__phys_to_pte_val 的拆解

return (phys | (phys >> 42)) & (PTE_ADDR_LOW | PTE_ADDR_HIGH);

// PTE_ADDR_LOW  = 0x3FFFFFFF_F000   ← bits[49:12], 38 bits
// PTE_ADDR_HIGH = 0x300             ← bits[9:8],   2 bits
// MASK = 0x3FFFFFFF_F300           ← 两者的 OR，互不重叠
// PTE_ADDR_HIGH_SHIFT = 42

为什么 `phys | (phys>>42)` 不会互相污染？— MASK 的精准切割

以 phys = 0x000C0000_00000000（PA[51:50]=11, PA[49:12]=0）为例，逐步推演：

// ============ 逐步推演 ============ phys = 0x000C 0000 0000 0000 ^^ PA[51:50] = 11 (原位，在 bits[51:50]) phys >> 42 = 0x0000 0000 0000 0300 ^^ PA[51:50] 挪到 bits[9:8] ✓ PA[49:42] 的垃圾也下来了, 在 bits[7:0] (但马上会被 MASK 切掉!) phys | (phys>>42) = 0x000C 0000 0000 0300 ^^^^ ^^^^ PA[51:50] 原位 折叠后 (∉ MASK，被切!) (∈ MASK bits[9:8]，保留!) & MASK = & 0x3FFF FFFF F300 ───────────── ─── PTE_ADDR_LOW PTE_ADDR_HIGH bits[49:12] bits[9:8] (38 bits) (2 bits) 结果 = 0x0000 0000 0000 0300 ^^^^^^^^^^^^^^ ^^ ^^^ 原位 PA[51:50] 0 只有 bits[9:8]=11 幸存 被 MASK 切除! → OA[51:50] = 11 ✓

三步各自的角色：

步骤表达式作用
① 折叠phys >> 42把 PA[51:50] 从 bits[51:50] 挪到 bits[9:8]
附带把 PA[49:42] 也挪下来了（垃圾）
② 合并phys | ...原位 OA[49:12] + 折叠后 OA[51:50]@bits[9:8]，两段互不重叠（一个在 [49:12]，一个在 [9:8]），OR 安全
③ 切除& MASKMASK = PTE_ADDR_LOW | PTE_ADDR_HIGH
两者没有交集且覆盖了 PTE 描述符中所有合法的地址位
垃圾 bits[7:0] 和 原位 PA[51:50] 都被精准切除
💡 关键理解：MASK 两个子字段 PTE_ADDR_LOW(bits[49:12]) 和 PTE_ADDR_HIGH(bits[9:8]) 完全分离、互不重叠。phys>>42 折叠下来的 bits[9:8] 恰好落在 PTE_ADDR_HIGH 窗内被保留；落在别处的垃圾（bits[7:0]、原位 bits[51:50]）全部被 MASK 挡掉。这就是为什么一条无分支语句能完美完成格式转换。

idmap 地址 (PA < 2^50)

phys = 0x40210000
phys >> 42 = 0

(0x40210000 | 0) & MASK
= 0x40210000   // 原样通过 ✓

PA[51:50] = 00，折叠操作是 no-op。
idmap 完全不感知分裂格式。

高位 PA (PA ≥ 2^50)

phys = 0xC0000_00000000
//          ^^ PA[51:50] = 11

phys >> 42 = 0x300  // 落到 bits[9:8]
(0xC0000_00000000 | 0x300) & MASK
= 0x300  // 全部地址在高位字段 ✓

低位全是 0，只有 bits[9:8] = 11。
硬件读回：PA[51:50] = PTE[9:8] = 11。

💡 总结：__phys_to_pte_val 做的是格式转换——把人类习惯的连续物理地址，转成 ARM 硬件理解的分裂 PTE 布局。对 idmap 来说这是一个透明的 no-op，因为它的 PA 全部 < 2^48，永远碰不到 bits[51:50]。

8.3 分配代码 — 逐层拆解

当 map_range 发现当前 entry 为空（pte_none(*tbl)）且需要深入下一层时，会创建一个新的 Table descriptor。关键代码只有一行：

*tbl = __pte(__phys_to_pte_val(*pte) |
             PMD_TYPE_TABLE | PMD_TABLE_UXN);
*pte += PTRS_PER_PTE * sizeof(pte_t);  // *pte 前进一个页表页

逐层拆解

层次表达式含义
输入*pte 当前空闲物理页的地址。例如 PGD 在 0x41730000，初始 *pte = 0x41731000（PGD 之后的第一个空闲页）
①__phys_to_pte_val(*pte) 将物理地址转为 PTE 格式。对于标准 48-bit PA，这个函数直接返回 *pte 本身（identity transform）。对于 52-bit PA，会将高位 PA bits 折叠到 PTE 的正确位置
②| PMD_TYPE_TABLE PMD_TYPE_TABLE = 3（bit[1:0] = 11）。标记此 entry 为 Table descriptor — 指向下一级页表，而非 leaf
注意：虽然宏名叫 PMD_TYPE_TABLE，但在 PGD/PUD/PMD 三级中都用它，因为 bits[1:0] 的 Table 编码（0b11）在所有层级都是相同的
③| PMD_TABLE_UXN PMD_TABLE_UXN = 1 << 60。设置 Unprivileged Execute Never — EL0 用户态不可执行此表中的任何代码。内核页表不需要被用户态执行，这是安全加固
④__pte(...) 把最终的值包装为 pte_t 类型

实例：分配第一个 PUD

假设 PGD 在物理地址 0x41730000，初始 *pte = 0x41731000：

// 输入:
*pte = 0x41731000   // 第一个空闲物理页

// 运算:
__phys_to_pte_val(0x41731000)  = 0x41731000
| PMD_TYPE_TABLE               = 0x00000003
| PMD_TABLE_UXN                = 0x10000000_00000000
---------------------------------------------
*tbl (PGD[0])                  = 0x10000000_41731003

写入后的 PGD[0] 含义：

PGD[0] = 0x10000000_41731003

  bits[1:0]   = 11  → Table descriptor ✓
  bits[47:12] = 0x41731 → 下一级在 0x41731000
  bit 60      = 1  → UXN (EL0 不可执行)

// 硬件读 PGD[0] 后:
// → 知道下一级是 Table (不是 leaf)
// → 从 bit[47:12] 提取 PUD 物理地址
// → 继续遍历 PUD

紧随其后：*pte 前进

*pte += PTRS_PER_PTE * sizeof(pte_t);
//    = 512 * 8 = 4096 = PAGE_SIZE

// 如果 *pte 原来是 0x41731000，现在变成 0x41732000
// 下次分配时用 0x41732000（下一空闲物理页）
💡 三个关键理解：
1. *pte 是物理地址（MMU off 时直接操作物理内存），被用作下一级页表的基址写入 descriptor 的 OA 字段
2. Table descriptor 不关心下一级是什么类型 — 同一个宏 PMD_TYPE_TABLE 在 PGD/PUD/PMD 三级都用，因为 ARM64 的 Table 编码在各级是一致的（bits[1:0] = 0b11）
3. 分配一次恰好消耗一个 4KB 物理页 — PTRS_PER_PTE * sizeof(pte_t) = 512 * 8 = 4096 = PAGE_SIZE，所以 *pte + 4096 正好指向下一个空闲物理页。这是 ARM64 4KB 页表设计的一个优雅巧合

define dump_pgtables

define verify_idmap
    # 用法: verify_idmap <VA> <PGD_phys>
    set $va = $arg0
    set $tbl = $arg1

    set $idx = ($va >> 39) & 0x1ff

        # Level 1: index = VA[38:30]
        set $idx = ($va >> 30) & 0x1ff
        set $ldesc = ((unsigned long long *)$tbl)[$idx]
