1. 概述：ARM64 内核 Image 是什么

ARM64 内核编译产出 vmlinux（ELF 可执行文件），但 bootloader 加载的实际文件是 Image（裸二进制）。Image 的前 64 字节是一个精心编排的自描述头部，它同时满足三套协议：

// ============ Image = vmlinux 剥离 ELF 头后的裸二进制 ============ vmlinux (ELF) Image (raw binary) ┌────────────────┐ ┌──────────────────────────┐ │ ELF Header │ objcopy -O │ 0x00 64-byte Image Header │ ← 本文分析对象 │ Program Hdrs │ binary ────▶│ │ │ Section Hdrs │ (--strip) ├──────────────────────────┤ ├────────────────┤ │ 0x40 .head.text / .text │ │ .head.text │ │ (代码段) │ │ .text │ │ │ │ .rodata │ ├──────────────────────────┤ │ .init.text │ │ .init.text / .init.data │ │ ... │ │ │ └────────────────┘ └──────────────────────────┘

核心问题：为什么需要 64 字节头部？

1. 传统 bootloader（GRUB/U-Boot）
把 Image 当作可跳转的原始代码，从偏移 0 开始执行。前 8 字节必须是可执行指令（NOP + B）。

2. UEFI 固件（支持 PE/COFF）
把 Image 当作 PE/COFF 可执行文件。文件必须以 "MZ"（0x4D 0x5A）开头。内核必须以"有效 NOP"的方式嵌入这个签名。

3. Linux boot protocol
头部必须包含魔数 "ARM\x64"、内核大小、页面大小等元数据，让 bootloader 在加载前就能验证和解析内核配置。

4. 向后兼容
头部的前 8 字节 == text_offset 字段。0 表示"内核不关心加载偏移"。非零值曾用于特殊平台（已废弃），但必须 >= 0 以保证向后兼容。

💡 核心矛盾："MZ" 在 x86 上是合法指令（dec bp; pop dx），但在 ARM64 上并不是。内核用了一个非常巧妙的方法：ccmp x18, #0, #0xd, pl — 这条 ARM64 指令的 opcode 恰好等于 "MZ"。它不是真正的"比较"，而是被精心挑选来生成正确的二进制字节。

2. 64 字节头部逐字段解析

// ============ ARM64 Image Header (64 bytes) ============ Offset Size Field Content Purpose 0x00 4 指令/NOP efi_signature_nop triple: ARM insn + MZ sig + NOP 0x04 4 跳转指令 b primary_entry 跳转到真正入口 0x08 8 text_offset .quad 0 加载偏移（0=不关心） 0x10 8 image_size le64sym _kernel_size_le 内核有效大小 0x18 8 flags le64sym _kernel_flags_le 标志位（字节序/页大小/物理基址）★ 0x20 8 reserved 1 .quad 0 保留 0x28 8 reserved 2 .quad 0 保留 0x30 8 reserved 3 .quad 0 保留 0x38 4 魔数 .ascii "ARM\x64" 标识为 ARM64 Linux Image 0x3C 4 PE header offset .long .Lpe_header_offset 指向 PE/COFF 头的偏移

2.1 逐字段详解

字段 1: 偏移 0x00 — efi_signature_nop (4 bytes)

// 启用 CONFIG_EFI 时:
ccmp  x18, #0, #0xd, pl
// opcode = 0xFA400D5A (小端)
//         ^^^^ ^^^^
//          MZ   ??  (0x5A4D = "MZ")
// 注意: 实际编码中 "MZ" = 0x5A4D
// ARM64 LE 存储: 低字节在前
// bytes: 5A 0D 40 FA → "Z\r@\xfa"
// 未启用 CONFIG_EFI 时:
nop
// opcode = 0xD503201F
// bytes: 1F 20 03 D5
💡 CCMP 指令的玄机：ccmp（Conditional Compare）只在条件满足时才执行比较。这里条件码 pl（plus，N=0）在冷启动时成立，所以会执行 cmp x18, #0，结果被丢弃（无后续 CSEL）。关键是这条指令的 opcode — 内核开发者从 ARM64 指令集中筛选出二进制编码恰好为 "MZ"（0x5A4D LE）的那一条指令！

字段 2: 偏移 0x04 — b primary_entry (4 bytes)

b  primary_entry
// ARM64 无条件跳转指令，opcode = 0x14000000 | imm26
// 跳转到 primary_entry，这是真正的内核入口
  • 传统 bootloader 加载 Image 后直接跳转到偏移 0，执行这条 b 进入内核代码
  • 注意：UEFI 固件不会执行这条指令，而是解析 PE/COFF 头，调用 __efistub_efi_pe_entry

字段 3: 偏移 0x08 — text_offset (8 bytes)

.quad  0    // text_offset = 0
  • 内核对 bootloader 说："我不在乎加载到哪个地址，你随便放"
  • ARM64 要求 2MB 对齐，bootloader 会加上 offset_text 到 2MB 边界
  • 历史：旧版本 ARM64 内核可能要求 text_offset 非零（特殊平台的固定加载地址），现已统一为 0

字段 4: 偏移 0x10 — image_size (8 bytes)

le64sym _kernel_size_le
// 展开为:
// .long _kernel_size_le_lo32
// .long _kernel_size_le_hi32
  • _kernel_size_le 是一个 小端编码的 64 位值，表示内核镜像有效大小
  • 通过 le64sym 宏拆成 lo32/hi32 两部分
  • bootloader 用这个值来计算需要从介质读入多少字节
  • 为什么用 le64sym 而不是 .quad？ 保证任何字节序下都是小端格式的二进制值（链接器默认会用目标字节序写入 .quad）

字段 5: 偏移 0x18 — flags (8 bytes, ★ 最复杂的字段)

le64sym _kernel_flags_le
// 同样拆成 lo32 / hi32，小端编码

flags 是一个位域编码，header flag bits 布局：

Bit名称编码含义
0ARM64_IMAGE_FLAG_BE0=LE, 1=BE内核字节序
1-2ARM64_IMAGE_FLAG_PAGE_SIZE1=4K, 2=16K, 3=64K页面大小
3ARM64_IMAGE_FLAG_PHYS_BASE0=任意, 1=固定物理地址基址是否固定
4-63(保留)0未来扩展
💡 flags 的设计意图：bootloader 在解析头部后就知道内核的页面大小、字节序等编译配置，从而在启动前做自检。例如，一个 4K 页面的内核不能在有 64K 页面硬件约束的平台上运行。

字段 6-8: 偏移 0x20/0x28/0x30 — reserved (3×8 bytes)

  • 三个保留字段，当前全部为 0
  • 为未来可能扩展留出空间（例如更大的物理地址、新的安全特性等）
  • 这种预留设计在 boot protocol 中非常常见 — 一旦定义了，就要兼容到将来

字段 9: 偏移 0x38 — ARM64_IMAGE_MAGIC (4 bytes)

.ascii "ARM\x64"    // 小端: bytes = 41 52 4D 00
  • 这是 Linux ARM64 boot protocol 的身份证
  • bootloader 检查这个魔数来确认这是一个 ARM64 Linux 内核镜像
  • 为什么是 "ARM\x64" 而不是其他？ "ARM" 是 ARM 架构，"64" 代表 64-bit（注意是 '\x64' = ASCII 'd'），避免与 32-bit ARM 混淆

字段 10: 偏移 0x3C — PE header offset (4 bytes)

.long .Lpe_header_offset    // PE/COFF 头在 Image 中的偏移
  • 告诉解析器去哪里找 PE/COFF 头
  • 如果未启用 CONFIG_EFI，这个值可能为 0
  • 这个字段本身是 PE/COFF DOS stub 的一部分

3. 三重身份：指令 / NOP / 魔数

// ============ 前 4 个字节的多重身份 ============ 偏移 0x00 的 4 字节，在 三个不同视角 下有不同的含义： ┌─────────────────────────────────────────────────────┐ │ 二进制: 5A 0D 40 FA │ │ │ │ 视角 1: ARM64 指令解码器 │ │ → ccmp x18, #0, #0xd, pl │ │ → 一条无实际效果的"条件比较"指令 │ │ │ │ 视角 2: UEFI PE/COFF 加载器 │ │ → 前 2 字节: 5A 4D = "MZ" │ │ → "这是一个有效的 PE 可执行文件" │ │ │ │ 视角 3: 传统 Linux bootloader │ │ → 这是一条 ARM64 指令，CPU 会正常执行它 │ │ → 执行完毕后，下一条是 b primary_entry │ └─────────────────────────────────────────────────────┘

3.1 为什么选择 CCMP？而不是其他 "MZ" 指令？

ARM64 指令集中，"MZ"（0x5A4D LE）恰好对应多条指令。内核开发者需要一条满足以下条件的：

  1. 无副作用：不能修改任何寄存器或内存（否则会影响 x0~x3 中的 bootloader 参数）
  2. 无条件执行或条件总是满足：指令必须正确执行，不能因条件码不满足而被跳过
  3. 不影响标志位：不能改变 N/Z/C/V，否则影响后续逻辑
  4. 不产生异常：不能触发 Undefined Instruction 或其他 trap

ccmp x18, #0, #0xd, pl 完美满足所有条件：

  • x18 是平台寄存器（Platform Register），修改它标志位不影响普通代码
  • pl（N=0）在冷启动时成立（大多数 CPU 上电后 PSTATE.N=0）
  • CCMP 只更新 NZCV 且条件为 PL 时执行，这确实会影响标志位 — 但后续代码中 cmp 和 tst 会重新设置标志位
  • 所有 ARMv8+ CPU 都支持 CCMP
⚠ PL 条件码的隐患：如果 CPU 上电时 N=1（极少见但理论上可能），ccmp 将不被执行，标志位保持原样。不过紧跟着的 b primary_entry 无条件跳转，不影响执行流。在 primary_entry 中，record_mmu_state 的 cmp 指令会重新设置标志位，所以即便 CCMP 被跳过也无害。

4. EFI PE/COFF 头嵌入

// ============ PE/COFF 结构嵌入 ============ Image 物理布局: ┌──────────────────────────┐ ← offset 0x000 │ Image Header (64 bytes) │ Linux boot protocol 头部 │ 0x3C: PE Header Offset │ ← 指向 PE signature ├──────────────────────────┤ │ PE Signature │ "PE\0\0" (PE签名+IMAGE_NT_SIGNATURE) │ COFF Header │ 机器类型: ARM64 (0xAA64) │ Optional Header │ 入口: __efistub_efi_pe_entry │ Section Table │ .text/.data 段描述 ├──────────────────────────┤ │ .head.text (代码) │ _text = primary_entry └──────────────────────────┘

UEFI 启动流程

UEFI 固件解析 PE/COFF 头 → 调用 AddressOfEntryPoint = __efistub_efi_pe_entry → EFI stub 初始化 (ExitBootServices 等) → 跳转到 primary_entry (MMU on, x0=FDT)

传统 bootloader 启动流程

bootloader 加载 Image 到内存 → 检查 "ARM\x64" 魔数 → 读取 image_size 分配内存 → 跳转到 Image 偏移 0 (b primary_entry)

关键设计点

机制说明
DOS stub 复用PE/COFF 格式要求文件头包含 DOS stub。ARM64 内核把 Linux Image Header 作为 DOS stub 的前 64 字节，0x3C 处的偏移值指向 PE signature。传统 PE 文件中这个偏移指向 0x80 或更远，这里指向紧跟在 Image Header 之后的位置。
入口地址分离PE/COFF 的 AddressOfEntryPoint 指向 __efistub_efi_pe_entry（EFI stub），而传统入口在偏移 4（b primary_entry）。两者的启动环境完全不同：EFI 入口 MMU on + EFI 服务可用，传统入口 MMU off。
Section Table 偏移计算.Lpe_header_offset 是链接时计算的相对偏移（. - .L_head），与运行时加载地址无关。这就是 PIE 编译的好处。

5. _kernel_flags 位域编码详解

// ============ _kernel_flags_le 位域布局 (64-bit) ============ 63 .... 4 3 2-1 0 ┌──────────────┬──────────────┬───────────┬───┐ │ reserved │ PHYS_BASE │ PAGE_SIZE │ BE│ │ (all 0) │ 1 bit │ 2 bits │ 1b│ └──────────────┴──────────────┴───────────┴───┘ PHYS_BASE: 0 = kernel can run at any PA 1 = kernel requires fixed PA PAGE_SIZE: 01 = 4KB, 10 = 16KB, 11 = 64KB BE: 0 = Little Endian 1 = Big Endian 为什么需要这些 flag？ 同一个内核二进制 (Image) 可能被多个 bootloader 加载。 bootloader 读取 flags 后可以 在加载前 验证兼容性： - "这个内核是 64K 页面的，这个平台只支持 4K → 拒绝加载" - "这个内核需要固定 PA，但我在非固定 PA 环境 → 拒绝加载"

flags 检查 — bootloader 视角

// bootloader 伪代码
struct arm64_image_header *hdr = (void *)kernel_image;

if (memcmp(hdr->magic, "ARM\x64", 4) != 0)
    die("Not an ARM64 Linux Image");

u64 flags = hdr->flags;

int page_size = (flags >> 1) & 3;
if (page_size == 0)        die("Invalid page size");
if (page_size == 1) ps = 4096;
if (page_size == 2) ps = 16384;  // 16K
if (page_size == 3) ps = 65536;  // 64K

int be = flags & 1;
if (be != my_endianness)
    die("Endianness mismatch");

int phys_base = (flags >> 3) & 1;
if (phys_base && !i_can_provide_fixed_pa())
    die("Fixed PA not supported");

6. 设计哲学与约束

6.1 约束清单

约束来源如何满足
前两字节必须是 "MZ" PE/COFF (DOS header 签名) efi_signature_nop → ccmp opcode = 5A 4D
偏移 0 必须是可执行指令 传统 bootloader 直接跳转 ccmp = 合法 ARM64 指令（条件比较，无副作用）
魔数必须是 "ARM\x64" Linux ARM64 boot protocol .ascii "ARM\x64" @ offset 0x38
text_offset 必须小端编码 多字节序兼容 le64sym 宏确保小端，与宿主字节序无关
PE header offset 必须在 0x3C PE/COFF (DOS header 布局) .long .Lpe_header_offset @ 0x3C
头部大小必须 >= 64 bytes ARM64 boot protocol 64 字节固定头部 + 后续 PE/COFF 头 + __EFI_PE_HEADER
链接脚本 .head.text 必须最前 vmlinux.lds.S 链接顺序 .head.text 在 _text 前排列

6.2 设计哲学

  1. "一份二进制，所有启动路径" — 同一个 Image 文件可以被传统 bootloader（GRUB/U-Boot）、UEFI 固件、QEMU -kernel 参数启动。不需要编译不同版本的 Image。
  2. "自描述" — bootloader 无需额外元数据文件，直接从 Image 头部读取页面大小、字节序、内核大小。这避免了像 x86 的 bzImage setup header 那样的复杂历史包袱。
  3. "最大兼容性 = 最小假设" — text_offset=0 表示"我不假设加载地址"，让 bootloader 自由选择。EE/页大小 flags 则提供编译时信息以便兼容性检查。
  4. "嵌入不侵入" — PE/COFF 头没有破坏 ARM64 boot protocol 的兼容性。PE header 偏移存储在 0x3C，传统 bootloader 直接忽略它。两者可以和平共存。
  5. "预留即远见" — 3 个 reserved 字段（8×3=24 bytes）看似浪费，但一旦未来需要新字段（例如更大的物理地址 PA bits > 48），就有空间添加而不破坏兼容性。
💡 对比 x86：x86 的 bzImage 有 setup header（512+ bytes，一个极其复杂的历史遗留结构），因为 x86 的实模式→保护模式切换需要大量参数。ARM64 只有简洁的 64 字节头部 — 没有实模式、没有段寄存器、没有 A20 gate，硬件架构的简洁性直接反映在软件设计上。
