1. 概述：record_mmu_state 的使命

调用位置

SYM_CODE_START(primary_entry)
    bl      record_mmu_state   // ★ 内核启动第一个函数调用
    bl      preserve_boot_args
    ...

核心使命

  • 检测当前 异常级别（EL1 or EL2）
  • 读取对应异常级别的 SCTLR 寄存器
  • 提取 M 位（MMU 启用标志）存入 x19
  • 检测 字节序是否匹配内核编译设置
  • 若不匹配：纠正字节序 + 禁用 MMU + 清除 x19

返回值：x19 编码含义

x19 值含义对应场景
0MMU 关闭（Cold Boot）内核从 bootloader 直接启动
1MMU 开启（Warm Boot）kexec / 从休眠唤醒
0（endian 路径）字节序不匹配，已纠正并关闭 MMU大端 bootloader 启动小端内核等
💡 x19 是 callee-saved 寄存器：record_mmu_state 选择 x19 存储 MMU 状态，是因为 x19 遵循 ARM64 AAPCS64 调用约定——被调用者保存。这意味着 primary_entry 中 x19 的值可以安全地跨越后续所有函数调用（直到 init_kernel_el 以 x0 接收它）。

2. 完整源码与上下文

2.1 完整源码

SYM_CODE_START_LOCAL(record_mmu_state)        // @ 134
    mrs     x19, CurrentEL                     // 读取当前异常级别
    cmp     x19, #CurrentEL_EL2                // 是否在 EL2？
    mrs     x19, sctlr_el1                     // (投机)读 EL1 的 SCTLR
    b.ne    0f                                 // 不在 EL2 → 跳转到 0f
    mrs     x19, sctlr_el2                     // 在 EL2 → 读 EL2 的 SCTLR
0:                                              // ← 两条路径在此汇合
    CPU_LE( tbnz    x19, #SCTLR_ELx_EE_SHIFT, 1f )  // LE 内核: 如果 EE 位=1 → 1f
    CPU_BE( tbz     x19, #SCTLR_ELx_EE_SHIFT, 1f )  // BE 内核: 如果 EE 位=0 → 1f
    tst     x19, #SCTLR_ELx_C                  // Z := (C == 0)
    and     x19, x19, #SCTLR_ELx_M             // 提取 M 位
    csel    x19, xzr, x19, eq                  // 如果 Z (C==0) 则清除 x19
    ret

    // === 字节序不匹配路径 ===
1:  eor     x19, x19, #SCTLR_ELx_EE            // 翻转 EE 位
    bic     x19, x19, #SCTLR_ELx_M             // 清除 M 位 (MMU off)
    b.ne    2f                                  // 如果 EE 位之前是 1 (LE内核+EE=1) → 2f
    pre_disable_mmu_workaround                  // QCOM FALKOR ERRATUM E1041
    msr     sctlr_el2, x19                     // 写回 EL2 SCTLR
    b       3f
2:  pre_disable_mmu_workaround
    msr     sctlr_el1, x19                     // 写回 EL1 SCTLR
3:  isb                                         // 同步屏障
    mov     x19, xzr                           // x19 = 0

SYM_CODE_END(record_mmu_state)

3.2 逐条详解

① mrs x19, CurrentEL — 读取当前异常级别

  • CurrentEL 是 ARM64 系统寄存器，bits[3:2] 编码当前异常级别
  • EL1 = 0b01（内核），EL2 = 0b10（虚拟机监视器），EL3 = 0b11（安全监控）
  • Linux 内核通常在 EL1 或 EL2 运行
  • 这里读取 CurrentEL 仅仅为了判断是否需要读 sctlr_el2

② cmp x19, #CurrentEL_EL2 — 是否在 EL2？

  • 注意： 此时 x19 存储的是 CurrentEL 的值（如 0x4 或 0x8），还不是 SCTLR
  • cmp Rn, #imm 等价于 subs xzr, Rn, #imm——做一次减法，结果丢弃，只更新 NZCV 四个条件标志位

cmp 影响的标志位：NZCV

标志名称cmp 后何时置 1在本指令中的含义
NNegative减法结果为负（最高位 = 1）一般不直接用于后续分支
ZZero减法结果 = 0（即 x19 == #imm）Z=1 → EQ（相等）→ 在 EL2
CCarry无借位（无符号 x19 >= #imm）一般不直接用于后续分支
VoVerflow有符号减法溢出本场景不涉及（值很小）

后续 b.ne 0f 只看 Z 位：NE = Not Equal = Z=0。

场景x19 (CurrentEL)比较NZCV条件含义
QEMU 在 EL10x44 - 8 ≠ 01000NE不在 EL2 → 138 行 b.ne 跳转
在 EL20x88 - 8 = 00110EQ在 EL2 → 138 行 b.ne 不跳，执行 139 行
cmp x19, #CurrentEL_EL2 (即 cmp x19, #0x8) 伪操作: subs xzr, x19, #0x8 // xzr 丢弃结果，只写 NZCV x19 = 0x4 (EL1): x19 = 0x8 (EL2): 4 - 8 ≠ 0 8 - 8 = 0 Z = 0 → NE Z = 1 → EQ b.ne 会跳转 ✓ b.ne 不跳转 ✓ ★ 137 行 mrs sctlr_el1 会覆盖 x19，但 NZCV 不变 ★ 138 行 b.ne 仍然根据 cmp 时的 Z 位决定跳转
💡 条件码与标志位对应关系（本函数用到的）： EQ = Z=1  |  NE = Z=0  |  b.ne = branch if Not Equal = branch if Z=0  |  csel ..., eq = 若 Z=1 则选择第一操作数（143–145 行的 tst+csel 路径）

③ mrs x19, sctlr_el1 — 先读 EL1 的 SCTLR（再决定要不要覆盖）

  • 把 SCTLR_EL1（EL1 系统控制寄存器）读入 x19，其中包含 M/C/EE 等关键位
  • 插在 cmp 和 b.ne 之间——会覆盖 x19，但不会破坏 cmp 设置的条件标志位（见 §3.3）
  • 若在 EL2，下一行会用 sctlr_el2 覆盖；若在 EL1，则保留本次读到的值
  • 这是一种代码布局技巧：用一次"可能白读"的 MRS，换掉额外的无条件跳转和标签（见 §3.3 对比表）

④ b.ne 0f — 依据 cmp 的标志位，而非 x19

  • 分支依据是 cmp 留下的 NZCV 标志位，不是 x19 的当前值
  • NE（CurrentEL ≠ EL2，即在 EL1）→ 跳到 0:，跳过下一行 mrs sctlr_el2
  • EQ（在 EL2）→ 不跳，执行下一行，用 sctlr_el2 覆盖 x19

⑤ mrs x19, sctlr_el2 — 在 EL2，用 sctlr_el2 覆盖

  • 只有当前在 EL2 时才会执行
  • 覆盖了③中读出的 sctlr_el1 值
  • 至此 x19 持有正确的 SCTLR 值：sctlr_el1（EL1下）或 sctlr_el2（EL2下）
// ============ 异常级别检测逻辑 ============ mrs x19, CurrentEL // x19 = CurrentEL cmp x19, #CurrentEL_EL2 // 设置标志位 mrs x19, sctlr_el1 // (投机) 先读 EL1 的 SCTLR ┌── b.ne 0f ────┐ │ NE (EL1) │ EQ (EL2) ▼ ▼ (跳过) mrs x19, sctlr_el2 │ │ └──── 0: 汇合 ───┘ x19 = 正确的 SCTLR

⑥ CPU_LE(tbnz x19, #SCTLR_ELx_EE_SHIFT, 1f)

  • 编译为 LE 内核时：tbnz w19, #25, 1f — 测试 bit 25 (EE 位)
  • EE 位（bit 25）= Endianness 配置位：0=小端，1=大端
  • 如果 EE 位 = 1（与 LE 内核期望相反）→ 跳转到 1f（字节序纠正路径）
  • 编译为 BE 内核时指令相反：tbz ... 1f — 如果 EE=0 跳转
  • 详见 §3.4.0 tbnz 与 tbz 的区别 及 §3.4 真实反汇编

⑦ tst x19, #SCTLR_ELx_C — 测试 C 位（Cache 启用）

  • SCTLR_ELx_C = bit 2，数据 cache 启用标志
  • tst 做按位与，设置 Z 标志：SCTLR 的 C 位 = 0 → Z=1；C 位 = 1 → Z=0（这里的「C」指 SCTLR bit 2，不是 NZCV 里的 C 标志）
  • 不写回 x19：tst 等价于 ands xzr, x19, #imm，结果丢弃，只更新 NZCV
  • 为什么检测 C 位而不是直接检测 M 位？见下面关键设计点
  • 内核注释 // Z := (C == 0) 解读见 §3.2.0；and / csel 详见 §3.2.3、§3.2.4
  • 实战演算（GDB 中 x19 = 0xc50838）见 §3.2.1 tst 指令详解；NZCV 判定逻辑见 §3.2.2

3.2.0 head.S 注释 // Z := (C == 0) 是什么意思？

源码 143 行：

tst  x19, #SCTLR_ELx_C    // Z := (C == 0)

这条注释是正确的，容易误解的是注释里的 C 和 NZCV 里的 C 不是同一个东西。

符号指什么本例 x19=0xc50838
注释中的 CSCTLR_ELx_C（bit 2，D-Cache 使能）0（D-Cache 关）
注释中的 ZPSTATE 的 Zero 标志1（因为下面 (C==0) 为真）
NZCV 中的 CCarry 进位标志（与 SCTLR 无关）1（逻辑 ands 架构固定）

Z := (C == 0) 是伪代码，含义是：把 Z 设成「SCTLR 的 C 位是否等于 0」这个布尔值：

SCTLR 的 C 位（bit 2）(C == 0) 真假tst 的按位与结果设置的 Z 标志
0（D-Cache 关）真x19 & 0x4 = 0Z = 1
1（D-Cache 开）假x19 & 0x4 ≠ 0Z = 0
注释说的： Z := (SCTLR_C == 0) 当 SCTLR_C=0 → Z=1 当 SCTLR_C=1 → Z=0 tst 实际做的：result = x19 & 0x4 当 result=0 → Z=1 ← 与上面完全一致 当 result≠0 → Z=0 ★ 注释与指令行为一致，没有矛盾
⚠ 为何会觉得「不对」？ 因为执行 tst 后 NZCV 里同时出现：
  • Z = 1 ← 注释关心的：SCTLR 的 C 位 = 0
  • C = 1 ← NZCV 的 Carry，逻辑运算固定值，与 SCTLR 的 C 位无关
看到「C=1」就以为和注释「C==0」矛盾 — 其实一个是 SCTLR bit 2，一个是 NZCV Carry，名字相同、含义完全不同。后续 csel eq 只看 Z，不看 NZCV 的 C。

3.2.1 tst 指令详解 — 以 x19 = 0xc50838 为例 ★

在 QEMU 中执行到 143 行时，mrs x19, sctlr_el1 后常见 x19 = 0x00c50838。下面逐步拆解这条 tst 的行为。

等价形式

tst  x19, #SCTLR_ELx_C          // head.S:143
# 汇编器等价于：
ands xzr, x19, #0x4             // 按位与，结果写入 xzr（丢弃），只更新 NZCV
⚠ 两个「C」不要混淆：（详见上方 §3.2.0 注释解读）
  • SCTLR_ELx_C（bit 2）：数据 Cache 使能位 — 注释 Z := (C == 0) 里的 C 就是它
  • NZCV 中的 C（Carry 进位标志）：tst 也会更新它，但与 SCTLR 的 C 位毫无关系

按位与计算

x19 = 0x00C50838 掩码 = 0x00000004 (SCTLR_ELx_C = BIT(2)) 按位与结果 = 0x00C50838 & 0x4 = 0x00000000 验证 bit 2（低字节 0x38 = 0b00111000）： bit2 ↓ ... 0 0 1 1 1 0 0 0 0 → D-Cache 关闭

NZCV 判定逻辑 — 按位与结果为 0 时，四个标志为何是 N=0 Z=1 C=1 V=0？

tst 更新 NZCV 的依据是：本次按位与运算的结果 + ARM 架构对逻辑运算的固定规则。不是根据 SCTLR 的 C 位直接赋值。

令 result = x19 & #0x4，本例 result = 0：

标志判定公式（ands / tst）本例 result=0说明
NN = result[63]0把结果当有符号数，看最高位。结果为 0 → 最高位为 0
ZZ = (result == 0) ? 1 : 01结果为 0 则 Z=1。这是 csel eq 依赖的标志
CC = 1（逻辑运算固定）1与 result 是否为 0 无关；不是 SCTLR 的 C 位，也不是进位
VV = 0（逻辑运算固定）0逻辑运算不存在有符号溢出
result = x19 & 0x4 = 0 N = result[63] = 0 ← 结果为 0，最高位为 0 Z = (result == 0) = 1 ← 结果为 0，所以 Z=1 C = 1 (架构规定) = 1 ← 逻辑 ands 固定置 1，与 result 无关 V = 0 (架构规定) = 0 ← 逻辑运算固定为 0 NZCV = N:0 Z:1 C:1 V:0 → 二进制 0b0110

反例：若 SCTLR 的 C 位 = 1（x19 = 0xc5083c）

result = 0xc5083c & 0x4 = 0x4 N = 0x4[63] = 0 ← 非零正数，最高位仍为 0 Z = (0x4 == 0) = 0 ← 结果非零 → Z=0 → csel eq 不成立 C = 1 (架构规定) = 1 ← 仍是 1，与 result 是否为 0 无关 V = 0 (架构规定) = 0 NZCV = N:0 Z:0 C:1 V:0 → 二进制 0b0100

  • N、Z 由 x19 & 掩码 的结果决定 — 结果为 0 → Z=1
  • C、V 在逻辑 tst/ands 中按 ARM 规范固定为 C=1、V=0，与按位与结果是否为 0 无关

💡 为什么检测 C（Cache）而不是 M（MMU）？
正常情况下，M=0（MMU off）时 C 也一定是 0。但有些 bootloader 可能关闭了 MMU 却忘记关闭 cache（M=0, C=1），这会导致 non-cacheable 写入操作发生后，cache 中有陈旧数据。检测 C 位而非 M 位可以在这种情况下也触发 cache 维护操作。

另外 csel 的逻辑：csel x19, xzr, x19, eq 表示"如果 Z=1（C==0），把 xzr(=0) 写入 x19，否则保持 x19 的 M 位值"。所以最终 x19 = (C==0) ? 0 : M_bit。

⑧ and x19, x19, #SCTLR_ELx_M — 提取 M 位（head.S:144）

and  x19, x19, #SCTLR_ELx_M    // isolate M bit
# 掩码 SCTLR_ELx_M = BIT(0) = 0x1

指令在做什么

对 x19 做按位与，只保留 bit 0（MMU 使能位 M），其余位全部清零。与 tst 不同，and 会把结果写回 x19。

x19_in = 0x00C50838 (完整 SCTLR 值) 掩码 = 0x00000001 (SCTLR_ELx_M) x19_out = x19_in & 1 = 0x00C50838 & 1 = 0 验证 bit 0：0x38 = 0b00111000 → bit0 = 0 → MMU 关闭
项目执行前（143 行 tst 之后）执行后（144 行 and 之后）
x190x00c50838（SCTLR 原值，tst 未改）0x0 或 0x1（仅 M 位）
NZCV完全不变 — and（无 s 后缀）不更新标志位
💡 与 tst / ands 的区别：
  • tst = ands xzr, ... → 更新 NZCV，不写目的寄存器
  • and = 普通逻辑与 → 写回 x19，不改 NZCV
  • 若写成 ands x19, x19, #1 则会同时更新 NZCV（本函数没有这么做，是故意的）

本例执行后 NZCV 仍保持 tst 设置的值：N=0, Z=1, C=1, V=0。这条 Z=1 将留给 145 行的 csel eq 使用。

⑨ csel x19, xzr, x19, eq — 条件选择（head.S:145）

若 cond 条件不成立：Rd = Rm

⚠ 核心问题：145 行 csel x19, xzr, x19, eq 中的条件码 eq 读的 Z 标志，到底是哪条指令设置的？为什么中间隔了一条 and 还能读到正确的 Z？

答案：143 行 tst 设置的 Z，不是 144 行 and

关键原因：144 行的 and（不带 s 后缀）不更新 NZCV。ARM64 中只有带 s 后缀的 ALU 指令（如 ands、subs）才会写 NZCV；普通 and 只写目的寄存器。因此 143 行 tst 写入的 Z 标志原封不动地穿越了 144 行，在 145 行被 csel 读取。

Z 标志的完整生命周期（143 → 144 → 145）

💡 三个关键事实：
  1. tst（143 行）等价于 ands xzr, x19, #0x4，写 NZCV，Z = (x19 & 0x4 == 0)
  2. and（144 行）不带 s 后缀，不写 NZCV，Z 保持 tst 所设的值不变
  3. csel（145 行）只读 NZCV，不写 NZCV。eq 条件 = Z=1 → 选第一操作数 xzr

3.3 cmp 与 b.ne 之间为何插入 mrs？能否 cmp 完就 b.ne？

很多人看到 cmp 之后没有立刻 b.ne，中间夹了一条 mrs x19, sctlr_el1，会疑惑：cmp 已经比完了，为什么不直接分支？

💡 核心：cmp 的结果存在 NZCV 标志位里，不在 x19 里。后续的 mrs 会覆盖 x19，但不会改写标志位，所以 b.ne 仍然能正确根据 cmp 的结果分支。
① mrs x19, CurrentEL → x19 = 当前 EL ② cmp x19, #CurrentEL_EL2 → 比较结果 → 写入 NZCV 标志位 ③ mrs x19, sctlr_el1 → x19 被覆盖为 SCTLR 值 ★ 标志位不受影响，cmp 结果仍在 ④ b.ne 0f → 根据标志位分支，不是看 x19

3.4 tbnz / tbz 指令详解 & 真实反汇编对照

3.4.0 tbnz 与 tbz 的区别

tbnz 和 tbz 是 ARM64 的按位测试分支指令，语法相同、编码相同，唯一差别是跳转条件相反。它们不经过 NZCV 标志位，直接测试通用寄存器中的某一位是否为 0/1。

项目tbnztbz
全称Test bit, branch if Not ZeroTest bit, branch if Zero
语法tbnz Rt, #bitnum, labeltbz Rt, #bitnum, label
操作数 Rt必须是 W 寄存器（32 位）；写 x19 时汇编器生成 w19
测试范围#bitnum = 0 ~ 31（W 寄存器的 bit 0 ~ bit 31）
跳转条件被测位 == 1 时跳转被测位 == 0 时跳转
不跳转时被测位 == 0 → 顺序执行下一条被测位 == 1 → 顺序执行下一条
是否改 NZCV否（与 cmp/tst 不同）

等价 C 伪代码（以 bit 25 为例）：

// tbnz w19, #25, label
if ((w19 >> 25) & 1)    // bit25 == 1
    goto label;
else
    fall_through;
// tbz w19, #25, label
if (((w19 >> 25) & 1) == 0)   // bit25 == 0
    goto label;
else
    fall_through;

被测位为 0 或 1 时的行为对照

被测 bit 值tbnz Rt, #n, labeltbz Rt, #n, label
0不跳转，继续下一条跳转到 label
1跳转到 label不跳转，继续下一条
同一 bit 上，tbnz 与 tbz 互为"反条件"分支： 测试 Rt 的 bit #n │ ┌────────┴────────┐ bit=0 bit=1 │ │ tbnz: 不跳 tbnz: 跳转 ★ tbz: 跳转 ★ tbz: 不跳 ★ = 该指令在此情况下会跳转

在 record_mmu_state 中为何 LE 用 tbnz、BE 用 tbz？

源码通过 CPU_LE() / CPU_BE() 在编译期二选一，目标都是：当前字节序与内核期望不一致时，跳到 1: 纠正。

内核编译选项选用的指令跳转条件何时跳到 1:含义
CONFIG_CPU_LITTLE_ENDIAN（LE）tbnz x19, #25, 1fEE == 1硬件是大端与 LE 内核不匹配 → 纠正
CONFIG_CPU_BIG_ENDIAN（BE）tbz x19, #25, 1fEE == 0硬件是小端与 BE 内核不匹配 → 纠正
// head.S:141-142（同一逻辑，编译期只保留一条）

CPU_LE( tbnz x19, #SCTLR_ELx_EE_SHIFT, 1f )   // LE 内核期望 EE=0
CPU_BE( tbz  x19, #SCTLR_ELx_EE_SHIFT, 1f )   // BE 内核期望 EE=1

// 统一语义：
if (SCTLR.EE != expected_endian_for_kernel)
    goto fix_endian;    // 1:
💡 与 cmp / tst 的对比：
  • cmp / tst：算术/逻辑运算 → 更新 NZCV → b.eq / b.ne / csel 读标志位
  • tbnz / tbz：直接读寄存器某一位 → 不碰 NZCV → 一条指令完成"测位 + 分支"
对单个标志位（如 EE bit 25），tbnz/tbz 比 tst + b.ne 更直接：无需先 tst #mask 再分支。
⚠ QEMU 小端冷启动：EE=0 → tbnz #25 不跳转（bit=0，tbnz 要求 bit=1 才跳）。若误用 tbz，EE=0 反而会跳进字节序纠正路径——这就是为什么必须用 CPU_LE/CPU_BE 在编译期选对指令。

3.4.2 为什么是 w19 而不是 x19？

AArch64 中 tbnz/tbz 指令只能编码 W 寄存器（32 位）。汇编里写 tbnz x19, #25 时，汇编器实际生成 tbnz w19, #25。由于 SCTLR 是 32 位、EE 在 bit 25，测 w19 的 bit 25 与测 x19 的 bit 25 完全等价。

# EL1: 应直接到 +20 (tbnz)，跳过 +16
# EL2: 应到 +16 (mrs sctlr_el2)

# --- 141 行：si 一次 ---
# EE=0: 不跳，继续 +24 (tst)

# --- 146 行 ret 后 ---

4.3 字节序纠正路径（endian 不匹配）

⚠ 这条路径非常罕见，但设计极为精巧。当 bootloader 以与内核相反的字节序启动时，CPU 上电后执行的第一条指令就可能因为字节序错误而崩溃。ARM64 通过这套机制在禁用 MMU 后安全切换字节序。
  1. 检测到不匹配：tbnz x19, #EE, 1f — EE 位与预期不同
  2. 翻转 EE 位：eor x19, x19, #SCTLR_ELx_EE — 异或 bit 25，得到正确的字节序配置
  3. 清除 M 位：bic x19, x19, #SCTLR_ELx_M — 强制关闭 MMU（因为字节序切换要求 MMU 关闭）
  4. 选择写入的 SCTLR：
    • b.ne 2f — 如果原 EE=1（LE内核+硬件大端）→ 写 sctlr_el1
    • 原 EE=0（BE内核+硬件小端）→ 写 sctlr_el2
  5. 写入 SCTLR + ISB：pre_disable_mmu_workaround + msr + isb — 写入正确的 SCTLR，同步屏障
  6. 清除 x19：mov x19, xzr — 返回 0（MMU 强制关闭）
💡 pre_disable_mmu_workaround 是一个针对 Qualcomm Falkor 勘误 E1041 的 workaround。该勘误影响某些 Qualcomm 服务器 CPU，在禁用 MMU 时可能需要 ISB 防止后续指令使用错误的翻译。大多数平台这个宏展开为空。

5. x19 返回值在各处的消费

x19 从 record_mmu_state 返回后，在 primary_entry 和 preserve_boot_args 中被多处使用：

5.1 在 primary_entry 中使用（line 101）

    cbnz    x19, 0f           // x19 != 0 → MMU was on → 跳转到 0
    // x19 == 0 → MMU was off
    dmb     sy
    mov     x1, x0            // x1 = ptep (页表使用结束)

    adr_l   x1, __idmap_text_end

5.2 在 preserve_boot_args 中使用（line 177）

SYM_CODE_START_LOCAL(preserve_boot_args)
    mov     x21, x0
    adr_l   x0, boot_args
    stp     x21, x1, [x0]       // boot_args[0..1] = x21(FDT), x1
    stp     x2, x3, [x0, #16]   // boot_args[2..3] = x2, x3

    cbnz    x19, 0f             // x19 != 0 → MMU on → 跳过 cache inval
    dmb     sy                  // MMU off: 需要内存屏障
    add     x1, x0, #0x20       // boot_args 4 × 8 = 32 字节
    b       dcache_inval_poc    // tail call: invalidate boot_args cache lines

💡 两条路径的对称设计：
  • MMU off → 页表写入是 non-cacheable 的，但 speculative load 可能缓存了陈旧值 → 需要 invalidate
  • MMU on → 页表写入是 cacheable 的，但在关闭 MMU 前需要把 dirty cache lines 写回内存 → 需要 clean
  • 这套对称的 cache 维护逻辑贯穿了整个 early boot 阶段

5.3 设计意图：探测器与消费者的协作 ★

record_mmu_state 本身不做任何缓存维护——它只是一个探测器，返回一个标记值。真正的缓存操作在调用方 primary_entry 和 preserve_boot_args 中执行。二者通过 x19 传递决策信息。

5.3.1 143–145 行的判断逻辑：数据缓存是否开着？

这三条指令回答一个简单的问题，并以返回值的形式传递给调用者：

// 伪代码等价
bool cache_was_on = (sctlr & SCTLR_C) != 0;   // line 143: tst
bool mmu_was_on   = sctlr & SCTLR_M;           // line 144: and

if (!cache_was_on)
    return 0;               // line 145: csel → "缓存没开，直接走"
else
    return mmu_was_on;      // "缓存开着，把 MMU 状态带回去"
// ============ 探测器（record_mmu_state）的返回值语义 ============ // // x19 = 0 → D-Cache 没开 → 冷启动 / 裸机直接进内核 // x19 = 1 → D-Cache 开着 + MMU 也开着 → 热重启（kexec/hibernate） // // ★ 为什么检测 C（Cache）而不是 M（MMU）？ // // 正常情况 M=0 时 C 一定为 0。但如果 bootloader 关了 MMU // 却忘了关 Cache（M=0, C=1），此时直接 invalidate 可能丢数据。 // 检测 C 位更安全——只有确认 Cache 开着才走 clean 路径。

5.3.2 消费者 ①：primary_entry 的缓存维护分流（line 101）

这是返回值最重要的消费点：

// ============ primary_entry 中的缓存策略 ============ // // cbnz x19, 0f ★ 根据 record_mmu_state 的返回值分流 // // ┌── x19 == 0 (缓存没开) ──────────────────────────┐ // │ │ // │ dmb sy │ // │ dcache_inval_poc(pg_dir_start, pg_dir_end) │ // │ ↓ │ // │ 只做 invalidate（丢弃缓存行，不写回） │ // │ 原因：缓存里没有脏数据，丢弃即可 │ // │ │ // └───────────────────────────────────────────────────┘ // // ┌── x19 != 0 (缓存开着) ───────────────────────────┐ // │ │ // │ dcache_clean_poc(__idmap_text_start, │ // │ __idmap_text_end) │ // │ ↓ │ // │ 做 clean to PoC（把脏缓存行写回内存） │ // │ 原因：后续要关 MMU，必须先刷脏数据 │ // │ │ // └───────────────────────────────────────────────────┘

5.3.3 消费者 ②：preserve_boot_args 的缓存决策（line 177）

同样的模式：

// preserve_boot_args 内部： // // cbnz x19, 0f ★ 再次使用 x19 // // x19 == 0 → dmb + dcache_inval_poc(boot_args) // 丢弃可能的陈旧缓存行 // x19 != 0 → str_l mmu_enabled_at_boot + ret // 缓存开着，直接写即可

mov     x0, x19           // x19 → x0，作为 cpu_boot_mode 参数

init_kernel_el 根据这个参数决定是否需要清理 HYP 模式的代码缓存等。

5.3.5 完整协作图

// ============ 探测器 → 消费者 协作全景 ============ // // record_mmu_state() primary_entry / preserve_boot_args // ══════════════════ ═══════════════════════════════════ // // 读 SCTLR // │ // 检测 EE ──不匹配──→ 翻转端序, 关 MMU, 返回 0 // │ // 匹配 // │ // 143 tst #C ──→ Z // 144 and #M ──→ x19 = M_bit // 145 csel eq ──→ if Z: x19=0 // │ // ├── x19 = 0 ──→ dcache_inval_poc (丢弃) // │ "缓存没开/不可信，直接丢掉" // │ // └── x19 = 1 ──→ dcache_clean_poc (写回) // "缓存开着且可信，先刷干净再关 MMU" // // ★ record_mmu_state 只负责"判断"和"返回" // ★ primary_entry 负责"执行"——选择 inval 还是 clean
💡 一句话总结：record_mmu_state 是一个纯判断函数——它检测「数据缓存是否开着」并返回标记值。真正的缓存操作由 primary_entry 根据这个标记值执行：缓存没开 → invalidate（丢弃），缓存开着 → clean（写回）。这种「探测器 + 消费者」的分离设计让判断逻辑可以复用于多个消费点（primary_entry、preserve_boot_args、init_kernel_el）。

N=0, C=1, V=0——逻辑 ands 的 C/V 固定规则，与 result 是否为 0 无关（见 §3.2.2、§6.4.0）
and x19, x19, #SCTLR_ELx_M不更新——写 x19 = M 位；NZCV 保持 tst 所设（见 §3.2.3）
csel x19, xzr, x19, eq不更新读 ZEQZ=1（tst：SCTLR C=0）→ x19=0；Z=0 → x19=M 位。见 §3.2.4
eor x19, x19, #EE（endian 路径）NZCV 全更新ZEQ / NE判断翻转前 EE 是 0 还是 1，决定写 sctlr_el1 还是 el2
💡 记忆要点：本函数里几乎所有分支/选择（b.ne、csel eq）都只依赖 Z 标志位——"结果是否为 0"。cmp 的 Z=1 表示相等；tst 的 Z=1 表示按位与结果为 0（被测位 = 0）。

8. 总结 & 关键要点

#要点说明
1 内核启动第一个函数调用 在 primary_entry 中，record_mmu_state 是第一条 bl 指令
2 返回值在 x19 中 x19 = 0（关闭）或 1（开启），受 C 位修正
3 投机执行 + 条件覆盖 先读 sctlr_el1，再根据异常级别决定是否用 sctlr_el2 覆盖
4 单条指令检测字节序 tbnz EE_bit 同时检查字节序兼容性，不匹配时跳转纠正路径
5 C 位修正而非 M 位修正 检测 Cache 位而不是 MMU 位来决策，更安全（M=0,C=1 的边缘情况）
6 字节序纠正路径 翻转 EE 位 + 关闭 MMU + 写回 SCTLR + ISB，处理跨字节序启动
7 条件执行三连击 tst → and → csel：测试 C 位 → 提取 M 位 → 条件选择，无分支
8 x19 贯穿整个 early boot 影响 cache 维护策略（invalidate vs clean）和 init_kernel_el 参数
