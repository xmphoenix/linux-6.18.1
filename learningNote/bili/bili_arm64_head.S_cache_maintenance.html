1. 问题的根源：D-cache 状态的两种可能

1.1 核心问题不在于 MMU，而在于 D-cache

很多资料将这两条路径描述为"Cold Boot"和"Warm Boot"的差异，但真正决定路径的不是启动类型，而是 bootloader 是否开启了 D-cache。

逐步演算：三个典型场景

这四条汇编指令的目的：用 SCTLR 的 C 和 M 两位确定 x19 的最终值。关键技巧——tst 在 and 之前执行，利用 tst 设置的 Z 标志驱动 csel，而 and 不影响标志位。

// ============ 场景一：U-Boot Cold Boot (C=0, M=0) ============ SCTLR = 0x00000000_30C50800 // U-Boot 未开启 MMU 和 D-cache [mrs] x19 = 0x00000000_30C50800 // 读取 SCTLR 全部 64 位 [tst C] x19 & 0x4 = 0x0 // bit2 = 0 → C=0 标志位: Z=1 (C==0) // tst: AND 但不存结果, 只设标志 x19 不变: 0x30C50800 // 指令未修改目标寄存器 [and M] x19 & 0x1 = 0x0 // bit0 = 0 → M=0 x19 = 0x00000000_00000000 // 只保留 bit 0 [csel] Z=1 → 选 xzr // 因为 C==0 (Z=1) ====== x19 = 0 ====== // 走 Inval 路径 ✓ // ============ 场景二：kexec Warm Boot (C=1, M=1) ============ SCTLR = 0x00000000_34D5D91D // kexec 启动, MMU 和 D-cache 都在运行 [mrs] x19 = 0x00000000_34D5D91D [tst C] x19 & 0x4 = 0x4 // bit2 = 1 → C=1 标志位: Z=0 (C==1) x19 不变: 0x34D5D91D [and M] x19 & 0x1 = 0x1 // bit0 = 1 → M=1 x19 = 0x00000000_00000001 [csel] Z=0 → 选 x19(保留 M=1) // 因为 C==1 (Z=0) ====== x19 = 1 ====== // 走 Clean 路径 ✓ // ============ 场景三：Broken Bootloader (C=1, M=0) ============ SCTLR = 0x00000000_00000004 // D-cache 开着但 MMU 关了 (非法状态) [mrs] x19 = 0x00000000_00000004 [tst C] x19 & 0x4 = 0x4 // bit2 = 1 → C=1 标志位: Z=0 (C==1) x19 不变: 0x00000004 [and M] x19 & 0x1 = 0x0 // bit0 = 0 → M=0 x19 = 0x00000000_00000000 [csel] Z=0 → 选 x19(保留 M=0) // 虽 C==1, 但 M=0 ====== x19 = 0 ====== // 走 Inval 路径 ✓ (保守处理)

设计精髓：为什么 `tst` 放在 `and` 之前

如果反过来写（先 and 再 tst）：

and x19, x19, #SCTLR_ELx_M   // x19 只剩 bit 0
tst x19, #SCTLR_ELx_C         // C=0x4, 但 x19 已经被 and 截断!
                               // 永远测到 0 → Z 永远为 1
csel x19, xzr, x19, eq        // 永远清 0 → 永远走 Inval

Warm Boot 永远被误判为 Cold Boot。

正确的顺序（先 tst 再 and）：

tst x19, #SCTLR_ELx_C         // C bit 还在 → Z 正确
and x19, x19, #SCTLR_ELx_M   // 提取 M bit, 不影响 Z
csel x19, xzr, x19, eq        // 用 tst 留下的 Z 做判决

`and` 不改变标志位，Z 保持 tst 的结果 ✓

💡 最终公式：x19 = (C==0 || M==0) ? 0 : 1。即只有 D-cache 和 MMU 同时开启时 x19=1，其余所有情况 x19=0。这是防御性编程——除非非常确定 cache 和 MMU 都在正常运行，否则按最坏情况（non-cacheable 写入）处理。

1.2 两种 D-cache 状态的完全不同需求

D-cache OFF (x19=0)

  • bootloader（如 U-Boot）未开启 D-cache
  • create_init_idmap 的 STP 指令 → 数据直达物理内存（non-cacheable）
  • 但 CPU 的 speculative load 不经过 MMU，可能在后台把旧数据预取到了 D-cache
  • → 需要 Invalidate：丢弃 D-cache 中 speculative 预取的旧数据

D-cache ON (x19=1)

  • bootloader / 前一内核实例开启了 D-cache
  • create_init_idmap 的 STP 指令 → 数据先进入 D-cache（cacheable）
  • D-cache 中的脏行尚未写回内存
  • 后续 enable_mmu() 会短暂关闭 MMU → 需要 Clean：把脏数据写回内存
💡 核心理解：分叉依据是 bootloader 的 D-cache 状态（SCTLR_ELx.C bit），而不是 cold/warm boot 本身。U-Boot 通常关闭 D-cache → x19=0 → inval 路径。kexec/EFI stub 通常开启 D-cache → x19=1 → clean 路径。但严格来说这是一个"D-cache 状态"判断，不是"启动类型"判断。

1.2 Speculative Load 详解 — 为什么 D-cache OFF 也逃不过 Cache

// ============ D-cache OFF 下的 Speculative Load 问题 ============ 时间线: ─────────────────────────────────────────────────────────────▶ 1. CPU 上电, MMU off, D-cache = unknown state │ 2. create_init_idmap() 写入页表 // STP 指令，non-cacheable 直达内存 │ 内存: [PGD] = 0x41731003 (正确) │ 3. CPU 的预取器 (prefetcher) 在后台悄悄工作 // 不经过 MMU，直接看物理地址 │ speculative load: 把 0x41731000 附近的数据预取到 D-cache // 此时 D-cache 中存的是旧值！ │ 4. D-cache: [0x41731000] = 0x00000000 (旧值/垃圾) // 与内存不一致！ │ 内存: [0x41731000] = 0x41731003 (正确) │ 5. __primary_switch → enable_mmu() → MMU ON! // 此后访问变成 cacheable │ 6. MMU 查表: 读 PGD → 命中 D-cache → 返回旧值 0x00000000 → 无效的页表项 → 异常！ 解决方案: 在步骤 5 之前，执行 D-cache invalidate，清除所有 speculatively loaded 的旧数据
⚠ 关键认知：即使 MMU 关闭、即使页表写入是 non-cacheable 的，CPU 硬件预取器仍然可能在后台将物理地址的数据加载到 D-cache。这不是 bug，而是现代 CPU 的正常行为 — speculative execution 和 prefetching 不经过 MMU 检查。

2. 两条路径的总览

// ============ primary_entry 中的 cache 维护分流 ============ bl __pi_create_init_idmap // 返回值 x0 = ptep (页表区域结束地址) │ ▼ cbnz x19, 0f // ★ 分叉点: x19 来自 record_mmu_state │ ├── x19 == 0 (D-cache was OFF) ──▶ Invalidate 路径 │ │ │ dmb sy // 内存屏障 │ mov x1, x0 // x1 = ptep (结束地址) │ adrp x0, __pi_init_idmap_pg_dir // x0 = 起始地址 │ adr_l x2, dcache_inval_poc │ blr x2 // invalidate [pg_dir .. ptep) │ b 1f │ └── x19 != 0 (D-cache was ON) ──▶ Clean 路径 0: adrp x0, __idmap_text_start // x0 = idmap 代码起始 adr_l x1, __idmap_text_end // x1 = idmap 代码结束 adr_l x2, dcache_clean_poc blr x2 // clean [__idmap_text_start .. end) 1: mov x0, x19 bl init_kernel_el // 继续启动

💡 操作范围为什么不同？
D-cache OFF 路径需要对刚刚写的页表（[pg_dir .. ptep)）做 invalidate — 清除 speculative load 带来的旧数据。页表区域恰好也是 identity mapping 映射的目标范围之外的区域。
D-cache ON 路径需要对idmap 代码段做 clean — 因为后续 enable_mmu() → MMU off 后，会执行 idmap 代码。CPU 关闭 MMU 时可能仍有 dirty cache lines，所以必须先 clean 回内存。

3. D-cache OFF 路径详解：Invalidate

3.1 流程分析

  1. dmb sy — 全系统数据内存屏障。确保 create_init_idmap 中所有的页表写入（STP）已经全局可见（到达 PoC — Point of Coherency）。在 non-cacheable 写入中，虽然数据直达内存，但仍然需要屏障确保写入完成。
  2. mov x1, x0 — x0 是 create_init_idmap 的返回值 ptep（页表使用区域的结束物理地址）。x1 = 结束地址。
  3. adrp x0, __pi_init_idmap_pg_dir — x0 = 页表区域的起始物理地址（PGD）。
  4. blr x2 (dcache_inval_poc) — 对 [x0, x1) 范围内的所有 cache lines 执行 DC IVAC（Invalidate by VA to PoC）。

3.2 为什么放在这个位置？

// ============ 时间窗口分析 ============ create_init_idmap 写入页表 (non-cacheable) │ ▼ speculative load 窗口打开 ← 此时 D-cache 中可能已有旧数据 │ ▼ dcache_inval_poc ← 清除 D-cache 中的旧数据 │ ▼ speculative load 窗口继续 │ ▼ enable_mmu() ← 此后访问变为 cacheable │ ▼ MMU ON, reads are cacheable → 如果 D-cache 中还有旧数据 → 读到错误的页表项 Inval 之后到 MMU ON 之间，speculative load 仍可能再次预取。 但这次预取的是我们已经写入内存的正确数据（因为 inval 清空了 cache）。 新的预取会拿到正确的值。
💡 为什么不在 create_init_idmap 内部做 inval？ 因为 speculative load 在写入完成后的任何时刻都可能发生。把 inval 放在 MMU 开启前的最晚时刻，可以最小化 inval 之后到 MMU ON 之间的窗口。如果在 create_init_idmap 中做，那之后到 MMU ON 还有大段代码（init_kernel_el、__cpu_setup 等），窗口更大。

4. D-cache ON 路径详解：Clean

4.1 场景分析：为什么 D-cache ON 的问题完全不同

// ============ D-cache ON (kexec / 休眠唤醒) 的缓存状态 ============ 进入 primary_entry 时的状态: ┌─────────────────────────────────────────────────────────┐ │ MMU ON → 前面的代码已经通过 identity mapping 正确运行 │ │ 而 identity mapping 本身尚未 "重新建立" │ │ │ │ D-cache 中: │ │ ✓ idmap 代码段 (cacheable, 已在使用) │ │ ✓ 各种内核数据 (上一个内核实例留下的) │ │ │ │ 内存中: │ │ ⚠ 某些 cache lines 是 dirty 的，内存可能不是最新的 │ └─────────────────────────────────────────────────────────┘ 后续 __primary_switch 流程: ┌─────────────────────────────────────────────────────────┐ │ 1. 重新创建 identity mapping 页表 │ │ 2. 切换到新的 TTBR │ │ 3. enable_mmu() → 短暂关闭 MMU → 重新开启 │ │ │ │ 在 MMU 关闭的瞬间: │ │ → CPU 无法通过 cacheable 方式访问内存 │ │ → 但 idmap 代码是放在 identity mapped 区域的 │ │ → 这些代码必须在内存中是干净的（clean） │ └─────────────────────────────────────────────────────────┘

4.2 Clean 的范围：为什么是 idmap 代码段？

D-cache ON 路径 clean 的范围是 [__idmap_text_start .. __idmap_text_end)，而不是页表区域。原因：

  • idmap 代码段：包含 __primary_switch、enable_mmu、__cpu_setup 等关键代码。这些代码在 MMU 关闭后仍会被执行（通过 identity mapping），所以必须在内存中是 clean 的。
  • 页表区域不需要 clean：create_init_idmap 刚写入的页表还在 D-cache 中（dirty 状态），但在新 TTBR 设置后、MMU 关闭前会通过 ISB 被硬件感知。MMU 重新开启后会重新读取这些页表，而 cacheable 访问会自然命中 D-cache 中的最新值。

4.3 时序图

// ============ D-cache ON 的完整 Cache 维护时序 ============ primary_entry (kexec 入口): │ ├─ record_mmu_state → x19 = 1 (MMU on) ├─ preserve_boot_args → x19 = 1 → 跳过 inval，记录 mmu_enabled_at_boot ├─ create_init_idmap → 写入新页表 (cacheable, dirty in D-cache) │ ├─ clean [__idmap_text_start .. end) → ★ 把 idmap 代码写回内存 │ ├─ init_kernel_el ├─ __cpu_setup → 配置 TCR/MAIR │ ▼ __primary_switch: ├─ 设置新的 TTBR ├─ enable_mmu() → MMU 短暂关闭 // 此时执行 idmap 代码，需要内存中有最新版本 ├─ MMU 重新开启 ▼ __primary_switched (VA 空间)

5. dcache_inval_poc 实现剖析 ★

5.1 完整源码

// arch/arm64/mm/cache.S:135-177

/*
 * dcache_inval_poc(start, end)
 *
 * Invalidate D-cache lines in [start, end).  Partially covered cache
 * lines at the boundaries are cleaned FIRST to avoid data loss, then
 * all lines are invalidated.
 *
 *  x0 = start (inclusive)
 *  x1 = end   (exclusive)
 */
SYM_FUNC_START(__pi_dcache_inval_poc)
    dcache_line_size x2, x3          // ① 读取 cache line 大小 → x2
    sub     x3, x2, #1               // ② x3 = line_size - 1 (对齐掩码)
    tst     x1, x3                   // ③ end 是否对齐？
    bic     x1, x1, x3               //    向下对齐 end
    b.eq    1f                        //    对齐 → 跳转到 1f
    dc      civac, x1                // ④ 不对齐: 先 CIVAC (clean+inval) 尾部
1:  tst     x0, x3                   // ⑤ start 是否对齐？
    bic     x0, x0, x3               //    向下对齐 start
    b.eq    2f                        //    对齐 → 跳转到 2f
    dc      civac, x0                // ⑥ 不对齐: CIVAC (clean+inval) 首部
    b       3f
2:  dc      ivac, x0                 // ⑦ 对齐: 直接 IVAC (inval only)
3:  add     x0, x0, x2               // ⑧ x0 += line_size
    cmp     x0, x1                   // ⑨ 还有更多行？
    b.lo    2b                       //    是 → 继续循环
    dsb     sy                       // ⑩ 全系统数据屏障
    ret

SYM_FUNC_END(__pi_dcache_inval_poc)


/*
 * dcache_clean_poc(start, end)    — 对比: dcache_clean 简洁得多
 * x0 = start, x1 = end
 */
SYM_FUNC_START(__pi_dcache_clean_poc)
    dcache_by_line_op cvac, sy, x0, x1, x2, x3
    ret
SYM_FUNC_END(__pi_dcache_clean_poc)

5.2 逐行剖析

① dcache_line_size x2, x3 — 读取 cache line 大小

// 展开为:
read_ctr  x3              // 读取 CTR_EL0 (Cache Type Register)
ubfm      x3, x3, #16, #19  // 提取 bits[19:16] = DminLine (log2 of line size in words)
mov       x2, #4           // 4 bytes per word
lsl       x2, x2, x3       // x2 = 4 << DminLine = actual cache line size in bytes
// 典型值: DminLine = 4 → x2 = 4 << 4 = 64 bytes (常见 cache line)

② 首尾不对齐的 "Clean First" 策略

// ============ 为什么不对齐部分要做 CIVAC 而不是直接 IVAC？============ Cache line 边界: |<-- 64 bytes -->| │ 内存地址空间: ─────────────────────────────────────────────▶ │◄────── invalidate range [start, end) ──────▶│ │ │ start (不对齐) end (不对齐) 问题: start 和 end 可能落在 cache line 中间 如果对首部做 IVAC (invalidate only): - 整个 cache line 被丢弃，包括 start 之前的合法数据 - start 之前的数据还没被写回内存 → 数据丢失！ 正确做法 — CIVAC (Clean + Invalidate): - 先把整个 cache line 写回内存 (clean) - 再丢弃 cache line (invalidate) - start 之前的数据安全写回，start 之后的数据被丢弃 ✓ 中间的对齐部分 — IVAC (Invalidate only): - 不需要写回 (我们知道这些页表数据是 non-cacheable 写入的) - 直接丢弃整个 cache line

④ dc civac, x1 — 尾部对齐修正

  • tst x1, x3 — 测试 end 地址的低位（cache line 对齐检查）
  • 如果不对齐 → DC CIVAC（Clean and Invalidate by VA to PoC）
  • CIVAC：先 clean（写回脏数据），再 invalidate（丢弃缓存行）
  • bic x1, x1, x3 — 向下对齐到 cache line 边界

⑥~⑦ 循环体：首部修正 + 对齐部分全 invalidate

// 首部 (start 不对齐): CIVAC → 安全清理
dc      civac, x0           // Clean + Invalidate

// 中间 (对齐): IVAC → 快速 invalidate
dc      ivac, x0            // Invalidate only (无需 clean)

// 循环:
add     x0, x0, x2          // x0 += line_size
cmp     x0, x1              // x0 < end ?
b.lo    2b                   // 是 → 继续循环

⑩ dsb sy — 全系统数据屏障

  • 确保所有 DC IVAC/DC CIVAC 操作对整个 Shareability Domain 可见
  • 在此之后，所有缓存行都被 invalidated，后续的 cacheable 访问将强制从内存重新读取

5.3 dcache_clean_poc — 对比的简洁

SYM_FUNC_START(__pi_dcache_clean_poc)
    dcache_by_line_op cvac, sy, x0, x1, x2, x3   // 展开为:
    //   ① 读 cache line size
    //   ② sub tmp, linesz, #1
    //   ③ bic start, start, tmp    (对齐 start)
    //   ④ 循环: DC CVAC, start  (Clean by VA to PoC)
    //      start += linesz
    //   ⑤ dsb sy
    ret
SYM_FUNC_END(__pi_dcache_clean_poc)

dcache_clean_poc 比 dcache_inval_poc 简单得多：不需要首尾 CIVAC 处理，因为 Clean 操作不会丢失数据 — 它只是把 dirty cache lines 写回内存，不丢弃缓存行。即使覆盖了范围外的数据也无害。

5.4 ARM64 Cache 维护指令速查

指令全称操作使用场景
DC IVACInvalidate by VA to PoC丢弃缓存行（不写回）缓存行数据无效时（如 speculative load 的旧数据）
DC CVACClean by VA to PoC写回脏数据（保留缓存行）需要在 PoC 级别看到最新数据时
DC CIVACClean + Invalidate by VA to PoC先写回，再丢弃缓存行部分有效、需要安全丢弃时（不对齐边界）
DSB SYData Synchronization Barrier等待所有操作全局完成所有 DC 操作之后，确保一致

6. 总结与设计哲学

6.1 为什么这是"第一阶段"的关键设计

// ============ 第一阶段（Identity Mapping）的子阶段 ============ primary_entry: ├─ record_mmu_state() → 感知当前状态 ├─ preserve_boot_args() → 保存 boot 参数 ├─ create_init_idmap() → 构建页表 │ ├─ ★ Cache 维护 (本次分析) │ ├─ MMU off → invalidate 页表区 │ └─ MMU on → clean idmap 代码 │ ├─ init_kernel_el() → 配置异常级别 ├─ __cpu_setup() → 配置 TCR/MAIR │ ▼ __primary_switch: └─ enable_mmu() → MMU ON (关键转换点)

6.2 设计哲学

#哲学体现
1单一变量决策只用 x19 一个寄存器决定两条完全不同的路径，简洁高效
2最小化窗口cache inval 放在 MMU 开启前最后时刻，最小化 speculative load 重新预取的窗口
3Clean First 策略不对齐的 cache line 先 clean 再 invalidate，保护共享数据
4精确范围只操作确实需要的地址范围（页表区域 / idmap 代码段），不 flush 整个 D-cache
5操作对称性Cold→Invalidate (废)，Warm→Clean (保)，两种操作语义完全对称
6PoC 级别所有 cache 维护都到 PoC（Point of Coherency）——保证所有 observer 看到一致数据

6.3 关键要点

  1. D-cache OFF 的核心矛盾：Non-cacheable 写入 vs Speculative Load 预取。即使 MMU 关闭、写入绕过 cache，CPU 预取器仍可能在后台将旧数据加载到 D-cache。必须在 MMU 开启前 invalidate。
  2. D-cache ON 的核心矛盾：Cacheable 写入 vs 即将关闭 MMU。页表写入在 D-cache 中（dirty），而 idmap 代码在 MMU 关闭后会从内存执行。必须 clean 写回。
  3. dcache_inval_poc 的 Clean First：不对齐的首尾缓存行用 CIVAC（先 clean 再 inval），保护共享数据。中间对齐部分用 IVAC（直接 inval），高效。
  4. DMB 的位置：在 dcache_inval_poc 调用前放 dmb sy 确保所有 STP（页表写入）完成。dsb sy 在 dcache_inval_poc 内部确保所有 DC 指令完成。
