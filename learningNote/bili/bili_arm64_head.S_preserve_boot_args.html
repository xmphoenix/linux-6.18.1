1. 概述：preserve_boot_args 的使命

调用位置

SYM_CODE_START(primary_entry)
    bl  record_mmu_state        // 记录 MMU 状态 → x19
    bl  preserve_boot_args      // ★ 保存启动参数

核心使命

  • 将 bootloader 传入的 x0~x3 保存到全局数组 boot_args[4]
  • 将 x0 (FDT 物理地址) 额外保存到 x21（后续仍会用到）
  • 根据 x19（MMU 状态）分两条路径处理 D-cache 一致性
  • MMU on 时：将 x19 记录到全局变量 mmu_enabled_at_boot

💡 为什么 x1~x3 必须是 0？——"Reserved for future use" 设计模式

Documentation/arch/arm64/booting.rst:166-168 的定义： 
x0 = physical address of device tree blob (dtb) in system RAM.
x1 = 0 (reserved for future use)
x2 = 0 (reserved for future use)
x3 = 0 (reserved for future use)
"Reserved for future use" 是接口设计的经典模式，x1~x3 必须为 0 的原因有三层：

① 向后兼容（Backward Compatibility）
如果未来 ARM64 Linux 需要从 bootloader 接收更多参数（如第二个 blob 地址、安全监控配置、随机数种子等），就可以用 x1/x2/x3 来传递，而不用改协议版本号。旧 bootloader 写 0 进来 → 新内核检测到 0 → 知道"这个 bootloader 不支持新特性"→ 自动退回到默认行为。

② 向前兼容（Forward Compatibility）
新 bootloader 传了非零值给旧内核 → 旧内核打印警告但继续运行（不 panic）→ 同一个 bootloader 可以启动新旧两种内核。

③ Broken Bootloader 检测
内核在 setup.c:372 检查 boot_args[1] || boot_args[2] || boot_args[3]，如果非零则打印警告。这条检查目前最大的实际意义是帮助检测 broken bootloader（如某些粗制滥造的 U-Boot 分支忘了清零这些寄存器，把垃圾值传了进来）。

类比：就像函数签名的保留参数——现在不用，但把位置占住，将来扩展时不用改调用约定（ABI）。

目前 x1~x3 有谁在用？ 没有人。
• ARM32 时代：ATAGS 启动方式中，r1 传 machine type number，r2 传 ATAGS 指针。切换到 FDT 后这些就废弃了。
• ARM64 时代：从第一天就只使用 FDT（x0 传地址），x1~x3 从未被正式使用过。一些早期的 UEFI stub 代码或 kexec 实现可能短暂地借用过这些寄存器，但都是非标准行为。
• 所以总结：x1~x3 是为将来的协议扩展预留的空白槽位，必须填 0 作为"我不支持扩展"的标记。

3.2 逐条详解

① mov x21, x0 — 保存 FDT 指针到 x21

  • x0 是 bootloader 传入的 FDT 物理地址（Device Tree Blob）
  • x21 是 callee-saved 寄存器，不会被后续函数调用破坏
  • 后续可通过 x21 随时访问 FDT（line 231: str_l x21, __fdt_pointer，line 517: mov x1, x21）
  • 为什么不用 x19？x19 已经被 record_mmu_state 占用了（MMU 状态标志）

② adr_l x0, boot_args — 获取 boot_args 数组地址

  • adr_l 是汇编宏，展开为两条指令：
// adr_l dst, sym 展开为:
adrp    dst, sym        // 加载符号所在 4KB 页基址
add     dst, dst, :lo12:sym  // 加上页内偏移
  • boot_args 是 u64 boot_args[4]，在 setup.c 中定义
  • 此时 MMU 可能关闭，CPU 跑在物理地址上，但 adrp 基于 PC 相对寻址，仍然正确
  • 关键理解：由于内核是 PIE（位置无关）编译，adrp 得到的是运行时物理地址，与 MMU 状态无关

③ stp x21, x1, [x0] — 写入 boot_args[0..1]

  • STP（Store Pair）指令：一条指令存储两个 64 位值
  • [x0] = boot_args[0] = x21（FDT 物理地址）
  • [x0+8] = boot_args[1] = x1（bootloader 传入的第 2 个参数，应为 0）
  • 相比两条 STR 指令，STP 节省了代码空间和指令发射带宽

④ stp x2, x3, [x0, #16] — 写入 boot_args[2..3]

  • STP 使用立即偏移 #16（16 字节偏移）
  • [x0+16] = boot_args[2] = x2
  • [x0+24] = boot_args[3] = x3
  • 至此 boot_args[4] 的 32 字节已全部填入

⑤ cbnz x19, 0f — 条件分支：MMU 状态判断

  • CBNZ（Compare and Branch if Non-Zero）：如果 x19 ≠ 0 → 跳转到 0f
  • x19 来自 record_mmu_state 的返回值：0 = MMU off, 1 = MMU on
  • MMU on (x19=1) → 跳转到 0f → str_l x19, mmu_enabled_at_boot
  • MMU off (x19=0) → 不跳转 → 执行 D-cache invalidate 序列

⑥ dmb sy — 内存屏障

dmb sy 是 ARM64 的 Data Memory Barrier 指令，SY 表示 full system shareability（全系统可见性域）。

一句话：强制所有在 dmb sy 之前的存储操作，在被之后的任何内存访问可见之前，先对所有观察者（所有 CPU、所有缓存）全局可见。

6.1 为什么在这个场景中必须

看 MMU off 路径的指令序列：

stp x21, x1, [x0] // ① non-cacheable 写入 boot_args[0..1] stp x2, x3, [x0, #16] // ② non-cacheable 写入 boot_args[2..3] cbnz x19, 0f // x19=0，不跳转 dmb sy // ③ ★ 内存屏障 add x1, x0, #0x20 // ④ 准备 dcache_inval_poc 的参数 b dcache_inval_poc // ⑤ 尾调用：执行 DC IVAC

MMU 关闭时，STP 的写入属性是 Device/nGnRnE（non-cacheable, non-gathering, non-reordering, no early write acknowledgement）。这意味着：

  • 数据不经过 cache，直接发到内存总线
  • 但 CPU 内部的 store buffer 可能还持有这些写操作，没有真正落地到 PoC（Point of Coherency）

危险的竞态场景（没有 dmb sy 时）：

// ============ 场景：STP 延迟 + DC IVAC 提前执行 ============ 时间线（没有 dmb sy）: CPU store buffer 内存 D-cache ───────────── ──── ─────── STP 写入 → [pending] (旧数据) (旧 cache line) │ 预取器看到内存访问 ────────────────────────────────────▶ 预取 模式，推测性预取 (旧数据) ←──────────── fill! (旧 cache line 回来了) │ STP 落地 ──────────────▶ (新数据) (旧 cache line!) ← 不一致！ │ DC IVAC ──────────────────────────────────────────────▶ invalidate old (新数据在内存中幸存) 上面的时序中最终结果"碰巧"正确。但如果 DC IVAC 在 STP 落地之前就执行了？
⚠ 关键风险：DC IVAC 可能在 STP 落地之前执行——此时 cache line 被 invalidate，但新数据还没到内存。等 MMU 打开后，后续 fetch 拿到的就是垃圾数据。多核场景下，另一个 CPU 也可能在 STP 落地前通过 cacheable 访问读到旧数据。
6.2 dmb sy 如何消除竞态
// ============ 有 dmb sy 的正确时序 ============ CPU store buffer 内存 D-cache ───────────── ──── ─────── STP 写入 → [pending] (旧数据) (旧 cache line) │ dmb sy ═══════════════════════════════════════ │ "等 STP 全部落地！" │ │ STP 落地 ──────────────▶ (新数据) │ │ dmb sy 通过 ✓ ─────────────────────────────── │ │ DC IVAC ──────────────────────────────────────▶│ invalidate! │ 保证：DC IVAC 执行时，新数据已经在内存中了 ✓
6.3 硬件层面的实现
步骤操作
1Stall 流水线，等待 store buffer 中所有 pending 写操作完成
2等待这些写操作到达 PoC（所有核、所有 cluster 都能看到）
3等待 acknowledgement 从 interconnect 返回
4释放流水线，允许后续指令（DC IVAC）执行

SY（Shareability）参数的含义：这个 barrier 的作用范围是整个系统——不仅是当前 CPU 核，还包括所有其他核、DMA 设备等。这是最强的 barrier 变体。

6.4 为什么 MMU on 路径不需要？
// ============ 两条路径对比 ============ cbnz x19, 0f // MMU on → 跳转到 0f dmb sy // ★ 只有 MMU off 执行这里 ... 0: str_l x19, mmu_enabled_at_boot, x0 ret // MMU on 路径直接返回 MMU off 路径: STP (non-cacheable) ──→ [store buffer] ──→ 内存 │ dmb sy ═══════════════════════════════════ │ 强制排空 store buffer │ DC IVAC ──────────────────────────────────▶│ 安全 invalidate cache MMU on 路径: STP (cacheable) ──→ [D-cache] ←→ 内存 (硬件一致性自动同步) │ 不需要 barrier ─────┘ cache 就是最新数据，无需 DC IVAC
  • MMU on 时，STP 写入是 cacheable 的，数据写入 D-cache，硬件缓存一致性协议自动管理可见性
  • 不需要 DC IVAC（cache 里的就是最新数据，为什么要 invalidate？）
  • 没有 cache maintenance → 不需要 barrier 来保序
💡 核心结论：dmb sy 在 STP（non-cacheable 写）和 DC IVAC（cache 操作）之间充当"同步点"，强制排空 store buffer，确保前者完全落地到 PoC 后后者才开始执行，消除 store buffer 延迟带来的竞态。

⑦ add x1, x0, #0x20 — 准备结束地址

  • x0 当前指向 boot_args[0]，x1 = x0 + 0x20 = x0 + 32
  • boot_args 总共 4×8 = 32 字节，所以 x1 指向 boot_args 的末尾
  • 这为 dcache_inval_poc 准备了 [x0, x1) 地址区间参数

⑧ b dcache_inval_poc — 尾调用

  • 这不是 bl（分支并链接），而是 b（无条件跳转）
  • 尾调用优化：不压栈、不保留返回地址，直接跳转到 dcache_inval_poc
  • dcache_inval_poc 执行完毕后会 ret，但返回到 preserve_boot_args 的调用者（primary_entry），而不是 preserve_boot_args 本身
  • 这消除了一个没有任何后续代码的 ret 指令

⑨ str_l x19, mmu_enabled_at_boot, x0 — 记录 MMU 状态

  • 仅在 MMU on (x19=1) 路径执行
  • str_l 是汇编宏，展开为：
// str_l src, sym, tmp 展开为:
adrp    tmp, sym         // tmp = &mmu_enabled_at_boot 页基址
str     src, [tmp, :lo12:sym]  // 写入 mmu_enabled_at_boot = x19
  • 这个全局变量在 setup.c 中定义（u64 mmu_enabled_at_boot __initdata）
  • 后续在 C 代码中检查该标志：如果非零且非 EFI 启动，则打印 FW_BUG 警告

⑩ ret — 返回

  • 只有 MMU on 路径执行到这里
  • MMU off 路径通过尾调用 dcache_inval_poc 返回，不会执行这个 ret

💡 为什么 Cold Boot 需要 D-cache invalidate？
当 STP 以 non-cacheable（MMU off）方式写入时，数据直接到达内存。但 D-cache 中可能残留着旧数据。如果不做 D-cache invalidate，后续当 MMU 开启后，cacheable 访问会命中这些陈旧缓存行，读到旧数据而不是刚写入的值。详细分析见 4.3 节。

4.3 深入：MMU 关闭后 D-cache 为什么会有旧数据？

核心矛盾在于：store 走了 non-cacheable 路径（绕过 D-cache 直接写内存），但 D-cache 里可能有之前留下的旧 cache line，这些旧数据不知道 store 已经发生。

原因一：Bootloader / 固件阶段遗留的脏 cache line（主要原因）

  • 在内核启动代码跑到这里之前，CPU 处于固件 / bootloader 控制下，那个阶段通常是 MMU on + cache on 的状态
  • 固件的代码和数据可能访问过与 boot_args 或页表区域相同的物理地址
  • 那些访问把数据留在了 D-cache 中（可能是 dirty cache line）
  • 当 MMU 关闭后，我们的 str 指令因为 MMU off 被当作 Device/nGnRnE 类型——写穿（write-through），不进 cache
  • 所以 str 只更新了内存，没有更新 D-cache 中的旧 cache line
  • 等 MMU 重新打开后，CPU 访问这些地址时会 hit D-cache，拿到的是旧数据

原因二：推测性数据加载（Speculative Load）

“推测性执行”是现代 CPU 提升性能的核心手段：遇到条件分支时，CPU 不会等待分支结果确定，而是先猜一个方向并提前执行。如果猜对了，就能继续全速运行；猜错了，回滚寄存器结果即可。

关键问题：错误推测时，CPU 会回滚架构寄存器的状态，但cache 的副作用不会自动清除。具体到我们这段代码的场景：

// ============ 推测性加载如何污染 D-cache ============ CPU 执行流: str x21, [x0] // non-cacheable write → 直接到内存 ✓ cbnz x19, 0f // 分支指令，CPU 开始预测... │ ├── 实际: x19=0，不跳转 (MMU off 路径) │ └── 预测: CPU 可能错误地预测会跳转 (x19≠0) │ ▼ 预先执行了: // 推测执行 adrp x0, mmu_enabled_at_boot ldr ... // ★ 推测性 load！ // 把物理地址上的旧数据拉进了 D-cache │ ▼ 预测错误! → CPU 回滚 x0 等寄存器 但 D-cache 中的旧数据没有被回滚！❌ // 同样，硬件数据预取器（HW Prefetcher）在遇到 str 对 boot_args // 区域的写入时，可能自动把相邻地址的数据提前拉进 D-cache
污染来源机制影响
固件遗留MMU on 时访问过同一物理地址，dirty cache line 残留在 D-cache主要来源
推测执行CPU 在分支结果确定前预先执行 load，数据被拉入 D-cache次要来源
硬件预取器硬件看到连续写入，自动预取相邻地址到 D-cache次要来源
⚠ 重要澄清：I-cache 与 D-cache 是独立硬件
指令预取（I-cache 侧）不会把数据加载到 D-cache 中。I-cache 和 D-cache 在硬件上是完全分离的——指令预取器获取的指令只进入 I-cache，不会污染 D-cache。以上讨论的两种污染来源都是 data-side 活动（D-cache 侧的历史 dirty line、data-side 的推测 load、硬件数据预取器），与 I-cache 无关。

解决：dcache_inval_poc 做了什么？

  • 遍历 [x0, x1) 区间的每一行 cache line
  • 对每一行执行 DC IVAC（Data Cache Invalidate by Address to Point of Coherency）
  • Invalidate 而不是 Clean：因为是 non-cacheable 写入，内存里已经是正确数据了，cache 里的旧数据直接丢弃即可，不需要写回
  • PoC（Point of Coherency）保证所有 CPU 都能看到一致的数据
💡 一句话总结：MMU 关闭后 str 绕过了 D-cache，但 D-cache 里残留的旧数据（固件遗留的 dirty line + 推测性 load 拉进的旧数据）不知道这些 store 已经发生。必须用 DC IVAC 显式 invalidate，确保 MMU 打开后读到的是内存里的最新值，而不是 cache 里的过期数据。

4.4 深入：dcache_inval_poc 逐条分析 ★

4.4.1 调用背景

回顾 preserve_boot_args 的 MMU off 路径（§3.2 ⑦⑧）：

// preserve_boot_args MMU off 路径 → 尾调用 dcache_inval_poc add x1, x0, #0x20 // x1 = boot_args + 32 (结束地址) b dcache_inval_poc // 尾调用: dcache_inval_poc(x0=boot_args, x1=boot_args+32)
  • x0 = boot_args 数组基地址（起始地址，4×8=32 字节）
  • x1 = boot_args + 0x20 = 结束地址（开区间 [x0, x1)）
  • 这是尾调用（b 而非 bl），b 不修改 LR 寄存器，所以 dcache_inval_poc 末尾的 ret 返回到 LR 当前值——即 primary_entry 中 bl preserve_boot_args 的下一条指令地址

// arch/arm64/mm/cache.S:135-163
/*
 *	dcache_inval_poc(start, end)
 *
 * 	Ensure that any D-cache lines for the interval [start, end)
 * 	are invalidated. Any partial lines at the ends of the interval are
 *	also cleaned to PoC to prevent data loss.
 *
 *	- start   - kernel start address of region   (x0)
 *	- end     - kernel end address of region     (x1)
 */
SYM_FUNC_START(__pi_dcache_inval_poc)
    dcache_line_size x2, x3        // ① 获取 cache line 大小 → x2, 临时用 x3
    sub     x3, x2, #1             // ② x3 = linesize - 1 (对齐掩码)
    tst     x1, x3                 // ③ end 是否对齐到 cache line 边界?
    bic     x1, x1, x3             // ④ 将 end 向下对齐到 cache line 边界
    b.eq    1f                     //    对齐 → 跳转到 1f
    dc      civac, x1              // ⑤ 不对齐: Clean+Invalidate 尾部 partial line
1:  tst     x0, x3                 // ⑥ start 是否对齐到 cache line 边界?
    bic     x0, x0, x3             // ⑦ 将 start 向下对齐到 cache line 边界
    b.eq    2f                     //    对齐 → 跳转到 2f (主循环)
    dc      civac, x0              // ⑧ 不对齐: Clean+Invalidate 首部 partial line
    b       3f                     //    跳转到循环递增
2:  dc      ivac, x0               // ⑨ 主循环: 对完整 cache line 做 IVAC（仅 Invalidate，不 Clean）
3:  add     x0, x0, x2             // ⑩ 递增地址 += linesize
    cmp     x0, x1                 // ⑪ 比较 当前地址 vs end
    b.lo    2b                     //    小于 → 继续循环
    dsb     sy                     // ⑫ 全系统内存屏障
    ret
SYM_FUNC_END(__pi_dcache_inval_poc)
SYM_FUNC_ALIAS(dcache_inval_poc, __pi_dcache_inval_poc)

4.4.3 指令逐条分析

① dcache_line_size x2, x3 — 获取 D-cache line 大小
  • ARM64 的 cache line 大小由 CTR_EL0.DminLine（bits [19:16]）编码决定，计算公式：cache_line_size = 4 << DminLine
  • 典型值：DminLine=0b0010(2) → 4<<2 = 16 bytes，DminLine=0b0100(4) → 4<<4 = 64 bytes，DminLine=0b0110(6) → 4<<6 = 256 bytes
  • 大多数 Cortex-A 核心 DminLine=4，即 64 bytes
// dcache_line_size 宏展开 (assembler.h:296-301)

💡 为什么要用 CTR_EL0 动态读取而非硬编码？内核需要运行在不同型号的 ARM64 CPU 上，cache line 大小因微架构而异（16~256 bytes）。如果在汇编中硬编码 64，在 Apple M1（256-byte line）上就会错误地只 invalidate 1/4 的 cache line，导致数据不一致。读取 CTR_EL0 保证了在所有 ARM64 平台上都正确。
⚠ 注意：CTR_EL0 报告的是 CPU 的最小 D-cache line 大小（DminLine）。如果 CPU 有多个层级的 cache 且 line 大小不同，软件应使用最小值以保证覆盖所有层级。实际上绝大多数 ARM64 设计在所有 cache 层级使用相同大小的 cache line，所以 DminLine = 实际 cache line 大小。
② sub x3, x2, #1 — 构造对齐掩码
  • 例如 cache line = 64 bytes → x3 = 63 = 0b111111
  • 用于检查地址是否对齐（低 6 位是否为 0）
  • 也用于将地址向下对齐（bic addr, addr, x3 清零低 6 位）
③④ tst + bic + b.eq — 处理 end 边界

先回顾源码中这四条指令的顺序：

tst     x1, x3              // ③ end & (linesize-1) == 0 ?
bic     x1, x1, x3           // ④ end = end & ~(linesize-1)，向下对齐
b.eq    1f                   //    对齐 → 跳过 CIVAC
dc      civac, x1             // ⑤ 不对齐 → Clean+Invalidate 尾部 line
逐条拆解

tst x1, x3 — 按位 AND 测试，不保存结果，只更新 NZCV 标志：

  • 类似于 ands xzr, x1, x3，但目标寄存器是 xzr（结果丢弃）
  • Z=1 → x1 的低 N 位全为 0 → end 已对齐 cache line 边界
  • Z=0 → x1 的低 N 位有非零位 → end 落入某个 cache line 的中部 → partial line

bic x1, x1, x3 — Bit Clear，将 end 向下对齐到 cache line 边界：

  • bic dst, src, mask = dst = src & ~mask
  • 例如 linesize=64, x3=63=0b111111：bic 将 end 的低 6 位清零
  • 效果：end = end - (end % linesize)，向下取整
深入：BIC 指令详解

BIC 是 ARM64 的位清除指令，对应 C 语言的 dst = src & (~mask)。它的作用是对 mask 中为 1 的位，将 src 中对应位清零。

// BIC 语法
BIC  Xd, Xn, Xm        // 寄存器形式: Xd = Xn & ~Xm
BIC  Xd, Xn, #imm      // 立即数形式（仅支持特定的位掩码模式）

与 AND 的区别：

// ============ BIC vs AND ============ // // AND Xd, Xn, Xm → Xd = Xn & Xm (保留 mask 为 1 的位) // BIC Xd, Xn, Xm → Xd = Xn & (~Xm) (清除 mask 为 1 的位) // // 示例: Xn=0b10101111, Xm=0b00001111 // AND: 0b10101111 & 0b00001111 = 0b00001111 (保留低4位) // BIC: 0b10101111 & ~(0b00001111) // = 0b10101111 & 0b11110000 = 0b10100000 (清除低4位)

为什么用 BIC 做对齐？— 位操作的数学原理

假设地址 A 需要向下对齐到 2^N 字节边界（如 64=2^6），则：

  • 对齐后的地址 = (A >> N) << N，即清零低 N 位
  • A & ~((1 << N) - 1) = A & ~(2^N - 1)
  • 令 mask = 2^N - 1（如 64-1=63=0b111111），则：BIC A, A, mask 一步完成

💡 BIC 为什么不更新 NZCV？ARM64 的数据处理指令默认不更新标志位（需要加 S 后缀，如 BICS 才会更新）。这个设计是故意的：BIC 不更新标志 → 前面 tst 设置的 Z 保持 → b.eq 跨两条指令仍能正确分支。详见下一节。

b.eq 1f — 利用步骤③的 tst 结果进行条件分支：

  • 如果 tst 结果为 Z=1（end 已对齐）→ 跳转到 1:，跳过 DC CIVAC
  • 如果 tst 结果为 Z=0（end 未对齐）→ 不跳转，执行下一条 dc civac, x1
  • 为什么对齐了就不需要 CIVAC？因为对齐的 end 之后的 cache line 是完全未触及的区域，不在目标范围内，也不需要保护
为什么要 tst 和 bic 分离？— 指令顺序的设计意图
// ============ 为什么不能合并为一条指令？============ // // 方案 A（错误）: 先 bic 再 tst // bic x1, x1, x3 // x1 被修改为对齐值 // tst x1_old, x3 // 没法测了！x1_old 已经丢失 // // 方案 B（编译器可以做到但汇编不行）: // ands tmp, x1, x3 // 需要额外寄存器保存测试结果 // bic x1, x1, x3 // b.eq 1f // → 多用了一个临时寄存器 (tmp) // // 方案 C（实际代码）: // tst x1, x3 // ① 先测试（不修改 x1） // bic x1, x1, x3 // ② 再修改（不影响 NZCV 标志） // b.eq 1f // ③ 消费 tst 留下的 Z 标志 // → 零额外寄存器，充分利用 NZCV 的跨指令保持特性
💡 关键知识点：ARM64 中 bic 等数据处理指令默认不更新 NZCV 标志（只有带 S 后缀的版本如 bics 才更新）。所以 bic 不会破坏 tst 设置的 Z 标志，b.eq 在两条指令之后仍然能正确读取 tst 的结果。这是 ARM64 汇编中常见的"测试-修改-消费标志"三连模式。

⑤ dc civac, x1 — Clean + Invalidate 尾部 partial line
💡 关键设计：尾部 partial line 用 DC CIVAC（Clean + Invalidate），而非 DC IVAC（仅 Invalidate）。因为该 cache line 中 [x1, x1+linesize-x1%linesize) 的部分不属于 boot_args，可能有其他数据已缓存在该 line 中。如果只用 Invalidate，这些数据会永久丢失（脏数据没有写回内存）。Clean+Invalidate 确保脏数据先写回到 PoC 再丢弃 cache line。

DC IVAC直接丢弃 cache line，不写回❌ 脏数据丢失
DC CIVAC先 Clean（写回脏数据）再 Invalidate✅ 安全
⑥⑦⑧ — 处理 start 边界（同上逻辑）
  • 如果 start 未对齐到 cache line 边界 → DC CIVAC Clean+Invalidate
  • 如果 start 已对齐 → 跳过，直接进入主循环
⑨ dc ivac, x0 — 主循环体：对每一行完整 cache line 执行 IVAC
  • ⑨⑩⑪ 构成一个 while 循环：每轮对 [x0, x0+linesize) 这一行完整 cache line 执行 DC IVAC，然后 x0 += linesize 前进到下一行，直到 x0 ≥ end 退出
  • 为什么完整 cache line 用 DC IVAC（仅 Invalidate，不 Clean）？
  • 因为：
    1. MMU 关闭时 STP 已经以 non-cacheable 方式把新数据写到了内存
    2. D-cache 中的旧数据不需要写回——内存里已经是正确的
    3. 直接 Invalidate 丢弃旧 cache line 即可（性能更高）
  • 这与首尾 partial line 的 DC CIVAC 策略相反——首尾是为了保护相邻数据，中间是为了性能
附：为什么要循环？— DC IVAC 的硬件限制

ARM64 的 cache maintenance 指令一次只能操作一行 cache line，不支持指定长度：

// ============ DC IVAC 指令仅操作一行 ============ // // DC IVAC, <addr> → Invalidate addr 所在的那一行 cache line（如 64 bytes） // 没有 "DC IVAC <addr>, <size>" 这种变体 // // 指令只关心 addr 落在哪个 cache line，自动从该行起始地址开始作用一整行。 // 要对 [start, end) 区间内每一行都执行 → 必须循环。

bl（假设的常规调用）bl 每次都写preserve_boot_args多一层

4.4.5 性能考量

  • 对于仅 32 字节的 boot_args，以 64-byte cache line 为例：
  • 最优情况（地址对齐到 cache line）：仅 1 次 DC IVAC
  • 最差情况（地址跨越两个 cache line 边界）：1 次 DC CIVAC (首部) + 0~1 次 DC IVAC + 1 次 DC CIVAC (尾部)
  • DC CIVAC 比 DC IVAC 昂贵——CIVAC 可能触发写回（write-back），产生总线事务
  • 因此设计上尽可能让中间完整 cache line 走 IVAC，只有首尾 partial line 走 CIVAC

4.4.6 涉及的 ARM64 系统指令速查

指令完整名称操作PoC/PoU
DC IVACInvalidate by VA to PoC丢弃 cache line，不写回PoC

💡 PoC（Point of Coherency）vs PoU（Point of Unification）：PoC 保证所有观察者（CPU 核、DMA 设备、GPU 等）看到一致数据；PoU 只保证当前 cluster 内的 CPU 核一致。D-cache 维护用 PoC 更安全，因为 boot_args 后续可能被 DMA 或非一致性 master 访问。

5. x21 FDT 指针生命周期

x21 在 preserve_boot_args 中被赋值为 FDT 物理地址，它在整个启动过程中被多次使用：

// ============ x21 (FDT pointer) 生命周期 ============ primary_entry: bl record_mmu_state bl preserve_boot_args // x21 = FDT (x0) ... bl __pi_create_init_idmap bl init_kernel_el bl __cpu_setup b __primary_switch │ ▼ __primary_switch: ... bl __primary_switched // 进入 C 世界 │ __primary_switched: str_l x21, __fdt_pointer, x5 // ★ 保存到全局 FDT 指针 (line 231) ... mov x0, x21 // ★ x0 = FDT (作为参数传给 C 函数) bl start_kernel // → 进入内核 C 代码主入口 ─────────────────────────────── setup_arch(): x0 就是 FDT 地址 → early_init_dt_scan() → unflatten_device_tree() 从此内核拥有了完整的设备树描述
💡 FDT 指针通过 x21 一路穿越 10+ 个函数调用，最终到达 start_kernel。ARM64 的 callee-saved 寄存器约定（x19~x28）保证了 x21 在穿越各函数时不被破坏。这种设计避免了在 MMU-off 环境下访问全局变量的复杂性。

6.3 消费点 2 — 参数合规检查 (boot_args)

// arch/arm64/kernel/setup.c ~line 372

if (boot_args[1] || boot_args[2] || boot_args[3]) {
    pr_err("WARNING: x1-x3 nonzero in violation of boot protocol:\n"
           "\tx1: %016llx\n\tx2: %016llx\n\tx3: %016llx\n"
           "This indicates a broken bootloader or old kernel\n",
           boot_args[1], boot_args[2], boot_args[3]);
}
  • ARM64 boot protocol 要求 x1~x3 必须为零（"reserved for future use"）
  • 如果非零，打印错误消息（但不 panic，内核继续运行）
  • 这是对 bootloader 兼容性的运行时检查

6.3.1 深入理解："Reserved for future use" 的设计哲学

// ============ Bootloader ↔ Kernel 接口契约 ============ ┌─────────────────────────────────────────────────────────┐ │ Boot Protocol │ │ x0 = FDT 物理地址 (必须提供，内核依赖此参数启动) │ │ x1 = 0 (reserved for future use) │ │ x2 = 0 (reserved for future use) │ │ x3 = 0 (reserved for future use) │ └─────────────────────────────────────────────────────────┘ "Reserved for future use" 的三层含义： 1. 占位（Slot Reservation） ┌──────────┐ ┌──────────┐ │Bootloader│ ─x0~x3→ │ Kernel │ 4 个寄存器 = 4 个参数槽位 └──────────┘ └──────────┘ 当前只用了 1 个，剩 3 个留给未来 2. 零值 = "我不支持扩展" 标记 旧 bootloader（不理解新特性） → 写 0 新内核（支持新特性） → 读到 0 → 知道 bootloader 没提供 → 回退到默认 3. 非零 = "我提供了额外信息" 标记 新 bootloader（理解新特性） → 写入有意义的非零值 旧内核（不理解新特性） → 读到非零 → 打印警告但不 panic → 继续运行

为什么只警告而不 panic？

  • panic 会阻止内核启动，但 x1~x3 非零本身不影响内核正常运行（内核不使用这些值）
  • 打印警告已经足够让开发者注意到问题（dmesg 中会有显眼的 ERROR 信息）
  • 保持宽松的兼容性策略：一个"不够规范"的 bootloader 总比一个完全启动不了的内核好

实际应用场景： 假设未来 Linux 需要从 bootloader 接收 "安全监控固件基地址" 参数：

// ============ 协议扩展场景（假设）============ 当前协议: 未来协议: x0 = FDT addr x0 = FDT addr x1 = 0 ←── 旧约定 x1 = S-EL1 monitor base addr ←── 新约定 x2 = 0 x2 = 0 (still reserved) x3 = 0 x3 = 0 (still reserved) 旧 bootloader 启新内核: 新 bootloader 启旧内核: x1 = 0 x1 = 0x48000000 (monitor base) ↓ ↓ 新内核检测 x1=0 旧内核检测 x1≠0 ↓ ↓ 知道 bootloader 不支持 打印 WARNING: x1 nonzero → 自动降级（不依赖 monitor） → 忽略该值，继续启动 ✓

与 ARM32 的历史对比：

ARM32 (ATAGS 方式)ARM64 (FDT 方式)
r0/x0必须为 0FDT 物理地址（唯一使用的参数）
r1/x1machine type number（如 0xffffffff 表示使用 FDT）0 (reserved)
r2/x2ATAGS 或 FDT 物理地址0 (reserved)
r3/x3未定义0 (reserved)
💡 ARM32 上的寄存器语义在切换到 FDT 后经历了不兼容的变更——machine type 从具体值变成了 ~0 的魔术数字，这很丑陋。ARM64 吸取了教训：从第一天起就把 x1~x3 全部预留，避免未来发生类似的协议断裂。
