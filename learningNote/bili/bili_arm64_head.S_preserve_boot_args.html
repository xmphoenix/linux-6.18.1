1. 概述：preserve_boot_args 的使命

调用位置

SYM_CODE_START(primary_entry)
    bl  record_mmu_state        // 记录 MMU 状态 → x19
    bl  preserve_boot_args      // ★ 保存启动参数
    adrp x1, early_init_stack
    mov sp, x1
    ...

核心使命

  • 将 bootloader 传入的 x0~x3 保存到全局数组 boot_args[4]
  • 将 x0 (FDT 物理地址) 额外保存到 x21（后续仍会用到）
  • 根据 x19（MMU 状态）分两条路径处理 D-cache 一致性
  • MMU on 时：将 x19 记录到全局变量 mmu_enabled_at_boot

ARM64 Boot Protocol 参数约定

寄存器内容类型
x0FDT（Flattened Device Tree）物理地址必须提供
x1保留（必须为 0）应为 0
x2保留（必须为 0）应为 0
x3保留（必须为 0）应为 0
💡 这些参数是 ARM64 Linux boot protocol 的定义。x1~x3 必须为 0，后续内核启动时会检查并在非零时发出警告。只有 x0（FDT 地址）是真正使用的参数。

2. 完整源码与上下文

2.1 完整源码

SYM_CODE_START_LOCAL(preserve_boot_args)           // @ 170
    mov     x21, x0                                // 保存 FDT 指针到 x21 (callee-saved)

    adr_l   x0, boot_args                          // x0 = &boot_args[0]
    stp     x21, x1, [x0]                          // boot_args[0] = FDT, boot_args[1] = x1
    stp     x2, x3, [x0, #16]                      // boot_args[2] = x2, boot_args[3] = x3

    cbnz    x19, 0f                                // x19 != 0 (MMU on) → 跳转到 0f
    dmb     sy                                     // MMU off: 内存屏障 (DC IVAC 需要)
    add     x1, x0, #0x20                          // x1 = boot_args + 32 (4×8 = 结束地址)
    b       dcache_inval_poc                       // 尾调用: invalidate D-cache
0:  str_l   x19, mmu_enabled_at_boot, x0           // 记录 MMU on 标志
    ret
SYM_CODE_END(preserve_boot_args)

2.2 调用上下文

// ============ primary_entry 中的调用顺序 ============ .section .head.text, "ax" _text: efi_signature_nop // EFI 签名 (不执行) b primary_entry // 跳转到实际入口 ... .section .init.text, "ax" primary_entry: bl record_mmu_state // x19 = 0 (MMU off) 或 1 (MMU on) bl preserve_boot_args // ★ 本函数 adrp x1, early_init_stack mov sp, x1 mov x29, xzr adrp x0, __pi_init_idmap_pg_dir mov x1, xzr bl __pi_create_init_idmap // 创建 identity mapping ... bl init_kernel_el // x0 = x19 (cpu_boot_mode) bl __cpu_setup b __primary_switch
💡 preserve_boot_args 是一个 尾调用（Tail Call）的典型示例——当 MMU off 时，最后一条指令直接 b dcache_inval_poc 而不是 bl，没有多余的 ret，精简了一个栈帧。

3.2 逐条详解

① mov x21, x0 — 保存 FDT 指针到 x21

  • x0 是 bootloader 传入的 FDT 物理地址（Device Tree Blob）
  • x21 是 callee-saved 寄存器，不会被后续函数调用破坏
  • 后续可通过 x21 随时访问 FDT（line 231: str_l x21, __fdt_pointer，line 517: mov x1, x21）
  • 为什么不用 x19？x19 已经被 record_mmu_state 占用了（MMU 状态标志）

② adr_l x0, boot_args — 获取 boot_args 数组地址

  • adr_l 是汇编宏，展开为两条指令：
// adr_l dst, sym 展开为:
adrp    dst, sym        // 加载符号所在 4KB 页基址
add     dst, dst, :lo12:sym  // 加上页内偏移
  • boot_args 是 u64 boot_args[4]，在 setup.c 中定义
  • 此时 MMU 可能关闭，CPU 跑在物理地址上，但 adrp 基于 PC 相对寻址，仍然正确
  • 关键理解：由于内核是 PIE（位置无关）编译，adrp 得到的是运行时物理地址，与 MMU 状态无关

③ stp x21, x1, [x0] — 写入 boot_args[0..1]

  • STP（Store Pair）指令：一条指令存储两个 64 位值
  • [x0] = boot_args[0] = x21（FDT 物理地址）
  • [x0+8] = boot_args[1] = x1（bootloader 传入的第 2 个参数，应为 0）
  • 相比两条 STR 指令，STP 节省了代码空间和指令发射带宽

④ stp x2, x3, [x0, #16] — 写入 boot_args[2..3]

  • STP 使用立即偏移 #16（16 字节偏移）
  • [x0+16] = boot_args[2] = x2
  • [x0+24] = boot_args[3] = x3
  • 至此 boot_args[4] 的 32 字节已全部填入

⑤ cbnz x19, 0f — 条件分支：MMU 状态判断

  • CBNZ（Compare and Branch if Non-Zero）：如果 x19 ≠ 0 → 跳转到 0f
  • x19 来自 record_mmu_state 的返回值：0 = MMU off, 1 = MMU on
  • MMU on (x19=1) → 跳转到 0f → str_l x19, mmu_enabled_at_boot
  • MMU off (x19=0) → 不跳转 → 执行 D-cache invalidate 序列

⑥ dmb sy — 内存屏障

  • 全系统数据内存屏障（Data Memory Barrier, Shareable）
  • 为什么需要？ 当 MMU 关闭时，STP 写入是 non-cacheable 的，但随后的 DC IVAC（Data Cache Invalidate by Address to PoC）需要保证所有之前的内存访问已经全局可见
  • DMB SY 确保所有之前的存储操作在 D-cache invalidation 之前完成
⚠ dmb sy 只在 MMU off 路径执行。MMU on 时跳过了它——因为 cacheable 写入是硬件自洽的，不需要额外的 barrier。

⑦ add x1, x0, #0x20 — 准备结束地址

  • x0 当前指向 boot_args[0]，x1 = x0 + 0x20 = x0 + 32
  • boot_args 总共 4×8 = 32 字节，所以 x1 指向 boot_args 的末尾
  • 这为 dcache_inval_poc 准备了 [x0, x1) 地址区间参数

⑧ b dcache_inval_poc — 尾调用

  • 这不是 bl（分支并链接），而是 b（无条件跳转）
  • 尾调用优化：不压栈、不保留返回地址，直接跳转到 dcache_inval_poc
  • dcache_inval_poc 执行完毕后会 ret，但返回到 preserve_boot_args 的调用者（primary_entry），而不是 preserve_boot_args 本身
  • 这消除了一个没有任何后续代码的 ret 指令

⑨ str_l x19, mmu_enabled_at_boot, x0 — 记录 MMU 状态

  • 仅在 MMU on (x19=1) 路径执行
  • str_l 是汇编宏，展开为：
// str_l src, sym, tmp 展开为:
adrp    tmp, sym         // tmp = &mmu_enabled_at_boot 页基址
str     src, [tmp, :lo12:sym]  // 写入 mmu_enabled_at_boot = x19
  • 这个全局变量在 setup.c 中定义（u64 mmu_enabled_at_boot __initdata）
  • 后续在 C 代码中检查该标志：如果非零且非 EFI 启动，则打印 FW_BUG 警告

⑩ ret — 返回

  • 只有 MMU on 路径执行到这里
  • MMU off 路径通过尾调用 dcache_inval_poc 返回，不会执行这个 ret

4. 两条路径与缓存维护

4.1 路径总览

// ============ preserve_boot_args 流程 ============ x0=FDT, x1/x2/x3=bootloader args, x19=MMU state mov x21, x0 // 保存 FDT adr_l x0, boot_args // 获取数组地址 stp x21, x1, [x0] // 写入 [0..1] stp x2, x3, [x0, #16] // 写入 [2..3] │ ▼ cbnz x19, 0f ──────────── 分支 │ │ x19=0 (MMU off) x19≠0 (MMU on) │ │ dmb sy str_l x19, mmu_enabled_at_boot add x1, x0, #0x20 │ b dcache_inval_poc ret │ │ └──── 汇合 ──────────────┘ (返回 primary_entry)

4.2 路径对比

Cold Boot (MMU off)Warm Boot (MMU on)
x19 值01
写入属性Non-cacheableCacheable
缓存操作dmb sy + dcache_inval_poc无（硬件自洽）
额外记录不记录mmu_enabled_at_boot = 1
返回方式尾调用（b dcache_inval_poc）正常 ret
💡 为什么 Cold Boot 需要 D-cache invalidate？
当 STP 以 non-cacheable（MMU off）方式写入时，数据直接到达内存。但 CPU 的 speculative load 可能在写入前就已经将对应地址的数据加载到了 D-cache 中（预取）。如果不做 D-cache invalidate，后续当 MMU 开启后，cacheable 访问会命中这些陈旧缓存行，读到旧数据而不是刚写入的值。

5. x21 FDT 指针生命周期

x21 在 preserve_boot_args 中被赋值为 FDT 物理地址，它在整个启动过程中被多次使用：

// ============ x21 (FDT pointer) 生命周期 ============ primary_entry: bl record_mmu_state bl preserve_boot_args // x21 = FDT (x0) ... bl __pi_create_init_idmap bl init_kernel_el bl __cpu_setup b __primary_switch │ ▼ __primary_switch: ... bl __primary_switched // 进入 C 世界 │ __primary_switched: str_l x21, __fdt_pointer, x5 // ★ 保存到全局 FDT 指针 (line 231) ... mov x0, x21 // ★ x0 = FDT (作为参数传给 C 函数) bl start_kernel // → 进入内核 C 代码主入口 ─────────────────────────────── setup_arch(): x0 就是 FDT 地址 → early_init_dt_scan() → unflatten_device_tree() 从此内核拥有了完整的设备树描述
💡 FDT 指针通过 x21 一路穿越 10+ 个函数调用，最终到达 start_kernel。ARM64 的 callee-saved 寄存器约定（x19~x28）保证了 x21 在穿越各函数时不被破坏。这种设计避免了在 MMU-off 环境下访问全局变量的复杂性。

6. boot_args 在 C 代码中的消费

6.1 定义

// arch/arm64/kernel/setup.c

u64 __cacheline_aligned boot_args[4];      // ★ 缓存行对齐，避免 false sharing
u64 mmu_enabled_at_boot __initdata;        // ★ 仅在初始化阶段使用

6.2 消费点 1 — FW_BUG 检查 (mmu_enabled_at_boot)

// arch/arm64/kernel/setup.c ~line 328

WARN_TAINT(mmu_enabled_at_boot, TAINT_FIRMWARE_WORKAROUND,
           FW_BUG "Booted with MMU enabled!");
  • 如果 bootloader 启动内核时 MMU 已经是开启状态，说明 bootloader 行为异常
  • 触发 FW_BUG 警告并打上 TAINT 标记
  • 非 EFI 启动时才会检查（EFI 启动 MMU on 是合法的）

6.3 消费点 2 — 参数合规检查 (boot_args)

// arch/arm64/kernel/setup.c ~line 372

if (boot_args[1] || boot_args[2] || boot_args[3]) {
    pr_err("WARNING: x1-x3 nonzero in violation of boot protocol:\n"
           "\tx1: %016llx\n\tx2: %016llx\n\tx3: %016llx\n"
           "This indicates a broken bootloader or old kernel\n",
           boot_args[1], boot_args[2], boot_args[3]);
}
  • ARM64 boot protocol 要求 x1~x3 必须为零
  • 如果非零，打印错误消息（但不 panic）
  • 这是对 bootloader 兼容性的运行时检查

6.4 消费点 3 — x0 (FDT) 的使用

// ============ FDT 地址的传递链 ============ bootloader head.S C 代码 ┌────────┐ ┌────────────┐ ┌──────────────────┐ │ x0=FDT │────▶│boot_args[0]│────▶│x0→start_kernel() │ │ │ │ x21 │────▶│ →setup_arch() │ │ │ │ │ │ →early_init_ │ │ │ │ __fdt_ │────▶│ dt_scan() │ │ │ │ pointer │ │ →unflatten_ │ │ │ │ │ │ device_tree()│ └────────┘ └────────────┘ └──────────────────┘ 三条路径： ① boot_args[0] → 检查/调试用途 ② x21 → 直接传参给 start_kernel (最快路径) ③ __fdt_pointer → 全局变量，任意位置可访问

8. 总结 & 关键要点

#要点说明
1 保存 4 个启动参数到 boot_args[4] STP 两条指令完成 32 字节写入，高效紧凑
2 FDT 地址 → x21 callee-saved 寄存器，一路穿越到 start_kernel
3 尾调用优化（Tail Call） MMU off 路径以 b dcache_inval_poc 结尾，消除冗余 ret
4 adr_l / str_l 宏 PIE 环境下使用 PC-relative 寻址全局变量，与 MMU 状态无关
5 两条路径对称设计 MMU off → invalidate cache；MMU on → 记录标志 + 后续 FW_BUG
6 DMB SY 内存屏障 MMU off 写入后需要保证操作全局可见性
7 boot protocol 合规检查 x1~x3 必须为 0，否则 setup.c 中打印警告
8 FDT 三条传递路径 boot_args[0] / x21 寄存器 / __fdt_pointer 全局变量，冗余备份
