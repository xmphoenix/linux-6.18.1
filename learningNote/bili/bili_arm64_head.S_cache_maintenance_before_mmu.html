1. 概述：这段代码做什么

这段代码位于 __pi_create_init_idmap（创建初始 identity mapping 页表）之后、init_kernel_el（初始化内核异常级别）之前。它在 即将开启 MMU 之前，根据内核是以什么方式启动的，选择执行不同的 Cache 维护操作。

位置：启动序列中的关键节点

primary_entry:
    bl  record_mmu_state       // x19 = 0(冷启动) 或 1(热启动)
    bl  preserve_boot_args
    bl  __pi_create_init_idmap // 创建 identity 映射页表
    // ★ 我们分析的代码在此 ★
    cbnz x19, 0f               // x19 决定走哪条路
    // x19==0: invalidate        x19!=0: clean
    ...
1:  mov x0, x19
    bl  init_kernel_el          // 初始化 CPU 异常级别
    bl  __cpu_setup             // 配置 TCR/MAIR 等 MMU 寄存器
    b   __primary_switch        // ★ 真正开启 MMU

一句话概括

在开启 MMU 之前，确保 CPU 能正确看到页表和启动代码。

  • 冷启动：页表是用 non-cacheable 方式写入的，需要 invalidate（无效化） 被 speculative load 污染的 cache 行，保证 MMU 读取到正确的页表内容
  • 热启动：idmap 代码是用 cacheable 方式运行的，需要 clean（清洗） dirty cache 行到内存，保证关闭 MMU 后依然能正确执行
💡 核心矛盾：开启 MMU 之前，CPU 对内存的所有访问都是物理地址。但 Cache 可能包含了与内存不一致的数据（speculative loads 写入了旧值，或者 dirty cache 行还没写回）。如果不做维护直接开 MMU，MMU 翻译后的地址访问可能读取到错误的缓存数据。

2.1 分析代码段（head.S:96-117）

     * accesses (MMU disabled), invalidate those tables again to

2.2 x19 的前世今生 —— 这个决定一切的寄存器从哪来

// ============ x19 的完整生命周期 ============ record_mmu_state(): // head.S:134 ← 详见上期视频 mrs x19, CurrentEL // 读异常级别 (EL1/EL2) ... (投机执行 + 条件覆盖) ... and x19, x19, #SCTLR_ELx_M // 提取 M 位 (bit 0) csel x19, xzr, x19, eq // C=0 时强制清零 ret // x19 = 0(冷启动) 或 1(热启动) preserve_boot_args(): // head.S:168 cbnz x19, 0f // 热启动 → 跳过 cache inval dmb sy b dcache_inval_poc // 冷启动 → 无效化 boot_args 区域 0: ret __pi_create_init_idmap() // head.S + map_kernel.c // 创建 identity mapping 页表 // x0 = ptep (页表已使用区域的结束地址) // ★ 我们分析的核心代码 (head.S:96-117) cbnz x19, 0f // x19 在此做最终决策 // x19==0: invalidate 页表 region // x19!=0: clean idmap code region 1: mov x0, x19 bl init_kernel_el // 此后 x19 不再使用
💡 x19 为什么重要：它是 record_mmu_state 的返回值，编码了内核启动时 MMU 是否已经开启。这个单一比特决定了整个 early boot 阶段的 Cache 维护策略——在 3 个地方被检查（preserve_boot_args、本段代码、primary_entry 末尾传给 init_kernel_el）。

3. 核心问题：为什么有两条截然不同的 Cache 路径？

代码的核心是一个二分叉：cbnz x19, 0f，根据 x19 的值走向完全不同的 Cache 操作。这两条路径反映了内核的两种启动方式：

维度x19 == 0（冷启动）x19 != 0（热启动）
启动方式从 bootloader 直接启动kexec / hibernate 唤醒
当前 MMU关闭 (M=0)开启 (M=1)
当前 Cache关闭 (C=0)开启 (C=1)
页表写入方式Non-cacheable（绕过 Cache，直写内存）Cacheable（写入 Cache，可能未回内存）
核心风险Speculative load 可能缓存了别的数据到页表地址idmap 代码的 dirty cache 行末写回，MMU 关后指令读取失败
Cache 操作Invalidate [pg_dir, ptep)Clean [__idmap_text_start, end)
操作对象页表区域idmap 代码段
⚠ 关键直觉：两条路径之所以不同，是因为"内存写入者"不同。冷启动时页表是 CPU 绕过 Cache 写的（non-cacheable），但 speculative loads 可能把别的数据拉到了这些地址的 cache line——所以需要 invalidate。热启动时 idmap 代码是 CPU 通过 Cache 写的（cacheable），dirty lines 还没写回——所以需要 clean。

4. 冷启动路径逐条分析（x19 == 0）

4.1 完整指令序列

    cbnz    x19, 0f            // x19==0 → 不跳转，顺序执行
    dmb     sy                  // ① 全系统内存屏障
    mov     x1, x0              // ② x1 = ptep (__pi_create_init_idmap 的返回值)
    adrp    x0, __pi_init_idmap_pg_dir  // ③ x0 = 页表起始地址
    adr_l   x2, dcache_inval_poc        // ④ x2 = dcache_inval_poc 函数地址
    blr     x2                  // ⑤ 调用 dcache_inval_poc(x0, x1)
    b       1f                  // ⑥ 跳过热启动路径

4.2 逐条详解

① dmb sy —— 全系统内存屏障

  • dmb = Data Memory Barrier，sy = 全系统范围
  • 确保在 barrier 之前的所有内存访问（包括 __pi_create_init_idmap 中的页表写入）对所有观察者可见
  • 为什么需要：页表写入可能还在 write buffer 中，没有真正到达内存。此时如果 speculative load 从内存拉数据，拉到的可能是旧值

② mov x1, x0 —— 设置结束地址

  • x0 是 __pi_create_init_idmap 返回的 ptep——指向页表已使用区域的下一个空闲位置
  • 作为 dcache_inval_poc 的第二个参数（结束地址）

③ adrp x0, __pi_init_idmap_pg_dir —— 设置起始地址

  • __pi_init_idmap_pg_dir 是 identity mapping 页表的基地址
  • adrp = 加载页地址（4KB 对齐），用于获取符号所在的 4KB 页基址
  • 作为 dcache_inval_poc 的第一个参数（起始地址）

④ adr_l x2, dcache_inval_poc —— 获取函数指针

  • adr_l = 加载 64 位绝对地址的宏（在 head.S 中用两条指令实现：adrp + add）
  • dcache_inval_poc 是 arch/arm64/mm/cache.S 中实现的底层 Cache 操作函数

⑤ blr x2 —— 调用 dcache_inval_poc

  • 对地址范围 [__pi_init_idmap_pg_dir, ptep) 执行 DC IVAC（Data Cache Invalidate by VA to PoC）
  • 逐 cache line 做：使该 VA 对应的所有 cache 行失效，强制后续访问从 PoC 重取

⑥ b 1f —— 跳过热启动路径

  • 无条件跳转到标签 1:，跳过 0: 处的热启动路径

4.3 为什么要 invalidate 页表区域？

// ============ Speculative Load 污染的视觉解释 ============ 时间线：页表创建过程 T1: __pi_create_init_idmap 写入页表 写入方式: STR xN, [ptep] ← MMU off, 绕过 cache (non-cacheable) 数据到了: DRAM 没有到: L1/L2 D-cache T2: 与此同时... CPU 的 speculative execution (推测执行) 可能在 T1 之前就投机地 LDR 了页表地址 → 把 DRAM 中的 旧数据 (全 0 或垃圾) 拉到了 D-cache T3: 现在 Cache 中的页表地址 = 旧数据 但 DRAM 中的页表地址 = 正确数据 (刚写入的) → D-cache 和 DRAM 不一致！ T4: 开启 MMU 后... MMU 做页表 walk 如果 Cache 命中 → 返回 旧数据 → 翻译错误 → 系统崩溃 💥 ★ 解决：在 T3 之后、T4 之前，执行 dcache_inval_poc → 强制 invalidate 页表地址对应的 cache 行 → T4 时 MMU 必然从 DRAM 重取 → 读到正确数据 ✅
💡 Speculative Load 的本质：ARM64 是弱序内存模型 + 推测执行的架构。即使 MMU 关闭，CPU 的预取器 (prefetcher) 和分支预测器可能在任何时候投机地发出内存读取请求。这些 speculative loads 完全可能刚好命中了页表所在的地址范围——因为它们和内核代码的地址接近。一旦拉进 Cache，就产生了"dirty by speculation"的 cache line。

5. 热启动路径逐条分析（x19 != 0）

5.1 完整指令序列

    cbnz    x19, 0f            // x19!=0 → 跳转到 0:
    // ... 冷启动路径 ...
    b       1f

0:  adrp    x0, __idmap_text_start  // ① x0 = idmap 代码段起始
    adr_l   x1, __idmap_text_end    // ② x1 = idmap 代码段结束
    adr_l   x2, dcache_clean_poc    // ③ x2 = dcache_clean_poc 函数地址
    blr     x2                      // ④ 调用 dcache_clean_poc(x0, x1)

1:  mov     x0, x19                 // x0 = MMU 状态

5.2 逐条详解

① adrp x0, __idmap_text_start —— idmap 代码段起始

  • __idmap_text_start 是链接脚本中标记的 .idmap.text 段起始
  • 这个段包含所有需要在 MMU 关闭期间执行的代码
  • 包括：primary_entry、__primary_switch、__enable_mmu 等

② adr_l x1, __idmap_text_end —— idmap 代码段结束

  • 标记 .idmap.text 段的结束位置

③ adr_l x2, dcache_clean_poc —— 获取 clean 函数指针

  • 与冷启动路径不同，这里是 dcache_clean_poc（不是 dcache_inval_poc）

④ blr x2 —— 调用 dcache_clean_poc

  • 对地址范围 [__idmap_text_start, __idmap_text_end) 执行 DC CVAC（Data Cache Clean by VA to PoC）
  • 逐 cache line 做：如果该 cache line 是 dirty 的，写回 DRAM；保留 cache 中的有效数据

5.3 为什么要 clean idmap 代码段？

// ============ 热启动的 Dirty Cache 问题 ============ 场景：从 kexec 启动新内核 T0: 旧内核运行中，MMU=on, Cache=on 代码段 .idmap.text 被加载到内存，进入 D-cache D-cache 可能标记了 dirty lines (修改过的数据未写回) T1: kexec 跳转到新内核入口 → 新内核的 primary_entry 开始执行 → 新代码覆盖了部分 .idmap.text → 这些修改可能还在 D-cache 中，没写到 DRAM T2: __cpu_setup → __primary_switch 准备开启 MMU → 先要关闭 MMU，执行 __enable_mmu 中的代码 T3: ★ 问题来了 ★ MMU 关闭后，CPU 直接从物理地址读取指令 但 .idmap.text 的 dirty cache 行还没写回！ → CPU 取指时可能： 方案 A（Cache hit）：从 D-cache 读到正确数据 ✅ 方案 B（Cache miss）：从 DRAM 读到旧数据 💥 → 不可预测！取决于 cache 状态和替换策略 ★ 解决：在 T2 之前、T1 之后，执行 dcache_clean_poc → 强制将 .idmap.text 的 dirty cache 行写回 DRAM → T3 时不管 Cache 命中与否，DRAM 都是最新的 ✅
💡 为什么是 clean 而不是 invalidate？如果 invalidate，相当于丢弃了 dirty cache 行中还没写回的正确数据——之后必须从 DRAM 重读，但 DRAM 中可能是旧的值。Clean 保留了 cache 中的正确数据，同时把它写回 DRAM，确保两处都是最新的。

──────────────────────────

  STR →绕过Cache→ DRAM ✅

  Speculative LDR → Cache ← DRAM(旧) ❌

  → 强制从 DRAM 重取

  STR → D-Cache (dirty) → DRAM(旧) ❌

7. dcache_inval_poc 与 dcache_clean_poc 源码分析

7.1 这两个函数在哪里

// arch/arm64/mm/cache.S

SYM_FUNC_START_LOCAL(dcache_inval_poc)
    dcache_by_line_op ivac, sy, x0, x1, x2, x3
    ret
SYM_FUNC_END(dcache_inval_poc)

SYM_FUNC_START_LOCAL(dcache_clean_poc)
    dcache_by_line_op cvac, sy, x0, x1, x2, x3
    ret
SYM_FUNC_END(dcache_clean_poc)

7.2 核心宏：dcache_by_line_op

// arch/arm64/include/asm/assembler.h
// 对地址范围 [x0, x1) 逐 cache line 执行指定的 op

.macro dcache_by_line_op op, domain, start, end, tmp1, tmp2
    // 将 start 和 end 对齐到 cache line 边界
    add     \start, \start, \tmp1   // 修正起始对齐
    sub     \tmp1, \tmp2, \tmp1     // 计算需要操作的字节数
    // ...
1:  dc      \op, \start             // ★ 对当前地址执行 DC 操作
    add     \start, \start, \tmp2   // 地址 += cache line 大小
    subs    \tmp1, \tmp1, \tmp2     // 剩余字节 -= cache line 大小
    b.hi    1b                       // 还有剩余 → 继续
.endm

// op = ivac → DC IVAC = Invalidate by VA to PoC
// op = cvac → DC CVAC = Clean by VA to PoC

7.3 ARM64 Cache 维护指令速查

指令全称操作Cache 行最终在哪DRAM 最终状态
DC IVACInvalidate by VA to PoC使指定 VA 的 cache 行失效被丢弃不变（下次 Miss 从 DRAM 读）
DC CVACClean by VA to PoC将 dirty 行写回 PoC保留，标记为 clean被更新为最新数据
DC CIVACClean+Invalidate by VA to PoC先 Clean 再 Invalidate被丢弃被更新为最新数据
💡 PoC = Point of Coherency：指系统中所有能访问内存的单元（CPU 核、DMA 控制器、GPU 等）都能看到一致数据的那一点。在大多数 ARM64 SoC 中，PoC 通常在最后一级共享 Cache（L3/SCF）或 DRAM 控制器处。

10. 总结 & 关键要点

#要点说明
1 x19 是唯一的决策变量 cbnz x19, 0f 根据 MMU 状态选择 Cache 维护策略，0=冷启动，非0=热启动
2 冷启动 invalidate 页表 解决 speculative load 污染 cache 的问题：丢弃错误 cache 行，强制从 DRAM 重取
3 热启动 clean idmap 代码 解决 dirty cache 未写回的问题：保留正确数据同时写回，保证 MMU 关闭后取指正确
4 操作对象完全不同 冷启动操作的是页表数据（MMU 要读的），热启动操作的是idmap 代码（CPU 要执行的）
5 ARM64 指令区别 invalidate = DC IVAC（丢弃 cache 行），clean = DC CVAC（写回并保留）
6 都操作到 PoC 两者都操作到 Point of Coherency，保证所有观察者（CPU 核、MMU page table walker）能看到一致结果
7 x19 在此之后传给 init_kernel_el mov x0, x19 然后 bl init_kernel_el，MMU 状态用于判断 warm boot 逻辑
8 这是开启 MMU 前的最后一道 Cache 关卡 执行完本段代码后，经过 init_kernel_el + __cpu_setup，就进入 __primary_switch → __enable_mmu 真正开启 MMU
