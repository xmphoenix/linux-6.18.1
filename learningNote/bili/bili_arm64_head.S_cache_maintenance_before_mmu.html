1. 概述：这段代码做什么

这段代码位于 __pi_create_init_idmap（创建初始 identity mapping 页表）之后、init_kernel_el（初始化内核异常级别）之前。它在 即将开启 MMU 之前，根据内核是以什么方式启动的，选择执行不同的 Cache 维护操作。

位置：启动序列中的关键节点

primary_entry:
    bl  record_mmu_state       // x19 = 0(冷启动) 或 1(热启动)
    bl  preserve_boot_args
    bl  __pi_create_init_idmap // 创建 identity 映射页表
    // ★ 我们分析的代码在此 ★
    cbnz x19, 0f               // x19 决定走哪条路
    // x19==0: invalidate        x19!=0: clean
    ...
1:  mov x0, x19
    bl  init_kernel_el          // 初始化 CPU 异常级别
    bl  __cpu_setup             // 配置 TCR/MAIR 等 MMU 寄存器
    b   __primary_switch        // ★ 真正开启 MMU

一句话概括

在开启 MMU 之前，确保 CPU 能正确看到页表和启动代码。

  • 冷启动：页表是用 non-cacheable 方式写入的，需要 invalidate（无效化） 被 speculative load 污染的 cache 行，保证 MMU 读取到正确的页表内容
  • 热启动：idmap 代码是用 cacheable 方式运行的，需要 clean（清洗） dirty cache 行到内存，保证关闭 MMU 后依然能正确执行
💡 核心矛盾：开启 MMU 之前，CPU 对内存的所有访问都是物理地址。但 Cache 可能包含了与内存不一致的数据（speculative loads 写入了旧值，或者 dirty cache 行还没写回）。如果不做维护直接开 MMU，MMU 翻译后的地址访问可能读取到错误的缓存数据。

2.2 Cache Line —— 不可分割的操作单元

Cache line 是 Cache 硬件的最小管理单元。ARM64 中每条 cache line 由三大块横向排布，在 PIPT 和 VIPT 两种模式下物理存储格式完全相同：

Tag（~48 bits）Data（64 B = 512 bits）Status（~5 bits）
存储 PA[63:13]
永远是物理地址
命中比对用		 从 DRAM 拷贝的实际缓存数据
永远是 DRAM 副本
Cache 操作最小单元		 V(1b): 0=无效 1=有效
D(1b): 0=Clean 1=Dirty
MESI(2-4b): 一致性状态
永远是硬件状态位
每 line 总宽度 ≈ 48 + 512 + 5 = 565 bits ≈ 71 bytes（其中 Data 占 90%，Tag+Status 是额外开销）

为什么 64B 是甜点位？两个独立的原因收敛到同一个数字：

因素32B line64B line128B line
Tag 开销占比 48b Tag / (256b Data) = 19% 48b Tag / 512b Data = 9% 48b Tag / 1024b Data = 4.5%
DDR Burst 对齐 一个 DDR4 burst 只能传 32B → 浪费另一半 一个 DDR4 burst = 8 拍 × 64-bit 总线 = 正好 64B 需 2 次 burst → 延迟翻倍，random access 浪费大
Spatial locality 利用 覆盖范围小，顺序访问时频繁 miss 覆盖 16 条 32-bit 指令或 8 个指针，匹配典型代码模式 random access 时拉入大量无用数据，污染 cache

"DDR burst 对齐" 的含义：DDR4 DRAM 芯片的物理接口是 64 位宽的并行总线。CPU 发起一次读请求后，DRAM 在总线上连续输出 8 拍数据（burst length = 8）——每拍 64 bits = 8 bytes，8 拍 × 8 bytes = 正好 64 bytes。这是 DRAM 的"原子传输单元"，传 64B 只消耗一次命令开销。如果 L1_CACHE_BYTES 选 32B，一次 burst 只用一半，另一半白白丢弃；选 128B 则需要两次 burst，延迟加倍。64B 刚好用完一次 DDR burst，不浪费、不超额，这是硬件层面的最优对齐。

2.3 Set-Associative Cache 的组织结构

ARMv8-A 架构中，数据 Cache 通常是 PIPT（Physically Indexed, Physically Tagged），但 L1 Cache 也可以实现为 VIPT（Virtually Indexed, Physically Tagged）以提升性能。以下以常见的 VIPT L1 为例说明 set-associative 结构：

参数取值推导
Cache 总大小（Data RAM）32 KB总数据容量，不含 Tag RAM
Way 数（Associativity）4每个 set 有 4 个候选槽位
Set 数128= 32KB / 4 / 64B
Cache Line 大小64 bytes= L1_CACHE_BYTES，最小操作粒度
Index bits7 bits [12:6]log2(128) = 7，选择 128 个 set 之一
Offset bits6 bits [5:0]log2(64) = 6，line 内字节偏移
Tag bits~48 bits [63:13]剩余高位，用于命中比对
💡 VIPT 的关键特性：Index bits 来自 VA、Tag bits 来自 PA，允许 TLB 翻译和 Cache 查找并行进行——这是 L1 使用 VIPT 的动机。ARMv8-A 要求 VIPT 实现必须是 non-aliasing 的：即 index bits 必须在 VA→PA 翻译中不变（即落在 4KB 页内 bit[11:0]），这意味着 VIPT L1 的最大容量受限于 ways × page_size。对于 4-way × 4KB = 16KB 以内可以安全使用 VIPT；更大的 L1（如 32KB 4-way）需要特殊处理（如对 index 超出页内的位做 alias 检测）。MMU off 时 VA=PA，VIPT 退化为 PIPT 行为。

无论 PIPT 还是 VIPT，同一条 cache line 的物理存储格式完全一样——都是 Tag + Data + Status。区别仅在于查找时，Index 和 Tag 分别取自 VA 还是 PA：

关键结论：

  • Cache line 的 Tag RAM 永远存的是 PA，不管 PIPT 还是 VIPT。VIPT 不是"虚拟 Tag"，只是"虚拟 Index"。
  • VIPT 的优势在第 2-3 步：Index 用 VA、Tag 用 PA，Cache 查找可以和 TLB 翻译并行进行，省去了等 PA 的延迟。

2.4 Write-Through vs Write-Back

策略写入行为Cache Line 状态数据安全性
Write-Through (WT) 同时写入 Cache 和下一级存储（L2/DRAM） 始终 Clean 安全：DRAM 总是最新的
Write-Back (WB) 仅写入 Cache，标记 dirty，延迟写回 可能 Dirty (Modified) 危险：DRAM 可能是旧的 ★
Write-Back + Write-Allocate Write miss 时先填充 cache line 再写入 可能 Dirty 主流 ARM64 CPU 默认策略

ARM64 CPU 几乎都使用 Write-Back + Write-Allocate 策略（由 SCTLR_EL1 和 MAIR_ELx 的 memory attribute 控制）。这就产生了 dirty cache line 的问题——数据修改后仅在 Cache 中，DRAM 是旧值。如果没有 clean 操作就关闭 MMU 或重置 Cache，数据就丢失了。

2.9 Cache 的硬件实现 —— 它到底是一个什么"设备"？

Cache 不是抽象概念，而是实实在在的片上 SRAM 电路。以下从晶体管级解释其物理组成。

核心存储单元：SRAM Cell（6 晶体管/bit）

组件数量功能

结论：boot_args 不需要长期驻留 Cache。__cacheline_aligned 的作用是让它独占一条 cache line，dc ivac 时不会误伤邻居——这是它唯一需要 cache 对齐的原因。

💡 核心认知：Cache 是一个概率性加速器，不是确定性存储。它依赖两个统计规律：时间局部性（刚访问的数据很可能再次被访问）和空间局部性（相邻地址的数据很可能一起被访问）。ARM64 的替换策略和 set-associative 结构都是为了最大化这两个局部性的收益。但对于 boot_args 这种"写入一次、读取一次、永不使用"的数据，Cache 对它既不友好（第一次写绕过 Cache，第一次读必然 miss）也不需要友好（反正只用一次）。

替换策略的运行机制：pLRU 如何跟踪"年龄"

ARM64 处理器（Cortex-A 系列）通常使用 pLRU（Pseudo-LRU）或 RRIP（Re-Reference Interval Prediction），而非真正的 LRU。下面是 pLRU 在 4-way set 中的实现原理：

pLRU 3-bit 二叉树编码（4-way）
bit00 = way0/1 分支更近被用过（victim 走 way2/3 分支）
1 = way2/3 分支更近被用过（victim 走 way0/1 分支）
bit10 = way0 比 way1 更近被用过 → victim=way1
1 = way1 比 way0 更近被用过 → victim=way0		仅 bit0=0 时有效
bit20 = way2 比 way3 更近被用过 → victim=way3
1 = way3 比 way2 更近被用过 → victim=way2		仅 bit0=1 时有效

更新规则：命中 wayX 时，翻转指向 wayX 的所有祖先 bit，使 wayX 看起来像"最近被使用"。选 victim：沿树的反方向走到底。

例：bit0=0, bit1=0, bit2=1 → victim = way1。仅需 3 bits 即可管理 4-way 的近似 LRU，硬件成本极低。

2.20 怎么写代码才能进 Cache 并跑得更快？

前面 19 个小节讲了 Cache 的原理、结构、维护。但最实际的问题是：怎么写代码才能让数据留在 Cache 里？答案不是靠特殊指令——只要访问的是 Normal Cacheable 内存（MMU on 的默认属性），数据自动进 Cache。真正决定性能的是访问模式是否对 Cache 友好。

原则 1：空间局部性 —— 顺序访问，别跳着走

✗ 糟糕：按列遍历（stride = 行宽）

int matrix[1024][1024];

// 每次内层循环跨 1024×4 = 4KB
// 每 16 次访问就 miss 一次
for (int j = 0; j < 1024; j++)
    for (int i = 0; i < 1024; i++)
        sum += matrix[i][j];  // stride=4KB!
// 耗时: ~100M cycles

✓ 好：按行遍历（stride = 1）

int matrix[1024][1024];

// 内层连续访问 1024 个 int = 4KB
// = 64 条 cache line，全部命中
for (int i = 0; i < 1024; i++)
    for (int j = 0; j < 1024; j++)
        sum += matrix[i][j];  // stride=1!
// 耗时: ~10M cycles（快 10 倍）

原则 2：时间局部性 —— 用完的数据赶紧再用，别等它被踢出

✗ 糟糕：两个大数组交替操作

// A 和 B 各占 512KB
// 处理完 A 再处理 B 时 A 已被 B 踢出 L1
for (int i = 0; i < N; i++)
    A[i] = f(A[i]);     // 512KB 填满又踢出
for (int i = 0; i < N; i++)
    B[i] = g(B[i]);     // 512KB 再次填满又踢出
// 每次 pass 都是 DRAM 速度

✓ 好：Blocking（分块），一次处理一块

// 每次只处理能塞进 L1 的小块
#define BLK 512  // 512×8B = 4KB << L1D 32KB
for (int b = 0; b < N; b += BLK) {
    for (int i = b; i < b + BLK; i++)
        A[i] = f(A[i]);
    for (int i = b; i < b + BLK; i++)
        B[i] = g(B[i]);
}
// 每块都在 L1 内处理完，才换下一块

原则 3：结构体布局 —— 热字段聚拢，冷字段靠边

✗ 糟糕：热字段散落，一条 line 装不下

struct task {
    int pid;           // 热：每次调度都访问
    char name[256];     // 冷：几乎不用
    int state;          // 热
    char comm[256];     // 冷
    int prio;           // 热
    char padding[192];  // 浪费
};
// 三个热字段跨了 ~700 bytes
// ≈ 11 条 cache line！
// 每次访问 {pid,state,prio} 要 miss 3 次

✓ 好：热字段集中，冷字段靠后

struct task {
    int pid;            // ┐
    int state;          // ├ 12 bytes
    int prio;           // ┘ 全在一条 line 里！
    // --- 冷数据放后面 ---
    char name[256];
    char comm[256];
    char padding[192];
};
// 每次访问热字段：1 次 cache miss
// 后续 63 字节也都命中

原则 4：False Sharing 避免 —— 每个 CPU 独占一条 line

✗ 糟糕：每核计数器挤在同一条 line

struct {
    int cpu0_counter;  // CPU0 频繁 ++
    int cpu1_counter;  // CPU1 频繁 ++
} counts;
// CPU0 写 counter0 → CPU1 的 line 被 invalidate
// CPU1 写 counter1 → CPU0 的 line 被 invalidate
// 即使访问的是"不同变量"也互相打架
// → cache line 在两个核间反复 bounce

✓ 好：每个核的变量独占一条 line

struct {
    int cpu0_counter;
    char __pad0[60];    // 填满 64B
    int cpu1_counter;
    char __pad1[60];
} counts __attribute__((aligned(64)));
// CPU0 写 counter0 → 只影响自己的 line
// CPU1 写 counter1 → 只影响自己的 line
// 互不干扰，各自 cache hit

原则 5：数据结构选择 —— 数组 > 链表

// ✗ 链表：每个节点 = 独立 malloc → 随机分布在内存各处
//    遍历 1000 个节点 ≈ 1000 次 cache miss
struct node { int val; struct node *next; };
for (struct node *p = head; p; p = p->next)
    sum += p->val;

// ✓ 数组：所有元素连续存储 → 遍历 1000 个元素 ≈ 1000/16 ≈ 63 次 miss
int arr[1000];  // 16 个 int = 64 bytes = 1 cache line

2.21 Spectre/Meltdown 是怎么回事 —— Cache 侧信道攻击原理

Spectre 和 Meltdown 是 2018 年公开的两类 CPU 漏洞，其核心攻击向量正是我们讲了 20 个小节的 Cache。理解它们的原理不需要密码学背景，只需要本文学过的两个概念：(1) 投机执行会填充 Cache Line（且不回滚），(2) 测量访问延迟可以区分 Cache Hit 和 Miss。

Meltdown：绕过权限，直接偷数据

攻击原理（4 步）：

1. 准备：攻击者在用户态分配一个 probe array（256 条 cache line × 64B = 16KB），全部 flush 出 Cache
2. 投机读：攻击者执行一条会触发异常的指令（如从内核地址 load 1 byte 密钥），但在异常被处理之前，CPU 已经投机执行了接下来的指令
3. 信号放大：投机执行中用偷来的那个 byte（0~255）做索引：probe_array[stolen_byte * 64]——这会把 probe array 的对应那条 cache line拉入 Cache
4. 测量：异常返回后，遍历 probe array 的 256 条 line，测量每条 line 的访问延迟。那条延迟特别低的（~4 cycles）= 命中了 L1 = 被投机执行填充的 = 偷来的那个 byte 的值

攻击原理（4 步）：

1. 训练：反复用合法输入调用 if (index < size) ...，训练分支预测器认为"条件为 true"
2. 误导：传入恶意的大 index（超出 size），CPU 仍按预测"条件为 true"投机执行越界读取

4. 测量：同 Meltdown——用延迟反推偷到的 byte

Cache Timing Side Channel Demo（Flush+Reload）

虽然无法在 QEMU 上复现完整的 Spectre/Meltdown（因为 QEMU 不模拟投机执行），但可以演示 Cache 侧信道的核心机制——Flush+Reload。以下程序用 Cache 延迟差异来"偷"另一个函数是否访问过某个地址：

// flush_reload.c - Cache Timing Side Channel Demo
// 交叉编译: aarch64-linux-gnu-gcc -O2 -static flush_reload.c -o flush_reload
#include <stdio.h>
#include <stdint.h>
#include <string.h>

static char secret __attribute__((aligned(64))) = 'X';

static inline uint64_t rdtsc(void) {
    uint64_t v; asm volatile("isb; mrs %0, cntvct_el0" : "=r"(v)); return v;
}

// 清除一条 cache line: dc civac = Clean+Invalidate by VA to PoC
static inline void clflush(void *addr) {
    asm volatile("dc civac, %0; dsb sy" :: "r"(addr) : "memory");
}

// 测量访问延迟
static int probe(void *addr) {
    uint64_t t0 = rdtsc();
    asm volatile("ldr x0, [%0]" :: "r"(addr) : "x0", "memory");
    uint64_t t1 = rdtsc();
    return (int)(t1 - t0);
}

int main(void) {
    int fast_count = 0, slow_count = 0;

    printf("=== Flush+Reload Cache Timing Demo ===\n");
    printf("secret at %p, value = '%c'\n\n", &secret, secret);

    for (int trial = 0; trial < 20; trial++) {
        // Step 1: Flush - 确保 secret 不在 cache
        clflush(&secret);

        // Step 2: 模拟"受害者"访问 (0=skip, 1=access)
        int victim_accesses = trial >= 10;  // 前10次不访问, 后10次访问
        if (victim_accesses)
            (void)secret;    // 访问 secret, 拉入 cache

        // Step 3: Reload - 测量访问 secret 的延迟
        int t = probe(&secret);

        printf("Trial %2d:  victim=%s  latency=%3d ticks  →  %s\n",
               trial,
               victim_accesses ? "access " : "skip   ",
               t,
               t < 30 ? "CACHE HIT  (victim accessed!)" : "CACHE MISS (victim skipped)");

        if (t < 30) fast_count++; else slow_count++;
    }

    printf("\nResult: fast=%d (victim accessed), slow=%d (victim skipped)\n",
           fast_count, slow_count);
    printf("→ Cache timing reveals whether victim accessed secret!\n");
    return 0;
}

2.22 head.S 为什么不直接禁止 D-cache 和 I-cache？

既然 Cache 在 MMU off 时是个麻烦，直接关掉不就完了？答案分两种情况，都不能直接关。

冷启动（x19=0）：Cache 本来就没开，但问题不来源于"开着"

冷启动时 SCTLR_ELx.C=0（D-cache off）、I=0?（I-cache 可能 on）。关键点：

SCTLR_ELx.C = 0 控制的是 CPU 的 load/store 指令是否查询 D-cache。"C=0" 意味着 STR/LDR 不走 Cache——直接访问 DRAM。 但它不阻止硬件预取器和投机执行把数据拉入 Cache。 SCTLR_ELx.C 位： C=1: load/store 查 Cache（正常模式） C=0: load/store 不查 Cache，直连 DRAM C=0 关掉的是"查"的行为，不是"写"的行为。 投机 load 仍然可能填充 cache line ← 这才是 head.S 要处理的！

所以"冷启动时再关一次 Cache"没有意义——它已经是 C=0 了，投机填充还是会发生。正确的做法是接受了投机填充的存在，然后把它清除掉——即 dc ivac。

热启动（x19=1）：不能关，关了当前执行代码就没了

热启动（kexec）时，内核从旧内核跳转到新内核的入口。此时 MMU=on, Cache=on。新内核的 .idmap.text 代码可能只在 Cache 中，还没写到 DRAM：

场景：kexec 跳转到新内核 primary_entry T1: 新代码覆盖了 .idmap.text（写入 Cache，标记 dirty） T2: 如果此时 关 D-cache（SCTLR_ELx.C=0）： → CPU 不再查 D-cache → 但指令取指走 I-cache → D-cache 和 I-cache 之间的硬件一致性不保证 → CPU 可能从 I-cache 取到旧指令（未更新的）→ 执行错误代码 T3: 如果此时 关 I-cache（SCTLR_ELx.I=0）： → CPU 取指直接从 DRAM 读 → 但 DRAM 中是旧代码（dirty 没写回）→ 一样执行错误 T4: 如果同时关 D+I cache： → 执行流程完全不可预测，几乎必定崩 唯一正确的做法：先 dcache_clean_poc（写回 dirty 代码到 DRAM），再关 MMU/Cache。 这正是 head.S 做的事。

那 SCTLR_ELx.C 到底是干什么的？

寄存器/位控制什么不控制什么
SCTLR_ELx.C (D-cache)load/store 指令查询 D-cache不阻止投机读取填充 cache line

SCTLR_ELx.I (I-cache)指令取指查询 I-cache不阻止指令预取填充 I-cache

C=0 只是让显式的 load/store 不走 Cache，但投机访问不受此约束。这就是为什么 preserve_boot_args 和页表填充（non-cacheable STR）之后仍然需要 dc ivac——投机 load 可能已经在后台静默地填充了 cache line。

💡 总结：不能靠"关 Cache"来解决 Cache 一致性问题，因为 (1) 关闭 Cache 不等于阻止投机填充；(2) 关闭 Cache 会导致当前正在执行的代码无法被正确取指（如果它只存在于 Cache 中的话）。ARM 架构提供的正确工具就是 VA-based Cache 维护指令（dc ivac/dc cvac）+ DSB 屏障——这正是 head.S 做的一切。

4.2 逐条详解

① dmb sy —— 全系统内存屏障

  • dmb = Data Memory Barrier，sy = 全系统范围
  • 确保在 barrier 之前的所有内存访问（包括 __pi_create_init_idmap 中的页表写入）对所有观察者可见
  • 为什么需要：页表写入可能还在 write buffer 中，没有真正到达内存。此时如果 speculative load 从内存拉数据，拉到的可能是旧值

② mov x1, x0 —— 设置结束地址

  • x0 是 __pi_create_init_idmap 返回的 ptep——指向页表已使用区域的下一个空闲位置
  • 作为 dcache_inval_poc 的第二个参数（结束地址）

③ adrp x0, __pi_init_idmap_pg_dir —— 设置起始地址

  • __pi_init_idmap_pg_dir 是 identity mapping 页表的基地址
  • adrp = 加载页地址（4KB 对齐），用于获取符号所在的 4KB 页基址
  • 作为 dcache_inval_poc 的第一个参数（起始地址）

④ adr_l x2, dcache_inval_poc —— 获取函数指针

  • adr_l = 加载 64 位绝对地址的宏（在 head.S 中用两条指令实现：adrp + add）

  • 逐 cache line 做：使该 VA 对应的所有 cache 行失效，强制后续访问从 PoC 重取

⑥ b 1f —— 跳过热启动路径

  • 无条件跳转到标签 1:，跳过 0: 处的热启动路径

4.3 为什么要 invalidate 页表区域？

💡 Speculative Load 的本质：ARM64 是弱序内存模型 + 推测执行的架构。即使 MMU 关闭，CPU 的预取器 (prefetcher) 和分支预测器可能在任何时候投机地发出内存读取请求。这些 speculative loads 完全可能刚好命中了页表所在的地址范围——因为它们和内核代码的地址接近。一旦拉进 Cache，就产生了"dirty by speculation"的 cache line。

💡 为什么是 clean 而不是 invalidate？如果 invalidate，相当于丢弃了 dirty cache 行中还没写回的正确数据——之后必须从 DRAM 重读，但 DRAM 中可能是旧的值。Clean 保留了 cache 中的正确数据，同时把它写回 DRAM，确保两处都是最新的。

8. dcache_inval_poc 与 dcache_clean_poc 源码分析

本文在两个位置调用了 dcache_inval_poc：preserve_boot_args（保护 boot_args，范围 32 字节）和冷启动页表路径（保护 idmap 页表，范围几 KB）。虽然调用场景不同，底层实现是同一个函数。本节给出真实源码的完整逐行分析。

8.1 真实实现：arch/arm64/mm/cache.S（非宏展开）

// arch/arm64/mm/cache.S:145-163 — 这是真正的源码，不是简化版

/*
 *	dcache_inval_poc(start, end)
 *
 * 	Ensure that any D-cache lines for the interval [start, end)
 * 	are invalidated. Any partial lines at the ends of the interval are
 *	also cleaned to PoC to prevent data loss.
 *
 *	- start   - kernel start address of region   (x0)
 *	- end     - kernel end address of region     (x1)
 */
SYM_FUNC_START(__pi_dcache_inval_poc)
    dcache_line_size x2, x3        // ① x2 = cache line size (64), x3 临时
    sub     x3, x2, #1             // ② x3 = 63 (对齐掩码)
    tst     x1, x3                 // ③ end 是否对齐到 cache line 边界?
    bic     x1, x1, x3             // ④ 将 end 向下对齐到 cache line 边界
    b.eq    1f                     //    对齐 → 跳转到 1f
    dc      civac, x1              // ⑤ 不对齐: Clean+Invalidate 尾部 partial line
1:  tst     x0, x3                 // ⑥ start 是否对齐到 cache line 边界?
    bic     x0, x0, x3             // ⑦ 将 start 向下对齐到 cache line 边界
    b.eq    2f                     //    对齐 → 跳转到 2f (主循环)
    dc      civac, x0              // ⑧ 不对齐: Clean+Invalidate 头部 partial line
    b       3f                     //    跳转到 3f (主循环递增)
2:  dc      ivac, x0               // ⑨ ★ 主循环: Invalidate 整条 aligned line
3:  add     x0, x0, x2             // ⑩ 地址 += cache line size
    cmp     x0, x1                 // ⑪ 到达对齐后的 end 了吗?
    b.lo    2b                     //    还没 → 跳回 2b 继续循环
    dsb     sy                      // ⑫ 全系统内存屏障，确保操作完成
    ret                             // ⑬ 返回

8.2 逐条详解

指令操作说明
① dcache_line_size x2, x3读 CTR_EL0 获取 DminLine → x2=64ARM64 的 cache line 固定 64 字节，x2=64, x3 用作临时寄存器
② sub x3, x2, #1x3 = 63 = 0b111111用作"对齐掩码"：addr & 63 == 0 表示对齐
③ tst x1, x3测试 end 是否对齐：end & 63 == 0 ?tst 执行按位 AND 但不保存结果，只设 NZ 标志。对齐时 Z=1，不对齐时 Z=0
④ bic x1, x1, x3将 end 向下对齐到 cache line 边界bic = Bit Clear：end = end & ~63，把低 6 位清零。注意：bic 不设标志位！
常见疑问：bic 之后 end 永远对齐了，b.eq 还有意义吗？
有！分支不是判断"现在对齐了没"，而是判断"原来有没有一条部分覆盖的尾部 line"。

范围是 [start, end)——end 是开区间，不包含在范围内。
• 若 end 原来就对齐（Z=1）：0x40009000 这条 line 完全不在 [start, end) 内，不能碰它 → 跳
• 若 end 原来不对齐（Z=0）：说明有部分 line 在范围内，必须 civac → 不跳

⑤ b.eq 1f 读的是③ tst 设的 Z 标志（bic 不带 s 后缀，不修改 PSTATE）。tst 设 Z=1 表示 end 原来就对齐。
⑤ dc civac, x1Clean+Invalidate 尾部 line为什么是 CIVAC 而非 IVAC？这条 line 可能和其他数据共享（end 落在 line 中间），如果纯 invalidate 会丢弃共享数据的脏修改。CIVAC 先写回再失效，保护共享数据
⑥ tst x0, x3测试 start 是否对齐：start & 63 == 0 ?与 ③ 同逻辑。对齐时 Z=1，不对齐时 Z=0
⑦ bic x0, x0, x3将 start 向下对齐到 cache line 边界start = start & ~63。与 ④ 同：bic 不设标志位，⑧ 的 b.eq 仍读 ⑥ tst 设的 Z
⑧ 分支Z=1 → b.eq 2f 跳到主循环
Z=0 → dc civac, x0 然后 b 3f		与 end 的 ④⑤ 完全对称。注意：civac 后多一条 b 3f 跳过主循环 dc ivac——这条 line 已被 civac 处理，不能再 ivac
⑨ dc ivac, x0★ 主循环核心：纯 Invalidate 当前 line此时 x0 已对齐，整条 line 都在操作范围内，可以安全地纯 invalidate（不写回），因为 non-cacheable 写入已经把正确数据放到 DRAM 了
⑩⑪ add + cmp + b.lo逐 line 循环每次前进 64 字节，直到追上对齐后的 end
⑫ dsb syData Synchronization Barrier，全系统确保所有 DC 操作对后续 observer 可见
⑬ ret返回对于 preserve_boot_args 的尾调用 (b)，返回到 primary_entry；对于 head.S:96-117 的 blr x2，返回到调用点下一条指令

③④ 详解：为什么 end 向下对齐？不向上？

以下用两个具体例子走查 ③④ 的寄存器变化。假设 cache line = 64 字节：

例 A：end 已对齐（end = 0x40009000）

指令操作x1 的值x3 的值NZ 标志
进入时—0x4000900063—
③ tst x1, x30x40009000 & 63 = 00x4000900063Z=1（对齐！）
④ bic x1, x1, x30x40009000 & ~63 = 0x400090000x40009000（不变）63—
⑤ b.eq 1fZ=1 → 跳转到 1f跳过 dc civac——end 已对齐，不需要处理尾部 partial line
→ 对齐后的 end = 0x40009000。主循环从 start 到 0x40009000，全部用 dc ivac。

例 B：end 不对齐（end = 0x40009020）—— 这才是整个算法的精髓

指令操作x1 的值x3 的值NZ 标志
进入时—0x4000902063—
③ tst x1, x30x40009020 & 63 = 32 ≠ 00x4000902063Z=0（不对齐！）
④ bic x1, x1, x30x40009020 & ~63 = 0x400090000x40009000 ← 向下对齐了！63—
⑤ b.eq 1fZ=0 → 不跳转顺序执行 dc civac, x1

关键：end 从 0x40009020 向下对齐到 0x40009000。 0x40009020~0x4000903F 这 32 字节是"部分覆盖的尾部 line"——这个范围在主循环之外，由 ⑤ dc civac 单独处理。

为什么向下对齐而不是向上？

原始范围: [0x40008000, 0x40009020)
处理策略:
├─ [0x40009000, 0x40009020) → ⑤ dc civac 单独处理（尾部 partial line，Clean+Invalidate）
└─ [0x40008000, 0x40009000) → 主循环 dc ivac 逐 line 处理（全部是对齐的，纯 Invalidate）

如果向上对齐 end (= 0x40009040):
└─ [0x40008000, 0x40009040) → 主循环全部 ivac
但 0x40009020~0x4000903F 这 32 字节不在调用者指定的范围内！
→ 这些字节可能属于其他变量，被纯 ivac 清除会丢数据！

所以向下对齐 + civac 才是安全的：
主循环只 ivac 完全在范围内的 line（安全——调用者拥有这些 line 的全部 64 字节）
边界 line 用 civac（安全——Clean 写回脏数据 + Invalidate，不会丢别人的数据）

⑥⑦⑧ 详解：start 对齐 —— 两个典型场景

start 的处理逻辑与 end 完全对称。以下用 boot_args（已对齐）和页表区域（假设不对齐）两个场景对比：

场景 1：start 已对齐（boot_args 场景，__cacheline_aligned 保证对齐）

指令操作x0 的值x3NZ
进入时—0x4000800063—
⑥ tst x0, x30x40008000 & 63 = 00x4000800063Z=1
⑦ bic x0, x0, x30x40008000 & ~630x40008000（不变）63—
⑧ b.eq 2fZ=1 → 跳转到 2f（主循环 dc ivac）跳过 dc civac——start 已对齐，整条 line 都在范围内，可以直接 ivac

场景 2：start 不对齐（假设页表地址 = 0x40008018，低 6 位 = 0x18 = 24）

指令操作x0 的值x3NZ

⑧ b.eq 2fZ=0 → 不跳转顺序执行 dc civac, x0（Clean+Invalidate 头部 partial line）

9. 为什么不一开始就 Flush 全部 Cache？

既然 cache 一致性在 MMU 开启前是个大问题，自然会想到：能不能一进入内核入口就把 D-cache 全部清空（比如 dc cisw），一劳永逸？答案是：ARM 架构不允许，语义上也不对。

8.1 Set/Way 操作不是干这个用的

ARM 架构明确规定：cache maintenance by set/way（如 dc cisw、dc isw、dc csw）仅用于 power-down/power-up 流程，不能用来维护正常运行期间的 cache 一致性。

操作方式你告诉 cache 什么cache 怎么做适用场景
dc ivac, <VA> 一个地址 硬件解析地址 → 定位 set → 匹配 tag → 操作该 line 运行时一致性维护（本文所有场景）
dc cisw, <set/way> 第 N 个 set、第 M 个 way 直接操作物理位置，不知道里面是什么数据 power-down/up 流程
⚠ Set/Way 操作的根本问题：从执行 dc cisw 到真正使用数据的这段时间窗口内，CPU 的硬件预取器、投机执行等机制可能已经把新的 cache line 又拉进来了。你无法在 set/way 操作和后续使用之间建立正确的 happens-before 关系。VA-based 操作配合 DSB 屏障才能提供架构级别的正确性保证。

8.2 不同区域需要不同的操作，一个 flush 搞不定

即使假设 set/way flush 是合法的，也不能用同一个操作处理所有区域：

区域需要的操作原因
boot_args Invalidate 写入是 non-cacheable 的，需要干掉投机进来的旧 line
__pi_init_idmap_pg_dir Invalidate 同上，页表写入时 MMU off，non-cacheable 写入
__idmap_text（MMU on 进来时） Clean to PoC 代码在 cache 里是脏的，必须先刷到 PoC，否则关了 MMU 之后指令取不到

"全部 invalidate"会毁掉第三种情况——如果启动时 MMU/cache 是 on 的，你需要把 __idmap_text 的代码clean（写出）到 PoC，而不是 invalidate（丢弃）。

8.3 性能确实也是考量

全 cache flush 遍历所有 set/way，对于现代 CPU（L1 32KB+，L2 几 MB）来说非常慢。用 VA-based 操作只处理真正需要的几个页面，时间差距可能是几百倍。虽然启动阶段对性能不那么敏感，但也没必要浪费。

💡 总结：V8 架构提供的正确工具就是用 VA-based 操作（dc ivac/dc cvac）配合 DSB 屏障，精确地处理每一块关心的内存区域。代码中这种"一块一块处理"的方式不是啰嗦，而是唯一的正确做法。

10. VA 操作如何精确定位目标 Cache Line？

你可能会担心：用 dc ivac, x0 做 cache 操作时，怎么保证失效的正是你想要的那条 cache line，而不是"碰运气"清错了？答案是：cache 控制器是按地址去定位 cache line 的，这是硬件保证的确定性映射。

9.1 Cache 硬件结构回顾

ARM64 的 L1 D-cache 典型是 VIPT（Virtually Indexed, Physically Tagged），假设参数：

参数值推导
总大小32 KB= Data RAM 容量
Way 数4Set-associative 4-way
Set 数128= 32KB / (4 × 64B)
Cache Line64 bytes= L1_CACHE_BYTES
Index bits7 bits [12:6]= log2(128)
Offset bits6 bits [5:0]= log2(64)

9.2 具体数字推演：boot_args 在地址 0x40008000

假设链接器把 boot_args 放在了物理地址 0x40008000。MMU off 时 VA 即 PA。

地址内容所属 Cache Line
0x40008000boot_args[0] = x0（FDT 指针）同一条 64B line
(0x40008000 ~ 0x4000803F)
boot_args 独占整条 line
0x40008008boot_args[1] = x1
0x40008010boot_args[2] = x2
0x40008018boot_args[3] = x3
0x40008020~3F未使用（__cacheline_aligned padding）
0x40008040next_var下一条 cache line

9.3 投机加载如何污染这条 line

假设 bootloader 在跳转到内核之前，它的代码曾经访问过 0x40008000 附近的内存。CPU 的硬件预取器或投机执行把这条 line 拉进了 D-cache：

Cache Set 0TagDataState
Way 00x40008_0旧数据/垃圾Modified (脏)
Way 10x12345_6...Shared
Way 20xABCDE_F...Exclusive
Way 3——INVALID

物理内存 @0x40008000: [x0,x1,x2,x3] 正确数据（non-cacheable STR 直写）。Cache way 0 是脏的旧数据 → 不一致。

9.4 dc ivac 的硬件执行流程

当 CPU 执行 dc ivac, 0x40008000 时：

步骤操作详情
1解析地址offset[5:0]=0, index[12:6]=0x00 → Set 0, tag=0x40008_0
2Set 内并行 Tag 比对Way 0: Tag=0x40008_0 → 命中！
Way 1: Tag=0x12345_6 → 不匹配
Way 2: Tag=0xABCDE_F → 不匹配
Way 3: INVALID → 跳过
3InvalidateWay 0: V→0 → Cache line 失效
物理内存数据不受影响

关键保证：地址 index bits 确定 set，tag 确定 way——不存在"清错 line"的可能。这是 ARM 架构级别的正确性保证。

💡 关键保证：地址的 index bits 唯一确定了 set，tag 唯一确定了 way。不存在"清错 line"这回事——只要地址正确，cache 控制器必然命中的是覆盖该地址的那条 cache line。这是 ARM 架构定义的基本正确性保证。

9.5 唯一可能的坑：Cache 别名（Aliasing），但这里不存在

Cache aliasing 是指不同的 VA 映射到同一个 PA，但落到了不同的 cache set——你用 VA1 做 dc ivac 清不掉 VA2 对应的那条 cache line。但在这里：

  • MMU off：VA 即 PA，不存在"不同 VA 映射同一 PA"的别名问题
  • boot_args 是 __cacheline_aligned：确保它独占一整条 cache line，不会跟邻居数据共享
  • 即使未来 MMU on 了，映射也是恒等的（identity mapping 区域），VA == PA 仍然成立

11. preserve_boot_args 的 0x20 字节与 __cacheline_aligned

10.1 为什么恰好是 0x20（32）字节？

先看 boot_args 的定义和 ARM64 启动协议：

// arch/arm64/kernel/setup.c:88

寄存器作用存储位置
x0FDT (Flattened Device Tree) 的物理地址boot_args[0]
x1保留（必须为 0）boot_args[1]

10.2 dcache_inval_poc 在 0x20 范围上的完整执行追踪

以 boot_args 在 0x40008000 为例，调用 dcache_inval_poc(0x40008000, 0x40008020)：

// arch/arm64/mm/cache.S: dcache_inval_poc 算法
// start=x0=0x40008000, end=x1=0x40008020
// cache line size=64 (x2), mask=63 (x3)

dcache_line_size x2, x3     // x2=64, no-op (line size already known)
sub  x3, x2, #1             // x3=63=0b111111 (mask)

// ---- 处理 end ----
tst  x1, x3                 // 0x20 & 63 = 32 ≠ 0  → end 不对齐
bic  x1, x1, x3             // x1 = 0x20 & ~63 = 0x00 (向下对齐到 0)
                             //   → 对齐后的 end = start = 0x40008000
b.eq 1f                     // 不跳（end 本来就不齐）
dc   civac, x1              // clean+invalidate 对齐后的 end line
                             //   → 对 0x40008000 做 civac（安全处理部分 line）

// ---- 处理 start ----
1: tst x0, x3               // 0x40008000 & 63 = 0  → start 对齐
bic x0, x0, x3              // x0 不变
b.eq 2f                     // 跳转到对齐循环

// ---- 对齐的逐 line 循环 ----
2: dc ivac, x0              // ★ dc ivac, 0x40008000（纯 invalidate）
3: add x0, x0, x2           // x0 = 0x40008040
cmp x0, x1                  // 0x40008040 vs 0x40008000 → x0 > x1
b.lo 2b                     // 不跳，循环结束

dsb sy
ret

关键观察：end 不对齐导致先做了一次 dc civac，再进入循环做 dc ivac，两次操作实际上命中了同一条 cache line！

操作地址命中 Cache Line说明
end 边界 civac0x40008020 向下对齐 → 0x40008000同一条 line
(0x40008000 ~ 0x4000803F)		因为 0x20=32 < 64(line size)，对齐后 end=start
循环 ivac0x40008000纯 invalidate，丢弃该 line

结果：civac（安全处理部分 line） + ivac（直接无效化）= 同一条 line 被操作两次。安全冗余，无副作用。

14. 总结 & 关键要点

#要点说明
1 x19 是唯一的决策变量 cbnz x19, 0f 根据 MMU 状态选择 Cache 维护策略，0=冷启动，非0=热启动
2 冷启动 invalidate 页表 解决 speculative load 污染 cache 的问题：丢弃错误 cache 行，强制从 DRAM 重取
3 热启动 clean idmap 代码 解决 dirty cache 未写回的问题：保留正确数据同时写回，保证 MMU 关闭后取指正确
4 操作对象完全不同 冷启动操作的是页表数据（MMU 要读的），热启动操作的是idmap 代码（CPU 要执行的）
5 ARM64 指令区别 invalidate = DC IVAC（丢弃 cache 行），clean = DC CVAC（写回并保留）
6 都操作到 PoC 两者都操作到 Point of Coherency，保证所有观察者（CPU 核、MMU page table walker）能看到一致结果
7 x19 在此之后传给 init_kernel_el mov x0, x19 然后 bl init_kernel_el，MMU 状态用于判断 warm boot 逻辑
8 这是开启 MMU 前的最后一道 Cache 关卡 执行完本段代码后，经过 init_kernel_el + __cpu_setup，就进入 __primary_switch → __enable_mmu 真正开启 MMU
