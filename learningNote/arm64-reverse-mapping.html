1. 反向映射的目标与设计动机

1.1 为什么需要反向映射？

核心问题：给定一个物理页框 (page frame)，如何找出所有映射了它的进程页表项 (PTE)？

在 Linux 虚拟内存管理中，"正向映射"是进程通过页表将虚拟地址翻译为物理地址。而反向映射 (Reverse Mapping, rmap) 则是反方向：从物理页框出发，找到所有映射了该页框的虚拟地址和对应页表项。

反向映射在以下场景中不可或缺：

场景需要的操作为什么需要反向映射
📄 页面回收 (Page Reclaim) 换出匿名页 / 回写文件页 必须解除所有进程对该页的映射才能安全回收
📦 页面迁移 (Page Migration) NUMA 平衡 / 内存规整 / 热插拔 需修改所有映射到旧物理页的 PTE 指向新位置
💥 内存错误处理 HWPoison 隔离损坏页面 向所有映射进程发送 SIGBUS，解除页表映射
🔀 KSM 页面去重 合并相同内容的匿名页 需要找到所有映射同一物理页的 VMA 并写保护
⚡ THP 大页管理 拆分/回收透明大页 大页可能被多个进程部分映射，需全部解除
📏 文件截断 (truncate) 截断文件时无效化映射 需找到所有 mmap 了该文件页范围的进程
🔎 引用检测 判断页面是否被访问过 遍历所有映射检查 PTE 的 Accessed/Dirty 位
设计哲学：反向映射是"先有物理页，再找虚拟地址"的能力，它使得内核可以在不遍历所有进程页表的情况下，精确地找到并修改某个物理页的所有映射。这是实现高效页面回收、迁移和内存管理的基石。

1.2 多进程相同虚拟地址如何区分？

这是理解反向映射最关键的认知跃迁：反向映射找到的不是"裸虚拟地址"，而是 (VMA, 虚拟地址) 二元组——其中 VMA 隐式包含了进程身份。 

错误的直觉：
  物理页 ──► 虚拟地址 0x7f000000
                 ↑
                 └── 这是进程A的还是进程B的？无法区分！

实际的设计：
                          ┌─────────────────────────────────┐
  物理页 ──► anon_vma ──► │  anon_vma_chain 的 interval tree │
                          │  (key = 虚拟地址, value = VMA)    │
                          └────────┬───────────┬────────────┘
                                   │           │
                    ┌──────────────┘           └──────────────┐
                    ▼                                         ▼
    ┌───────────────────────────┐       ┌───────────────────────────┐
    │ avc1 → VMA_A              │       │ avc2 → VMA_B              │
    │  .vma → vm_area_struct_A  │       │  .vma → vm_area_struct_B  │
    │  VMA_A.vm_mm → 进程A的mm  │       │  VMA_B.vm_mm → 进程B的mm  │
    │  VMA_A.vm_start = 0x...   │       │  VMA_B.vm_start = 0x...   │
    │  虚拟地址 = 0x7f000000    │       │  虚拟地址 = 0x7f000000    │
    └───────────────────────────┘       └───────────────────────────┘
              ↑                                       ↑
         "0x7f000000                            "0x7f000000
          属于进程A"                              属于进程B"

关键数据结构链：

层级包含的信息如何区分进程
struct vm_area_struct (VMA) vm_mm (指向进程), vm_start/vm_end (虚拟地址范围), vm_file (文件映射) 等 vma->vm_mm 是进程的 mm_struct 指针，天然区分进程
struct anon_vma_chain 包含指向 VMA 的指针，插入在 anon_vma 的 interval tree 中 (key = 虚拟地址偏移) 通过 avc->vma->vm_mm 获取进程身份
struct mm_struct 进程的地址空间描述符，包含 PGD 基地址、所有 VMA 等 一个 mm_struct = 一个进程地址空间

完整遍历流程 — 以匿名页 try_to_unmap 为例：

try_to_unmap(folio)
  │
  └─► rmap_walk_anon(folio, &rwc)
        │
        │  1. 通过 folio→mapping 找到 anon_vma
        │    folio→mapping = anon_vma | ANON_FLAG
        │
        │  2. 遍历 anon_vma→rb_root (interval tree)
        │    anon_vma_interval_tree_foreach(avc, &anon_vma→rb_root, ...)
        │    │
        │    ├─► avc_1 → vma_A (属于进程A的mm)  → 虚拟地址 = 0x7f000000
        │    │    │
        │    │    └─► try_to_unmap_one(folio, vma_A, 0x7f000000)
        │    │           │
        │    │           └─► 通过 vma_A→vm_mm→pgd 找到进程A的页表
        │    │               修改 PTE(0x7f000000) → swap entry
        │    │
        │    ├─► avc_2 → vma_B (属于进程B的mm)  → 虚拟地址 = 0x7f000000
        │    │    │
        │    │    └─► try_to_unmap_one(folio, vma_B, 0x7f000000)
        │    │           │
        │    │           └─► 通过 vma_B→vm_mm→pgd 找到进程B的页表
        │    │               修改 PTE(0x7f000000) → swap entry
        │    │
        │    └─► avc_3 → vma_C (进程A fork出的子进程) → 虚拟地址 = 0x7f000000
        │           │
        │           └─► try_to_unmap_one(folio, vma_C, 0x7f000000)
        │                  └─► 通过 vma_C→vm_mm (不同于 vma_A→vm_mm!) 找到子进程页表
        │
        └─► 三个调用分别操作三个不同进程的页表，虚拟地址相同但互不干扰
核心要点：
① 反向映射通过 VMA (而非裸虚拟地址) 来定位映射，VMA 天然携带进程身份 (vm_mm)
② 即使 100 个进程的同一虚拟地址映射同一物理页，反向映射也能通过 100 个不同的 VMA 对象 逐一区分
③ Interval tree 的 key 是 虚拟地址偏移量 (pgoff)，value 是 anon_vma_chain (→ VMA)，所以同地址不同进程的映射会作为不同节点存储在树中
④ 解除映射时，使用 vma→vm_mm→pgd 定位正确的进程页表进行 PTE 修改

🔑 深入理解："裸虚拟地址" vs "(VMA, 虚拟地址) 二元组"

这两个术语的区别是理解反向映射设计的关键认知跃迁，我们逐一拆解。

裸虚拟地址

就是一个单纯的 64 位数字，比如 0x7f000000。

把它想象成门牌号：你知道"38号房间"，但不知道是哪栋楼的 38 号——整条街可能有十栋楼，每栋都有 38 号房间。裸虚拟地址就是"38号"这个数字本身，脱离了进程上下文它毫无意义。 

    裸虚拟地址 = 0x7f000000

    进程A 的地址空间              进程B 的地址空间              进程C 的地址空间
  ┌─────────────────────┐   ┌─────────────────────┐   ┌─────────────────────┐
  │ 0x7f000000 → 物理页X │   │ 0x7f000000 → 物理页X │   │ 0x7f000000 → 物理页X │
  │                     │   │                     │   │                     │
  │ PGD 基址: 0xAAAA000 │   │ PGD 基址: 0xBBBB000 │   │ PGD 基址: 0xCCCC000 │
  └─────────────────────┘   └─────────────────────┘   └─────────────────────┘
          ↑                         ↑                         ↑
          └── 仅仅 "0x7f000000" 这个数字，无法知道该改哪个 PGD 下的页表！

(VMA, 虚拟地址) 二元组

就是 "(哪栋楼的38号房间, 38)"——把门牌号和楼栋绑定在一起。

概念日常类比内核中的 C 类型
裸虚拟地址房号 "38"unsigned long address = 0x7f000000
VMA (进程身份)哪栋楼struct vm_area_struct *vma
二元组楼栋 + 房号(vma, address) —— 两者绑定传递

为什么必须用二元组？—— 看内核代码

try_to_unmap_one 的函数签名直接体现了这个设计：

// mm/rmap.c:1865
static bool try_to_unmap_one(struct folio *folio,
                             struct vm_area_struct *vma,   // ← 哪栋楼（哪个进程的哪段映射）
                             unsigned long address,         // ← 几号房（哪个虚拟地址）
                             void *arg)

函数内部通过 VMA 获取进程的 mm_struct，再获取该进程的页表基址：

// try_to_unmap_one 内部 (mm/rmap.c:1867)
struct mm_struct *mm = vma->vm_mm;   // 从 VMA 拿到进程的 mm_struct
// 之后通过 mm->pgd 找到该进程的页表基地址
// page_vma_mapped_walk() 使用 mm->pgd 去遍历该进程的页表

// 伪代码：如果只有裸虚拟地址，根本无法定位 PTE
pte = find_pte(address);           // ❌ 在谁的页表里找？不知道！

// 实际代码：必须通过 VMA 提供页表基址
mm   = vma->vm_mm;                  // 从 VMA 获取进程的 mm_struct
pgd  = mm->pgd;                     // 该进程的页表基地址（每个进程不同！）
pte  = find_pte_in(pgd, address);   // ✅ 在指定进程的页表里找

完整场景对比

场景：三个进程都用 mmap 分配了匿名内存，碰巧系统给了它们相同的虚拟地址

进程A:  mmap → 0x7f000000 ──→ 物理页 X
进程B:  mmap → 0x7f000000 ──→ 物理页 X  (同一个物理页！比如 fork 后还没 COW)
进程C:  mmap → 0x7f000000 ──→ 物理页 X

现在要回收物理页 X，反向映射遍历 interval tree：

┌─────────────────────────────────────────────────────────────────────┐
│  anon_vma 的 interval tree 中存的是：                                  │
│                                                                     │
│  裸地址 0x7f000000 → 如果只存这个，三次查找返回一样的值                     │
│  → 完全无法区分！❌                                                    │
│                                                                     │
│  (VMA_A, 0x7f000000) → 进程A的页表 → 修改进程A的 PTE ✅               │
│  (VMA_B, 0x7f000000) → 进程B的页表 → 修改进程B的 PTE ✅               │
│  (VMA_C, 0x7f000000) → 进程C的页表 → 修改进程C的 PTE ✅               │
│                                                                     │
│  三个不同的 VMA 对象 → 三个不同的 mm_struct →                           │
│  三个不同的 PGD 基址 → 三个不同页表中的 PTE 被各自修改                    │
└─────────────────────────────────────────────────────────────────────┘
一句话总结：
裸虚拟地址只是一个数字；二元组 (VMA, address) 是"谁的地址空间 + 哪个地址"。
VMA 通过 vma→vm_mm 告诉你页表在哪里，address 告诉你找到页表后在哪个偏移量修改 PTE——两者缺一不可。

🔑 深入理解："VMA 天然携带进程身份"到底是什么意思？

"进程身份"很容易被误解为 PID，但它在反向映射语境中的含义完全不同——它指的是"地址空间"。

你可能以为的实际上是什么
PID = 5678❌ 就一个数字，不能用来找页表
task_struct 指针❌ 也不是，太臃肿，反向映射不需要调度信息
mm_struct 指针✅ 这才是"身份"——指向进程的地址空间描述符

看一眼内核代码：

// include/linux/mm_types.h
struct vm_area_struct {
    struct mm_struct *vm_mm;   // ← 这就是"进程身份"的全部
    unsigned long vm_start;
    unsigned long vm_end;
    // ...
};

struct mm_struct {
    pgd_t *pgd;              // ← 页表根物理地址，这才是反向映射真正需要的
    // ...
};

反向映射的最终目的不是"知道这个地址属于 PID 几"，而是找到并修改正确的页表项 (PTE)。要做到这一点，只需要知道页表的根在哪里 (PGD 基址)。而 vma→vm_mm→pgd 恰好提供了这个信息——两个进程只要 vm_mm 不同，pgd 就一定不同。

举例 ①：没有 fork 的场景（最简单）

两个独立进程各自 mmap 了匿名内存，恰好分配到了相同的虚拟地址

进程A (PID=1001)                          进程B (PID=1002)
┌──────────────────────────────┐    ┌──────────────────────────────┐
│ mm_struct_A (地址 0xFFFF...A)│    │ mm_struct_B (地址 0xFFFF...B)│
│  .pgd = 0xAAAA000            │    │  .pgd = 0xBBBB000            │ ← 关键！不同
│                              │    │                              │
│ VMA_A:                       │    │ VMA_B:                       │
│  .vm_mm = → mm_struct_A     │    │  .vm_mm = → mm_struct_B     │
│  .vm_start = 0x7f000000      │    │  .vm_start = 0x7f000000      │
│  .vm_end   = 0x7f001000      │    │  .vm_end   = 0x7f001000      │
└──────────────┬───────────────┘    └──────────────┬───────────────┘
               │                                   │
               │    都映射到同一个物理页 X             │
               └───────────────┬───────────────────┘
                               ▼
                     ┌─────────────────┐
                     │   物理页 X       │
                     │   folio→mapping  │
                     │   = anon_vma     │
                     └────────┬────────┘
                              │
                     anon_vma 的 interval tree:
                     ┌──────────────────────────┐
                     │ avc1 → VMA_A (vm_mm_A)   │ ← 不同对象！
                     │ avc2 → VMA_B (vm_mm_B)   │ ← 不同对象！
                     └──────────────────────────┘

反向映射遍历时：
  avc1 → VMA_A → vm_mm_A → pgd=0xAAAA000 → 在进程A的页表中找 PTE(0x7f000000) ✅
  avc2 → VMA_B → vm_mm_B → pgd=0xBBBB000 → 在进程B的页表中找 PTE(0x7f000000) ✅

虽然虚拟地址相同 (都是 0x7f000000)，但因为 pgd 不同，PTE 在物理内存中的位置完全不同！

举例 ②：fork 之后的场景（更有趣）

进程A mmap 了一段匿名内存，然后 fork 出子进程B

fork 之前:
  进程A 的 VMA_A → anon_vma_root → interval tree 中只有一个 avc (指向 VMA_A)

fork 之后 (anon_vma_fork 被调用):
  进程A (父)                     进程B (子，fork 出来的)
  ┌────────────────────┐        ┌────────────────────┐
  │ mm_struct_A        │        │ mm_struct_B  ← 新的！│
  │  .pgd = 0xAAAA000  │        │  .pgd = 0xBBBB000  │ ← 子进程有自己独立的 PGD！
  │                    │        │                    │
  │ VMA_A:             │        │ VMA_B:             │
  │  .vm_mm = mm_A    │        │  .vm_mm = mm_B    │ ← 不同的 mm_struct
  │  .anon_vma = root  │        │  .anon_vma = root  │ ← 共享同一个 anon_vma
  └────────┬───────────┘        └────────┬───────────┘
           │                             │
           │    VMA_A 和 VMA_B 都挂在同一个 anon_vma 的 interval tree 里
           │    物理页仍然是同一个（fork 后还没 COW）
           │                             │
           └──────────┬──────────────────┘
                      ▼
            ┌─────────────────┐
            │   物理页 X       │
            │   (映射计数 = 2) │
            └────────┬────────┘
                     │
            anon_vma_root 的 interval tree:
            ┌──────────────────────────────┐
            │ avc1 → VMA_A → vm_mm = mm_A │
            │ avc2 → VMA_B → vm_mm = mm_B │ ← 不同！
            └──────────────────────────────┘

反向映射回收物理页 X 时：
  avc1 → VMA_A → mm_A → pgd=0xAAAA000 → 修改父进程 PTE(0x7f000000) ✅
  avc2 → VMA_B → mm_B → pgd=0xBBBB000 → 修改子进程 PTE(0x7f000000) ✅

两个 VMA 的虚拟地址范围完全相同（都是 fork 继承的），
anon_vma 也是同一个，但因为 vm_mm 不同，pgd 不同 → 修改到不同的物理页表！
核心要点：
① "进程身份" = mm_struct，不是 PID。反向映射不关心 PID 是多少，只关心页表根在哪。
② fork 后父子进程共享 anon_vma 但拥有独立的 mm_struct。所以同一物理页会被两个 avc 节点指向（分别指向父和子的 VMA），各自携带不同的 mm_struct → 不同的 pgd → 不同页表。
③ 这就是为什么 interval tree 中必须存 VMA 指针而非裸地址：如果只存虚拟地址 0x7f000000，fork 之后到底去改父进程还是子进程的 PTE？无法决定。存 VMA 就天然解决了这个问题。

2.1 ARM64 架构级配置

ARM64 架构通过 arch/arm64/Kconfig 反向选择 (select) 了大量与反向映射相关的通用内核特性：

ARCH_WANT_BATCHED_UNMAP_TLB_FLUSH 第 114 行 性能 批量延迟 TLB 刷新，减少 unmap 时的 IPI 开销

调用链：页面回收 (kswapd / direct reclaim)

  │
  ├─ folio_mapped(folio)?

  │                │

  │                │     │
  │                │     ├─ rmap_walk_anon() ─► anon_vma interval tree
  │                │     │       └─ 对每个 VMA 调用 try_to_unmap_one()
  │                │     ├─ rmap_walk_file() ─► mapping->i_mmap interval tree
  │                │     │       └─ 对每个 VMA 调用 try_to_unmap_one()

  │                │

  │

if (folio_mapped(folio)) {
    enum ttu_flags flags = TTU_BATCH_FLUSH;
    bool was_swapbacked = folio_test_swapbacked(folio);

    if (folio_test_pmd_mappable(folio))

🧪 实验一：匿名页 swap-out 反向映射

目标：观察匿名页被换出时 try_to_unmap 的调用过程。

场景描述：

一个匿名页被多个进程通过 fork() 共享（COW 之前），当内存压力触发 swap-out 时，反向映射需要找到所有进程的 PTE 并替换为 swap entry。

实验步骤： 
#!/bin/bash

cd /sys/kernel/tracing
echo 1 > events/rmap/enable              # 启用所有 rmap tracepoint
echo 1 > events/vmscan/enable            # 启用 vmscan tracepoint
echo 1 > tracing_on

# 步骤2: 运行测试程序 (分配匿名内存，fork，触发内存压力)
# 编译: gcc -o test_anon_swap test_anon_swap.c -lpthread
./test_anon_swap &
PID=$!

# 步骤3: 创建内存压力 (分配大量内存触发 swap)
stress-ng --vm 1 --vm-bytes 80% --timeout 30s

# 步骤4: 查看 trace 结果
echo 0 > tracing_on
cat trace | grep -E 'try_to_unmap|folio_referenced|rmap_walk' | head -50

# 步骤5: 观察 /proc/PID/smaps 中的 Swap 字段
cat /proc/$PID/smaps | grep -A 20 '[anon]'
测试程序 test_anon_swap.c： 
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/wait.h>

#define SIZE (128 * 1024 * 1024)  // 128 MB

int main() {
    char *p = mmap(NULL, SIZE, PROT_READ|PROT_WRITE,
                     MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
    memset(p, 0xAB, SIZE);        // 实际分配物理页
    printf("Allocated 128MB anon memory at %p\n", p);

    pid_t pid = fork();
    if (pid == 0) {
        // 子进程：读取共享的匿名页
        printf("Child: first byte = 0x%02x\n", p[0]);
        pause();
    } else {
        // 父进程：等待子进程就绪
        sleep(1);
        printf("Parent: first byte = 0x%02x, pid=%d\n", p[0], pid);
        printf("Press Enter to exit (observe /proc/PID/smaps)...\n");
        getchar();
        kill(pid, SIGTERM);
        wait(NULL);
    }
    return 0;
}

  • /proc/PID/smaps 中匿名映射的 Swap 字段非零

测试程序 test_ksm_rmap.c： 
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/wait.h>

#define NPAGES 100
#define PAGESZ 4096

int main() {
    char *regions[3];

    // 创建3个独立进程，各自分配匿名内存并写入相同内容
    for (int i = 0; i < 3; i++) {
        pid_t pid = fork();
        if (pid == 0) {
            regions[i] = mmap(NULL, NPAGES*PAGESZ,
                              PROT_READ|PROT_WRITE,
                              MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
            madvise(regions[i], NPAGES*PAGESZ, MADV_MERGEABLE);
            // 写入相同内容以触发 KSM 合并
            for (int j = 0; j < NPAGES; j++)
                memset(regions[i] + j*PAGESZ, 0x42, PAGESZ);
            printf("Child %d: region at %p\n", i, regions[i]);
            pause();
            exit(0);
        }
    }
    printf("Parent PID=%d: waiting for KSM to merge...\n", getpid());
    getchar();
    return 0;
}

    printf("Received SIGBUS (hwpoison) at %p\n", p);
