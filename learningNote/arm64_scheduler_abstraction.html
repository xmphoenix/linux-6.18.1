一、整体架构总览

ARM64 内核调度子系统分为六个抽象层，自底向上从硬件描述到调度策略逐层堆叠：

┌─────────────────────────────────────────────────────────────────┐ │ Layer 6: 调度类 (Scheduling Classes) │ │ struct sched_class — 策略层，定义"怎么调度" │ │ stop / deadline / rt / fair(CFS/EEVDF) / idle │ ├─────────────────────────────────────────────────────────────────┤ │ Layer 5: 任务组 & 带宽控制 (Task Groups & Bandwidth) │ │ struct task_group — cgroup 层级，CFS/RT 带宽隔离 │ ├─────────────────────────────────────────────────────────────────┤ │ Layer 4: 调度域 & 根域 (Scheduling Domains & Root Domain) │ │ struct sched_domain → struct sched_group │ │ struct root_domain → struct perf_domain (EAS) │ │ — 拓扑感知负载均衡 + 能耗感知调度 │ ├─────────────────────────────────────────────────────────────────┤ │ Layer 3: 调度实体 (Scheduling Entities) │ │ struct sched_entity / sched_rt_entity / sched_dl_entity │ │ — 代表"可被调度的对象"（任务或任务组） │ ├─────────────────────────────────────────────────────────────────┤ │ Layer 2: Per-CPU 运行队列 (Runqueue) │ │ struct rq { .cfs, .rt, .dl } │ │ — CPU 上所有调度状态的集合点 │ ├─────────────────────────────────────────────────────────────────┤ │ Layer 1: 硬件拓扑描述 (Hardware Topology) │ │ struct cpu_topology — DT/ACPI → thread/core/cluster/pkg │ │ capacity_freq_ref, arch_freq_scale — capacity & freq scaling │ │ Energy Model (struct em_perf_domain) — 功耗模型 │ └─────────────────────────────────────────────────────────────────┘

ARM64 相对于 x86 的关键差异在于：Layer 1（拓扑通过 DT/ACPI 而非固有 CPUID 架构检测）和 Layer 4 的 EAS 路径（find_energy_efficient_cpu 替代纯负载驱动放置策略）。其余调度类框架是架构无关的。

二、Layer 1: 硬件拓扑描述

核心问题： "硬件长什么样？" — 将 ARM64 SoC 的物理拓扑（big.LITTLE、DynamIQ、多 cluster）转化为内核可查询的结构化数据。

2.1 拓扑检测入口

ARM64 的 CPU 拓扑检测在 init_cpu_topology() 中完成（位于 drivers/base/arch_topology.c），根据系统固件类型分两条路径：

固件类型 核心函数 数据来源
Device Tree parse_dt_topology() DT /cpus/cpu-map 节点（cluster → core → thread）
ACPI parse_acpi_topology() ACPI PPTT 表（Processor Properties Topology Table）

解析完成后，通过 store_cpu_topology(cpu) 将结果写入 cpu_topology[] 数组，然后用 update_siblings_masks(cpu) 构建各层级 sibling cpumask。

2.2 struct cpu_topology

定义位于 include/linux/arch_topology.h:62：

struct cpu_topology {
    int thread_id;                    // SMT 线程 ID
    int core_id;                      // 物理核 ID
    int cluster_id;                   // 簇 ID (ARM DynamIQ 特有层级)
    int package_id;                   // 封装/插座 ID
    cpumask_t thread_sibling;         // 同一核的兄弟线程
    cpumask_t core_sibling;           // 共享同一 cluster 的兄弟核
    cpumask_t cluster_sibling;        // 同 cluster 的兄弟
    cpumask_t llc_sibling;            // 共享末级缓存的兄弟
};

ARM64 DynamIQ 典型拓扑映射

以 Cortex-X4/A720/A520 三簇 DynamIQ 为例（8 核）：

cpu0 (Cortex-X4):  thread_id=0  core_id=0  cluster_id=0  package_id=0
cpu1 (Cortex-X4):  thread_id=0  core_id=1  cluster_id=0  package_id=0
cpu2 (Cortex-A720):thread_id=0  core_id=2  cluster_id=1  package_id=0
cpu3 (Cortex-A720):thread_id=0  core_id=3  cluster_id=1  package_id=0
cpu4 (Cortex-A720):thread_id=0  core_id=4  cluster_id=1  package_id=0
cpu5 (Cortex-A520):thread_id=0  core_id=5  cluster_id=2  package_id=0
cpu6 (Cortex-A520):thread_id=0  core_id=6  cluster_id=2  package_id=0
cpu7 (Cortex-A520):thread_id=0  core_id=7  cluster_id=2  package_id=0

各 CPU 的 cluster_sibling cpumask 分别对应 {0-1}、{2-4}、{5-7}，而 llc_sibling 取决于 SoC 是否配置了共享 L3。

2.2.1 thread / core / cluster / package 的硬件含义

cpu_topology 的四个 ID 字段不是随意划分的——每个字段对应硬件中的一个资源共享层级：

字段CONFIG英文全称中文共享的硬件典型形态ARM64?
thread_idSCHED_SMTSimultaneous Multithreading同时多线程同一物理核的全部：L1 cache、执行单元、寄存器堆x86 HyperThreading（1核2线程）❌
cluster_idSCHED_CLUSTERCluster簇L2 cache 或 mid-level cache、内部总线ARM DynamIQ 大小核簇✅
core_idSCHED_MCMulti-Core多核最后一级缓存 LLC（通常 L3）chiplet/ring bus 上共享 L3 的所有核✅
package_id（固定）Package封装/插槽同一物理封装 / die / socket整个 SoC 或 NUMA 节点✅

这四层的包含关系是：SMT ⊂ CLS ⊂ MC ⊂ PKG。即在同一个 cluster 里的核一定在同一个 MC 域里，在同一个 MC 域里的核一定在同一个 package 里。

2.2.3 从 cpu_topology 到 sched_domain：冗余层级的自动折叠

default_topology[]（见 §5.4）是静态模板——定义了 最大可能 的层级组合（SMT → CLS → MC → PKG）。但在运行时，cpu_attach_domain()（kernel/sched/topology.c:716）会根据实际的 cpu_topology[] 数据将冗余层级从链表里摘除。

什么叫 span？

span = 调度域覆盖的 CPU 集合（cpumask）。例如 QEMU virt 的 MC 层 span = {0,1,2,3}——"这层域管这 4 个 CPU"。

"span 相同" 就是两个层级覆盖完全一样的 CPU。QEMU virt 中 MC 和 PKG 的 span 都是 {0,1,2,3}，"4 个核的负载均衡"这件事 MC 层已经做了，PKG 层没有任何额外的 CPU 需要协调 → PKG 就是冗余的。

折叠规则

折叠发生在 cpu_attach_domain() 中（topology.c:716），本质是 对 sd→parent→child 链表做剪枝：

自底向上遍历 (tmp = rq->sd; tmp; ):
  parent = tmp->parent
  if sd_parent_degenerate(tmp, parent):    // parent 冗余?
      tmp->parent = parent->parent           // splice out parent
      destroy parent

两个判断函数决定一个域是否被折叠：

sd_degenerate(sd)（topology.c:170）—— 这个域本身是否无用？

① span 只有 1 个 CPU → 退化（就一个核，不需要均衡）
② 没有 SD_WAKE_AFFINE 等有意义 flag → 退化
③ 否则 → 不退化

sd_parent_degenerate(sd, parent)（topology.c:187）—— parent 相对于 sd 是否冗余？

① parent 自己退化 → 折叠
② sd 和 parent 的 span 不同 → 不折叠（覆盖范围不同，parent 有额外 CPU 需要协调）
③ parent 有 sd 没有的 flag → 不折叠（parent 有独特语义）
④ 以上都不满足 → 折叠（span 相同 + 无额外 flag = 重复层级）
三个场景走一遍

① QEMU virt（同构 A57） — 最终只剩 MC 一层：

折叠前: rq->sd → MC(span=0-3, SD_SHARE_LLC) → PKG(span=0-3, 无flag) → NULL
            MC vs PKG: span相同+PKG无额外flag → 折叠 PKG → MC->parent=NULL
折叠后: rq->sd → MC(span=0-3, SD_SHARE_LLC) → NULL     ← 只剩一层

② 大小核手机 SoC — 三层都保留：

折叠前: MC(span=0-7,SD_SHARE_LLC)→CLS(span=各cluster,SD_CLUSTER)→PKG(span=0-7)→NULL
            CLS vs PKG: span不同(CLS各2-3个, PKG=0-7) → 不折叠
            MC vs CLS: span不同(MC=0-7, CLS各2-3) → 不折叠
折叠后: MC → CLS → PKG → NULL                             ← 三层都保留

③ 双 socket 服务器 — PKG 被保留：

折叠前: MC(span=0-7)→PKG(span=socket0=0-63)→NUMA(span=0-127)→NULL
            MC vs PKG:  span不同(0-7≠0-63) → 不折叠
            PKG vs NUMA: span不同(0-63≠0-127) → 不折叠
折叠后: MC → PKG → NUMA → NULL                           ← 三层都保留

关键洞察：default_topology[] 是最大可能集合的静态模板。运行时根据 cpu_topology[] 的实际数据自动折叠——span 相同且无额外 flags 的父子层就是冗余的。

QEMU virt 的具体代码证据

证据 ①：MC 和 PKG 的 span 为什么相同。 每个层级的 span 由 mask 函数决定，MC 和 PKG 调用不同的函数，但在 QEMU virt 同构单节点下返回了相同的 cpumask：

MC 层 — topology.c:1757：

const struct cpumask *tl_mc_mask(..., int cpu) {
    return cpu_coregroup_mask(cpu);   // → cpu_topology[cpu].core_sibling
}

cpu_coregroup_mask() — arch_topology.c:698：

const struct cpumask *cpu_coregroup_mask(int cpu) {
    const cpumask_t *core_mask = cpumask_of_node(cpu_to_node(cpu));
    if (cpumask_subset(&cpu_topology[cpu].core_sibling, core_mask))
        core_mask = &cpu_topology[cpu].core_sibling;  // ← 取 core_sibling={0-3}
    return core_mask;
}

PKG 层 — topology.c:1763：

const struct cpumask *tl_pkg_mask(..., int cpu) {
    return cpu_node_mask(cpu);        // → NUMA node 0 = {0-3}（单节点）
}

QEMU virt DT 解析后 core_sibling = {0,1,2,3}，NUMA node 0 也是 {0,1,2,3} → 两者 span 完全一致。

证据 ②：折叠的发生位置。 topology.c:716 的 cpu_attach_domain() 遍历 sd 链表：

for (tmp = sd; tmp; ) {
    struct sched_domain *parent = tmp->parent;
    if (!parent) break;
    if (sd_parent_degenerate(tmp, parent)) {  // PKG 冗余?
        tmp->parent = parent->parent;          // splice out PKG
        destroy_sched_domain(parent);
    } else
        tmp = tmp->parent;
}

证据 ③：判定 PKG 冗余。 topology.c:187 对着 MC(span=0-3, flags=SD_SHARE_LLC) 和 PKG(span=0-3, flags=0) 逐条判断：

sd_parent_degenerate(MC, PKG):
  ① sd_degenerate(PKG)?     → span=4>1, 不触发
  ② span不同?               → {0-3}=={0-3}, 不触发
  ③ PKG有MC没有的flag?      → ~SD_SHARE_LLC & 0 = 0, 不触发
  ④ 以上都不满足            → return 1  // PKG 冗余!

2.4 QEMU virt 拓扑初始化全流程追踪

以项目 launch.sh 中的 qemu-system-aarch64 -machine virt -cpu cortex-a57 -smp 4 为基准，从头到尾追踪硬件拓扑数据是如何初始化的。

2.4.1 调用链总览

2.4.2 关键代码逐段追踪

第①步：reset_cpu_topology() — arch_topology.c:794，全部清零：

for_each_possible_cpu(cpu) {
    cpu_topology[cpu].thread_id  = -1;
    cpu_topology[cpu].core_id    = -1;
    cpu_topology[cpu].cluster_id = -1;
    cpu_topology[cpu].package_id = -1;
    clear_cpu_topology(cpu);
}

第②步：parse_acpi_topology() — arch/arm64/kernel/topology.c:60，if (acpi_disabled) return 0; QEMU DT 启动，直接返回。

第③步：parse_dt_topology() — arch_topology.c:651，解析设备树中的 /cpus/cpu-map。QEMU DT 中 cpu-map 直接包含 cluster0，没有 socket0 子节点，因此 parse_socket()（line 612）的 has_socket 为 false，走 parse_cluster(socket, 0, -1, 0) 分支——把整个 map 当 cluster 处理，package_id 固定为 0。

parse_cluster() 递归两轮：depth=0 找到 cluster0 → depth=1 找到 core0~3 → 调用 parse_core()（line 493）：

cpu = get_cpu_for_node(core);   // cpu phandle → Linux cpu number (0~3)
cpu_topology[cpu].package_id = 0;
cpu_topology[cpu].cluster_id = 0;
cpu_topology[cpu].core_id    = core_id;  // 0,1,2,3
// thread_id 保持 -1（没有 thread0 子节点 → 无 SMT）

第④步：fetch_cache_info() — arch_topology.c:850，为后续 llc_sibling 做准备。

第⑤步：store_cpu_topology() → update_siblings_masks() — arch_topology.c:860。DT 已填充 topology（package_id=0≠-1），跳到 topology_populated 标签，调用 update_siblings_masks()（line 738）：遍历所有 online CPU，根据 package_id/cluster_id/core_id 的相等关系填充各 sibling cpumask。

2.4.4 验证结论

结论 1：QEMU virt + Cortex-A57 是纯同构系统。 所有 CPU 的 core_sibling = cluster_sibling = llc_sibling = {0,1,2,3}，四核完全等价。capacity 全为 1024（DT 中无 capacity-dmips-mhz，保持 SCHED_CAPACITY_SCALE 默认值）。

结论 2：cluster_id 虽为 0 而非 -1，但 cluster_sibling 等于 core_sibling。 QEMU DT 中所有 4 个 core 都在同一个 cluster0 下，cluster 没有提供比 package 更细的划分。调度域构建时 CLS 层即使 #ifdef CONFIG_SCHED_CLUSTER 存在，其 mask 也等于 MC 的 mask → 被 §2.2.3 的折叠逻辑消除。

结论 3：thread_id 全为 -1。 Cortex-A57 不支持 SMT，QEMU DT 中 cpu 节点没有 thread0 子节点，parse_core() 的 thread 遍历第一轮就 break。

结论 4：后续 sched_init_smp() → sched_init_domains() 构建调度域时，default_topology[] 中的 SMT 和 CLS 层各自 mask 函数返回的 cpumask 要么只含单核（SMT: cpu_smt_mask 对无 SMT 核返回自身），要么与 MC 相同（CLS），最终经折叠后只剩 MC（span=0-3, flags=SD_SHARE_LLC）一层有效调度域。

2.4.5 运行时验证 — sysfs 直接读取拓扑数据

内核已将 cpu_topology[] 的所有字段导出到 sysfs，无需添加任何打印代码。在 QEMU 虚拟机内直接读文件即可验证上述所有结论：

# 每个 CPU 的 topology ID
for cpu in 0 1 2 3; do
    echo "=== cpu$cpu ==="
    cat /sys/devices/system/cpu/cpu$cpu/topology/core_id
    cat /sys/devices/system/cpu/cpu$cpu/topology/cluster_id
    cat /sys/devices/system/cpu/cpu$cpu/topology/physical_package_id
done

预期输出：

cpu0: core_id=0  cluster_id=0  package_id=0
cpu1: core_id=1  cluster_id=0  package_id=0
cpu2: core_id=2  cluster_id=0  package_id=0
cpu3: core_id=3  cluster_id=0  package_id=0
# 各层级 sibling cpumask
cat /sys/devices/system/cpu/cpu0/topology/thread_siblings_list     # 预期: 0       (无 SMT)
cat /sys/devices/system/cpu/cpu0/topology/core_siblings_list       # 预期: 0-3     (同 package)
cat /sys/devices/system/cpu/cpu0/topology/cluster_cpus_list        # 预期: 0-3     (同 cluster)
cat /sys/devices/system/cpu/cpu0/topology/package_cpus_list        # 预期: 0-3     (同 package)

# 验证 capacity 全对称
cat /sys/devices/system/cpu/cpu*/cpu_capacity                      # 预期: 1024 × 4

这些 sysfs 文件直接对应 cpu_topology[] 的字段——core_siblings_list 就是 cpu_topology[cpu].core_sibling 的字符串表示，physical_package_id 就是 cpu_topology[cpu].package_id。读出结果与 §2.4.3 表格完全一致即可验证。

若想看到内核内部的日志，store_cpu_topology() 中已有 pr_debug（arch_topology.c:871），在启动参数中加 loglevel=8 或通过 dynamic_debug 启用即可：

# 运行时方式:
mount -t debugfs none /sys/kernel/debug

2.3 ARM64 算力解析

ARM64 big.LITTLE/DynamIQ 体系的关键在于 CPU capacity（算力）——从 DT 的 capacity-dmips-mhz 属性解析并归一化：

// Device Tree 中每个 CPU 节点声明其 DMIPS/MHz 值：
cpu@0 { capacity-dmips-mhz = <1024>; };  // 大核 (Cortex-X4)
cpu@5 { capacity-dmips-mhz = <386>; };   // 小核 (Cortex-A520)

解析函数 topology_parse_cpu_capacity()（位于 drivers/base/arch_topology.c）读取该值，经过 topology_normalize_cpu_scale() 归一化到 SCHED_CAPACITY_SCALE（1024）范围内：

// 归一化公式：
// cpu_capacity = (raw_capacity * SCHED_CAPACITY_SCALE) / max_raw_capacity
//
// 结果：大核 capacity = 1024, 小核 capacity ≈ 386

这个 capacity 值被写入 rq->cpu_capacity（Layer 2），后续负载均衡和EAS 任务放置都依赖它来区分"大核够不够用"和"小核是否过载（misfit）"。

三、Layer 2: Per-CPU 运行队列

核心问题： "这个 CPU 上有什么？" — 每个 CPU 的一个 rq 实例是所有调度活动的"锚点"。

3.1 struct rq 核心字段

定义位于 kernel/sched/sched.h:1119：

struct rq {
    raw_spinlock_t    __lock;         // rq 自旋锁，所有调度操作都需持锁
    unsigned int      nr_running;     // rq 上的可运行任务总数

    struct cfs_rq     cfs;            // 内嵌的 CFS 就绪队列
    struct rt_rq      rt;             // 内嵌的 RT 就绪队列
    struct dl_rq      dl;             // 内嵌的 DL 就绪队列

    struct task_struct *donor;        // 当前调度上下文 (donor)
    struct task_struct *idle;         // idle 任务 (per-CPU)
    struct task_struct *stop;         // stop 任务 (per-CPU, CPU 热插拔用)

    struct root_domain    *rd;        // → 所属 root_domain (Layer 4)
    struct sched_domain   *sd;        // → 所属调度域链表 (Layer 4)
    unsigned long   cpu_capacity;     // CPU 算力值 (ARM64 big.LITTLE 关键)

    int    cpu;                       // 所属 CPU 编号
    int    online;                    // 是否在线

    u64    clock;                     // rq 时钟
    u64    clock_task;                // 任务运行时间时钟
    u64    clock_pelt;                // PELT 负载跟踪时钟

    unsigned long  nr_uninterruptible;// 不可中断睡眠任务数
    atomic_t       nr_iowait;         // 等待 IO 的任务数

    struct list_head leaf_cfs_rq_list; // 该 CPU 上所有叶子 cfs_rq 的链表
};

rq → rd → sd 指针链

每个 rq 通过两个指针向上连接到 Layer 4 的拓扑抽象：

  • rq->rd：指向 root_domain，决定了"这个 CPU 属于哪个调度隔离域"（cpuset 会创建独立的 rd）
  • rq->sd：指向该 CPU 对应的最低层（最底层）调度域的链表头，通过 sd->parent 向上遍历可覆盖所有层级

3.2 内嵌三层队列

rq 不存储指向各调度类队列的指针，而是直接内嵌它们：

内嵌成员 类型 含义
rq->cfs struct cfs_rq 根 CFS 就绪队列。内部包含 EEVDF 红黑树（tasks_timeline），存储按 vruntime 排序的 sched_entity
rq->rt struct rt_rq 根 RT 就绪队列。内部包含按优先级分组的 bitmap + 链表
rq->dl struct dl_rq 根 Deadline 就绪队列。内部包含红黑树（按 deadline 排序）

这种"内嵌"而非"指针引用"的设计避免了额外的间接访问，cache 友好。在有 cgroup 的情况下（CONFIG_FAIR_GROUP_SCHED），task_group 还会额外分配 per-CPU 的 cfs_rq，形成层级树。

四、Layer 3: 调度实体

核心问题： "谁可以被调度？" — 将"可调度性"从 task_struct 中抽离为独立结构。

4.1 三类调度实体

每个 task_struct 内嵌了全部三种调度实体，任务根据其调度策略使用对应的实体：

实体类型 task_struct 中的字段 对应调度类
struct sched_entity task_struct.se CFS (SCHED_NORMAL, SCHED_BATCH, SCHED_IDLE)
struct sched_rt_entity task_struct.rt RT (SCHED_FIFO, SCHED_RR)
struct sched_dl_entity task_struct.dl Deadline (SCHED_DEADLINE)

sched_entity 的核心字段（定义在 include/linux/sched.h）：

struct sched_entity {
    struct load_weight    load;          // 负载权重（决定时间片比例）
    struct rb_node        run_node;      // EEVDF 红黑树节点
    u64                   vruntime;      // 虚拟运行时间（红黑树 key）
    u64                   deadline;      // EEVDF 期限
    u64                   min_vruntime;  // EEVDF 最小虚拟截止时间
    struct sched_avg      avg;           // PELT 负载跟踪（util_avg, load_avg）
};

4.2 实体与 task_group 的关系

实体的关键设计在于它不仅代表任务，也代表任务组：

  • 每个 task_group 拥有 per-CPU 的 struct sched_entity **se 指针数组——该 se 是 task_group 在某个 CPU 上的"代理"，参与该 CPU 的 CFS 调度
  • task 的 se 入队到其所属 task_group 的 cfs_rq 中，而 task_group 的 se 入队到父 task_group 的 cfs_rq 中，形成层级嵌套
  • 最终，所有可运行实体通过 rq->cfs.tasks_timeline（EEVDF 红黑树）统一排序

五、Layer 4: 调度域与根域

核心问题： "CPU 之间如何组织？" — 为负载均衡和任务放置提供拓扑感知的 CPU 分组。

5.1 struct sched_domain

定义位于 include/linux/sched/topology.h:73。每个调度域代表一个 CPU 集合，层叠形成父子层级：

struct sched_domain {
    struct sched_domain *parent;      // 上级域（覆盖更大范围）
    struct sched_domain *child;       // 下级域（覆盖更小范围）
    struct sched_group *groups;       // 调度组循环链表（负载均衡的基本单位）
    unsigned long span[];             // 本域覆盖的 CPU 位图（变长数组，紧邻结构体分配）
    int flags;                        // SD_BALANCE_*, SD_SHARE_* 等标志位
    int level;                        // 层级编号

    unsigned long min_interval;       // 最小均衡间隔 (ms)
    unsigned long max_interval;       // 最大均衡间隔 (ms)
    unsigned int  imbalance_pct;      // 不平衡阈值 (默认 117，即 17% 差异)
    unsigned int  busy_factor;        // 忙时均衡频率衰减因子
    unsigned int  cache_nice_tries;   // 保留缓存热任务的尝试次数

    unsigned long last_balance;       // 上次做均衡的时间戳 (jiffies)
    unsigned int  nr_balance_failed;  // 连续均衡失败次数
};

关键 sd_flags 释义

标志含义
SD_BALANCE_NEWIDLECPU 进入 idle 时触发负载均衡
SD_BALANCE_EXECexec() 时触发负载均衡
SD_BALANCE_FORKfork() 时触发负载均衡
SD_BALANCE_WAKE唤醒时触发负载均衡（通常仅在最高层设置）

5.2 struct sched_group

定义位于 kernel/sched/sched.h:2095。调度域内部由调度组环路组成——每个组是负载均衡中"迁移任务"的基本单位：

struct sched_group {
    struct sched_group *next;              // 循环链表的下一个组
    atomic_t   ref;                        // 引用计数
    unsigned int   group_weight;           // 组内 CPU 数量
    struct sched_group_capacity *sgc;      // → 组的算力描述
    int        asym_prefer_cpu;            // 非对称算力下优先使用的 CPU
    unsigned long  cpumask[];              // 组内 CPU 位图（变长数组）
};

sched_group_capacity 是附着在每个 group 上的辅助结构，记录该组的总算力和当前利用率，供 find_busiest_group() 判断哪个组需要"拉"任务。

5.3 struct root_domain

定义位于 kernel/sched/sched.h:985。root_domain 是调度域层级的"顶层容器"，也是 cpuset 隔离的边界：

struct root_domain {
    atomic_t     refcount;                // 引用计数 (rq 引用 + 外部引用)
    cpumask_var_t span;                   // 管辖的所有 CPU
    cpumask_var_t online;                 // 其中在线的 CPU
    bool overloaded;                      // 是否有 CPU 的 rq 上多于一个可运行任务
    bool overutilized;                    // 是否有 CPU 利用率超过 tipping point (~80%)

    cpumask_var_t dlo_mask;               // DL 过载 CPU
    cpumask_var_t rto_mask;               // RT 过载 CPU
    struct dl_bw  dl_bw;                  // DL 带宽管理（全局准入控制）
    struct cpudl  cpudl;                  // DL 最早截止时间堆

    struct perf_domain *pd;               // → 性能域链表 (EAS 关键，ARM64 上至关重要)
};

rd->overutilized：EAS 的开关

overutilized 是 ARM64 EAS 路径的关键标志位。当某个 CPU 的利用率超过 80% tipping point 时，rd 被标记为 overutilized，后续的任务唤醒路径将跳过 EAS（find_energy_efficient_cpu() 直接返回 -1），回退到传统的负载均衡放置策略。EAS 只在系统非过载时生效，因为能耗优化的边际收益在系统繁忙时不足以弥补算力优先的损失。

六、Layer 5: 任务组与带宽控制

核心问题： "如何在任务集合之间分配 CPU 时间？" — cgroup 接口的调度后端。

6.1 struct task_group

定义位于 kernel/sched/sched.h:471：

struct task_group {
    struct cgroup_subsys_state css;           // cgroup 通用子系统状态

    struct sched_entity  **se;                // per-CPU CFS 调度实体指针数组
    struct cfs_rq        **cfs_rq;            // per-CPU CFS 运行队列指针数组
    unsigned long         shares;             // CPU 相对份额 (默认 NICE_0_LOAD=1024)

    struct sched_rt_entity **rt_se;           // per-CPU RT 调度实体指针数组
    struct rt_rq           **rt_rq;           // per-CPU RT 运行队列指针数组

    struct task_group     *parent;            // 父任务组
    struct list_head       siblings;          // 兄弟任务组链表
    struct list_head       children;          // 子任务组链表

    struct cfs_bandwidth   cfs_bandwidth;     // CFS 带宽限制 (cpu.max)
    struct rt_bandwidth    rt_bandwidth;      // RT 带宽限制
};

6.2 cgroup 层级调度模型

启用 CONFIG_FAIR_GROUP_SCHED 后，每个 cgroup cpu 子系统目录对应一个 task_group，形成树状层级。调度器按层级递归分配 CPU 时间：

                    root_task_group (shares=1024)
                     │        se (per-CPU 代理实体)
                     │
            ┌────────┼────────┐
            ▼                 ▼
      tg:A (shares=512)  tg:B (shares=512)
       │    se             │    se
       │                   │
   ┌───┴───┐           ┌───┴───┐
   ▼       ▼           ▼       ▼
 task1   task2       task3   task4
 (se)    (se)        (se)    (se)

在 CPU x 上的调度流程：

  1. EEVDF 从 rq->cfs.tasks_timeline 红黑树取出最左节点
  2. 如果该节点是 task_group 的 se（而非普通 task），则递归进入该 task_group 在 CPU x 上的 cfs_rq[x]，取出其内部红黑树的最左节点
  3. 重复直到遇到普通 task，完成 pick_next_task_fair()

带宽控制（cfs_bandwidth）以周期性定时器控制每个 task_group 的 CPU 时间配额（cpu.max = quota / period），超出配额的组被"节流（throttle）"——其所有 se 被移出红黑树，直到下一个周期刷新。

七、Layer 6: 调度类

核心问题： "按什么策略调度？" — 将调度策略封装为可插拔的类接口。

7.1 struct sched_class

定义位于 kernel/sched/sched.h:2398。这是整个调度子系统的策略抽象层，每个调度类实现一组函数指针：

struct sched_class {
    // == 入队/出队 ==
    void (*enqueue_task)(struct rq *rq, struct task_struct *p, int flags);
    bool (*dequeue_task)(struct rq *rq, struct task_struct *p, int flags);
    void (*yield_task)(struct rq *rq);

    // == 选下一个任务 ==
    struct task_struct *(*pick_next_task)(struct rq *rq);
    void (*put_prev_task)(struct rq *rq, struct task_struct *p, ...);
    void (*set_next_task)(struct rq *rq, struct task_struct *p, bool first);

    // == 任务放置（ARM64 上为 EAS 关键路径）==
    int  (*select_task_rq)(struct task_struct *p, int task_cpu, int flags);
    void (*migrate_task_rq)(struct task_struct *p, int new_cpu);
    void (*wakeup_preempt)(struct rq *rq, struct task_struct *p, int flags);

    // == CPU 热插拔 ==
    void (*rq_online)(struct rq *rq);
    void (*rq_offline)(struct rq *rq);

    // == 调度 tick ==
    void (*task_tick)(struct rq *rq, struct task_struct *p, int queued);
    void (*task_fork)(struct task_struct *p);
    void (*task_dead)(struct task_struct *p);

    // == 负载均衡 ==

    void (*update_curr)(struct rq *rq);   // 更新当前任务的 vruntime/runtime

7.3 调度类的优先级顺序

调度类按严格优先级排列（通过链接脚本将各 DEFINE_SCHED_CLASS 实例放入独立 section 并排序——高优先级先被检查）：

优先级 调度类 策略 典型用途
0 (最高)stop_sched_class强制抢占一切CPU 热插拔、RCU stall
1dl_sched_class最早截止时间优先 (EDF)实时音视频、硬实时工作负载
2rt_sched_class固定优先级 + 时间片轮转软实时应用
3fair_sched_classEEVDF (完全公平)所有普通任务
4 (最低)idle_sched_class仅 CPU 空闲时运行进入低功耗状态

每次 __schedule() → pick_next_task() 按此顺序遍历，第一个拥有可运行任务的类胜出。

八、ARM64 特有关键路径

核心问题： "ARM64 的调度与 x86 有什么不同？" — Energy-Aware Scheduling 和拓扑不对称性。

8.1 select_task_rq_fair 任务放置

定义位于 kernel/sched/fair.c:8566。这是任务唤醒时选择目标 CPU 的核心函数，ARM64 上的关键差异在步骤①：

select_task_rq_fair(p, prev_cpu, wake_flags)
  │
  ├── ① rd->overutilized == false？
  │       └── find_energy_efficient_cpu(p, prev_cpu)   ← EAS 路径 (ARM64 特有)
  │            遍历 perf_domain 中各 CPU:
  │            · 计算 如果把 p 放在此 CPU，总能耗增量
  │            · 选能耗增量最小且不造成算力过载的 CPU
  │            · 若找到 → 直接返回
  │
  ├── ② SD_WAKE_AFFINE 路径
  │       └── wake_affine(): 比较唤醒者 CPU 和任务前次 CPU
  │            通过负载和缓存热度权衡选哪个
  │
  └── ③ 快速路径：select_idle_sibling()
          ├── select_idle_capacity()  // 非对称算力 (ARM64)：找有空闲算力的 CPU
          ├── has_idle_core? → 优先选空闲核
          └── select_idle_cpu(): 在 LLC 域内扫描空闲 CPU

8.2 find_energy_efficient_cpu

定义位于 kernel/sched/fair.c:8368。EAS 的核心：

static int find_energy_efficient_cpu(struct task_struct *p, int prev_cpu)
{
    // 1. 遍历 rd->pd 链表上的每个性能域 (perf_domain)
    // 2. 对每个候选 CPU:
    //    a. 预测 p 放上后的 utilization (util + task_util(p))
    //    b. 查 EM (Energy Model) 频率-功耗表：根据 utilization 确定 OPP
    //    c. 计算 energy = power[OPP] * (util / capacity_of(OPP))
    //    d. 累计该性能域内其他受影响 CPU 的能耗变化
    // 3. 比较 prev_cpu 的能耗 vs 最佳候选 CPU 的能耗
    // 4. 如果节能超过 ~6% (migration margin)且不造成 overutilized
    //    → 返回最佳 CPU；否则返回 prev_cpu
}

EAS 启用条件（全部满足）：

  1. CONFIG_ENERGY_MODEL=y
  2. CONFIG_CPU_FREQ_GOV_SCHEDUTIL=y（schedutil cpufreq 调速器）
  3. 系统为非对称算力（big.LITTLE/DynamIQ）或者用户通过 sysfs 显式启用
  4. Energy Model 被成功注册并关联到 CPU
  5. 当前 root_domain 未被标记为 overutilized

8.3 perf_domain 与 Energy Model

性能域是 EAS 中将 CPU 分组为"共享同一性能级别"的最小单位：

root_domain
  └── .pd → perf_domain → perf_domain → ...
                 │
                 └── .em_pd → struct em_perf_domain (EM 框架提供)
                                 │
                                 ├── nr_perf_states   // 支持的 OPP 数量
                                 ├── table[]:           // 频率-功耗表
                                 │     { frequency, power, cost }
                                 └── cpus[]             // 该性能域内的 CPU 掩码

perf_domain 定义在 kernel/sched/sched.h:971，通过 pd_init()

（位于 kernel/sched/topology.c:342）从 EM 框架的 em_cpu_get(cpu) 获取 em_perf_domain 后构建。ARM64 平台通过 em_dev_register_perf_domain() 在 cpufreq 驱动初始化时注册 EM 数据。

8.4 算力与频率不变性

ARM64 调度器依赖三个 per-CPU 变体实现负载跟踪的频率/算力不变性：

Per-CPU 变量 来源 用途
rq->cpu_capacity DT capacity-dmips-mhz，归一化到 SCHED_CAPACITY_SCALE 负载均衡：判断 misfit，决定任务迁移方向（小核→大核）
capacity_freq_ref 架构/CPPC 提供 频率不变性标度参考值（最大频率下的 capacity）
arch_freq_scale cpufreq/CPPC 更新 当前运行频率相对于最大频率的缩放因子

通过 arch_scale_cpu_capacity(cpu) 返回归一化后的 CPU 最大算力。在 misfit 检测中，如果小核上的任务 util_avg 超过了小核的 capacity，该任务被标记为"misfit"，负载均衡器会将其主动迁移到大核。

以下展示从定时器 tick、任务唤醒到负载均衡的三条关键路径，标注每一层参与的函数和数据流向：

路径一：定时器 Tick → 调度决策

  │  [Layer 2: 获取当前 rq]
  └── fair_sched_class.task_tick()
        └── task_tick_fair()                // [Layer 6: 策略 — fair.c]
              └── update_curr_fair()         // 更新 curr->vruntime
              └── check_preempt_tick()       // vruntime 差超过 granularity?

                          │
                          ▼

  └── pick_next_task(rq)
        └── for_each_class(class)            // [Layer 6: 按优先级遍历]
              └── fair_sched_class.pick_next_task()
                    └── __pick_next_task_fair()  // [Layer 2-3: cfs_rq 红黑树]
                          └── pick_eevdf()       // 取 vruntime 最小的 sched_entity
  └── context_switch()                       // 架构相关的上下文切换

  └── fair_sched_class.select_task_rq()

              │

        └── load_balance(cpu, sd, ...)

十、总结

六层抽象的职责划分

层抽象结构核心问题ARM64 特质
6struct sched_class按什么策略调度？架构无关
5struct task_group如何在 cgroup 之间分配 CPU？架构无关
4sched_domain / sched_group / root_domainCPU 之间如何组织、均衡、放置？EAS 路径：perf_domain + Energy Model
CLS 层级：DynamIQ cluster
3struct sched_entity谁可以被调度？架构无关
2struct rqCPU 上有什么？cpu_capacity 体现非对称算力
1struct cpu_topology硬件长什么样？DT/ACPI 拓扑检测（非 CPUID）
capacity-dmips-mhz 算力解析
Energy Model 频率-功耗表

ARM64 调度子系统的设计遵循一个原则：硬件相关的差异尽可能封装在 Layer 1（拓扑描述）和 Layer 4（EAS 扩展）中，Layer 2/3/5/6 保持架构无关。这使得 CFS/EEVDF 的核心算法可以跨架构复用，而 ARM64 在可感知能耗和非对称算力的前提下，通过 find_energy_efficient_cpu 和 misfit 迁移机制实现最优的任务放置。

理解这个分层体系后，再去看具体的调度代码（如 enqueue_task_fair、load_balance 等），就能清晰地知道"这段代码操作的是哪一层的哪个数据结构"，从而快速定位问题。

本文基于 Linux 6.18.1，源码路径 kernel/sched/、arch/arm64/kernel/topology.c、drivers/base/arch_topology.c
