ARM64 bootmem_init 深度解析

从 memblock 到 buddy 分配器的交接：struct page、zone、CMA 是怎么建立的

1. bootmem_init 在启动流程中的位置

bootmem_init() 是 paging_init() 的下一步,也是 memblock 时代的「收官」动作。它在 setup_arch() 里位于 paging_init() 之后(arch/arm64/kernel/setup.c:344):

arm64_memblock_init();   // ① 解析 FDT，建立 memblock
paging_init();           // ② 建立线性映射 + 身份映射
...
unflatten_device_tree();
bootmem_init();          // ③ 建立 struct page + zone（本文主角）
kasan_init();            // ④ KASAN 影子内存（依赖 struct page 已就绪）

它的定位可以用一句话概括:把「内存」从 memblock 的粗粒度 region 描述,转化成 buddy 分配器所需的细粒度数据结构(struct page 数组 + zone 空闲链表)。

与 paging_init 的关系:paging_init 解决「能不能访问到内存」(建页表映射);bootmem_init 解决「怎么管理内存」(建 memmap + zone)。前者是后者的前提——分配 struct page 数组本身就需要通过线性映射访问。

2. bootmem_init 源码总览

完整源码(arch/arm64/mm/init.c:292):

void __init bootmem_init(void)
{
    unsigned long min, max;

    min = PFN_UP(memblock_start_of_DRAM());   // ① 起始 PFN
    max = PFN_DOWN(memblock_end_of_DRAM());   // ② 结束 PFN

    early_memtest(min << PAGE_SHIFT, max << PAGE_SHIFT);  // ③ 内存测试

    max_pfn = max_low_pfn = max;              // ④ 记录全局 PFN 边界
    min_low_pfn = min;

    arch_numa_init();                          // ⑤ NUMA 初始化

    arm64_hugetlb_cma_reserve();               // ⑥ 巨页 CMA（条件编译）
    kvm_hyp_reserve();                         // ⑦ KVM hyp 内存预留

    sparse_init();                             // ⑧ 分配 struct page 数组（memmap）
    zone_sizes_init();                         // ⑨ 建立 zone + free_area（buddy 骨架）

    dma_contiguous_reserve(arm64_dma_phys_limit);  // ⑩ 预留 CMA（32MB）

    arch_reserve_crashkernel();                // ⑪ crashkernel 预留

    memblock_dump_all();                       // ⑫ 打印最终 memblock 状态
}

每一步都承上启下,下面逐条展开。注意其中的顺序约束:注释里明确写了「sparse_init() 要从 memblock 分配内存,所以必须在固定预留之后」「arch_numa_init() 要先于 hugetlb_cma_reserve()」。

3. 逐步分析

3.1 计算 PFN 范围

min = PFN_UP(memblock_start_of_DRAM());   // 向上取整到页
max = PFN_DOWN(memblock_end_of_DRAM());   // 向下取整到页

从 memblock 的 DRAM 起止地址算出 页帧号(PFN) 范围。PFN_UP / PFN_DOWN 分别向上/向下对齐到页。这一步把「物理地址」换算成 buddy 系统里的基本单位「页号」。在本机 QEMU 上:DRAM 为 [0x40000000, 0x7fffffff],所以 min = 0x40000、max = 0x80000,共 0x40000 = 262144 页(正好对上日志里的 Total pages: 262144)。

3.2 early_memtest 内存测试

early_memtest(min << PAGE_SHIFT, max << PAGE_SHIFT);

如果命令行带了 memtest=...,这里会对 DRAM 做早期读写测试(检测坏内存)。默认(本机)不开启,是个 no-op。

3.3 arch_numa_init

初始化 NUMA 拓扑:解析 FDT/ACPI 里的 memory node,建立 node_data[]、node_online_map 等。单节点机器(本机 QEMU)会「Faking a node」——伪造一个覆盖全部内存的 node 0,对应日志:

NUMA: Faking a node at [mem 0x0000000040000000-0x000000007fffffff]
NODE_DATA(0) allocated [mem 0x7fdf9a00-0x7fdfc07f]

注意它必须在 sparse_init 之前:后面分配 struct page 需要知道每个页属于哪个 node。

3.4 各类预留（hugetlb CMA / KVM hyp）

arm64_hugetlb_cma_reserve();   // CONFIG_HUGETLB_PAGE && CONFIG_CMA 时
kvm_hyp_reserve();             // 预留 KVM 虚拟机监控器的物理内存

这两步是固定预留:提前用 memblock 划出巨页 CMA、KVM hypervisor 需要的内存。注释强调它们必须先于 sparse_init()——因为 sparse_init 自己也要从 memblock 分配 memmap,顺序乱了会互相抢占地址空间。

3.5 sparse_init 分配 struct page

sparse_init();   // 建立稀疏内存模型的 mem_section + struct page 数组

这是整个函数里最关键的一步:分配并初始化 struct page 数组(即 memmap)。每个物理页对应一个 struct page(本机 64 字节),buddy 分配器以后就是靠这些 struct page 里的 flags、_mapcount、lru 等字段来管理页的。

在本机 1GB RAM 上:262144 页 × 64B = 16MB 的 struct page 数组,日志里精确对应:

memblock_alloc_exact_nid_raw: 16777216 bytes align=0x200000 ... memmap_alloc+0x20/0x38
__memblock_reserve: [0x7ec00000-0x7fbfffff] ...   // 16MB @ 0x7ec00000

3.6 zone_sizes_init 建立 zone

源码(arch/arm64/mm/init.c:121):

static void __init zone_sizes_init(void)
{
    unsigned long max_zone_pfns[MAX_NR_ZONES] = {0};
    ...
    max_zone_pfns[ZONE_DMA]   = PFN_DOWN(arm64_dma_phys_limit);  // DMA 上限
    max_zone_pfns[ZONE_DMA32] = PFN_DOWN(dma32_phys_limit);      // DMA32 上限
    max_zone_pfns[ZONE_NORMAL] = max_pfn;                        // Normal 上限

    free_area_init(max_zone_pfns);   // ← 核心：建立 zone 结构与 free_area 链表
}

它算出每个 zone 的 PFN 上界,然后调 free_area_init() 建立 buddy 分配器的骨架——每个 zone 的 free_area[order] 空闲链表(此时还是空的)、zone->managed_pages、zone->present_pages 等元数据。对应日志:

Zone ranges:
  DMA      [mem 0x0000000040000000-0x000000007fffffff]
  DMA32    empty
  Normal   empty
Early memory node ranges
  node   0: [mem 0x0000000040000000-0x000000007fffffff]
Initmem setup node 0 [mem 0x0000000040000000-0x000000007fffffff]
本机 1GB 内存全部落在 DMA zone,所以 DMA32 / Normal 为空——这是 arm64 上「小内存机器」的典型现象。

3.7 dma_contiguous_reserve 预留 CMA

dma_contiguous_reserve(arm64_dma_phys_limit);

预留连续内存区(CMA),供 DMA、设备驱动后续分配大块连续物理内存。对应日志:

__memblock_reserve: [0x7cc00000-0x7ebfffff] ...   // 32MB
cma: Reserved 32 MiB at 0x000000007cc00000

3.8 arch_reserve_crashkernel

arch_reserve_crashkernel();   // 解析 crashkernel= 参数并预留 kdump 内存

如果命令行指定了 crashkernel=...,这里为 kdump 内核预留内存。本机没配,no-op。

3.9 memblock_dump_all

memblock_dump_all();   // 打印 memblock 最终状态

最后,如果开启了 memblock=debug(本机就开了),这里打印 memblock 的最终形态——也就是日志里的 MEMBLOCK configuration 段落(10 个 reserved region 那张表)。它标志着 memblock 时代的「账本」到此定格。

4. 关键区分：bootmem_init vs memblock_free_all

一个最常见的误解是「bootmem_init 把内存交给了 buddy」。实际上 并没有——它只是建好了数据结构(struct page + zone),真正的「释放」发生在更后面的 mm_core_init() → memblock_free_all()。

bootmem_init（arch 层）

  • 做什么：建 struct page 数组 + 建 zone 骨架
  • 空闲链表：此时 free_area[order] 还是空的
  • 位置：setup_arch() 内
  • 本质：准备「容器」

memblock_free_all（mm 层）

  • 做什么：把 memblock.memory 的空闲页真正加入 buddy 空闲链表
  • 空闲链表：__free_pages_core() 逐页挂进 free_area
  • 位置：start_kernel() → mm_core_init()（mm/mm_init.c:2706）
  • 本质：往容器里「装货」

memblock_free_all() 的实现(mm/memblock.c:2339):

void __init memblock_free_all(void)
{
    free_unused_memmap();              // 释放多余的 struct page
    reset_all_zones_managed_pages();   // 重置 zone 托管页计数
    pages = free_low_memory_core_early();  // ★ 把空闲页真正加入 buddy
    totalram_pages_add(pages);
}

真正把页挂进 free_area 的是 free_low_memory_core_early()。它遍历 memblock.memory 的空闲区间,对每个页调用 __free_pages_core(),设置 struct page 的 order、挂进对应 free_area[order] 链表。之后 mem_init() 打印那句:

Memory: 952884K/1048576K available (...)   // 对应 serial.logs [0.169305]
一句话记住:bootmem_init 建「骨架」,memblock_free_all 灌「血肉」。两者之间,系统处于「zone 已就绪、但 buddy 还没有任何空闲页」的过渡态。

几个能互相印证的交叉验证:

6. 总结表

核心结论

  1. bootmem_init 是「建骨架」:它把 memblock 的粗粒度 region,转成 buddy 需要的 struct page 数组 + zone 空闲链表结构。
  2. 顺序即依赖:NUMA → sparse(memmap) → zone → CMA → crashkernel → dump,每步都建立在前一步的基础上(注释里反复强调)。
  3. 交接点其实在 memblock_free_all:bootmem_init 之后 buddy 还「空着」,直到 mm_core_init → memblock_free_all 才真正把空闲页灌进去。
  4. 真实数据可交叉验证:Total pages × 64B = 16MB memmap、available + reserved = 总内存、CMA = 32MB,三组数字在日志里严丝合缝。
