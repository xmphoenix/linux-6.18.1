1. 调试环境整体架构

┌─────────────────────────────────────────────────────────────┐ │ launch.sh │ │ │ │ ┌─────────────────────┐ ┌──────────────────────────┐ │ │ │ QEMU 启动 │────▶│ gdb-multiarch 启动 │ │ │ │ -s -S │ │ ~/.gdbinit 自动加载： │ │ │ │ -kernel Image │ │ ① add-symbol-file │ │ │ │ nokaslr │ │ → 符号 @ 物理地址 │ │ │ │ QEMU_PID=$! │ │ ② 6 个断点 │ │ │ └─────────────────────┘ │ ③ target remote :1234 │ │ │ │ ④ TUI 自动开启 │ │ │ kill $QEMU_PID ◀────────────└──────────┬───────────────┘ │ │ (GDB quit 后自动清理) │ │ └─────────────────────────────────────────────────────────────┘

设计要点

  • QEMU -s -S: 开启 GDB stub 监听 :1234，CPU 暂停等待调试器连接
  • nokaslr: 禁用内核地址空间随机化，保证断点地址每次一致
  • $QEMU_PID: 捕获 QEMU 进程 PID，退出时精确 kill，不伤及其他 QEMU 实例
  • sleep 0.5: 等待 QEMU GDB stub 端口就绪后再启动 gdb-multiarch

踩过的坑

  • ❌ gdb (仅 x86_64 target) — 不支持 aarch64 架构
  • ✅ 改为 gdb-multiarch (支持 aarch64)
  • ❌ killall qemu-system-aarch64 — 可能误杀其他 QEMU 实例
  • ✅ 改为 kill $QEMU_PID 精确清理
  • ❌ 每次手动输入 target remote :1234
  • ✅ .gdbinit 中自动连接

2. vmlinux 虚拟地址 → 物理地址映射

核心问题

vmlinux 是 PIE (位置无关可执行文件)，所有符号链接在虚拟地址 0xffff80008xxxxxxx。
QEMU 用 -kernel Image 将内核加载到物理地址 0x40200000。
MMU 关闭期间，CPU 使用物理地址，因此 GDB 符号必须映射到物理地址才能正确匹配 PC 寄存器。

fix_vmlinux_head_entry.sh 转换公式

phys = (VMA_lower32 + 0x40200000 - 0x80000000) & 0xffffffff
     = virt - 0xffff800080000000 + 0x40200000
符号虚拟地址 (vmlinux)物理地址 (QEMU)ELF 绑定所在段
_text0xffff8000800000000x40200000GLOBAL.head.text
primary_entry0xffff80008143c0f00x4163c0f0GLOBAL.rodata.text
__primary_switch0xffff80008143c6580x4163c658LOCAL.rodata.text
record_mmu_state0xffff80008145a6480x4165a648LOCAL.init.text
preserve_boot_args0xffff80008145a69c0x4165a69cLOCAL.init.text
__primary_switched0xffff80008145a6cc0x4165a6ccLOCAL.init.text

生成的 add-symbol-file 命令：

add-symbol-file vmlinux -s .head.text  0x40200000 \
                        -s .text       0x40210000 \
                        -s .rodata     0x410f0000 \
                        -s .rodata.text 0x41637800 \
                        -s .init.text  0x41650000 \
                        -s .init.data  0x41738000
⚠ preserve_boot_args 是 LOCAL 符号（由 SYM_CODE_START_LOCAL 定义），GDB 无法通过名称找到它，必须使用地址断点: b *0x4165a69c

3. head.S 执行流程（物理地址视角）

CPU 上电复位 │ ▼ 0x40000000 ┌ QEMU Bootloader (6 条指令) ──────────────────┐ │ ldr x0, =DTB ; x0 = 0x48000000 │ │ mov x1/x2/x3, xzr ; 清零 │ │ ldr x4, =entry ; x4 = 0x40200000 │ │ br x4 ; 跳转到内核 │ └───────────────────────────────────────────────┘ │ br x4 ▼ 0x40200000 ┌ _text ───────────────────────────────────────┐ ← BP1 (GLOBAL) │ efi_signature_nop │ │ b primary_entry │ └──────────────────────────────────────────────┘ │ b primary_entry (这条跳转跨了 ~20MB) ▼ 0x4163c0f0 ┌ primary_entry ─────────────────────────────┐ ← BP2 (GLOBAL) │ bl record_mmu_state ───▶ 0x4165a648 BP3 │ │ bl preserve_boot_args ───▶ 0x4165a69c BP4 │ ★ 调试目标 │ adrp x1, early_init_stack │ │ mov sp, x1 │ │ adrp x0, __pi_init_idmap_pg_dir │ │ mov x1, xzr │ │ bl __pi_create_init_idmap │ │ ... 创建 identity mapping ... │ │ ... 无效化/清理 D-cache ... │ └─────────────────────────────────────────────┘ │ ▼ 0x4163c658 __primary_switch ← BP6 (LOCAL, MMU 即将开启) │ (MMU ON — 此后地址切换到虚拟地址) ▼ 0x4165a6cc __primary_switched → start_kernel → 内核 C 代码世界
💡 所有 6 个断点均配置了 commands 块：silent 抑制默认消息，printf 打印上下文信息，不调用 continue，因此 GDB 会在每个断点处停下来等待用户操作。

4. preserve_boot_args 逐条指令分析 ★

源码 (head.S:170-185)

SYM_CODE_START_LOCAL(preserve_boot_args)
    mov     x21, x0              // x21 = FDT
    adr_l   x0, boot_args        // x0 = &boot_args
    stp     x21, x1, [x0]        // boot_args[0]=x21(FDT)
                                  // boot_args[1]=x1
    stp     x2, x3, [x0, #16]    // boot_args[2]=x2
                                  // boot_args[3]=x3
    cbnz    x19, 0f   // MMU was on? skip
    dmb     sy         // memory barrier
    add     x1, x0, #0x20
    b       dcache_inval_poc     // tail call
0:  str_l   x19, mmu_enabled_at_boot, x0
    ret
SYM_CODE_END(preserve_boot_args)

指令布局 & 断点位置

偏移物理地址指令
+0x000x4165a69cmov x21, x0 BP4
+0x040x4165a6a0adrp x0, boot_args
+0x080x4165a6a4add x0, x0, #lo12
+0x0C0x4165a6a8stp x21, x1, [x0]
+0x100x4165a6acstp x2, x3, [x0, #16]
+0x140x4165a6b0cbnz x19, 0f BP5
+0x180x4165a6b4dmb sy
+0x1C0x4165a6b8add x1, x0, #0x20
+0x200x4165a6bcb dcache_inval_poc

函数功能

保存 bootloader 传入的 4 个参数 (x0~x3) 到全局数组 boot_args[]。x0 保存的是 FDT (设备树) 物理地址，是内核后续解析硬件的关键入口。

两条路径

  • x19 == 0 (MMU off): 执行 D-cache 无效化尾调用
  • x19 != 0 (MMU on): 记录 mmu_enabled_at_boot 标志并返回

5. QEMU ARM64 virt 机器内存布局

0x40000000 ┌──────────────────────────────────────┐ │ QEMU Bootloader (6 条指令，~40 字节) │ ← 源码: hw/arm/boot.c │ ldr x0, =DTB ; → 0x48000000 │ bootloader_aarch64[] │ mov x1, xzr │ │ mov x2, xzr │ │ mov x3, xzr │ │ ldr x4, =entry ; → 0x40200000 │ │ br x4 │ 0x40000028 ├──────────────────────────────────────┤ │ │ │ ... 全零 (~2044KB) ... │ ← 2MB 对齐带来的间隙， │ │ 不是"预留空间" 0x40200000 ├──────────────────────────────────────┤ │ kernel Image (_text) │ ← ARM64 2MB 对齐要求 │ efi_signature_nop │ │ b primary_entry │ │ .quad 0 ; text_offset = 0 │ │ le64sym _kernel_size_le │ │ le64sym _kernel_flags_le │ │ ... │ 0x48000000 ├──────────────────────────────────────┤ │ DTB (Device Tree Blob) │ ← RAM base + 128MB │ 魔数: 0xd00dfeed │ QEMU 在此放置硬件拓扑 │ 内容: CPU/内存/外设描述 │ └──────────────────────────────────────┘

为什么内核加载在 0x40200000 而不是 0x40000000？

内核 text_offset = 0 → QEMU: 0 < 4KB ? → + 2MB (ARM64 2MB 对齐) → 加载到 0x40200000

ARM64 内核要求加载到 2MB 对齐的地址。内核的 text_offset = 0 表示"随便放，由 bootloader 决定"。QEMU 检测到 0 < 4KB (会覆盖 bootloader)，于是加上 2MB 对齐到下一个边界，得到 0x40000000 + 0x200000 = 0x40200000。中间 2MB-4KB 几乎是全零，纯粹是 2MB 对齐的副产品。

6. QEMU Bootloader 源码 & GDB 验证

QEMU 源码 (hw/arm/boot.c:47-59)

static const ARMInsnFixup
bootloader_aarch64[] = {
   { 0x580000c0 }, // ldr x0, arg
   { 0xaa1f03e1 }, // mov x1, xzr
   { 0xaa1f03e2 }, // mov x2, xzr
   { 0xaa1f03e3 }, // mov x3, xzr
   { 0x58000084 }, // ldr x4, entry
   { 0xd61f0080 }, // br  x4
   { 0, FIXUP_ARGPTR_LO },     // DTB 低 32 位
   { 0, FIXUP_ARGPTR_HI },     // DTB 高 32 位
   { 0, FIXUP_ENTRYPOINT_LO }, // 内核入口低 32 位
   { 0, FIXUP_ENTRYPOINT_HI }, // 内核入口高 32 位
   { 0, FIXUP_TERMINATOR }
};

执行流程

  1. CPU 上电，PC = 0x40000000，开始执行 bootloader
  2. ldr x0, [pc, #24] — 从 PC+24 (即 0x40000018) 加载 DTB 地址到 x0
  3. mov x1/x2/x3, xzr — 将 x1~x3 清零 (Linux boot protocol 要求)
  4. ldr x4, [pc, #16] — 从 PC+16 (即 0x40000020) 加载内核入口地址到 x4
  5. br x4 — 无条件跳转到内核 (_text @ 0x40200000)
Fixup 数据在 QEMU 启动时动态填充：DTB 地址 = 0x48000000，内核入口 = 0x40200000

在 GDB 中逐步验证 (3 个步骤)

步骤 1 — 反汇编 bootloader 指令

(gdb) x/6i 0x40000000

预期输出：

0x40000000:  ldr  x0, 0x40000018     ; x0 = DTB 地址 (从 offset 0x18 加载)
0x40000004:  mov  x1, xzr            ; x1 = 0
0x40000008:  mov  x2, xzr            ; x2 = 0
0x4000000c:  mov  x3, xzr            ; x3 = 0
0x40000010:  ldr  x4, 0x40000020     ; x4 = 内核入口地址 (从 offset 0x20 加载)
0x40000014:  br   x4                 ; 跳转到内核

步骤 2 — 验证指令编码

(gdb) x/6xw 0x40000000

预期匹配 QEMU 源码中的编码：

步骤 3 — 验证 fixup 数据 (紧跟指令之后)

8. GDB 脚本踩坑记录

#问题现象根因修复
1 gdb 不支持 aarch64 Target description specified unknown architecture "aarch64"
Truncated register 37 in remote 'g' packet		 Ubuntu gdb 包只编译了 x86_64 target 改用 gdb-multiarch
2 define 内嵌 commands/end 块 所有断点、符号加载、target remote 均未执行，GDB 直接进入交互提示符 GDB 解析器将 commands 块的 end 误匹配为外层 define 的终止符，导致整个 define 被截断 把 if 块内只放简单命令；断点的 commands 块放到 .gdbinit 顶层
3 define 内嵌双层 if/else/end memins / memdump 命令提示 Undefined command 外层 define/end 与内层 if/else/end 嵌套导致解析冲突 用 "default-then-override" 模式消除内层 else
4 GDB 退出后 QEMU 进程残留 退出 GDB 后 QEMU 仍在后台运行，占用 1234 端口 killall qemu-system-aarch64 不够精确，且可能误杀 kill $QEMU_PID 精确清理 + hook-quit disconnect

GDB 解析器核心限制

核心规则：define ... end 内部不能包含任何其他以 end 结尾的块（commands、if/else、while），否则 define 会被第一个 end 截断。

解决方案：将所有 GDB 命令块放在 .gdbinit 顶层（不嵌套在 define 内），使用 Python 控制条件分支。
