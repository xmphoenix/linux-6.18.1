2. ARM64 内存拓扑类型

定义：内存拓扑（Memory Topology）描述的是系统中 CPU 与物理内存之间的距离关系——即哪些 CPU 与哪些内存在物理上更近、访问延迟更低。它回答的问题是：
"这块内存属于谁？哪个 CPU 访问它最快？"

内核依据拓扑关系将内存划分为若干 node（节点），在分配内存时优先选择距当前 CPU 最近的 node，以最大化带宽、最小化延迟（NUMA-aware 分配）。

内存拓扑描述处理器与内存之间的访问关系，ARM64 支持以下两种类型：

2.1 UMA（Uniform Memory Access）

所有 CPU 访问所有内存的延迟相同，内核视为单一 node 0。

CPU0  CPU1  CPU2  CPU3
  └────┴────┴────┘
         │
      统一内存总线
         │
       DRAM
  • CONFIG_NUMA 未开启时的默认模式
  • 内核只有 NODE_DATA(0) 一个节点
  • 典型平台：单 socket 嵌入式系统、开发板

2.2 NUMA（Non-Uniform Memory Access）

不同 CPU 访问不同内存区域的延迟不同，内存按访问延迟分组为若干 node。

  Socket 0                Socket 1
┌─────────────┐        ┌─────────────┐
│  CPU0 CPU1  │◄─慢───►│  CPU2 CPU3  │
│   Node 0    │        │   Node 1    │
│   Memory    │        │   Memory    │
└─────────────┘        └─────────────┘
   本地 10ns               跨节点 30ns
  • CONFIG_NUMA 开启
  • 每个节点有独立 pg_data_t（NODE_DATA(nid)）
  • ARM64 通过 ACPI SRAT 表或 Device Tree numa-node-id 描述拓扑
  • 典型平台：多 socket ARM64 服务器（如 Ampere、Kunpeng、Neoverse）

2.3 NUMA 距离矩阵

节点间访问代价由 ACPI SLIT 表或 DT distance-matrix 属性提供：

        Node0  Node1  Node2
Node0 [  10     20     30  ]
Node1 [  20     10     20  ]
Node2 [  30     20     10  ]
  • LOCAL_DISTANCE = 10（同节点本地访问）
  • 跨节点距离通常为 20、30、40…
  • 内核用此矩阵构建 zonelist 备用节点回退顺序

3. NUMA 详解

定义：NUMA（Non-Uniform Memory Access，非一致性内存访问）是一种硬件内存拓扑模型，也是内核对应的软件管理框架。

- 硬件层面：多 socket 系统中每个 socket 拥有本地内存，CPU 访问本地内存比访问远端 socket 的内存延迟更低、带宽更大。
- 软件层面：内核将物理内存按 node 分组，每个 node 用 pg_data_t 描述，分配器优先从当前 CPU 所在 node 取页，同时维护节点间距离矩阵（SLIT/distance-matrix）用于回退决策。

NUMA 描述的核心问题：
1. 内存段 [start_pfn, end_pfn) 属于哪个 node？
2. CPU x 属于哪个 node？
3. node a 到 node b 的访问距离是多少？

3.1 设计思想

NUMA（Non-Uniform Memory Access）将物理内存按访问延迟分组为若干 node。
内核优先从当前 CPU 所在的本地节点分配内存，以减少跨节点访问延迟。

  Socket 0                Socket 1
┌─────────────┐        ┌─────────────┐
│  CPU0 CPU1  │◄─慢───►│  CPU2 CPU3  │
│   Node 0    │        │   Node 1    │
│   Memory    │        │   Memory    │
└─────────────┘        └─────────────┘
   本地 10ns               跨节点 30ns

3.4 ARM64 初始化路径选择

void __init arch_numa_init(void)
{
    if (!numa_off) {
        // ACPI 平台（x86 风格服务器）
        if (!acpi_disabled && !numa_init(arch_acpi_numa_init))
            return;
        // DT 平台（ARM64 典型路径）
        if (acpi_disabled && !numa_init(of_numa_init))
            return;
    }
    // 兜底：单节点 dummy 模式
    numa_init(dummy_numa_init);
}

3.5 NUMA 内存分配策略

用户态通过 mbind() / set_mempolicy() 系统调用，内核通过 mm/mempolicy.c 实现以下策略：

策略 宏定义 行为
默认 MPOL_DEFAULT 本地节点优先，不够再按 zonelist 顺序回退
绑定 MPOL_BIND 只从指定节点集合分配，失败则 OOM
交织 MPOL_INTERLEAVE 跨节点轮询分配，适合大数据均衡访问
优先 MPOL_PREFERRED 优先指定节点，失败后允许回退其他节点
本地 MPOL_LOCAL 强制使用当前运行 CPU 所在节点 
// 内核内部分配时的 NUMA 感知
alloc_pages_node(nid, gfp_mask, order)  // 指定节点
alloc_pages(gfp_mask, order)            // 当前节点（默认）

4. 物理内存模型

定义：物理内存模型（Physical Memory Model）描述的是内核如何组织和索引所有物理内存页，即建立从物理页帧号（PFN）到 struct page 描述符的映射关系。

它回答的问题是：
"给定一个物理地址（或 PFN），如何快速找到对应的 struct page？反之，给定 struct page *，如何得到它的物理地址？"

选择哪种模型取决于系统物理地址空间的连续性：
- 地址空间连续 → FLATMEM（简单线性数组）
- 地址空间稀疏/有大量空洞 → SPARSEMEM（ARM64 实际情况）

物理内存模型解决的问题：如何将物理页帧号（pfn）映射到 struct page。

4.1 三种模型对比

模型 ARM64 支持 特点
FLATMEM ✗ 全局线性 mem_map[] 数组；要求内存完全连续；ARM64 不使用
DISCONTIGMEM ✗ 每节点一个 mem_map[]；已废弃，被 SPARSEMEM 替代
SPARSEMEM ✓ 按 section（128MB）分段管理；支持内存热插拔和稀疏地址
SPARSEMEM_VMEMMAP ✓ 默认 在 SPARSEMEM 基础上用 vmemmap 虚拟映射，pfn→page 为 O(1)

ARM64 强制使用 SPARSEMEM_VMEMMAP，由 arch/arm64/Kconfig 中 select SPARSEMEM_VMEMMAP 决定。

4.2 模型演进关系

FLATMEM          — 简单但要求内存连续
    │ 无法处理稀疏地址
    ▼
DISCONTIGMEM     — 按节点分段，但管理粗糙（已废弃）
    │ 需要更细粒度
    ▼
SPARSEMEM        — 按 128MB section 管理，支持热插拔
    │ pfn→page 需要两次间接寻址，有性能开销
    ▼
SPARSEMEM_VMEMMAP — vmemmap 直接映射，pfn→page 为 O(1)，ARM64 默认

4.3 SPARSEMEM_VMEMMAP 的性能优势

// FLATMEM（仅供参考）
#define pfn_to_page(pfn)  (mem_map + (pfn))          // O(1) 但要求连续

// SPARSEMEM（无 vmemmap）
#define pfn_to_page(pfn)  section_mem_map 间接两跳   // 有开销

// SPARSEMEM_VMEMMAP（ARM64 实际）
#define pfn_to_page(pfn)  (vmemmap + (pfn))          // O(1)，等效 FLATMEM 性能

5. SPARSEMEM_VMEMMAP 详解

定义：SPARSEMEM_VMEMMAP 是 Linux 内核在 SPARSEMEM 基础上的优化变体，是 ARM64 唯一使用的物理内存模型实现。

- SPARSEMEM：将物理地址空间按固定大小（128MB 为一个 section）切分，每段独立存在，天然支持稀疏地址和内存热插拔，但 pfn → struct page 需要两次间接寻址，有性能损耗。
- VMEMMAP 扩展：通过在内核虚拟地址空间中预留一段连续区域 vmemmap，将所有 section 的 struct page 数组虚拟地址连续地映射进来，使得 pfn → struct page 退化为一次加法，性能与 FLATMEM 相当。

SPARSEMEM_VMEMMAP 描述的核心内容：
1. 物理地址空间被切分为哪些 section？每个 section 对应的 struct page 数组在哪里？
2. vmemmap[pfn] → 直接寻址任意物理页的描述符（O(1)）
3. 哪些 section 存在（SECTION_MARKED_PRESENT），哪些是空洞？

5.1 设计思想

ARM64 物理地址空间存在大量空洞（MMIO、固件保留等），无法用线性数组表示所有 struct page。

SPARSEMEM 将物理地址空间切分为固定大小的 section（默认 128MB），每个 section 独立存在。
VMEMMAP 在此基础上将所有 struct page 映射到一段连续虚拟地址区域，实现 O(1) 的 pfn → page 转换。

物理地址（有空洞）             vmemmap 虚拟地址（连续）
┌──────────┐                 ┌──────────────────────┐
│ section0 │ ──────────────► │ struct page[0..N]    │
├──────────┤                 ├──────────────────────┤
│  (空洞)  │   不映射        │ struct page[N+1..M]  │
├──────────┤                 ├──────────────────────┤
│ section1 │ ──────────────► │ ...                  │
└──────────┘                 └──────────────────────┘
                                      ↑
                                  vmemmap 基址
                          pfn → &vmemmap[pfn]  O(1)

5.2 关键数据结构

mem_section（include/linux/mmzone.h）

struct mem_section {
    unsigned long section_mem_map;
    // 低位存标志位（SECTION_MARKED_PRESENT 等）
    // 高位指向该 section 的 struct page 基址（vmemmap 模式下不直接用）

    struct mem_section_usage *usage; // pageblock 迁移类型位图
};

// 全局二维数组（稀疏两级索引）
extern struct mem_section mem_section[NR_SECTION_ROOTS][SECTIONS_PER_ROOT];

// section 大小：PAGES_PER_SECTION = 1 << (SECTION_SIZE_BITS - PAGE_SHIFT)
// ARM64 默认：SECTION_SIZE_BITS = 27，即每 section = 128MB

struct page（include/linux/mm_types.h）

每个物理页对应一个 struct page（40~64 字节），通过 vmemmap 连续排列：

struct page {
    unsigned long flags;        // PG_locked / PG_dirty / PG_uptodate ...
    union {
        struct { // 匿名页/文件页
            struct list_head lru;
            struct address_space *mapping;
            pgoff_t index;
        };
        struct { // Buddy System 空闲页
            unsigned long private; // order
        };
        struct { // slab 页
            struct kmem_cache *slab_cache;
            void *freelist;
        };
    };
    atomic_t    _refcount;
    atomic_t    _mapcount;
    // ...
};

vmemmap（ARM64 虚拟地址布局）

vmemmap 基址（ARM64 48-bit VA，4K页）：
  VMEMMAP_START = 0xFFFFFFBDC0000000（示例）

pfn → struct page：
  page = vmemmap + pfn * sizeof(struct page)
  即：vmemmap[pfn]

struct page → pfn：
  pfn = (page - vmemmap) / sizeof(struct page)
  即：page - vmemmap

5.4 vmemmap 建立算法（ARM64）

sparse_init()
    └── sparse_init_nid()          // 按 node 初始化
            └── sparse_mem_map_populate()
                    └── vmemmap_populate(start, end, nid)
                            // ARM64 实现：
                            // 1. 按 PMD/PUD 对齐尝试用大页（2MB）映射
                            // 2. 不对齐则退回 4KB 页映射

6. ARM64 虚拟地址空间与页大小

6.1 虚拟地址空间布局（48-bit，4K 页）

6.1.1 为什么分「用户」和「内核」两半

ARM64 用 两个独立的基址寄存器分别翻译用户态和内核态的地址：

TTBR0_EL1 → 用户空间页表（进程自己的 pgd）
TTBR1_EL1 → 内核空间页表（swapper_pg_dir，所有进程共享）

判断规则只看最高位 bit[63]：
  bit[63] = 0  → 用户地址，走 TTBR0
  bit[63] = 1  → 内核地址，走 TTBR1

这是 ARM64 与 x86 最大的不同：x86 用户和内核共用一套页表（内核映射塞在用户页表的高地址区），而 ARM64 用两套基址寄存器天然隔离，切换进程时只需改 TTBR0，内核页表始终不变。

6.1.2 完整地址布局（含精确地址值）

48-bit / 4K 页（VA_BITS=48，无 KASAN）下，全 64 位虚拟地址空间被切成三大段：

0xFFFF_FFFF_FFFF_FFFF ───────────────────────────── 内核空间顶
  Fixmap（固定映射）        0xFFFF_FFFF_FF80_0000 起，8MB   ← FIXADDR_TOP
  PCI I/O 空间             0xFFFF_FFFF_C080_0000 起，16MB
  vmemmap（struct page 映射）0xFFFF_FDFF_C000_0000 起，2TB
  vmalloc / ioremap 区域    动态（内核映像之上，见下）
  kernel image             0xFFFF_8000_8000_0000 起   ← KIMAGE_VADDR
  modules 区域             0xFFFF_8000_0000_0000 起，2GB
  ───────────────────────────────────────────────
  Linear Map（线性映射）     0xFFFF_0000_0000_0000     ← PAGE_OFFSET
                           ~ 0xFFFF_8000_0000_0000   ← PAGE_END（128TB）
0xFFFF_0000_0000_0000 ───────────────────────────── 内核空间底

        （非规范地址空洞，访问即 fault）

0x0000_FFFF_FFFF_FFFF ───────────────────────────── 用户空间顶
  用户空间                 0x0000_0000_0000_0000
                           （栈向下增长 / 堆向上增长）
0x0000_0000_0000_0000 ───────────────────────────── 用户空间底

规范地址（canonical address）规则：48-bit 有效位意味着 bit[63:48] 必须全为 0（用户）或全为 1（内核），否则是「非规范地址」，硬件直接报 translation fault。中间那段 `0x0000_FFFF_FFFF_FFFF ~ 0xFFFF_0000_0000_0000` 的巨大空洞就是因此产生的——虽然物理上存在这些位模式，但 CPU 拒绝翻译。

6.1.3 内核空间各区域详解

区域 起始地址 结束地址 大小 来源宏
Linear Map（线性映射） 0xFFFF_0000_0000_0000 0xFFFF_8000_0000_0000 128TB PAGE_OFFSET → PAGE_END
modules 0xFFFF_8000_0000_0000 0xFFFF_8000_8000_0000 2GB MODULES_VADDR + MODULES_VSIZE
kernel image 0xFFFF_8000_8000_0000 向上增长 几十 MB KIMAGE_VADDR = MODULES_END
vmalloc / ioremap 动态 动态 可配置 VMALLOC_START / VMALLOC_END
vmemmap 0xFFFF_FDFF_C000_0000 0xFFFF_FFFF_C000_0000 2TB VMEMMAP_START / VMEMMAP_END
PCI I/O 0xFFFF_FFFF_C080_0000 0xFFFF_FFFF_C180_0000 16MB PCI_IO_START / PCI_IO_END
Fixmap FIXADDR_TOT_START 0xFFFF_FFFF_FF80_0000 ~数 MB FIXADDR_TOP

6.1.4 关键宏的数学推导

这些地址不是随便拍的，全部由 memory.h 里的宏算出来：

// arch/arm64/include/asm/memory.h
#define VA_BITS           48                        // 有效虚拟地址位数
#define _PAGE_OFFSET(va)  (-(UL(1) << (va)))        // 负数技巧：2^48 的补码
#define PAGE_OFFSET       (_PAGE_OFFSET(VA_BITS))   // = 0xFFFF_0000_0000_0000

#define _PAGE_END(va)     (-(UL(1) << ((va) - 1)))  // 2^47 的补码
#define PAGE_END          (_PAGE_END(VA_BITS_MIN))  // = 0xFFFF_8000_0000_0000

#define MODULES_VADDR     (_PAGE_END(VA_BITS_MIN))  // = PAGE_END（紧贴线性映射顶）
#define MODULES_VSIZE     (SZ_2G)                   // 2GB
#define MODULES_END       (MODULES_VADDR + MODULES_VSIZE)
#define KIMAGE_VADDR      (MODULES_END)             // 内核映像 = modules 之上

#define VMEMMAP_END       (-UL(SZ_1G))              // = 0xFFFF_FFFF_C000_0000
#define VMEMMAP_RANGE     (_PAGE_END(VA_BITS_MIN) - PAGE_OFFSET)   // 128TB
#define VMEMMAP_SIZE      ((VMEMMAP_RANGE >> PAGE_SHIFT) * sizeof(struct page))  // 2TB
#define VMEMMAP_START     (VMEMMAP_END - VMEMMAP_SIZE)

#define PCI_IO_START      (VMEMMAP_END + SZ_8M)     // vmemmap 顶 + 8MB
#define PCI_IO_END        (PCI_IO_START + SZ_16M)
#define FIXADDR_TOP       (-UL(SZ_8M))              // = 0xFFFF_FFFF_FF80_0000

「负数宏」技巧：-(1UL << 48) 在无符号 64 位里就是 0xFFFF_0000_0000_0000，因为补码取反再加一。用负数写可以保证「离地址空间顶部有多远」这个语义直接看数值大小——VMEMMAP_END = -SZ_1G 就是「从顶部往下 1GB」，FIXADDR_TOP = -SZ_8M 就是「从顶部往下 8MB」。

6.1.5 Linear Map 与 vmemmap 的关系

这两块最容易混淆，本质是同一块物理内存的两种不同视角：

物理内存（假设 1GB @ 0x4000_0000）

  Linear Map（线性映射）:
    目的：让内核能「直接解引用」物理内存的任意字节
    映射：物理地址 + PAGE_OFFSET = 虚拟地址（恒等偏移）
    例子：物理 0x4000_0000 → 虚拟 0xFFFF_0000_4000_0000

  vmemmap（struct page 元数据）:
    目的：为每个物理页放一个 64 字节的 struct page 描述符
    映射：不是 1:1，而是把所有 struct page 密集排布在虚拟空间
    例子：物理 pfn → 虚拟 vmemmap + pfn × 64 字节

区别：
  Linear Map 映射的是「物理内存本身」（1GB 物理 → 1GB 虚拟）
  vmemmap 映射的是「物理内存的元数据」（1GB 物理 → 16MB 元数据）

这就是为什么 VMEMMAP_SIZE 的公式是 (128TB / 4KB) × 64B = 2TB——如果 128TB 的物理内存全装 struct page，需要 2TB 的虚拟空间来放描述符，但只占物理内存的 1/64（因为 4KB 物理页配 64 字节描述符）。

Linear Map：128TB 的精确推导
PAGE_OFFSET = -(1UL << 48)   = 0xFFFF_0000_0000_0000   ← 线性映射起点
PAGE_END    = -(1UL << 47)   = 0xFFFF_8000_0000_0000   ← 线性映射终点

大小 = PAGE_END - PAGE_OFFSET
     = 0xFFFF_8000_0000_0000 - 0xFFFF_0000_0000_0000
     = 0x0000_8000_0000_0000
     = 2^47 = 128 TB

为什么是 128TB？因为 48-bit VA 下，PAGE_OFFSET 占掉最高位（bit 47=1 区分内核），剩下的 47 个有效位 全部留给线性映射。所以线性映射理论上最多能容纳 2^47 = 128TB 的物理内存——这正好是 48-bit 物理地址空间的一半。

关键理解：128TB 是「上限容量」，不是「实际占用」。实际映射多少取决于机器装了多少物理 RAM。1GB 内存的机器，线性映射只用了 128TB 里的 1GB；128TB 内存的服务器才刚好装满。空洞和未装内存的部分没有页表映射。

vmemmap：2TB 的精确推导
VMEMMAP_END   = -UL(SZ_1G)    = 0xFFFF_FFFF_C000_0000   ← 从顶部往下 1GB
VMEMMAP_RANGE = PAGE_END - PAGE_OFFSET = 2^47 = 128 TB   ← 对应线性映射的容量
VMEMMAP_SIZE  = (128TB / 4KB) × 64 字节
              = (2^47 / 2^12) × 2^6
              = 2^35 × 2^6
              = 2^41 = 2 TB
VMEMMAP_START = VMEMMAP_END - VMEMMAP_SIZE
              = 0xFFFF_FFFF_C000_0000 - 0x2_0000_0000_0000
              = 0xFFFF_FDFF_C000_0000

推导逻辑：vmemmap 要为「线性映射能覆盖的每一页物理内存」准备一个 64 字节的 struct page。线性映射上限 128TB = 2^35 个 4KB 页，每页 64 字节 → 共 2^41 = 2TB。

两者的数学关系：1/64 的黄金比例
线性映射容量 : vmemmap 容量 = 128TB : 2TB = 64 : 1

这 64 不是巧合：
  4KB 物理页 = 4096 字节
  struct page = 64 字节
  4096 / 64 = 64

所以 struct page 描述符总体积 = 物理内存 / 64
即：管理 64GB 物理内存，只需 1GB 的元数据
vmemmap 基址的巧妙偏移：memstart_addr

物理内存几乎从不从地址 0 开始（ARM64 上通常从 0x4000_0000 起）。如果 pfn_to_page(0) 直接指向 VMEMMAP_START，那么物理内存起点（pfn=0x40000）对应的 struct page 会偏到 VMEMMAP_START 之后 0x40000×64 字节，浪费前端虚拟空间。内核用一个「基址指针前移」的技巧解决：

// arch/arm64/include/asm/pgtable.h:31
#define vmemmap  ((struct page *)VMEMMAP_START - (memstart_addr >> PAGE_SHIFT))

// include/asm-generic/memory_model.h:46
#define __pfn_to_page(pfn)  (vmemmap + (pfn))
#define __page_to_pfn(page) ((unsigned long)((page) - vmemmap))

展开 pfn_to_page(pfn)：

pfn_to_page(pfn)
  = vmemmap + pfn
  = VMEMMAP_START - (memstart_addr >> 12) + pfn
  = VMEMMAP_START - memstart_pfn + pfn

当 pfn = memstart_pfn（第一页物理内存）时：
  = VMEMMAP_START - memstart_pfn + memstart_pfn
  = VMEMMAP_START   ← 第一页的 struct page 正好落在 VMEMMAP_START，零浪费！
具体例子：1GB @ 0x4000_0000

还是用前面那台 1GB 机器（物理内存 0x4000_0000 ~ 0x8000_0000）：

memstart_addr = 0x4000_0000
memstart_pfn  = 0x4000_0000 / 0x1000 = 0x40000 = 262144

【Linear Map 视角】—— 访问物理内存「内容」
  物理 0x4000_0000  →  虚拟 0xFFFF_0000_4000_0000  （+ PAGE_OFFSET）
  物理 0x8000_0000  →  虚拟 0xFFFF_0000_8000_0000
  内核读这 1GB，就是读 0xFFFF_0000_4000_0000 起的 1GB 虚拟区间

【vmemmap 视角】—— 访问物理内存「描述符」
  vmemmap 指针 = VMEMMAP_START - 0x40000
  pfn_to_page(0x40000) = vmemmap + 0x40000 = VMEMMAP_START
                        = 0xFFFF_FDFF_C000_0000
  所以 1GB 内存的 struct page 数组从 0xFFFF_FDFF_C000_0000 起，
  共 262144 × 64 字节 = 16MB

【对比】
  1GB 物理内存
   → Linear Map 用 1GB 虚拟空间（1:1 映射内容）
   → vmemmap 用 16MB 虚拟空间（只映射 64 字节描述符）

一句话总结两者：Linear Map 是「物理内存内容的搬运工」，vmemmap 是「物理内存的档案柜」。前者 1:1 照搬 128TB 上限，后者按 1/64 比例浓缩成 2TB 描述符。

6.1.6 Linear Map 映射的具体内容

Linear Map 不是把 128TB 虚拟空间全映射，而是只映射实际存在的物理 RAM（DRAM）。建立过程在 map_mem()（arch/arm64/mm/mmu.c:1071）：

static void __init map_mem(pgd_t *pgdp)
{
    ...
    /* 1. 先把内核映像 [_text, __init_begin) 标记为 NOMAP，
          避免在下面的循环里为它建立「可写的线性别名」 */
    memblock_mark_nomap(kernel_start, kernel_end - kernel_start);

    /* 2. 遍历 memblock 所有内存 bank（RAM 区间） */
    for_each_mem_range(i, &start, &end) {
        __map_memblock(pgdp, start, end,
                       pgprot_tagged(PAGE_KERNEL),   // RW + NX + 写回缓存
                       NO_EXEC_MAPPINGS);            // 线性映射不可执行
    }

    /* 3. 再单独映射内核映像的线性别名，属性 NX + 后续转只读 */
    __map_memblock(pgdp, kernel_start, kernel_end,
                   PAGE_KERNEL, NO_CONT_MAPPINGS);
    memblock_clear_nomap(kernel_start, kernel_end - kernel_start);
}

映射结果可以用一句话概括：

Linear Map = 把所有「物理 RAM」线性平铺到 PAGE_OFFSET 之上
           映射关系：虚拟地址 = 物理地址 + PAGE_OFFSET（恒等偏移）
           映射属性：PAGE_KERNEL = 可读可写 + 不可执行(NX) + 写回缓存
① 映射什么：所有物理 RAM

for_each_mem_range() 遍历的是 memblock.memory[]——即固件（DTB/ACPI）报告给内核的所有内存 bank。每个 bank 独立映射，bank 之间的空洞（MMIO、flash）不映射：

物理地址空间（示意）:
0x0000_0000 [flash/MMIO 空洞] ← 不映射
0x4000_0000 [RAM bank 0: 1GB] ← 映射到 PAGE_OFFSET + 0x4000_0000
0x8000_0000 [MMIO 空洞]       ← 不映射
0x1_0000_0000 [RAM bank 1]   ← 映射到 PAGE_OFFSET + 0x1_0000_0000

所以 virt_to_phys() 只能安全作用于「确实有 RAM 的线性映射地址」。如果对空洞地址调用，结果毫无意义。

② 特殊处理：内核映像的「线性别名」

内核映像（代码/数据）本来在 kimg 虚拟地址区（KIMAGE_VADDR 起），但它对应的物理内存也落在某个 RAM bank 里。如果不做特殊处理，for_each_mem_range() 循环会顺带把内核映像的物理内存也映射成「可写」的线性地址，造成同一块物理内存有两个虚拟映射、且其中一个可写，破坏只读保护。

所以 map_mem() 先 memblock_mark_nomap() 跳过内核映像，再单独映射它的线性别名，属性为 NX（不可执行），后续 mark_rodata_ro() 再把它转成只读：

同一块内核映像物理内存的两个虚拟映射:

  kimg 映射（KIMAGE_VADDR 起）:   用于执行内核代码（RX 开头，rodata 转 RO）
  Linear Map 线性别名:            用于 hibernation 等需要「按线性地址访问内核映像」
                                 属性 NX + RO，不能执行、不能写
③ 线性映射为什么必须 NX（不可执行）

map_mem() 传了 NO_EXEC_MAPPINGS，意味着整个 Linear Map 都带 NX 位。这是安全设计：内核代码只能从 kimg 区执行，任何「跳到线性映射地址执行」的尝试（如 ret2dir 攻击、内核 bug）都会立刻触发 instruction fault。

④ Linear Map 的用途
用途 说明
virt_to_phys() / phys_to_virt() 线性映射地址和物理地址之间做「加减偏移」的 O(1) 转换，不查页表
访问任意物理页 内核拿到一个 pfn 后，直接 __va(pfn<<12) 就能读写该页内容（如 DMA 缓冲区）
页表 / 描述符解析 __va() 把页表项里的物理地址转成内核可解引用的指针
page cache / 匿名页内容 文件 IO、内存回收等场景需要直接操作页内容时走线性映射

关键前提：线性映射在启动早期（paging_init()）就建立，早于 buddy 系统，所以内核的页表创建、early_ioremap 等早期操作都依赖它。这也是为什么 fixmap 那套东西在更早阶段还要靠 __pa_symbol() + kimage_voffset——那时连线性映射都还没建好。

6.1.7 内核映像与 vmalloc 共享的空间

理解内核映像的「大小」要分清两个完全不同的概念：

① 内核映像本身的真实大小：约 35MB（链接期固定）

从实际 vmlinux 符号表实测（不同配置会略有差异）：

_text  = 0xFFFF_8000_8000_0000   ← 正好等于 KIMAGE_VADDR
_end   = 0xFFFF_8000_8232_0000

内核映像大小 = _end - _text = 0x232_0000 = 36,831,232 字节 ≈ 35 MB

这个大小是编译链接时定死的，运行期不再变化。里面包含 .text（代码）、.rodata（只读数据）、.data、.bss、以及页表、异常向量表等。

② 内核映像「可使用的」虚拟地址空间：126 TB（与 vmalloc 共享）

关键设计：内核映像和 vmalloc 共享同一块虚拟区域，它们的起点相同：

// arch/arm64/include/asm/pgtable.h
#define VMALLOC_START  (MODULES_END)          // = KIMAGE_VADDR，同一个起点！
#define VMALLOC_END    (VMEMMAP_START - SZ_8M)
0xFFFF_FDFF_BF80_0000  ← VMALLOC_END（= vmemmap 起点 - 8MB）
        ▲
        │  vmalloc / ioremap 从这里向上分配
        │
        │  （内核映像只占底部 ~35MB，其余全是 vmalloc 空间）
        │
0xFFFF_8000_8232_0000  ← 内核映像终点 _end
0xFFFF_8000_8000_0000  ← KIMAGE_VADDR = VMALLOC_START = MODULES_END

整个区域大小：

VMALLOC_END - VMALLOC_START
= 0xFFFF_FDFF_BF80_0000 - 0xFFFF_8000_8000_0000
= 0x7DFF_3F80_0000
≈ 126 TB
③ 完整内核 VA 空间的 256TB 账本
0xFFFF_FFFF_FFFF_FFFF
  ├─ fixmap + PCI I/O       ~2GB 区（顶部）
  ├─ vmemmap                2 TB   (0xFFFF_FDFF_C000_0000 ~ 0xFFFF_FFFF_C000_0000)
  ├─ kernel image + vmalloc 126 TB (0xFFFF_8000_8000_0000 ~ 0xFFFF_FDFF_BF80_0000) ★
  ├─ modules                2 GB   (0xFFFF_8000_0000_0000 ~ 0xFFFF_8000_8000_0000)
  ├─ linear map             128 TB (0xFFFF_0000_0000_0000 ~ 0xFFFF_8000_0000_0000)
0xFFFF_0000_0000_0000
────────────────────────────
合计 ≈ 256 TB (= 2^48)

结论：内核映像本身的代码/数据只有 ~35MB，但它和 vmalloc 共享一块 126TB 的虚拟地址空间。内核映像占底部 35MB，其余 126TB 减去这 35MB 全是 vmalloc/ioremap 的动态分配空间。这也解释了为什么 ARM64 上 vmalloc 区域几乎用不完——126TB 对任何内核模块、ioremap 映射都绰绰有余。

6.1.8 用户空间：进程视角

每个用户进程拥有独立的 128TB 用户空间，从低到高典型布局：

0x0000_0000_0000_0000
  NULL / 保护页（前 4KB 不可访问，捕获空指针）
  .text   代码段（只读可执行）
  .rodata 只读数据
  .data   已初始化数据
  .bss    未初始化数据
  heap    堆（brk/mmap 向上增长）
  mmap    内存映射区（共享库、文件映射）
  stack   栈（向下增长，初始 ~132KB）
  ...
0x0000_FFFF_FFFF_FFFF

用户空间地址通过 TTBR0 翻译，进程切换时 switch_mm() 只换 TTBR0 指向新的进程页表，内核侧（TTBR1）不受影响。

ARM64 虚拟地址有效位数（VA_BITS）由页大小和页表级数共同决定：

7. Zone 管理

定义：Zone（内存区域）是内核在单个 NUMA node 内部对物理内存按地址范围和用途进行的二次分类。

- 产生原因：不同硬件设备对 DMA 操作有地址限制（如某些设备只能访问 < 4GB 的地址），内核必须能单独管理这些受限内存。
- 每个 Zone 维护独立的 Buddy System 空闲页链表，分配器根据 GFP 标志（GFP_DMA、GFP_DMA32 等）选择合适的 Zone。

Zone 描述的核心内容：
1. 该地址范围内有多少可用物理页（managed_pages）？
2. 当前空闲多少页？水位（min/low/high watermark）是否健康？
3. 按 2 的幂次（order 0~10）组织的空闲块链表（free_area[]）状态如何？

与 NUMA 的关系：NUMA 描述的是 node 粒度（哪块内存离哪个 CPU 近），Zone 描述的是 node 内部的地址约束分区；一个 node 包含多个 Zone，一个 Zone 不跨 node。

7.1 设计思想

由于历史遗留（DMA 限制）和硬件约束，物理内存按地址范围划分为 Zone，
Buddy System 在每个 Zone 内独立维护空闲页链表。

7.2 ARM64 Zone 布局

物理地址低 ──────────────────────────────────── 物理地址高
┌──────────┬──────────┬────────────────────────┐
│ ZONE_DMA │ZONE_DMA32│     ZONE_NORMAL         │
│ (可选)   │ (<4GB)   │  (其余所有内存)          │
└──────────┴──────────┴────────────────────────┘
Zone 地址范围 用途
ZONE_DMA 平台相关（如 < 1GB） 旧式 DMA 设备限制
ZONE_DMA32 < 4GB 32-bit DMA 设备
ZONE_NORMAL 剩余所有内存 通用内存
ZONE_MOVABLE 可配置 热插拔/内存碎片整理

7.3 关键数据结构

struct zone（include/linux/mmzone.h）

struct zone {
    unsigned long _watermark[NR_WMARK]; // min/low/high 水位线
    unsigned long watermark_boost;

    struct pglist_data *zone_pgdat;    // 所属节点
    struct per_cpu_pages __percpu *per_cpu_pageset; // per-CPU 页缓存

    unsigned long zone_start_pfn;      // zone 起始 pfn
    unsigned long managed_pages;       // Buddy 管理的页数
    unsigned long spanned_pages;       // 包含空洞的跨度
    unsigned long present_pages;       // 实际存在的页数

    // Buddy System 核心：11个 order 的空闲链表
    struct free_area free_area[MAX_ORDER];

    // 迁移类型（反碎片化）
    // MIGRATE_UNMOVABLE / MIGRATE_MOVABLE / MIGRATE_RECLAIMABLE

    spinlock_t lock;
    const char *name;
} ____cacheline_internodealigned_in_smp;

struct free_area（Buddy System）

struct free_area {
    struct list_head free_list[MIGRATE_TYPES]; // 按迁移类型分链表
    unsigned long    nr_free;                  // 该 order 的空闲块数
};
// order 0: 4KB, order 1: 8KB, ..., order 10: 4MB (MAX_ORDER=11)

struct per_cpu_pages {

    int count;           // 当前缓存页数

    int batch;           // 每次批量操作数量
    struct list_head lists[NR_PCP_LISTS]; // 按迁移类型和 order 缓存
};
// 减少多核竞争 Buddy System 的 spinlock

7.4 Buddy System 算法

核心思想：将空闲页按 2 的幂次（order）组织，合并相邻的"伙伴"块。

分配 order=1（8KB）：
  free_area[1] 有空闲？
    是 → 直接取出，更新 nr_free
    否 → 从 free_area[2] 取一个 16KB 块，拆分为两个 8KB，
          一个返回，一个加入 free_area[1]

释放 order=0（4KB）的页 pfn：
  计算 buddy_pfn = pfn ^ (1 << order)
  buddy 也空闲？
    是 → 合并为 order=1 的块，递归检查更高 order
    否 → 加入 free_area[0]

Buddy 计算公式：
$$buddy_{pfn} = pfn \oplus 2^{order}$$

其中 ⊕ 是异或（XOR），2^{order} 等价于 C 代码里的 1UL << order——即把 pfn 的第 order 位翻转，得到它的伙伴页框号。

9. THP 与 HugePage

9.1 静态大页（HugePage）

通过 hugetlbfs 预先分配，用户通过 mmap(MAP_HUGETLB) 使用：

页大小 大页尺寸 映射级别
4KB 2MB（默认） PMD（L2）
4KB 1GB PUD（L1）
16KB 32MB PMD
64KB 512MB PMD

9.2 透明大页（THP，Transparent HugePage）

内核自动将连续普通页合并为大页，无需应用程序修改：

CONFIG_TRANSPARENT_HUGEPAGE=y

控制接口：
/sys/kernel/mm/transparent_hugepage/enabled
  [always]  madvise  never
  • always：尽可能使用 THP
  • madvise：仅对 madvise(MADV_HUGEPAGE) 的区域使用
  • never：禁用

9.3 ARM64 Contiguous PTE（连续 PTE 优化）

ARM64 特有特性：将 16 个连续 PTE 合并为一个 contiguous hint，处理器 TLB 可以用一个条目覆盖整块区域：

普通 PTE：每个 4KB 页占一个 TLB 条目
Contiguous PTE：16 × 4KB = 64KB 共享一个 TLB 条目
                → TLB 效率提升 16x（针对该区域）

内核在建立页表时（set_pte_at 路径）自动判断是否设置 PTE_CONT 标志。
